# 编辑器工具与批处理架构

一个可靠工具不只是按钮加脚本。它要让用户理解会发生什么，能预览、撤销、取消、复现，并在交互模式和无人值守批处理中复用同一套业务规则。

## 从工作流而不是 API 开始

先描述用户任务：

1. 用户从哪里选择输入；
2. 工具如何显示当前状态和问题；
3. 哪些参数必须提供，哪些有安全默认值；
4. 执行前能否 Preview/Dry-run；
5. 执行中如何显示 Progress 和 Cancel；
6. 部分失败如何处理；
7. 结果、日志和 Undo 在哪里。

如果流程需要用户先按隐藏顺序选中三个对象、切到特定模式、再点按钮，脚本虽然短，却不是稳定工具。

## 分层

建议职责：

```text
UI / Command Line
    -> Application Service
        -> Domain Rules / Operations
            -> DCC or Engine Adapter
            -> File / VCS / Process Adapter
```

- UI 负责输入、展示和交互，不承载批处理算法；
- Application Service 编排用例、事务和进度；
- Domain 层处理命名、验证、映射和转换规则；
- Adapter 封装 Maya/Blender/Unity/Unreal API 和外部进程。

这样 Headless CLI、Editor Window 和 CI 可以调用同一核心逻辑，避免“面板能用，命令行是另一套实现”。

## Context 与显式输入

DCC API 常有两种风格：

- Operator/Command 依赖当前 Selection、Mode、Active View；
- Data API 直接读取和修改对象。

交互操作可以借助 Context，但批处理应尽量显式传入对象、场景、路径和设置。必须使用 Operator 时，先验证 Context，再在 `finally` 中恢复 Selection/Mode。

不要把 UI 显示名作为稳定身份。应使用 Object Reference、GUID、Package Path 或自有 Stable ID。

## 序列化层

编辑器通常需要把任意对象映射成可读写属性树。Serialized Object/Property 可以提供：

- 字段名称、类型与 Attribute Metadata；
- 嵌套对象、数组和引用；
- 读取旧值、验证新值；
- 生成 Patch；
- 保存和版本升级。

UI Drawer 只根据 Property Type/Attribute 决定用输入框、Slider、Asset Picker 或列表。Drawer 不直接绕过序列化层修改业务对象。

若 Inspector 走 Serialized Property，而 Gizmo 直接写 Transform，就形成两套数据真相，Undo、Save 和 Runtime Sync 会不一致。

## Command、Patch 与 Transaction

一次可撤销操作应记录足够信息：

- Target Stable ID；
- Property/Operation；
- Old Value / New Value；
- Apply / Revert；
- 显示名称和时间。

一次用户手势可能产生许多 Patch。拖动十帧不应让用户 Undo 十次，应合并成一个 Transaction。

Transaction 的 Undo 通常按子操作反序执行，Redo 按正序。创建/删除、层级变更和跨对象操作必须一起进入同一事务，不能只记录最后一个字段。

## Unity 与 Unreal 的撤销

Unity 工具应在修改前记录 `Undo.RecordObject` 或使用对应创建/销毁 API，并正确标记 Dirty/Prefab/Scene。直接改序列化外的数据可能无法 Undo 或保存。

Unreal 编辑器对象通常需要 Transaction/`Modify()`，工具还要区分 Asset、Actor、Component 和 Package 的保存职责。

具体 API 会随版本变化，应使用当前官方文档并写集成测试。核心原则是不绕过引擎事务和序列化系统。

## Preview 与 Dry-run

Preview 不只是弹窗问“确定吗”。它应显示实际变更集：

- 将处理/跳过哪些资产；
- Rename/Move 的旧路径与新路径；
- 哪些 Setting 会变化；
- 哪些文件会覆盖或创建；
- Validator Error/Warning；
- 预计耗时与不可撤销操作。

Dry-run 与 Execute 应走同一 Planning 逻辑。若 Preview 单独重写一次规则，它可能和真实执行不一致。

可先生成 `Plan`，Review 后由 Executor 应用：

```text
Input -> Analyze -> Plan -> Validate Plan -> Execute -> Verify -> Report
```

## 批处理

批处理不是对 Selection 做一个 `for` 循环。需要考虑：

- 输入枚举与稳定排序；
- 单项 Timeout、Retry 和 Failure Isolation；
- 进度、取消和断点续跑；
- 重入与幂等；
- 并行度和 DCC/引擎线程限制；
- 临时目录与原子写入；
- 汇总报告与退出码。

每项写独立结果，整个任务保存 Checkpoint。崩溃后可以从未完成项继续，而不是重新修改全部资产。

## 幂等与可重入

同一输入运行两次，应得到相同最终状态，第二次尽量不产生修改。

例如批量重命名：

- 先构建完整 Rename Map；
- 检查目标冲突和大小写问题；
- 必要时经临时名完成交换；
- 更新引用；
- 已符合目标的项目标记 Skip。

直接边遍历边改名，会让后续查询看到混合状态，也容易出现 A→B、B→A 冲突。

## 文件写入

输出到临时文件，Flush/Close 后验证，再用安全替换更新目标。不要在生成过程中直接截断正式文件。

跨多个文件的任务使用 Staging Directory 和 Manifest。所有输出成功后再 Commit/Publish；失败时删除或保留带状态的 Staging，正式目录保持旧版本。

覆盖源文件前要确认版本控制状态、锁与权限。工具不应擅自覆盖用户未提交修改。

## 进度与取消

进度应基于可度量 Work Item，而不是窗口里永远转圈。每项状态：Pending、Running、Succeeded、Failed、Skipped、Cancelled。

Cancel 是协作式的：在安全点检查 Token，完成当前原子步骤后停止。不能在写到一半时强杀，留下损坏文件。

长任务应释放 UI Thread。DCC/Engine API 若只能主线程调用，可把文件分析等纯计算放后台，把实际对象修改调度回主线程。

## 错误模型

区分：

- User Input Error：立即指出字段和修法；
- Asset Validation Error：该项失败，其他项可继续；
- Environment Error：工具/插件/权限/磁盘问题；
- Transient Error：IO/服务短暂失败，可有限重试；
- Internal Error：记录 Stack、版本和输入，停止高风险写入。

不要用一个巨大 `try/catch` 把全部错误改成“执行失败”。日志应包含 Operation ID、Asset、Stage、Tool Version 和可复制诊断。

## 配置与 Schema

配置应版本化并有默认值、验证和迁移。读取旧配置时显式升级 Schema，不能因字段缺失静默使用错误行为。

项目级规则、用户偏好和本次参数应分层：

- Project Policy 进入版本控制；
- User Preference 只影响 UI，不改变构建结果；
- Invocation 参数进入日志/Manifest；
- Secret/Token 使用安全存储，不写项目配置。

## 插件部署

团队工具需要：

- 明确支持的 DCC/Engine/Python/.NET 版本；
- 安装、升级、回滚和卸载；
- 依赖隔离；
- 变更记录和兼容策略；
- Telemetry/错误报告的隐私边界；
- 旧项目锁定工具版本的方法。

自动更新如果没有项目锁定，会让同一提交在不同成员机器上产生不同结果。

## Editor 与 Runtime 隔离

编辑器工具可以访问 Asset Database、文件系统、反射和调试数据，Runtime Build 不应携带这些入口。

- Editor Assembly/Module 与 Runtime Assembly/Module 分开；
- 编辑器依赖只在 Editor Target 编译；
- Runtime 使用经过 Cook 的数据，不直接解析 DCC Source；
- 命令行构建明确加载哪些 Editor Module；
- 发布检查扫描 Editor-only 类型和资源引用。

隔离不仅减少包体。把任意场景修改、资源浏览或调试命令编进正式版本，会扩大安全和外挂攻击面。

## 工具可用性

面向美术的工具应使用领域语言，不暴露实现字段。路径选择器、枚举、颜色、资产引用和数值范围使用合适控件，危险操作与普通操作有清楚层级。

高频流程应支持键盘、批量选择和最近使用值，但这些用户偏好不能改变 CI 结果。错误应定位到具体对象并提供 Select/Ping/Fix，而不是让用户从 Console 手工找路径。

工具需要处理空状态、只读资产、锁冲突、部分选择不兼容、场景未保存和项目正在 Import 等正常状态。只有“理想选择集”能运行的面板会把失败成本转给使用者。

## 可观测性

团队工具至少记录版本、Operation ID、输入数量、成功/失败、耗时和主要阶段。Telemetry 的目的应是发现高频失败和慢步骤，不是监控个人产量。

对失败率高的规则，先判断默认值、交互和 Auto-fix 是否有问题。反复培训同一个手工步骤，通常说明流程还没有被工具真正吸收。

## 测试

- Domain Rule 使用纯数据 Unit Test。
- Adapter 使用小型 Fixture/Golden Scene 做 Integration Test。
- UI 测输入验证、Disabled/Loading/Error/Cancel 状态。
- Batch 测空输入、冲突、部分失败、重试、取消和断点恢复。
- Undo/Redo 测多对象、创建删除、层级变化和保存后重载。
- 同一输入连续运行两次，第二次应无 Diff。
- Headless CI 与交互工具应输出一致 Plan/Result。
