# 网络协议、时钟与 RPC

网络层的目标不是“把本地函数搬到另一台机器”，而是在延迟、丢包、乱序、带宽限制和恶意输入都存在时，仍然让双方对重要事实达成足够一致的理解。

## TCP 与 UDP

TCP 提供有序、可靠的字节流，带拥塞控制，适合登录、聊天、配置和不频繁的事务。一个前部包丢失会阻塞后续字节交付，实时状态若全部走同一连接可能产生 Head-of-Line Blocking。

UDP 是数据报，不保证到达、顺序和唯一性，但应用可以决定哪些数据值得重传。高频位置快照过期后通常无需补发，关键技能和库存操作则需要可靠确认。选择 UDP 不等于忽略拥塞与安全，也不等于天然更快。

可靠 UDP 常加入 Sequence Number、ACK/NACK、滑动窗口、超时重传和重复包过滤。不同消息可设置可靠有序、可靠无序或不可靠。重传策略必须考虑 RTT 和拥塞；无上限地补包会在网络恶化时进一步堵塞链路。

## 数据包与序列化

协议需要明确包头、消息类型、长度、版本、序号和校验方式。TCP 是字节流，没有天然消息边界，因此必须 Length Prefix 或其他 Framing。UDP 保留数据报边界，但还要处理 MTU，尽量避免 IP Fragmentation。

多字节数字要约定 Endianness。序列化格式应限制长度、层级和枚举范围，不能信任远端给出的数组大小。高频状态可用 Bit Packing、Quantization 和 Delta Compression，控制面消息更看重兼容与可诊断性。

协议演进要区分可选字段和破坏性修改。客户端、服务端版本不一致时应明确拒绝或走兼容分支，不能靠解析异常猜测。

## RTT 与时钟偏移

Round-Trip Time 是请求发出到响应返回的总时间。只用一次采样会受抖动影响，通常维护平滑 RTT 与偏差。若本地在 $t_0$ 发出，服务端时间为 $t_s$，本地在 $t_1$ 收到，并假设上下行大致对称，可粗略估计：

$$offset\approx t_s-\frac{t_0+t_1}{2}$$

上下行并不总对称，因此这是估计，不是绝对时间。游戏通常更关心共同 Tick、事件年龄和插值时间线。系统墙钟可能跳变，测量间隔应使用 Monotonic Clock。

## RPC

RPC 由 IDL/Schema 描述可调用消息，生成或手写 Stub 负责序列化、发送和分发。网络 RPC 不具有本地调用的可靠语义：它可能延迟、超时、重复执行，也可能在响应回来前连接断开。

每个请求应有 Request ID、权限上下文和超时。自动重试只适合幂等操作，或服务端用唯一事务号去重。`SetName(A)` 可以设计成幂等，`AddGold(100)` 若重复执行就会出错。关键交易最好表达为“提交事务 X”，并保存处理结果。

客户端 RPC 只是请求，服务端必须重新验证位置、冷却、资源和身份。函数名叫 `ServerDealDamage` 并不会让传入伤害可信。

## 安全边界

握手阶段验证版本与身份，传输层按需要使用成熟的加密和认证协议。不要自创密码学。解析器限制包大小、频率和嵌套深度，网关按连接与账号做 Rate Limit。错误日志避免回显令牌和敏感载荷。

UDP 需要额外防止地址伪造与放大攻击。建立会话前不要对小请求返回巨大数据，关键消息带会话验证信息。断线重连时旧连接和重放包也必须失效。

## 诊断

网络问题至少记录时间、连接、消息类型、序号、字节数、RTT、丢包率、重传和队列长度。抓包能看见传输事实，游戏内 Network Profiler 则要关联到实体和系统。模拟延迟、抖动、丢包、乱序和限带宽，比只在本机回环测试更接近真实环境。
