# 引擎工具链高级概念与应用：World Editor、Plugin 架构、反射系统与协作式编辑

---

## 一、核心知识点与原理剖析

### 1. 游戏生产（Production）全景与工具链的基本挑战

#### (1) 商业级游戏的生产流程

*   **Production 的真实状态**：在一个真实的游戏工作室（如育碧）中，艺术家会使用各种各样的工具协同完成游戏制作：有人在搭建场景的 **layout**（布局），有人在设计 **gameplay**（玩法），当按下"一键 Play"之后，游戏会产生大量复杂行为。
*   生产过程中大量使用 **PGC（Procedural Generation Content，程序化内容生成）**——即用程序自动生成内容，例如艺术家甚至可以自动生成**一整座城市**；同时也有大量为 **designer**（设计师）准备的 framework（框架）性工具。
*   角色分工：
    *   **concept artist（概念艺术家）**：设定角色和场景的外观；
    *   **modeler（模型师）**：生成大量的 3D 模型；
    *   这些工作全部连接在一起，才形成真正的商业级游戏 production。
*   最终交付到玩家手上的东西，**所有内容都是有语义的**，尽可能让玩家**可交互、可 playable**（可游玩）。

#### (2) Genre 对工具链的影响

*   **Genre（读作"让"，来自法语）**：表示各种各样不同类型的游戏，例如 RPG、FPS、MOBA 都叫 genre。
*   不同 genre 的游戏，其**编辑操作、gameplay 设置、关卡 layout、关卡的组织规范都会完全不同**，这是工具体系非常复杂的一个原因。
*   工具链体系设计本质上要解决的是：**来自完全不同思维方式的人——艺术家、设计师、程序员——如何在同一套工具中协同协作**的问题。

#### (3) WYSIWYG（所见即所得）原则

*   **核心概念**：**WYSIWYG（What You See Is What You Get）**，即"所见即所得"，是现代游戏生产中一个非常重要的指标。
*   **为什么要坚持 WYSIWYG**：如果工具层无法保证所见即所得，会极大地影响游戏产品的**效率**（开发周期变长）和**质量**。例如 level designer（关卡设计师）如果不能快速看到自己调整后的关卡长什么样、并身临其境地在其中行走，那么他对于"这里落石、那里蹦出小怪"的体验判断**很可能全是错的**——因为无法带入用户的真实体验，给出的设计一定不好。
*   **WYSIWYG 的挑战**：做工具时，我们会有大量的额外信息、额外操作才能让艺术家/设计师编辑调整，还要解决版本控制的同步问题；但同时又要求一切看起来跟真实游戏一模一样，这两个需求有时"忠孝不可两全"。
*   **公认的解决方案**：**把工具直接包在游戏引擎外面**，这是目前公认比较好的方案，但也会给游戏引擎本身带来一些挑战（后面详述）。

### 2. World Editor（地图编辑器）架构：作为 Hub 的平台

#### A. 总体定位：Editor 是一个 Hub 而非拖拽工具

*   **核心概念**：从专业游戏引擎架构思想看，**world editor 并不是一个"拖拖拽拽"的工具，而是一个 hub（集线器/平台）**——把游戏世界里需要构建的各种逻辑、玩法、场景内容插进去的平台。
*   **最重要的架构思想**：千万不要一上来就写编辑器，去写类似 3ds Max 那种拖拽、选取的逻辑。拖拽逻辑虽然重要，但会让你很快得到一个"看上去很酷"的编辑器，甚至产生"我是不是可以跟 Unreal 一较高下"的错觉。
*   **商业级引擎的核心不在一个一个的 feature，而在于整个体系按什么逻辑架构起来**。
*   打开 Unreal 源码界面会看到大量的面板与组件：**VIEWPORT、layout、layers、levels、outliner、details、content browser** 等等。面板可以切换成很多种 view；同一个引擎，做动画的、做场景编辑的、做玩法编辑的团队，其面板完全不同——这正是 world editor 是 hub 的体现：**集成了很多功能，但对不同用户呈现不同的 view**。

#### B. VIEWPORT：运行于 Editor Mode 的完整游戏

*   **核心概念**：**VIEWPORT 是用户与"想构建的游戏世界"交互的窗口**，是 world editor 最重要的体系，最好不要做成 plugin（也没有必要做）。
*   **本质实现**：VIEWPORT 下面跑的就是一个**完整的游戏引擎、一个真实的游戏**，只是打上了一个叫 **editor mode** 的 flag。在 editor mode 下能做真实游戏不能做的事：
    *   相机可以**自由飞来飞去**；
    *   可以**无视所有碰撞**；
    *   可以把很多物体**变成透明**；
    *   可以显示大量的 **debug draw**（调试绘制）与 **wireframe mode**（线框模式）。
*   **Gadget（小工具）**：VIEWPORT 提供很多基础编辑操作小工具，例如显示小坐标系、选点、选中、**grouping（成组）**、**snap（吸附）** 等，这些最基础的操作需要用 **native code**（原生代码）在引擎里实现，效率最高；更复杂的逻辑则交给编辑器自己处理。
*   **Editor Only 代码**：引擎中会有一部分代码叫 **editor only** 的代码，它的编译版本与发布版本不一样。**必须严格区分编辑器代码与发布代码**，否则会把编辑器代码编译进上线的游戏，极可能成为别人写**外挂**的入口（例如让整个世界透明、直接选取、直接飞行）。
*   **为什么 VIEWPORT 必须跑完整游戏**：这是保证 WYSIWYG 的最基本机制。特别是对 artist 敏感的**材质（如法线贴图）、光照与反射**：光从某个方向打过来反射几下把角色照亮、过场动画中角色正好走进阴影等细腻效果，只有通过"编辑视口=真游戏渲染"的架构才能实现。
*   **多 Viewport 支持**：商业级 world editor 中 VIEWPORT 往往不止一个（例如做过场动画时一个视口编辑、一个视口观看，甚至做"画中画"）。这要求引擎架构**能兼容多个 view**——不能把数据拷贝多份再同步（那等于在本地写了一个小型的网络同步系统），编辑一个数据时多个视口必须共享同一份数据。

#### C. Object 系统：一切皆可编辑的对象

*   **核心概念**：世界中的一切（天空、地面、语音、NPC、树、一花一木一草）都是 **object（物体/对象）**，而所有 object 都是 **editable（可被编辑）** 的。不同引擎叫法不同：Unreal 叫 **Actor**，Unity 叫 **GameObject**，PICO 引擎叫 **Object**，名字不重要，重要的是共性。
*   **可编辑性的最小要求**：至少能**选中**、能改变**位置**、能**旋转**，点中时能编辑其**属性**。
*   **架构要求**：要把世界中的一切抽象成一个 common 的 **editable object**——它相当于在引擎 runtime 的 object 之上再往上走一步。
*   **对象数量规模**：一个真实场景的对象数**至少是几千个，甚至上万、更多**。面对上万个对象（而且大量是同一类资源的 **instance（实例）**），必须提供多种管理视图。
*   **多种 View 的组织方式**：
    *   树状 view：按目录归类存储；
    *   **layer（图层）**：例如"地上的植被""城市左边的建筑群""地上的石头"，用大图层归类；
    *   **group（分组）**：把对象成组管理；
    *   **search（搜索）**：按条件检索。
*   **按艺术家习惯定制 View**：例如做 environment（环境）的 artist 专注天空大气系统时，可以把其他 view 都锁住/隐藏，专注调整天空云雨效果，之后再把其他层接回来看整体效果。
*   **回顾 MVVM 模型**：object 系统要贯彻上一节课的 **MVVM（Model-View-ViewModel）** 模型——**数据 model 一定要动起来**，而 view 可以提供很多种，完全可以根据艺术家/设计师的情况，未来甚至允许不同人用不同 view 管理各自的对象。

#### D. Schema 驱动的属性编辑面板（Detail / Properties）

*   **核心概念**：选中一个对象后直接编辑它的属性，这是最直观的编辑方式（例如选中 NPC 设置它的血量）。此时**上一节课讲的 schema 系统就非常关键**：点中对象，通过 schema 反射出它身上挂了哪些属性数据，编辑器**根据属性类型自动生成对应的编辑界面**。
*   几乎所有引擎的 world editor 都有这样一个 panel：Unreal 里叫 **detail**，有的引擎叫 **properties**，这是构建 world editor 时**必须要有的窗口**。

#### E. Content Browser：从静态目录到资源海洋

*   **背景与痛点**：真实游戏引擎要管理**几万到几十万件资产**——动画、3D 模型、声音效果、UI 贴图、动图等，它们非常丰富和复杂。
*   **早期做法（Halo 3 时代）**：没有 content browser，由一位非常有经验的 **technical artist** 根据产品把资产目录设定好（objects、foliage 植被、vehicle 载具、weapon 枪等），再细分贴图目录、模型目录、原始数据目录，形成一个非常深的**树状目录结构**。
    *   **问题一**：跨项目复用困难——做完 Halo 3 做 Halo 4 时，Halo 4 的艺术家想用 Halo 3 的某把枪，得去 Halo 3 的目录里找，资产归属"到底放哪个项目目录"说不清楚。
    *   **问题二**：目录结构往往是 3~4 年前由一个人设定的，**无法预判游戏发展后出现的复杂变化**。
*   **Content Browser 的诞生（约 10 年前提出）**：把资产从**静态的文件目录**变成一个**资源的海洋（ocean）/大池子**。它仍支持基于文件夹的结构，但**文件夹更多只是一种 view**。
    *   资产扔进池子后，你只需要知道要什么、叫什么名字，就能**检索**到它、**引用**它；
    *   可以**根据不同的项目形成资产的不同 view**，用树状管理也行；
    *   **资产甚至可以不放在本地**，而是放在一个 **studio 中央数据仓库/数据库**里。早期研究过"本地都不存资产"：数据特别大，放在中央仓库，每个人需要时只把它加载进内存（本质上是跑游戏），从而**省去几个 TB 的资产在上百台机器间来回拷贝的时间**，很多**预计算也可以提前做掉**。
*   **结论**：面向未来的游戏引擎，**content browser 是必须要考虑的东西**。

#### F. World Editor 的三大功能维度

*   分析 world editor 上的各种小元件，它无非解决三个问题：
    1.  **layout（布局）**：各种物体的摆放、碰撞检测；
    2.  以**地形为基础**的植被、**decorator（装饰物）**（各种小杂物）；
    3.  **environment（环境）**：天空、天光、光源等。
*   这些分别对应 world editor 中使用的各种 unit（单元）或各个系统。

### 3. World Editor 的核心编辑功能

#### A. 鼠标选取（Picking）

*   **核心概念**：架构没有问题的话，**第一个要写的功能就是鼠标选取**——因为鼠标选取是一切的基础，编辑器"顺手不顺手"与鼠标选取写得好坏关系极大，甚至很多时候鼠标选取要"模糊一点"才让艺术家用起来更自然。
*   **做法一：Raycast（射线检测）**：所有物体都有包围盒，发射射线做碰撞检测（`raycast`/`cast`）命中即选中。它实际用的是**物理引擎**对世界的物理表示，做粗粒度很快。
    *   **缺点**：物体形状复杂（一个角色可能有几万个三角形面片），用胶囊体做选取时，你想选的是角色身后的树，结果**误选了前面的人**。
*   **做法二：额外选取帧（Object ID Frame）**：增加一个 **extra pass（额外渲染通道）**，把每个 **object id** 打在 **frame buffer**（帧缓冲）上，然后读取鼠标位置像素得到 object id 即可。
    *   editor mode 下要多渲染一张带 object id 的 texture，会费一点性能，但**没关系**：做编辑用的开发机配置比玩家电脑更好（主机平台也有 **dev mode** 开发者版本，额外加内存、配最好的显卡）。
    *   **由此引出一个经典坑**："在我本机跑起来完全没问题，为什么用户那边卡？"——很多是因为开发/编辑用电脑配置太高，掩盖了性能问题。
*   **透明物体的选取**：场景里有很多透明物体（particle 粒子、玻璃）。若按透明物体的常规处理（不写入 depth buffer，被过滤掉），会选不中。
    *   **解决思路**：写特殊代码/逻辑表达。例如 particle（粒子）：在粒子发生器处放一个**虚拟体（root）**，你选中的不是粒子本身，而是根虚拟体，拖来拖去即可。
    *   更复杂的选取情况一般都需要特殊的 code 解决——游戏引擎的选取要考虑的情况特别多。

#### B. Transform 操作（平移 / 旋转 / 缩放）

*   **核心概念**：能选中物体后，就要支持大量 transform（变换）操作——平移、旋转、缩放。
*   **难点不在算法，而在手感习惯**：3ds Max、Maya 以及其它游戏引擎给 artist 形成了非常多经过多年项目总结的优良操作习惯。一个简单的旋转就有很多讲究：按哪个热键出现旋转 gizmo（操作控件）、鼠标移动到 gizmo 百分之多少时高亮 X/Y/Z 轴的旋转、整度数旋转（每 5 度一跳，方便对齐 90°、45°、180°、135°、30°、60°）等等。**做得不好，别人用起来就非常不顺**。
*   **工程量**：把 transform 操作真正写好，往往需要**好几个月的精心打磨**。这正说明：world editor / 工具链的大框架容易讲清楚，**真正写好门槛很高**，这也是商业级引擎让人敬畏的地方。

#### C. 地形与笔刷系统

*   **Height Brush（高度笔刷）**：
    *   地形在图形学里很简单——**height field（高度图）**加 texture 即可，高度图可用 **PCG（程序化生成）** 生成。
    *   **真正的难点是平滑（smooth）**：对有限密度的 height field 网格做笔刷操作时，对信号做合理的 smooth 是最重要的。艺术家拉不出想要的山形，往往不是笔刷种类不够，而是**过渡不够自然**。
    *   高度图网格是"斜着一个个过去"的（可理解为布料沿某一轴向被切割），拉不好会看到**沿 45 度切向的明显过渡角**，产生 zz（锯齿感/不平滑）的感觉。**如何让刷出的山更 smooth、更自然是高度笔刷非常重要的一件事**。
    *   **扩展性需求**：艺术家需要**可扩展能力**——强烈建议提供"艺术家自己导入高度图、自己定义笔刷"的能力，这会让艺术家乐此不疲（Houdini 在这方面做得更强大）。做工具**首先不要专注算法多厉害，而要看扩展性有多强**。
*   **Instance Brush（实例笔刷）**：
    *   用来刷各种实体：刷小的 detail、刷 decorator（地面小草）、刷 tree（树）。
    *   **优点**：非常直觉，大面积刷草种树；**每一棵树独立存储、所有属性静态**——编辑时树在这个位置、游戏跑起来一定在这个位置，颜色、属性完全一致，**所见即所得**；对某棵树不满意可以逐个修改。
    *   **缺点**：以实战型游戏看（方圆几十平方公里），光存树的位置**内存占用就非常大**，很多预处理很麻烦，后续需要用 PCG 方法解决（本节不展开）。但 instance 笔刷仍是游戏引擎很关键的笔刷。
*   **Environment / 光照**：现代游戏引擎 GPU 能力越来越强，越来越像电影行业——电影拍摄场景时艺术家会布置大量**辅助性光源**来刻画角色、渲染气氛。现在游戏的气氛也常靠**光、滤镜、天空的云、天光**打出来。这些 environment 功能由各种插件协作完成，做 world editor 时**一定要给这些插件留下空间**。

#### D. 环境编辑的规则系统（Rule System）

*   **核心概念**：各个编辑插件"坐下来做"都不难，**真正难的是它们彼此之间的规则**。
*   **修路例子（Roll / Road System）**：
    *   简单想，路系统就是拉一条 line 完事；但真实 world 里修路非常麻烦，因为有很多规则：
        *   路上**不能长树**、杂草不应长在路两边；
        *   路应该**沿 terrain（地形）的起伏**走，但又必须**修改 terrain**（路要平，很少见路修成倾斜 10°~15°）；
        *   石头、碎石子应**沿路两边形成路基**。
    *   **不处理规则的工作量**：先修好路，再由 artist 手动砍树、清理 decorator、修 terrain——工作量巨大；更严重的是，**设计师随时可能要求改路的方向**（例如为了战斗需要做个拐角设埋伏），此前所有手工工作全部重做。
    *   **正确方案：用程序化（procedure）方法自动解决**。建立一套 **rule system（规则系统）**，通过一套复杂的 **graph（图结构）** 把规则表达出来，并把原始数据**分层分得很清楚**：树的分布、road 的分布、object 的分布、河流水的位置……然后把所有地形元素交给计算机，用规则体系生成一套合理的分布。例如：树不会长进房子里面，房子周边多少米内不能长树。
*   **Deterministic（确定性）与 Locality（局部性）**：
    *   **核心问题**：树的分布希望是随机的，但当我修改一个局部区域时，已经生成好且满意的区域**不应被全部重新生成**。
    *   即生成数据必须具有 **locality（局部性）**——这是实战化的 world editor 很重要的属性。
*   **规则体系的深度**：十几年前 **Crytek 引擎**就在做这类事情，精细到：热带地区的植被是什么规则、高纬度寒带地区是什么规则、东半球西半球有细微差异；用程序自动生成城市时，亚洲风格、日本风格、欧美/欧洲风格、美国大都市风格都完全不一样。
*   **真正的难点**：如何**定义一套形式化的语言**，让设计师能定义这套规则，且简单易懂、很好维护。这曾是难题，但今天基于 **Houdini（DEPLANAI? 转录音近，指 Houdini 等程序化工具）** 技术的成熟，这类"刷植被时自动避开路和石头、改造路时植被相应变化"的能力已成为商业引擎都提供的 well-studied（被研究得很充分）的问题。

### 4. Plugin 架构设计

#### A. World Editor 的插件矩阵

*   **核心概念**：大量商业软件实践（**Qt、浏览器、Unreal** 等）都使用 plugin 机制；world editor 中的插件不能一上来全部内建，而要用 plugin 机制承载。
*   **插件矩阵**：world editor 可看作一个矩阵，两个维度：
    *   **横向：各个系统**——mesh 编辑系统、particle（粒子）系统、动画系统……正好与 object component（对象组件）中的一个个 component 类型发生勾连；
    *   **纵向：各种类型的物体**——NPC、环境、群/种群（flock/herd，一群物种）、天空等系统。
*   **Plugin 切分方式**：按纵向 object 类型切分，还是按横向系统切分？**答案是"都要"**：
    *   例如 particle system 适合用 plugin 单独做（可能有普通粒子、GPU driven particle / GPU particle 等多种实现，通过 plugin 替换）；
    *   而一个 NPC 行为插件会影响随机外观、性格、animation（动画）、行为、可交互内容——需要**矩阵性的数据支撑访问**，让任何一个 plugin 能纵向、横向地对世界产生影响。

#### B. 四种 Plugin 协作模型

*   软件工程中 plugin 有非常多的模型，world editor 里至少会用到以下四种（**要保持开放性，各种模型都会用到，千万不要预先假设所有 plugin 都按同一个模式走**）：
1.  **覆盖模型（Override）**：新版本 plugin 直接把老 plugin 的功能全部盖掉。
    *   应用：要做一个与引擎内置地形编辑完全不同的问题域的地形插件（例如"小小星球"——希望整个地面是 curved（弯曲的）、形成一个星球曲面，所有摆放都在上面做），新地形 plugin 最好能**覆盖**掉旧的地形 plugin。
2.  **分布式模型（Distribute）**：所有 plugin 独自工作，每个人解决自己的问题，互不影响，最后结果合到一起。
    *   应用：world editor 中大部分 plugin 都是这种——做 particle 的和地形没关系，做光照部署的和粒子没关系，各干各的再合并。
3.  **Pipeline 模型（流水线）**：数据一个串一个传递。
    *   应用：主要用于**数据处理和导出**。例如做物理效果：先用几何插件对对象做 **partition（几何切割）** 生成碎片类型，物理插件再进来设置物理属性——前一个 plugin 的输出是后一个的输入，插在前面对数据先处理。
4.  **洋葱圈模型（Onion）**：与别的 plugin 进行输入输出**同时操作**（互相 talk，读入数据、处理、写回）。
    *   应用：**rule system 就是洋葱圈**——它几乎会与所有 plugin 对话：读地形笔刷 plugin、读所有 decorator plugin、读所有 tree/foliage plugin，根据读到的数据处理后**把结果反写回去**、改写别人的状态。
*   **架构原则**：站在引擎视角架构 world editor 或各类 editor 时，**设计结构上一定要保持很强的开放性**；在一个真实游戏 production 需求面前，各种 plugin 模型都会用到。
*   **实用主义原则**：软件工程往往是在"体系严谨性和一致性"与"解决复杂工程 scenario 需要妥协"之间达到平衡。例如关于"世界上最好的语言"的争论——从学术上讲某语言不够 elegant（优雅），但工程师会认为**优雅没有用，能帮我解决问题的语言都是好语言**。研究 plugin 设计 pattern 也要秉持这种实用主义：**任何架构只要能解决我们的问题，就是好架构**。

#### C. Plugin 版本兼容问题

*   **问题背景**：游戏引擎体系庞大，引擎内核会不停升级（版本结构、数据结构升级），但**很多 plugin 并不能严格保证按版本结构升级**。理想情况是每次引擎升级所有 plugin 一起升级，但大型商业引擎有成千上万的人为其写插件，**做不到**。
*   **对策：接口版本编号**：对接口进行版本编号——plugin 只用了某一版本 SDK（Software Development Kit，软件开发工具包），版本号不变则判定 plugin 有效，版本号变化则无效。
*   **真正的难点**：作为引擎研发者，你开放出接口后**根本不知道插件开发者是怎么用这些接口的**——他可能用了你完全想不到的方式修改内部数据。当你升级内部结构时，那个插件可能直接崩掉，而你认为"接口函数没变、服务都提供了"。**如何在升级中保持插件兼容，特别能体现引擎设计的功力**，非常难。
*   **工程建议**：刚入门写引擎不要对自己提太高要求（**PICO 就没有认真考虑这个问题，做得很简单**）；从业 5~10 年可以认真考虑；**编程 10 年以下考虑这个问题为时过早**——技术开发的复杂度与体系丰富度，往往需要 10~20 年沉淀才能真正理解。**架构师是程序员的终极归宿**。

### 5. 线性叙事系统：Sequencer 与 Timeline

#### A. Storytelling 与时间轴

*   **核心概念**：游戏最大的挑战之一是 **storytelling（叙事）**——很多 3A 游戏做到后来更像"交互电影"。游戏越来越像电影：每一个镜头、角色的每一个动作、每一道光、每一次爆炸、每一次入场都经过精心设计。
*   这一切发生在**一条时间轴**上：到什么时候播放什么背景音、播放什么爆炸效果、希望角色做什么动作（打招呼、开枪、躲进掩体）……大量元素/参数在时间上发生着变化。
*   **适用范围**：线性系统绝不止 Sequencer——很多系统都是线性的（点 play 开始，然后依次发生所有你想发生的事情），例如**特效、游戏 UI**。

#### B. Sequencer 的核心概念

*   **track（轨道）**：对每一个 object（Unreal 中叫 actor）定义一个 track，在 track 里对它的**任何一条属性**定义一条在时间轴上的变化。
*   **keyframe（关键帧）**：设定一些关键变化节点，在关键帧之间做**插值**（可以选择线性插值或曲线插值）。
    *   线性插值公式：$$f(t) = (1 - t) \cdot P_0 + t \cdot P_1, \quad t \in [0, 1]$$ 其中 $P_0$、$P_1$ 是两个关键帧的属性值。
*   **sequence（序列）**：把多个 track 的变化集中在一条 timeline 上，形成 sequence。
*   **电影导演比喻**：拍电影是"三个演员，123 action，所有人同时说话动作"；但游戏世界里要**一个要素一个要素地去生成**——演员一的动作是走到桌前拿起书开始读（分别指定各段耗时），演员二坐到椅子上开口说话，演员三坐在对面开口讲话；把三个演员的 timeline align（对齐）到一起后点 play，画面里所有事就"同时发生"了。
*   **工程观感**：这就是游戏难做的原因——用户看到的事"顺理成章"，但在引擎和游戏世界里，一切都要用零和一、一行行脚本代码**逐个要素生成**，合到一起还要非常合理、符合人对自然的认知。**"我们是躲在像素（零一）之后的人"**。

#### C. 一个完整的例子：让一只小鸡动起来

1.  把小鸡绑定成一个 **track**（绑定到 object 上）；
2.  把它的 **transform**（位移）绑上去，得到一个 **property track（属性轨道）**；
3.  在每个不同位置设置一个 **keyframe（关键帧）**——第一段时间轴放位置一、第二段时间轴放位置二，沿着时间轴一走就形成插值；
4.  想要路径规划时，让它**在几个 keyframe 之间来回走**即可。
*   本质上看，我们修改的就是它的 **component 的一个 parameter（transform 的位置）**。
*   例子虽简单（小鸡很傻），但游戏视频里那些酷炫的表演（如《黑客帝国》系列的镜头、《战地》的宣传视频），本质上就是**一个角色、一个效果在 timeline 上一个一个序列排放好**的结果。
*   **工具体系的一大类需求**：**在时间轴上去让 parameter 动起来或让对象动起来**。UI 也大量如此：暴击后产生击杀头衔、显示"who killed who"、暴击率、命中画面等，全在一条时间轴上发生。很多过场动画甚至**偷偷把场景切换掉**，也是用这套架构。

#### D. Sequencer 与反射的关系

*   Sequencer 最核心的工作是**在时间轴上修改 component 里的几个 parameter**。
*   问题：工具怎么知道去修改 runtime（运行时）里那个对象的数据？中间链接是怎么建立起来的？—— schema 只是描述，你还需要**找到数据、set and get**（先知道当前数据，再修改数据）。
*   **答案：reflection（反射）**——反射是 Sequencer 的 **foundation（基础）之一**。

### 6. 反射系统（Reflection）与 Gameplay

#### A. 反射的本质与价值

*   **核心概念**：引擎不可能预先知道未来基于它开发的游戏会有什么样的 gameplay（例如"顶上去之后射出一根箭、箭能拉动东西"这类玩法）——这些不可能写进引擎。
*   **数据配置有上限**：有的玩法用数据配不出来（**任何语言（数据本身也是一种语言）的表达都是有上限的**），所以必须允许游戏开发团队基于引擎**不断扩展玩法、不断增加新的接口和功能**，工具层必须支持这种扩展。
*   **反射的定义**：在 C++/C（早期语言，没有反射）与 Java、C# 等高级语言的区别在于——**当我写完代码后，系统会告诉我到底有哪些新的功能被暴露出来**，其他调用者**不需要与你的代码链接编译到一起**，就能知道并调取这些新功能的入口。
*   **反射的构成（代码与工具之间的桥梁）**：
    *   引擎实现好功能后，通过反射**生成一个表**，说明引擎开放了哪些类的接口、有哪些功能、有哪些数据可以访问；
    *   生成一堆 **invoke**（调用函数的入口）和一堆 **set/get**（修改和读取变量的入口）。
*   **工程动机**：老师最早搭前几代引擎时用 C/C++，用了大量奇怪的**模板 hack**，核心目的就是找到类似反射的感觉——"我定义了结构和方法，外部接口不需要重新编译就能找到并调用你的方法"。有了反射之后才发现这些工作全是无用功。
*   **举例**：写脚本语言时，若发现你定义的功能"人"有很多属性（身高、体重、血量）可 set/get，有走、跑、跳等动作可 invoke——在可视化脚本语言里创建一个"人"的节点时，其所有属性参数和功能节点全部自动显示出来：动作（走跑跳）是可 invoke 的三角标记节点，属性是可显示可编辑的 property。

#### B. Visual Scripting（可视化脚本）与反射

*   **核心概念**：**Blueprint（蓝图）只是 visual scripting（可视化脚本语言）的一种**，很多引擎甚至游戏之外的应用都会用到，本质类似现在流行的**低代码/零代码开发**——不需要写代码就能构建内容。游戏引擎中的可视化脚本语言，处理的情况是最最复杂的。
*   **核心要解决的问题：可扩展性**。如果语言是预设好的各种节点、只是开放接口让你连接，实现"有点挑战但可以做"，但有个很大缺陷：**每次加新 feature，工具层也要加一行代码**使节点增加接口并能正确调用函数（invoke）。例如今天定义角色有"跳"的动作，明天支持"停止跳"，工具就要改。虽然 C++ 可以通过派生继承新类而不改基本结构，但**工具那边会变得非常复杂**——这是不可扩展、不可维护的。
*   **反射如何解决**：有了反射，写代码后系统自动暴露新功能，工具自动生成对应节点和接口，无需每次手改工具。
*   **为什么设计师不用文本脚本**：程序员天然觉得脚本方便（debug 效率高），但对大量设计师和艺术家，**建立一套语言的编译环境、按语法正确书写**的门槛非常高。他们需要的是"块拖进来，蓝色接口连蓝色线、红色接口连红色线、三角对三角、圆形对圆形"——这是最自然的表达方式。
*   **老师观点**：visual scripting 是**引擎未来发展的方向**，因为它能把引擎开放给足够多的用户；如果认同这个方向，**reflection（反射）就是构建在引擎和工具之间的重要桥梁**。

#### C. PICO 反射系统实现细节

*   **总体原理**：所有现代高级语言都要通过类似规范定义的编译系统编译出去，编译 pipeline 是固定的：**语法分析（parsing）→ 生成抽象语法树（AST，Abstract Syntax Tree）→ 生成中间代码 → 生成 target code（机器能跑的代码）**。
*   **利用 Clang 解析 C++**：大量开源编译器（如 **Clang**）可以把语言翻译成 **AST**。观察一个 C++ 类及其变量定义经过 Clang 分析后，会形成**一个非常好解读的、树状结构的表**——可以很容易地提取任何一个类的接口函数和 member variable（成员变量）。它**不区分语言**，其它语言扔进去也能处理。有了它，生成想要的 **schema** 就很简单。
*   **为什么 PICO 选 Clang**：开源性好、非常模块化、可以自由加载，且本身非常稳定成熟、被最广泛验证过。PICO 选择"最简单最可靠的插件"，Clang 是很好的选择。
*   **内存中的 schema**：PICO **没有显式地把 schema 文件存出来**，只在内存中定义了一个数据结构（可在代码中找到）。
*   **反射的精准控制**：引擎可能有几百个数据结构，**并不是所有数据结构都需要反射**（只有需要和资源打交道、要读写的数据才要反射）。通过**描述词（描述宏）**控制：
    *   第一种描述词：`CLASS` 类（如 `PIC_CLASS` 宏），表示该 class 内**所有 member variable 都要被反射**；
    *   第二种描述词：**`WHITE_LIST_ONLY`（仅白名单）**——类里虽然有十个 member variable，但只有标记了 **`META_ENABLE`** 关键词的成员才被反射（因为有些变量只是计算中间结果，不需要与磁盘/文件交换）。
*   **实现机制（宏 + Clang annotation）**：
    *   C++ 编译器真正编译成可执行文件（exe）时，这些描述词全部是**无效的**；但编译获取反射信息时，通过 `#ifdef`/`#define` 把它 define 成特殊标识；
    *   **Clang 提供了 attribute（属性）机制**：AST 中有一类叫 **annotation（标记）** 的类型，可以把各种标记打进去；最后生成的 AST 代码里会出现 `attribute((annotation(...)))`，把文字放进去。**只要检测到这个东西，就知道下面想让你干什么**。
*   **总结**：看起来很神秘的"给一段 C++ 代码就能生成所有反射"，本质上是一个**简单的"字符游戏"**——程序员到最后对字符非常敏感（缩进、逗号、大括号是否同行都能引发争论），因为**所有精妙的游戏本质上都是字符游戏**。
*   **Unreal 反射**：Unreal 的反射比 PICO 复杂，但**基础的方法和结构跟这个非常接近**，可以类比学习。
*   **Accessor（访问器）**：只有 schema 描述还不够，工具还要大量访问、修改数据、调用方法。每个 reflection 还要生成很多 **accessor**，可理解为三类函数：**get（获取数值）、set（改变数据）、invoke（找到方法并调用）**。
*   **代码生成（Code Generation / 代码渲染）**：
    *   问题：引擎需要反射的类可能有几十个，这些 get/set/invoke 函数**谁去写**？如果程序员手写：第一，代码非常冗余；第二，"说好了接口自动生成，为什么又让我写代码？"
    *   **代码生成（代码渲染）概念**：Web 端早就发现——要生成大量逻辑大同小异、只有数据不同的页面，前端代码应该自动生成。它几乎找不到缺点：
        1.  **大量减少冗余代码开发**；
        2.  **减少犯错**——生成出来的代码一次性通过之后很少出错（PICO 的 schema 系统代码放了**快 10 年几乎不出错**，因为全是自动生成的，"如果出错早就出错了"，写 10 万行、生成 100 万行也不会出错）；
        3.  **把数据和逻辑完美分离（decoupling，彻底解耦）**。
    *   **架构原则**：能通过自动化生成的代码**尽量自动化生成，不要手写**——手写过程不可控，很容易"昨天版本没问题，后天版本有问题"。
    *   **PICO 使用的工具：Mustache**（英文原意"胡子"，因为描述代码时要加很多大括号，像人套了很多大胡子）。它通过数据语法的翻译，**自动渲染出你想要的代码**，非常简单、稳定。
    *   **PICO 完整反射流程**：① 调用 **Clang** 生成内存中的 **schema**；② 生成 schema 之后，根据预先写好的**程序模板**；③ 再调用 **Mustache** 生成大量的 **accessor code**。最终实现：**引擎里定义任何一个结构，编辑器里就能互相看到**。

#### D. 反射与运行效率

*   **对引擎本身**：反射代码不用它，就不会产生任何 **overhead（额外开销）**，对引擎运行没什么影响。
*   **在工具里的频繁调用**：在工具里频繁调用反射代码（get/set/invoke）时，很多时候**通过字符串去查找函数指针/map**（按字符串 search），会有效率影响。**优化手段：把字符串优化成 string id**，反射查找会更快。
*   **大批量数据编辑场景**：刷草和植被的刷子会一下子创建很多物体、很多物体属性都要被反射一遍；sequencer 要改变很多 parameter——**编辑时可能有效率影响**。
*   **Runtime（运行时）**：这些数据不会影响，**反射主要是在 editing（编辑）时使用的东西**。

### 7. 协作式编辑（Collaborative Editing）

#### A. 为什么要协作编辑

*   **核心概念**：现代 3A 游戏、开放世界的数据量和维度，**远远超过一个人能够 handle 的能力**，客观上需要很多人共同编辑。**协作式编辑被认为是下一代游戏引擎发展的重点方向**。
*   **为什么不全靠程序化生成**：P4（Perforce）版本管理 + PCG（程序化生成）方法听起来很了不起，但游戏真正的核心是 **novelty（新鲜度/生动度/创新度）**——一个 PCG 算法足够成熟之后，其 pattern（模式）很容易被玩家发现，所以仍需要大量 artist 的**灵光一闪的创意**。（假设强人工智能还很遥远；若如 Altman 设想 2030 年实现强人工智能，novelty 可以交给 AI 解决，工具体系会重新设计。）
*   **协作最容易出的问题：冲突**——我改的东西和你改的东西发生冲突。

#### B. 三种空间划分思路（传统协同编辑）

1.  **按图层分层（Layer）**：把世界进行分层——编辑地形的编辑地形、编辑植被的编辑植被、编辑建筑物的编辑建筑物，甚至区分"建筑物"和"周围小装饰物"。每个 artist 只编辑自己的层。
    *   **优点**：古老的、很早就被引擎支持的方法。
    *   **问题**：
        *   分层**很难分得特别好**，且不同层的东西**相互依赖**——地形 artist 改地形后，上面的植被排布必须相应变化；一个 artist 改了房子位置，周边种的树、地面的调整都要变。若是三个互相看不见的 artist 一起做，会产生**无数的问题**。
        *   "轮流做"（第一个做完锁定分层，另一个基于它继续做）可行，但**同时做效果很差**。
2.  **按地块划分（Tile / Chunk）**：把世界分成一块一块，这块归你、那块归我。
    *   **优点**：简单好用。
    *   **问题**：**跨块（cross-boundary）的对象**——跨界房子、跨两界的山脉、植被分布、湖泊怎么办？是否要支持**不规则的世界划分**？就像欧洲某些国家的国界上，一栋房子左边属于一个国家、右边属于另一个国家。而且**玩家看到的场景是连续的**，如果边界处有明显区别，艺术家和玩家都接受不了（可最后安排一波 artist 专门修边界）。
3.  **Unreal 5 的 One File Per Actor（OFPA，每 Actor 一文件）**：很极端的方案——既然世界容易冲突，就给**每个对象创建一个文件**，每个人只改自己的文件，彼此再也不会冲突。
    *   **优点**：确实能**彻底解决协同编辑里的冲突问题**（虽然会产生大量小文件，引擎会做很多机制管理小文件）。
    *   **问题（两个现实问题）**：
        *   **版本管理痛苦**：场景做完提交新版本时，需要提交**非常多的文件**；Perforce（P4）、SVN 等 source control 软件对**大量文件的版本管理非常痛苦**，最后整个工作室都卡住、更新不了数据。
        *   **Cooking 打包**：碎文件不能直接放在内存中（否则游戏性能特别低），cooking（烘焙/打包）时**必须把所有这些文件打包到一个 level 文件里**——多了一个额外过程，且面对的是**上万个文件**。**操作系统最恨的就是小文件**，会产生很多额外负载。
    *   **结论**：这是一个非常值得关注的**前沿方向**——本节讲的每个问题总有技术方法可以绕过去，而 OFPA 是能彻底解决冲突问题的方向。

#### C. 实时协同编辑的技术基础

*   **终极状态**：张三、李四、王五同时在编辑，彼此之间都能看到对方。这需要一套**网络架构**——一般在**工作室局域网（内网性能非常高）**里实现。
*   **真正的难度不是状态同步，而是保持语义的高度一致性**。
*   **Command（命令）原子化**（回顾上节课的 command 概念）：把用户的每一个操作——一个拖动、一个选取、一个平移、一个改颜色、一个改材质、一个改参数，包括 **sequence 里每一个 keyframe 的增删**——全部变成**原子化的操作（command）**，然后在所有人的电脑上**同步 command**。这样协同编辑才能真的做下去。
    *   **没有这个基础，所谓的协同编辑一定是个 hack**——看上去大概很像那么回事，但艺术家真正使用时会发现很多地方**违反人的直觉**。
*   **人的直觉例子**：几个小朋友在画布上画画——你画了蓝色，我画了紫色，蓝色先画下去、紫色后画下去，紫色穿过蓝色区域就应该覆盖蓝色（因为我在你后面）；另一个小朋友又点了一个绿点，一半在蓝色区、一半在紫色区；此时画紫色的小朋友说"我想 undo（撤销）一下"——问题就来了：绿点和那条紫色杠杠之间到底是什么关系？
*   **Undo / Redo 的复杂性**：创建了一个 instance 并编辑，别人觉得很好又做了其他调整，而你随后觉得不对想 undo（重种一棵树）——可能**别人做的所有操作当场就崩掉**。
*   **处理冲突的方案**：
    1.  **加锁（Lock）**：给一个对象加锁——"这一片都是我的，锁上了你们不能编辑"，保证没有冲突，但**会产生竞争**；"这个资源是我的、你不能动"有时也有用（例如我要改模型的材质，不希望别人同时改材质冲突，就显示地告诉你该资源被锁上了——锁信号可以以**几十毫秒**的速度瞬间同步给别人）。
    2.  **OT（Operational Transform，操作转换）**：通过转换操作来协调并发，理论性很强、很难。
    3.  **CRDT（Conflict-free Replicated Data Type，无冲突复制数据类型）**：引擎里常用的方法——通过一套规则体系让 conflict 变成 free，同时让各个状态在各个终端同步。（展开细节非常深，本节不深入。）
*   **Server 统一结算模型（C/S 模型）**：现在比较推荐的做法——**把所有的操作不要直接 apply 到最终结果上，先找一个 server，把所有操作收在一起，结算完之后再统一地发给大家**。类似网络架构里的 **C/S（客户端/服务器）模型**：所有客户端只发起动作，由 server 统一结算后把最终结果返回给每个 client 自己去看。
    *   **好处**：没有争议（无冲突）；
    *   **代价**：一点点延迟——在局域网情况下可以接受；
    *   这是现在很多协同编辑游戏引擎采用的结构。
    *   **风险**：客户端机器炸了没关系，但**被选做服务器的艺术家机器炸掉，一群人直接就崩掉**——系统的**健壮性（鲁棒性）**还需要专门设计。
*   **行业现状**：协同编辑是理论上非常热门的领域（网络普及使协同操作成为越来越重要的需求）。文本编辑领域（Google Docs 早期功能很受限，第一次发现彼此能看到对方的边界时很震撼；如今的 PS 等工具协同已做得很成熟）经历了非常漫长的演进过程。**游戏引擎的实时协同编辑仍处于非常早期的阶段**，是下一代引擎研发很关键、很前沿的方向。

## 二、重点术语与概念解析

### 1. WYSIWYG
*   **定义**：What You See Is What You Get，所见即所得——编辑器里看到的效果与真实游戏运行效果一致。
*   **应用/注意点**：现代游戏生产的重要指标；view 需要呈现"编辑效果 = 游戏效果"；这是把工具包在引擎外面架构方案的核心理由。

### 2. Genre
*   **定义**：读作"让"，源自法语，指游戏类型，如 RPG、FPS、MOBA。
*   **应用/注意点**：不同 genre 的编辑操作、gameplay 设置、关卡 layout 与组织规范完全不同，是工具链复杂性的来源之一。

### 3. Editor Mode
*   **定义**：引擎运行的一个模式 flag，VIEWPORT 在编辑器里以该模式运行。
*   **应用/注意点**：editor mode 下可以做真实游戏不能做的事：自由飞行相机、无视碰撞、透明化、debug draw、wireframe、额外渲染选取帧等。

### 4. Editor Only 代码
*   **定义**：只在编辑器编译版本中存在的引擎代码，发布版本被剔除。
*   **应用/注意点**：若不严格区分，编辑器代码被编译进上线游戏会成为外挂入口（透明世界、直接选取、自由飞行等）。

### 5. Gadget
*   **定义**：编辑器里的基础操作小工具，如小坐标系、选点、选中、grouping、snap。
*   **应用/注意点**：最基础操作用 native code 实现效率最高；复杂逻辑交给编辑器层。

### 6. Content Browser
*   **定义**：内容浏览器，把资产从静态文件目录变成"资源海洋/大池子"的资产管理方案。
*   **应用/注意点**：按名字检索、按项目形成不同 view；资产可放中央数据库（studio 数据仓库），需要时才加载进内存；面向未来的引擎必须考虑。

### 7. Height Field / Height Brush
*   **定义**：高度图——以二维网格存储高度值的地形表示；高度笔刷是对高度图做编辑的笔刷。
*   **应用/注意点**：地形 = height field + texture；笔刷操作时对信号做 smooth 最重要，否则会出现沿 45° 切向的过渡角（锯齿感）。

### 8. Instance Brush
*   **定义**：实例笔刷，用于刷 detail、decorator（小草）、tree 等大量实体。
*   **应用/注意点**：每棵树独立存储、静态属性、所见即所得；缺点是几十平方公里时内存占用大、预处理麻烦，后续需 PCG 解决。

### 9. Rule System（规则系统）
*   **定义**：用一套形式化规则（graph 图结构）表达环境编辑约束，把原始数据分层后交给计算机自动生成合理分布的系统。
*   **应用/注意点**：解决"修路后树不能长路上、草不长路边、路要平整又要贴合地形"等跨插件约束；真正难点是定义简单易懂、好维护的形式化语言。

### 10. Deterministic / Locality
*   **定义**：程序化生成的确定性——局部修改时其他已生成区域不变；局部性（locality）即生成数据只受局部输入影响。
*   **应用/注意点**：是实战化 world editor 的重要属性，避免"满意区域被全部重新生成"。

### 11. Plugin 协作模型
*   **定义**：插件之间的四种协作方式：Override（覆盖模型）、Distribute（分布式）、Pipeline（流水线）、Onion（洋葱圈）。
*   **应用/注意点**：真实 production 中四种模型都会用到，架构要保持强开放性，不要预设单一模式。

### 12. Sequencer / Track / Keyframe / Sequence
*   **定义**：Sequencer 是 Unreal 的线性叙事工具；track 是每个 actor/object 的一条属性轨道；keyframe 是属性变化的关键节点；sequence 是多个 track 在 timeline 上组合成的序列。
*   **应用/注意点**：在时间轴上驱动 parameter/对象变化，是过场动画、特效、UI 事件序列的通用架构；其 foundation 之一是反射。

### 13. Reflection（反射）
*   **定义**：程序在运行时自我描述的能力——系统告诉调用者某个类暴露了哪些接口、功能、数据，并提供 invoke 与 set/get 入口。
*   **应用/注意点**：代码与工具之间的桥梁；C++ 没有原生反射，PICO 通过 Clang + 宏 + 代码生成实现；反射主要在编辑期使用。

### 14. Schema
*   **定义**：对数据类型/结构的描述（描述哪些字段、字段类型、是否可编辑）。
*   **应用/注意点**：编辑器根据 schema 反射属性、自动生成编辑界面；PICO 在内存中维护 schema 数据结构，不显式存文件。

### 15. AST（Abstract Syntax Tree，抽象语法树）
*   **定义**：编译器在语法分析后生成的树状结构语言描述表。
*   **应用/注意点**：Clang 可将 C++ 翻译成 AST，从中可提取类的接口函数与成员变量，是反射生成 schema 的基础。

### 16. Clang
*   **定义**：一个开源、模块化、成熟稳定的 C/C++ 编译器前端（可解析成 AST）。
*   **应用/注意点**：PICO 反射管线第一步用它生成内存中的 schema；其 annotation 机制（`attribute((annotation))`）用于识别用户自定义标记。

### 17. Mustache
*   **定义**：一个代码/模板渲染工具，英文原意"胡子"，用大量大括号描述模板，根据数据语法翻译自动渲染出目标代码。
*   **应用/注意点**：PICO 用它根据 schema + 模板生成大量 accessor 代码；简单稳定，属于代码生成实践。

### 18. Accessor（get / set / invoke）
*   **定义**：反射生成的访问器函数：get 读取数值、set 修改数据、invoke 调用方法。
*   **应用/注意点**：工具访问/修改 runtime 数据的入口；频繁字符串查找时可优化为 string id 提高效率。

### 19. Code Generation（代码生成）
*   **定义**：通过模板 + 数据自动生成源代码的技术。
*   **应用/注意点**：减少冗余代码、减少犯错（生成代码一次通过后很少出错）、数据与逻辑彻底解耦；架构大系统时能自动生成就自动生成。

### 20. Visual Scripting
*   **定义**：可视化脚本语言，Blueprint 只是其中一种；类似低代码/零代码开发。
*   **应用/注意点**：核心问题是可扩展性——靠反射自动暴露新接口；对设计师/艺术家门槛低（颜色/形状对口连接），是引擎未来发展方向。

### 21. Blueprint
*   **定义**：Unreal 引擎的可视化脚本语言（visual scripting 的一种）。
*   **应用/注意点**：程序员觉得脚本 debug 效率更高，但设计师与艺术家需要更直观的块状连接方式。

### 22. Command（命令）
*   **定义**：把用户的每个编辑操作（拖动、选取、平移、改参数、增删 keyframe 等）原子化后的操作单元。
*   **应用/注意点**：同步 command 而非最终结果，是实时协同编辑的基础；没有原子化 command，协同编辑必然是 hack。

### 23. OT（Operational Transform）
*   **定义**：操作转换，一种处理并发协同编辑冲突的理论方法。
*   **应用/注意点**：通过转换不同终端的操作序列来保证一致性；理论性很强、非常难，常用于文本协同编辑（Google Docs 等）。

### 24. CRDT（Conflict-free Replicated Data Type）
*   **定义**：无冲突复制数据类型，通过设计使并发的写操作天然可合并、无冲突。
*   **应用/注意点**：游戏引擎协同编辑常用方法；通过规则体系让 conflict free，并使各终端状态同步。

### 25. OFPA（One File Per Actor）
*   **定义**：Unreal 5 提出的"每个 Actor 一个文件"的资产组织方式。
*   **应用/注意点**：彻底避免对象级冲突；缺点是版本管理提交大量文件（P4/SVN 痛苦）与 cooking 时要打包上万小文件（操作系统最恨小文件）。

### 26. DCC
*   **定义**：Digital Content Creation，数字内容创作工具（3ds Max、Maya、ZBrush、Houdini 等）。
*   **应用/注意点**：与引擎工具的分工边界是动态的，趋势是两者大量融合（DCC 提供引擎 runtime preview；引擎集成 K 动画、雕刻等 DCC 功能）。

### 27. PGC / PCG
*   **定义**：Procedural Content Generation，程序化内容生成（如程序化生成地形、城市、植被分布）。
*   **应用/注意点**：PGC 生成的内容 pattern 易被玩家发现，仍需要 artist 的创意（novelty）；生成需满足 deterministic/locality。

### 28. P4 / SVN
*   **定义**：Perforce（P4）与 Subversion（SVN），常见的游戏行业版本控制（源码/资产管理）软件。
*   **应用/注意点**：大量小文件的版本管理会让它们非常痛苦，导致工作室卡住、更新不了数据。

### 29. String ID
*   **定义**：把字符串映射为整数 id 的优化技术。
*   **应用/注意点**：反射查找函数指针时用字符串 search 较慢，优化成 string id 后反射查找更快。

### 30. Novelty
*   **定义**：新鲜度/生动度/创新度——游戏内容中不可被程序化算法完全复现的创意部分。
*   **应用/注意点**：这是仍需大量 artist 协作、不能被 PCG 完全替代的核心价值。

### 31. Intermedia Format
*   **定义**：中间格式，如 FBX 等 DCC 导出格式，用于在不同工作室/工序之间传输文件。
*   **应用/注意点**：适合传输，但不是 engine-friendly（引擎友好）的格式——引擎数据要求效率、可打包（packaging）、可加密、可流式传输。

### 32. MVVM
*   **定义**：Model-View-ViewModel 架构模式，数据模型与视图分离。
*   **应用/注意点**：object 系统要"数据 model 动起来"，view 可提供多种不同呈现方式。

## 三、工程经验与避坑指南

### 1. 开课 Q&A 与课程决策

*   **上一节作业延期**：考虑到很多同学速度快、也有同学需要时间熟悉小引擎代码，且 B 站持续有新同学补课，上一节课作业延期到**本月下旬**，具体时间争取在下一节课或微信群里同步，尽量 flexible（灵活）。
*   **为什么 PICO 不用 FBX 等公开格式**：
    *   这些格式直接来自 DCC 软件，很多人使用，但当时最核心的考虑有两点：
        1.  **让 PICO 引擎越简单越好**——FBX 格式非常成熟丰富完善，接入它需要引入完整的第三方库，还要做复杂的数据转换；
        2.  **教学目的**：从 schema 反射到 custom format（自定义格式）是一个完整的组合关系，希望同学们一上来就习惯、适应这种设计。
    *   商业级引擎**一般不会直接用 DCC 格式**——FBX 是很好的 **intermedia format（中间格式）**，但不是效率/engine-friendly 的格式。游戏数据格式要求效率、**packaging（打包）、加密、流式传输、流市场（实时流送）**，要求非常高。
*   **为什么 Mac 版不用 Metal 而是用 MoltenVK（转译）**：
    *   Vulkan 相比 OpenGL 复杂很多（老师已被同学"狂喷"），选 Vulkan 是因为**让同学们直接接触现代 GPU API 结构**——它非常接近 driver 的写法，效率最高、最具有工业化基础。
    *   Vulkan 本身已很复杂，如果再上 DX12、Metal 版本，开发团队工作量巨大（开源小引擎、同学们业余时间写），学习门槛也更高。
    *   **方案**：统一用 Vulkan 一个版本，其它平台用一个**中间件把它翻译过去**（如 Mac 上实际跑的还是 Metal 指令，只是由中间件自动翻译成原生指令）。

### 2. 引擎与 World Editor 架构避坑

*   **VIEWPORT 跑的是完整游戏**：这是 WYSIWYG 的最基本保证，一定要记牢。材质、光照反射、过场动画等细腻效果依赖此架构。
*   **编辑器代码与外挂**：务必把编辑器代码包在 editor only 宏下面，不要编译进发布游戏。大型团队（引擎工程师上百人）里，没有经验的开发者应策划/设计师要求做了好用的工具，却**忘了把代码包在 editor only 里**，结果被编译出去——这是新入行同学特别容易犯的错误。
*   **不要一上来写拖拽编辑器**：一上来写 3ds Max 式拖拽逻辑会快速得到"很酷"的编辑器并产生错觉；要先把 world editor 定义为 **hub**，架构优先于 feature。
*   **尊重商业级引擎**：商业引擎核心不在一个 feature，而在于**整个体系架构的逻辑**。
*   **多 Viewport 需要引擎改造**：多个 view 不能拷贝多份数据做同步（等于本地写小网络）；编辑器视口架构要求引擎**兼容多个 view**，也服务于游戏里的"画中画"需求。
*   **object 系统要坚持 MVVM**：数据 model 动起来，view 可多变，适应不同 artist 的习惯。

### 3. 编辑器开发与工具链实战经验

*   **开发机性能陷阱**：做编辑的开发机配置远高于玩家机器（主机有 dev mode 额外内存、PC 配最好显卡），导致"本机没问题、用户那边卡"的经典误判。
*   **鼠标选取的细节**：
    *   粗选（raycast 包围盒）快但可能误选（胶囊体 vs 几万面片）；
    *   精准选可用**额外选取帧（object id 打到 frame buffer）**，费一点性能没关系；
    *   **透明物体（particle/玻璃）不写 depth buffer 会被过滤掉**，需要特殊逻辑（particle 选中根虚拟体）。
*   **Transform 操作要打磨**：热键、gizmo 高亮、整度数旋转（5° 步进、90°/45°/180°/135°/30°/60°）、对齐等习惯细节，写好几需要数月，是商业引擎的门槛所在。
*   **高度笔刷要重 smooth**：刷出来的山"不自然"的差距不在笔刷种类，而在**过渡平滑**；避免沿 45° 切向的明显过渡角（zz 锯齿感）。
*   **工具要可扩展**：提供"艺术家自己导入高度图/定义笔刷"的能力会让他们乐此不疲（Houdini 更强大）；做工具**首先看扩展性，而不是算法多厉害**。
*   **环境编辑必须用规则系统**：修路若不处理"路不长树、沿地形起伏、路要平、两边有路基"的规则，artist 手工工作量巨大，且设计师一改方向全部重做——必须用程序化 + rule system 自动解决。
*   **程序化生成要有确定性/局部性**：改局部时不要重新生成已满意的区域；这是实战化 world editor 的重要属性。
*   **插件设计保持开放**：Override、Distribute、Pipeline、Onion 四种模型在真实 production 中都会用到，**不要预设所有 plugin 按一种模式走**；坚持实用主义——能解决问题的架构就是好架构。
*   **插件版本兼容是硬功夫**：给接口做版本编号（SDK 版本号不变则 plugin 有效）；要警惕插件开发者用你完全想不到的方式使用接口，导致内部升级后插件崩溃。这是引擎设计功力最难体现处之一，**编程 10 年以下考虑这个为时过早**。
*   **能自动生成的代码就不要手写**：手写不可控（昨天没问题、后天出问题）；自动生成代码（如 Mustache + schema）一次通过后几乎永不出错（PICO schema 系统 10 年几乎零错误），且数据与逻辑彻底解耦。

### 4. 协作式编辑的实践经验

*   **传统分层的坑**：分层难以分好，且不同层相互依赖（改地形 → 植被排布变、改房子位置 → 周边树和地面都要变），三个互相看不见的 artist 一起做会产生无数问题；"轮流做、锁定分层"可行但无法同时做。
*   **分块的坑**：跨块对象（房子、山脉、湖泊）归属难解决；玩家看场景是连续的，边界明显差别不可接受（可安排专门 artist 修边界）。
*   **OFPA 的坑**：版本管理提交大量文件会让 P4/SVN 卡死整个工作室；cooking 时面对上万小文件打包，而**操作系统最恨小文件**。
*   **协同编辑没有 command 原子化就是 hack**：必须把每个操作（含 keyframe 增删）变成原子化 command 再同步，否则违反人的直觉。
*   **Undo/Redo 是协同编辑最难的题**：一个人 undo 可能崩掉别人基于其结果的后续操作（如"重新种一棵树"撤销掉别人对那棵树的调整）。
*   **Server 统一结算的鲁棒性**：C/S 结算模型无争议、延迟局域网可接受，但**服务器那台 artist 机器炸掉会导致一群人崩溃**，需要专门设计健壮性/鲁棒性。

### 5. 职业发展与架构心法

*   **架构师是程序员的终极归宿**：技术开发的复杂度、体系的丰富度需要 10~20 年沉淀才能真正理解；不建议写几年代码就急着转管理。
*   **语言的优雅与实用**："优雅有什么用？能帮我解决问题的语言都是好语言"——研究 plugin 设计 pattern 要秉持实用主义。
*   **编程是字符游戏**：程序员对缩进、逗号、大括号位置等字符细节极度敏感（甚至为此争吵），是因为所有精妙的游戏本质上都是字符游戏。
*   **尊重行业规律**：3A 游戏的 storytelling 让游戏"越来越像电影"，虽然老师个人调侃"这违反游戏精神"，但作为玩家仍很 enjoy，且"云游戏"能覆盖 80% 内容。

### 6. 结课 Q&A

*   **Q：小引擎的反射系统会输出详细的代码讲解文档吗？**
    *   A：课程组确实在准备，可能会通过 **wiki 的形式**（系统更全面），也可能通过视频形式呈现。
*   **Q：反射会不会影响运行效率？**
    *   A：反射代码不用时**不会产生任何 overhead**，对引擎本身没有影响；但在工具里频繁调用反射代码（get/set/invoke）时，**通过字符串查找函数指针/map 的 search** 会有影响，**可优化成 string id** 让反射查找更快。大批量数据编辑（刷草刷植被创建大量物体、sequencer 改变大量 parameter）时**编辑期**可能有效率影响；**runtime 时不受影响**，因为反射主要是在 editing 时使用的东西。
*   **Q：在现在的游戏开发中，DCC 工具和引擎工具之间的分工到底是什么？**
    *   A：这个问题非常大也非常难，**边界是动态的、一直在变化**。两个趋势：
        *   趋势一：现代 DCC 工具（3ds Max、Maya、ZBrush、Houdini）越来越强大，它们都 prefer 你在工具里做尽可能多的东西，甚至提供**类引擎 runtime 的 preview**，可以把引擎集成进来做一个 **viewer**；
        *   趋势二：一些前沿引擎希望把很多 DCC 的功能**直接集成到引擎里面**。例子：Unreal 5 的 **rig 系统**（在引擎里直接手 K 动画）。传统做法是"角色手抓扶手说话"这种动画：把场景导出成建模到 3ds Max/Maya，artist 精准地把手放上去做动画，再导回引擎对准位置——过程非常痛苦。所以 artist 希望引擎直接手 K；有些引擎甚至直接把 DCC 工具买进来集成到体系里。
    *   结论：**两边不是分家，而是大量融合**——这符合引擎作为生产力工具的客观需求，**以艺术家怎么方便怎么来**。老师个人关注的方向：**把 DCC 功能直接集成到引擎里**，减少 artist 在不同工具间来回切换的痛苦。因为数据每次 exporter/importer 来回倒一次，就多一次**产生错误的机会**，还会极大地下降内容生产效率、让内容生产变得更不直观、更容易出错。

## 四、本期作业：开放性命题——打通"资产 → 反射/Schema → 编辑器"链路

### 1. 作业背景与目标

*   PICO 小引擎最核心的就是它的资产系统：同学们常问"为什么用自己的 format（JSON 格式）"——配合自动的 schema 和反射系统，编辑器里可以自动产生所有编辑界面，还做了一个小小的 content browser、旁边的 property panel。
*   **作业命题（开放性）**：在资产（asset）里**定义一种自己的属性**，把这条链路全部打通：
    1.  **资产层**：从 JSON 格式的资产文件读进来；
    2.  **引擎数据层**：反射 schema 能把自定义数据**反射上来**（数据能读进来、存出去）；
    3.  **编辑器层**：在编辑器里能看到并编辑它；
    4.  **Gameplay 层**：一键点 Play 时，这些属性**真的能和引擎代码起作用**，产生真实的 gameplay 效果。

### 2. 作业示例

*   第一个实例是角色（rigid body、mesh、animation），可以给它加一点小小的逻辑，例如：
    *   角色自动打枪；
    *   增加一个**血量（HP）**属性——从高处跳下来会摔死，定义"从多高摔下来受到多少伤害"这两个变量，尝试在 PICO 引擎里把属性增加到 character 里面。
*   同学们可以自由发挥——**只要定义了自己的 custom data，通过整套反射/schema 系统反射上来，资产里数据真的能读进来、存出去，并且真实产生 gameplay 效果，作业就算完成**。
*   **注意**：因为二次开发接口还没完全开放，需要**直接改 PICO 的代码**，没关系。

### 3. 提交方式与支持

*   沿用老方法：把自己的**作业思路、实现的代码、效果的截图**展示出来发给课程组，课程组会给大家反馈与帮助；有困难时课程组（公社观的小伙伴）也会帮助解决。
*   更详细的作业要求会放到**官网上**，同学们有问题随时可以问。
*   本次是第一次尝试开放性作业，对写引擎的人来说很简单，但对同学们来说**一上来摸一摸还是有些挑战**。
