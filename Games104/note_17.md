# 高级 AI 技术：层次任务网络（HTN）、目标导向规划（GOAP）与蒙特卡洛树搜索（MCTS）

## 一、 核心知识点与原理剖析

### 1. 课程引入：从行为树到高级 AI

*   **行为树（Behavior Tree）的本质是"反应机器"（reaction machine）**：当世界给出各种各样的输入时，AI 做出各种各样的反应。它更像无脑的条件反射（像巴甫洛夫的狗，看见、闻到什么东西就做出固定的几个动作），缺少人类的**意识（consciousness）**——即**主观意图（goal）**（"我想让自己变得更好"这类目标驱动）。
*   **行为树的局限**：设计师在构建行为树时，表面上是在逐个展开节点（如 `selector`、`sequencer`），但实际心理是"希望 AI 完成某件事"（保护自己、成为战场上最猛的 AI）。然而行为树把目标**隐含**在树的结构中，只能通过注释表达"这棵子树是干什么的"，**目标不直观**。行为树无法直接表达"我为什么要做这些动作"。
*   **HTN（Hierarchical Task Network，层次任务网络）**从另一个角度解决问题：从**任务目标**出发，把 AI 的行为表述成"若干个我要完成的任务 + 完成每个任务所需的多种子任务 + 每个子任务的选项"。其使用者和代表作包括《地平线》（Horizon）、《杀出重围》（Deus Ex）等 3A 大作。
*   **本节课程预告**：依次讲解 HTN、GOAP（基于目标的行为规划）、MCTS（蒙特卡洛树搜索），以及基于机器学习的方法（本节后半部分与后续内容）。

### 2. 层次任务网络（HTN）

#### (1) HTN 总体框架

HTN 框架由以下部分组成：

*   **World State（世界状态）**：AI 体大脑中对世界的认知状态。
*   **Sensor（感知器）**：从游戏环境中抓取各种状态（类似之前的 `perception`）。
*   **Domain（任务域）**：层次化的树状结构 `task` 以及它们之间的关联关系。
*   **Planner（规划器）**：根据当前感知到的世界状态，选择任务并制定计划（make a plan）。
*   **Plan Runner（计划执行器）**：依次执行计划中的 task，并监控所有正在执行 task 的状态。
*   **Replanning（重新规划）**：当计划执行失败或世界状态发生重大变化时，重新制定计划。

#### (2) World State 与 Sensor 的辨析（易错点）

*   **World State 不是对客观世界的真实描述**，而是 **AI 大脑中对世界关键要素的主观提炼与思想**。这是初学者最容易犯的错误——会误以为它记录"面前有几个敌人、关卡处于什么阶段、自己的血量"等客观事实。老师点评：提出这个算法的作者带有**主观唯心主义**式的哲学思维（世界是"在我的认知里构造的"）。**区分 world state 与 sensor 非常重要**，因为后面算法计算时二者各自发挥作用。
*   **Sensor 更像是 perception**：负责从游戏环境抓取各种状态。
*   人类行为类比：`perception` 感知世界 → `consciousness`（主观意识）做出行为 → 行为产生的结果反过来**改造世界**。

#### (3) Primitive Task（原子任务）

*   **定义**：最简单的任务，本质是一个**动作（action）**，可通过脚本等方式执行。
*   **与行为树叶子节点的区别**：行为树并不强制要求每个叶子节点有 `precondition`，也不明确描述动作做完后对世界的影响；而 HTN 中每个 primitive task 有**三个关键要素**：
    1.  **动作本身**：写脚本或代码执行。
    2.  **Precondition（前置条件）**：对 world state 的**读操作**——满足哪些 state 条件时该 task 才会真正执行，否则返回 `false`。
    3.  **Effect（效果 / 修改器）**：对 world state 的**反向写操作**——动作成功完成后对世界状态的修改。
*   **注意**：即使所有 precondition 都满足，task 执行过程中仍**可能失败**，并非所有 task 一定会成功。
*   **示例：使用解药（use potion）**
    *   Precondition：我首先需要有一瓶解药。
    *   Effect：解除我的中毒状态；解药数量减一。
*   **示例：使用万能药（super potion）**
    *   Precondition：有万能药。
    *   Effect：万能药数量减一；无论中毒还是 `sleeping` 等状态全部解除。

#### (4) Compound Task（复合任务）

*   **定义**：HTN 的**核心与精华**，由很多个 **method** 构成。
*   **Method 与 Priority**：
    *   每个 method 有一组 `precondition`，method 从上到下本身暗含 **priority（优先级）**。
    *   每个 method 可理解为完成该任务的一种**方案**：优先选择第一种方案，若其 precondition 不满足则尝试第二种、第三种……若全部不满足，则该复合任务整体失败。
    *   类比行为树：method 之间的选择关系**类似 `selector`**。
*   **Method 内部的子任务序列**：每个 method 指向的**不是单一 task，而是一串 task（task 序列）**，这些子任务必须**依次成功执行完**，该 method 才算成立——**类似行为树的 `sequencer`**。
*   **通俗理解**：compound task ≈ `selector` + `sequencer` 的组合（老师说这是团队精读论文后的总结，但**存在很多细微差别**，实现自己的 HTN 时切勿被这个简单类比带偏）。
*   **设计师友好**：HTN 把"用 selector/sequencer 构建逻辑"的抽象思维**打包**成了"原子任务 / 复合任务"。设计师只需理解：复合任务里有一组带优先级的选项，选好之后依次完成一列子任务即可，无需记忆 selector/sequencer 这些抽象名词。
*   **示例：解读（cure poison）任务**
    *   方案一（优先）：材料足够 → `make a potion`（制造解药：检查材料 → 材料减掉 → 药数量增加）→ `use a potion`（确认有药 → 状态恢复 → 药数量减一）。
    *   方案二：没有材料 → 去买药水（先 `buy a potion` 再去用它），进一步展开：先跑到 NPC store，与 NPC 对话等细节。
    *   体现的"小气 NPC"行为偏好：优先造药、其次买药、实在不行才用自己的药水。

#### (5) Root Task（根任务）与任务构建

*   **Root Task**：整个 HTN 网络中唯一的特殊任务，一般是一个 **compound task**，从最高层（high level）定义 AI 的核心行为。以精英小怪为例：优先砍人；血量不行/中毒时要自救；遇到打不过的敌人要逃跑；没有敌人也没有异常状态时就闲晃（idle）。
*   **构建方式**：用 primitive task 与 compound task 两大"神兽"（核心构件）即可像用 0 和 1 一样构建整个 HTN 网络，从 root task 一层层展开，最终展开到 primitive task。

#### (6) Planning（规划）过程

1.  根据当前 world state 与 root task 中 task 的 priority，**优先选择一个当前目标 task（goal）**。
2.  从该 task 的 method 开始，把所有 task 一层层展开，直到全部展开为 primitive task。
3.  **关键细节一（脑内推演与草稿拷贝）**：规划展开的推演过程是"电光火石之间"在脑中完成的。由于每个 primitive task 完成成功后会通过 `effect` 修改世界状态，而这些修改会成为后续（可能相隔几步的）task 的 `precondition`，因此规划时必须**对 world state 做一份拷贝（想象成抄到一张草稿纸上）**，在拷贝上推演"找到 NPC → 买到药水（药水数量 +1）→ 启动使用药水操作"这样的因果链，否则后续计划无法成立。
4.  **关键细节二（乐观假设）**：规划时**假设所有 action 都会成功**（其实执行会持续几秒甚至几分钟，期间世界会发生很多变化，这个问题由 Replanning 解决）。
5.  **失败回溯**：若某个 task 的 precondition 无法满足（例如要买药水但需要"坐骑"，而当前没有坐骑、NPC 商店在另一个城市且无法传送），则返回 `false`，错误信息一路往回返（回溯），跳到父级尝试下一个方案；若一路打回 root task 仍无更好选择，则该最高层任务整体失败，再依次尝试 root 的下一个任务。
6.  整个树按此规则遍历完成后，输出的 task 序列**一定是一串 primitive task**，交给 Plan Runner 依次执行。

#### (7) Plan Runner 与 Replanning（重新规划）

*   **Plan Runner**：愉快地依次执行制定好的计划（"Sounds like a plan"）。由于游戏世界高度动态（玩家、其他 AI 都在向世界输入），很多 task 会失败。
*   **混沌系统视角**：类比"三体理论"，当世界参与者不再是单一个体时，世界是**混沌系统**——即使每个 AI 的算法都很简单，放入足够多的 AI 后整个系统的输出不可预计。老师分享的乐趣：做完 AI 后静静看着 bot 互打互殴可以看一两个小时，然后调参数让它们再打（"养蛊"般的过程）。
*   **触发 Replanning 的三种情况**：
    1.  当前没有计划。
    2.  当前计划已成功执行完，或执行到一半失败。
    3.  **主观认知中世界状态发生重大变化**（例如 sensor 告知：原本计划是去抢补给点支撑 A 点夺取，但 A 点突然丢了、所有人都向 B 点冲）——计划不能僵化执行，不能"闭目塞听"，大格局变量变化时必须重新制定计划。
*   **Replanning 是 HTN 网络非常重要的体系**：很多系统做得好不好，Replanning 的设计影响非常大。

#### (8) HTN 的优缺点

*   **优点**：
    *   是对行为树非常好的抽象和总结，易于理解（跟小学生/中学生解释游戏 AI 设计都讲得通）。
    *   方便设计师规划**长期性行为**。
    *   **执行效率比行为树高**：行为树每次 AI 被唤醒 tick 都要从 root 把整棵树跑一遍，而 **90% 的时候从头 tick 一遍没有意义**（上次 action 没做完，这次仍要等它做完），整棵树的遍历会吃掉 **70%~80% 的计算 budget**（引擎团队的血泪教训）；HTN 则除非世界改变、task 失效或没做完，否则不需要重新计算。
*   **缺点**：
    *   **Precondition / Condition / Effect 形成逻辑链路**：前面规划的动作对世界的改变需正好满足后面（可能隔几步的）动作的 precondition。面对几十上百个 primitive task 时，设计师很容易出现"计划无法形成"的小错误，**需要静态检查工具帮助及早发现**（典型错误：设计了一个 primitive task 却忘记加 `effect`，导致该任务永远生成不了——可行性检查总发现某个 state 不满足而被跳过）。
    *   **长期计划在高不确定性环境下不稳定**：计划链路长时容易中途失败、被迫频繁 replanning，导致 AI 行为出现**震荡或不稳定**（类比：同学总花一晚上做一年规划，但环境一变几天就失效、被迫重做，外人看来他的行为"很不靠谱"——今天要练世界冠军肌肉、明天要当游泳冠军、后天要做数学小能手）。

### 3. 目标导向行为规划（GOAP）

#### (1) GOAP 总体框架与核心区别

*   **全称**：Goal-Oriented Action Planning（基于目标的行为规划）。
*   **代表作**：《古墓丽影》（Tomb Raider）、《刺客信条：奥德赛》等大作。
*   **"Planning"的翻译**：此处 planning 更准确的翻译是**规划**（参考动态规划）。确定性规划尚可，加上随机变量的规划极其困难。
*   **结构图与 HTN 几乎同源**（老师怀疑二者是"同门师兄弟"）：上方有 `sensor` 感知世界，旁边有 `world state`（对世界的主观认知），中间原来是 HTN Domain 的位置换成了 **Goal Set + Action Set**，之后由 Planner 计算产生 plan，再由 **Plan Runner** 执行。
*   **与 HTN 的三大核心区别**：
    1.  **目标集（Goal Set）**：所有可达成目标的集合。
    2.  **动作集（Action Set）**：所有可执行动作的集合。
    3.  **规划问题（Planning Problem）**：有了目标后，如何规划出一个 action 序列来完成它。

#### (2) Goal Set（目标集）

*   **与 HTN 相似处**：Goal Set 很像 HTN 的 compound task——目标**有优先级**（第一个塞进去的是最想达成的，依次形成 prioritized 序列）；每个 goal 一般设一个 `precondition`（当条件满足时优先达成该目标，例如：中毒时最优先的目标是解读而非杀敌；未中毒时才看有没有敌人、才去争取杀人得分）。
*   **最根本的不同——目标被严格数学化定义**：
    *   **在行为树与 HTN 中，目标是隐含在树状结构里的**（只能写在注释中，不是真正的目标）；**在 GOAP 中，每个 goal 用一系列期望世界达成的状态（states）来定量表达**。
    *   goal 不是单一的世界状态要求，而是**世界目标状态的组合（conjunction / combination of states）**——例如"我的存活为 `true`、中毒状态为 `false`"等。
    *   一般都用**布尔值**表达这些状态，因为用"变量大于等于某值"等其他表达方式会给系统添加大量不必要的复杂度。这是 GOAP 系统很高的一个要求。

#### (3) Action Set（动作集）与 Cost

*   **与 primitive task 类似**：每个 action 有 `precondition`（满足才可执行）、动作本身、`effect`（对世界状态的读与写）。
*   **额外引入 `cost`（代价）**：GOAP 没有树状或图状结构把所有 action 串在一起，当目标确定后，选择沿 A 方向还是 B 方向需要"好坏评价"，此时**设计师的经验输出**发挥作用——例如"造草药成本最便宜；徒步走到 NPC 商店买药要花很久，中途还可能被怪物打，所以 cost 高"。
*   **为什么需要 cost**：几乎所有动态规划问题都要考虑 cost（最短路径问题本质上就是追求成本最低），这里"规划（planning）"一词再次被激活。

#### (4) 以终为始的规划思想

*   **GOAP 最核心的一点是"倒着计划"（逆向推导）**，非常像人类的思维方式：目标（成为社会精英）→ 需要好工作 → 需要读好学校 → 需要认真读书 → 现在去图书馆找书 → 放下游戏去图书馆。人类的正确做法**不是正向推导，而是以终为始**。
*   **示例**：目标是解读 → 必须做的动作是喝解药 → 找到"喝解药"这个 action → 它的前提是要有解药 → 有两个选择（喝万能药 / 专门的解毒药）→ 找到"获取解药水"的 action → 其前提是要走到 NPC 商店去买 → 依次倒推。

#### (5) 规划算法与 Unsatisfied State 堆栈

1.  选择一个 goal，将 goal 内**所有 state 与当前 world state 逐一比较**；已满足的 state 直接忽略，**未满足的 state 放入"未满足状态堆栈"（stack of unsatisfied states）**。
2.  取出第一个未满足的 state，在 action set 中寻找**其 `effect` 正好能把这个 state 写对、且 `precondition` 当前能满足**的 action。
3.  找到后，假设执行该 action 能满足这个 state，将该 state 从堆栈中**移出**。
4.  但该 action 自身可能需要一些 `precondition`，若这些 precondition 当前不满足，则把它们**反向加回未满足状态堆栈**（"为了完成你的任务我要做这个动作，但做这个动作又需要一个前提条件，于是它又变成需要满足的东西"）。
5.  如此**动态维护堆栈**，目标是规划出一条路径：按这些 action 依次执行后，**未满足状态堆栈全部清空**。
6.  **额外要求**：所有 action 的 cost 总和**最小**。两个目标同时满足，且**优先保证完成目标，其次追求代价最小**——这就构成了一个动态规划问题。

#### (6) 转化为图问题与 A* 搜索

*   **计算复杂度问题**：若 goal 有五六个 state、action 空间假设有 100 个，每走一步展开 100 种可能性、再往下层层展开，这是**指数爆炸（NP hard）**。
*   **关键变换——把 GOAP 问题变成图（graph）问题**：
    *   **Node（节点） = state 的组合（combination of states），而不是单个 state**（最易犯的错误）。因为规划是逆向的，**优化的起点是目标（goal），优化的终点是当前状态（current state）**。例如把 goal 中最需要的五个 state 都为 `true` 写进节点。
    *   **边（edge） = action**：只有**当前状态倒序推演下 precondition 能满足的 action** 才有效；边的权重是 action 的 `cost`（相当于 distance）。
    *   执行 action 会修改 state、产生新的 state，从而得到新的节点，以此类推把整个 action 展开成**一个巨大的图**。
    *   核心任务变为：**在图上寻找从目标（goal）到当前状态之间的一条最短路径**——即一个最短路径搜索问题。
*   **用 A* 算法求解**：
    *   A* 是启发式（heuristic）算法，用于对世界的探索。
    *   **启发式部分**：优先选择"与当前状态最接近的状态"方向，并给其较高权重，使算法优先往该方向搜索。
    *   A* 能保证：**若通路存在则一定能找到**；但它约莫给出较近的路径，**并不能保证最优路径**。
    *   **不保证最优反而是优点**：世界状态一直在变，NPC 不会永远做最优选择。若一个人所有选择都最优，会显得像极度冷血、极度理性的机器人，不好玩；我们希望角色偶尔做一些"合理但看似很笨"的选择，让行为更自然。这也是 GOAP 的 AI 有时让人觉得很惊艳、很"活"的原因。

#### (7) GOAP 的优缺点

*   **优点**：
    *   行为**更加动态、更具环境适应性**。
    *   设计师无需做大量预先的 action 梳理。
    *   **第一次真正把"目标"与"行为"解耦（decoupling）**：FSM、行为树乃至 HTN，行为都通过拓扑结构本质锁死成一个目标；GOAP 中即使目标相同，因环境一直在变，执行路径可以完全不同，且很多时候路径**超出设计师想象**（设计师会觉得"哇它居然会这么干"），还能规避 HTN 因数据配置不当陷入"思索状态"的问题。
*   **缺点**：
    *   **计算量大**（"比较废"）：图的构建复杂，还要做 A* 动态规划，计算量大于传统 BT 与 HTN（尤其 HTN 效率很高）。
    *   **挑战——状态定量化**：把整个游戏状态变成定量的布尔值表达非常困难。对于高度复杂的游戏（如《星际争霸》），很难用一堆 `true/false` 表达当前状态。
    *   **适用范围**：适合**确定性较高**的游戏（1V1 对抗、几个小 AI 对抗、关注变量较少且可量化成布尔值——如是否残血、是否中毒、对手是什么类型的怪物）；**不适合** RTS 这类超复杂、多维度的博弈环境。GOAP 常见的应用场景是单机、顺序性、刷关类游戏。

### 4. 蒙特卡洛树搜索（MCTS）

#### (1) 应用背景与围棋

*   **MCTS（Monte Carlo Tree Search）**是经典游戏 AI 方法，介于传统算法与机器学习之间（跨界）。
*   **著名应用**：**AlphaGo**（下围棋击败人类所有顶级高手）；**《全面战争》（Total War）**系列近几作基本上用 MCTS 形成其大世界策略。
*   **围棋规则科普**：黑子白子轮流落子；只要己方棋子被对方围住、没有"气"（不能透气）时就被吃掉；最终看黑棋白棋谁占据的空间大。规则一页纸就能讲完，但变化精妙无穷。
*   **搜索空间规模**：
    *   围棋搜索空间约为 $3^{380}$，即约 $10^{171}$（老师调侃"我们解决的问题比宇宙中的原子都要多"——宇宙原子数量约为 $10^{80}$，远小于围棋的变化数）。
    *   国际象棋搜索空间约为 $10^{50}$。
    *   **深蓝（Deep Blue）**击败人类国际象棋冠军本质是**暴力搜索法**；而围棋因变化量太大，AI 在很长一段时间内**连业余选手都打不过**。
    *   **历史**：约 2006 年，**雷米（Rémi）**最早提出用 MCTS 方法让围棋 AI 基本达到人类业余选手水平；后来的 AlphaGo"大力出奇迹"，最终击败人类职业选手。MCTS 是这一切的 **foundation**。
*   **思想精髓**：面对巨大、复杂、需要大量推算的问题时，**用随机的方法也能给出非常好的解**——选择每一步时在脑中推演几百上千种与对方对弈的路数，最后选择己方胜率最大的走法，这非常像人类下棋的思路。

#### (2) 基本建模：State 与 Action

*   **建模思想**：计算机只能处理数学模型，任何问题都要先抽象成数学模型（老师强调"数学建模比赛"是很好的训练，建模定量化是工作中最需要的能力）。
*   **State（状态）**：这场博弈当前所有棋子的分布——可理解为对整个局面**拍一张快照（snapshot）**。
*   **Action（动作）**：在当前状态下要做的事，如围棋中落子位置（XY 坐标）。
*   **Tree structured state space**：从一个初始 state 出发，根据不同的 action 形成一个**只有一个子节点**的链；有多个可选 action 时展开成树，对方再各有多重选择……整个棋盘可能发生的情况构成一个巨大的空间。老师认为 `state space` 这个说法不够准确，更准确的说法是 **tree structured state space**——state 之间不是孤立存放的，而是被**树状拓扑结构连接**起来的。
*   **极限推演**：若有无限算力和无限内存，把每一步所有情况全部展开，一定能找到最优解——博弈论中推演过，所有确定性规则的游戏一般都有必胜策略，只是由于搜索空间过大无法全搜索。

#### (3) Simulation（模拟）与 Default Policy

*   **经典 MCTS 每次从当前状态重新建树**：根据当前棋局状态重新构建蒙特卡洛树进行搜索。这是大家容易犯迷糊的地方——因为最后只需要决定"下一步走什么"。若内存足够且不介意算法复杂，两次搜索之间其实可以 `reuse`（复用）很多节点（前沿工作的优化方向），但本课讲的是最古典的方法：**每一次的根节点就是当前状态**（大概率是对手走完后的局面），然后探索所有可能性。
*   **Simulation（模拟）**：把一盘棋**快速下完**。例如当前局面已定，我决定在棋盘左侧某位置落子，接下来让计算机用相对合理的方法快速下完这盘棋，报告这次模拟赢还是输。
*   **Default Policy（默认策略）**：
    *   `policy` 一词来自**机器人学/控制理论**（机器学习很多基础概念并非来自计算机或游戏引擎，而是来自机器人学），指**一套操作的基础方法**（一个缺省的策略）。
    *   在下棋场景中，default policy 就是**预先输入电脑的人类棋谱**（几百张、上万张），AI 看到对方走完一步后直接从棋谱里调出对应走法。好处：不用再 search、速度快；下棋指点相对合理；可以非常快速地从头下到尾。
    *   在 AlphaGo 这类复杂系统中，default policy 可以是**自己训练好的神经网络**（而非棋谱），这里不展开。
*   **一次模拟的成败不等于该节点的整体成败**：一次模拟赢了，只是无数可能性中**很小的一条链路**的结果。论文示意图中用一条小折线（像小蛇）表示一次探索，不代表该节点下所有 state space 都成功。

#### (4) Q/N 值与 Back Propagation

*   **Q/N 值（核心数值）**：从某节点出发，`N` = 做了多少次模拟（例如 100 次），`Q` = 这 N 次模拟中赢的次数（例如 50 或 60）。**成功率 = $Q/N$**。这一对 Q 和 N 是 MCTS 算法最核心的数值，后面几乎所有东西都围绕它展开。
*   **Back Propagation（反向传播）**：一次模拟结束后，**不是只修改被模拟节点自身的 Q/N 值**，还要把父节点所有数值**依次往上调整**（Q 加相应值、N 加相应值）。站在父节点立场看，它确实又多做了一次模拟。
*   **示例**：root 做了 1000 次模拟，胜率五五开（约 500/1000）；有七种选择：第一种模拟 100 次、胜率 70%；另一个节点模拟 200 次、Q 大 N 也大。模拟做完后，所有被探索过的 state 都有 Q/N 值，告诉我们"探索了多少次、胜了多少次"。

#### (5) MCTS 四步迭代

MCTS 是一个不断循环的四步过程（先理解基础概念再理解框架，就不会对 selection/expansion 等名词发晕）：

1.  **Selection（选择）**：选择一个**最有希望且没有被完全展开**的节点（此时树已展开几十个或几个节点）。
2.  **Expansion（展开）**：对该节点进行一次展开，加入一个新的探索。
3.  **Simulation（模拟）**：做一次模拟，评估该探索方向是好是坏。
4.  **Back Propagation（反向传播）**：得到结果后，将数据反向传播回去，把所有相关节点的数据更新一遍。

如此一直迭代下去，直到达到停止条件。

#### (6) UCB 公式与 Exploitation / Exploration

*   **可扩张节点（Expandable Node）**：该节点**所有可能性没有被穷尽**——例如按棋谱下一步有 20 种选择，但目前只试了 10 种，则它是可扩张节点。
*   **两种选择策略（博弈论/机器学习的核心概念）**：
    *   **Exploitation（开发）**：优先选**访问次数足够多（N 大）且胜率最高（Q/N 比值高）**的点。
    *   **Exploration（探索）**：优先选**N 小（没探索过）**的点，并给它相对高的权重，冒一次"砸锅"的风险去尝试。
    *   生活类比：exploitation 型选手总去最喜欢最熟悉的餐馆（反复验证一定好）；exploration 型选手总逼自己去没吃过的餐馆（万一好吃呢）。人生很多选择就是在**开发与探索之间做平衡（balance）**。
*   **UCB（Upper Confidence Bound，上置信界）理论**：
    *   对随机世界采样时，若采样数量特别少，采样到的数值偏低**很可能只是采样不够，而非真的低**。当采样满足大数定理（大致满足高斯分布）时，有一套数学方法可以估计"它的上置信界大概能大到什么样子"。
    *   MCTS 中该公式很朴素：第一考量是 $Q/N$（开发部分）；再与**父节点总访问次数**比较，若父节点已完成 100 次探索而自己只有两三次，则通过**取自然对数**的方式给出置信区间上界。
    *   **公式**（UCB/UCT）：
        $$UCB(n) = \frac{Q}{N} + C \sqrt{\frac{\ln N_{parent}}{N_{node}}}$$
    *   **常数 C 是"黑客"技巧**：原公式是一个相对严格的数学定理（假设随机变量恒在 0~1 之间波动、采样几次后算出期望），而做游戏引擎/计算机开发的人常常加一个常数 C 来调节。**C 大 → 策略更 aggressive（更多探索）**，被访问较少的节点更容易被选中；**C 小 → 策略更保守**。具体取值需要根据自己场景去调——老师调侃做人工智能有时"跟炼丹一样"，很多地方需要上手调参。
*   UCT（也是 UCB 公式在 MCTS 中的应用叫法，有人叫 UCT）。

#### (7) Selection 与 Expansion 细节

*   **Selection 细节**：**每次都要从 root 开始**（这是一个很有意思的细节）。先比较第一层所有 child node 的 UCB 值，**UCB 值最大的作为下一个探索方向**，再问它的子节点、继续往下走，一直走到第一个 **expandable node**，把它作为 current/select node 去展开。
*   **直观类比**：感觉像**广度优先搜索**，只是树的数据一直在变；每次选择下一个要展开的节点时，都从根节点公平地比较所有 child。
*   **不会"死掉"**：像围棋 $10^{171}$ 量级的搜索空间，任何分支都不可能探索完，所以按此算法一定能找到未完全展开的节点。
*   **Expansion 细节**：可以从 select node 只展开**一种**可能性，也可以展开**一组**可能性。若算力允许，展开一种可能稍好一些，但这意味着每种可能性都要做一次 simulation、内存消耗增加更快；一次展开一组则会让树更平衡。
*   **具体示例**：从红色 select state 出发给出三种探索方向，做三次 simulation，结果分别为输、赢、输。随后把每个节点的 Q/N 值一层层向上传递：select node 的 Q 从 0 变 1、N 从 1 变 4（加 3）；往上找父节点，每个节点 Q 加 1、N 加 3，整条链路的数值全部被更新。

#### (8) 停止条件与最终选择策略

*   **停止条件（budget 预算）**：
    *   **内存预算**：树越变越大，内存超过一定限额就停止探索。
    *   **Simulation 次数限制**：例如规定每一步思考最多做 1000 次 simulation（脑中推演 1000 次下完棋的情况）。计算量依然惊人、内存消耗也很大。
    *   也可设定计算时间（whatever 你喜欢的方式），然后停止搜索。
*   **停止后**：得到一棵很大的树，根节点 = 当前棋盘状态。**只需要选择下一步**——即根节点下第一环的子节点，下面深层展开的东西对当前决策没有用处。
*   **最终选择策略（各有所爱的"玄学"）**：
    1.  **Max Child（最大孩子）**：选 **Q 值最高**的节点（从该分支走下去胜的盘数最多）。问题：Q 值高但 N 也可能很大（例如某节点被测试 100 次 Q=55，另一个测 80 次胜 70 盘），单看 Q 值不一定可靠。
    2.  **Robust Child（鲁棒孩子）**：选**被访问最多的子节点**（测试最充分）。隐含细节：每次 selection 是用 UCB/UCT 公式做的，**已经综合考虑了 Q/N 比值**，被反复试的节点说明在整个展开过程中一直被认为有希望，因此**访问次数本身代表节点的靠谱程度**，且 simulation 次数足够多所以很 robust。
    3.  **Max-Robust Child（Q 与 N 都最大的孩子）**：要求 Q 值和 N 值**都最大**（"小孩子才做选择，成年人什么都要"）。老师个人认为做 MCTS 时这是最好的选择。若当前没有满足的节点——**继续跑**，直到该节点出现为止。
    4.  **LCB（Lower Confidence Bound，下置信界）**：把 UCB 公式的加号变减号：
        $$LCB(n) = \frac{Q}{N} - C \sqrt{\frac{\ln N_{parent}}{N_{node}}}$$
        采样次数大的节点优势更大；它把 max child 与 robust child 结合在一起考虑，通过神奇的数学变换加权重，两个问题都解决了。C 的设置又是个玄学问题。
*   实践中可根据自己喜好尝试（哪个 work 用哪个），不必长篇累牍向别人证明其合理性。

#### (9) MCTS 的优缺点与适用范围

*   **优点**：
    *   让 AI 行为**灵活灵动**——算法中有随机数，世界开始变得有趣。
    *   Agent 的决策**基本由自己做出**，行为常常**超出设计师的想象**（就像 AlphaGo 下到最后人类已经下不明白了）。
    *   对于非常复杂的搜索空间问题都能给出好的解。
*   **缺点**：
    *   对较复杂的游戏情况，**很难精确表达到底是赢还是输**（胜负判定难以定义）。
    *   很难精确地定义"做了某个动作后对世界的影响"。
    *   **计算复杂度很高**、内存消耗大。
*   **适用范围与选型建议**：
    *   **不适合所有游戏类型**：例如直接用它做 MOBA 游戏 AI 会有问题，必须对世界进行转换。
    *   **适合**：**turn base 回合制游戏**（你一下我一下）+ **每个动作输出结果非常明确**的游戏。例如回合制战斗游戏里输出一个技能，能精准计算出对方掉多少血、自己改变什么状态，就像下棋一样——此时 MCTS 是很好的框架。
    *   《全面战争》案例：大世界各 NPC 势力（领主、君主）的决策（此时出兵、攻打某城、还是结盟）就是其可选 action，每个攻城的后果容易估算，且其大世界策略本质是 turn based（战斗实时，但大世界策略是回合制的），所以非常适合 MCTS。
    *   **更高层、更复杂的游戏环境不能纯用 MCTS**：需要把 MCTS 与行为树（BT）、GOAP、HTN 等**结合使用**，甚至底层可能放一个**有限状态机（FSM）**。**一定要把每种算法放到它合适的位置**。

## 二、 重点术语与概念解析

### 1. HTN（Hierarchical Task Network，层次任务网络）
*   **定义**：从任务目标出发的规划型 AI 架构，把 AI 行为表述为任务及子任务的层次结构。
*   **应用/注意点**：《地平线》《杀出重围》等使用；类似"selector + sequencer"的组合，但有细微差别。

### 2. World State（世界状态）
*   **定义**：AI 大脑中对世界的主观认知（提炼/思想），**不是客观世界**的镜像。
*   **应用/注意点**：规划时需对其做"草稿拷贝"用于推演；与 sensor 务必区分。

### 3. Sensor（感知器）
*   **定义**：从游戏环境抓取各种状态的组件，类似 `perception`。

### 4. Primitive Task（原子任务）
*   **定义**：HTN 中最简单的任务，本质是一个动作。
*   **应用/注意点**：包含三个要素——动作本身、`precondition`（读世界状态，不满足返回 `false`）、`effect`（写世界状态）；执行仍可能失败。

### 5. Compound Task（复合任务）
*   **定义**：由多个带 precondition 的 method 组成，method 间暗含优先级，method 内部是一串须依次成功的子任务。

### 6. Method（方法）
*   **定义**：复合任务中完成目标的一种方案，含一组 `precondition` 和一个 task 序列。

### 7. Precondition（前置条件） / Effect（效果）
*   **定义**：前置条件是对世界状态的**读操作**；效果是对世界状态的**写操作**。

### 8. Root Task（根任务）
*   **定义**：HTN 网络的根，通常是复合任务，定义 AI 最高层核心行为。
*   **应用/注意点**：必须配置足够鲁棒的 **default task**（如 `default idle`，NPC 无事可做时搔首弄姿/打招呼），否则环境不满足时 NPC 会傻站（看似 bug 实则无输出）。

### 9. Planner / Plan Runner
*   **定义**：Planner 负责根据世界状态制定任务计划；Plan Runner 负责依次执行计划并监控 task 状态。

### 10. Replanning（重新规划）
*   **定义**：计划缺失、执行完成/失败、或世界状态发生重大变化时重新制定计划。
*   **应用/注意点**：是 HTN 系统好坏的关键。

### 11. GOAP（Goal-Oriented Action Planning，基于目标的行为规划）
*   **定义**：以终为始（逆向推导）的规划算法，目标用期望世界状态的组合定量表达，用 A* 求解最短路径。
*   **应用/注意点**：《古墓丽影》《刺客信条：奥德赛》使用；适合确定性高的游戏，不适合超复杂博弈环境。

### 12. Goal Set（目标集）
*   **定义**：所有可达成目标的集合，有优先级与 precondition。
*   **应用/注意点**：每个 goal 必须用布尔状态组合严格数学化定义——这是与 BT/HTN 的本质区别。

### 13. Action Set（动作集）
*   **定义**：所有可执行动作的集合，每个 action 含 precondition、动作、effect。
*   **应用/注意点**：额外引入 `cost`（代价），是设计师经验输出。

### 14. Unsatisfied State Stack（未满足状态堆栈）
*   **定义**：GOAP 规划中动态维护的堆栈，存放当前未满足的目标状态；每选一个 action 就移出被满足的状态、反向加入其 precondition，直到堆栈清空。

### 15. A*（A Star 算法）
*   **定义**：启发式最短路径搜索算法。
*   **应用/注意点**：用于 GOAP 求解"目标→当前状态"最短路径；保证能找到通路（若存在）但不保证最优；不保证最优反而让 AI 更自然。

### 16. MCTS（Monte Carlo Tree Search，蒙特卡洛树搜索）
*   **定义**：通过随机模拟与统计胜率来选择最优动作的搜索算法。
*   **应用/注意点**：AlphaGo、《全面战争》使用；四步迭代为 selection → expansion → simulation → back propagation。

### 17. Simulation（模拟）/ Default Policy（默认策略）
*   **定义**：Simulation 指把一盘棋快速下完；Default Policy 是快速下棋所依据的基础策略（如预置棋谱，或 AlphaGo 中训练好的神经网络）。

### 18. Q / N 值
*   **定义**：N 为某节点被模拟的次数，Q 为其中获胜的次数，成功率 $Q/N$。

### 19. Back Propagation（反向传播）
*   **定义**：把一次模拟的胜负结果沿节点链向上逐层更新 Q/N 值。

### 20. Expandable Node（可扩张节点）
*   **定义**：所有可能行动尚未被穷尽的节点。

### 21. Exploitation（开发） / Exploration（探索）
*   **定义**：开发 = 优先选胜率高、访问多的点；探索 = 优先选访问少的点。MCTS 在二者间取平衡。

### 22. UCB（Upper Confidence Bound，上置信界） / UCT
*   **定义**：选择节点的评分公式 $UCB(n) = \frac{Q}{N} + C\sqrt{\frac{\ln N_{parent}}{N_{node}}}$。
*   **应用/注意点**：常数 C 控制探索强度（大 C 更 aggressive、小 C 更保守），需按场景调参。

### 23. Max Child / Robust Child / Max-Robust Child / LCB
*   **定义**：停止搜索后选择最终走法的四种策略——最大 Q 值孩子、被访问最多（最鲁棒）孩子、Q 与 N 都最大的孩子、用下置信界公式 $LCB(n) = \frac{Q}{N} - C\sqrt{\frac{\ln N_{parent}}{N_{node}}}$ 综合评分。

### 24. Decoupling（解耦）
*   **定义**：把目标与行为分离、把计算变成独立可维护的服务。
*   **应用/注意点**：GOAP 首次真正把目标与行为解耦；分布式 AI 架构也符合引擎架构的 decoupling 原则。

### 25. Perception（感知）
*   **定义**：AI 不断从当前世界抓取各种状态的过程，是 AI 计算的重要前提。

### 26. FSM（Finite State Machine，有限状态机）
*   **定义**：经典 AI 状态机架构。
*   **应用/注意点**：可在 MCTS 等高层算法之下作为底层执行机制。

## 三、 工程经验与避坑指南

### 1. Q&A：课堂答疑

#### (1) 关于《艾尔登法环》AI 读取玩家输入的讨论

*   **提问背景**：有传言说老头环的 AI 会"读玩家的输入"，这算不算 AI 未来主流发展方向？
*   **老师的观点**：
    *   从经典教育上的游戏 AI 来看，这是**作弊**。游戏 AI 的核心**道德规范**是：**不能超越玩家获取额外的信息**，否则行为看上去就是作弊。
    *   例如做 CS 的 AI，不会让 AI 知道整个地图；AI 必须只能通过"你能看见什么人""你听到的脚步声"来行动，这样 AI 的行为才像期待的"人工智能体行为"。
    *   但对于**动作打击、交互要求很敏感的 AI bot**：从玩家的最终行为（位移、位置变化）反向推导其 intention（意图）确实非常难（真实做过 AI 就知道）。
    *   作为**游戏研发者（practice）**，老头环的选择完全合理、可以接受——它让 AI 更灵敏、反应更敏捷，实际上**增加了游戏乐趣**。
    *   但**不是所有游戏 AI 都该这么做**：例如做 RTS 游戏就**不要读玩家的双击操作**——玩家有大量无效点击（"手抖"），把这些 input 全部放进 AI 体系，AI 会疯掉，不知道你要干什么。

#### (2) 游戏引擎给 AI 分配多少计算预算（Budget）

*   **总体原则**：仁者见仁、智者见智，根据不同类型游戏产品给 AI 的 budget 完全不一样。
*   **参考数值**：传统会给 AI 约 **1ms~2ms** 的计算时间。
*   **按游戏类型区分**：
    *   **回合制策略游戏（turn base strategy game）**：有巨大世界、需要模拟上百个君主的行为时，可以把 budget 给高一点，让 AI 大量进行精细计算，使每个 NPC 王国的君主行为更像人类。
    *   **实时射击游戏等快速类型**：AI 的 budget 相对给小一点。
    *   **单机游戏**：AI 体数量不多时，每个 AI 的 budget 可以比较高。
*   **为什么网游 AI 显得笨、单机 AI 聪明？** 因为预算不一样。
*   **关键细节：AI 的 ticking 与渲染彻底分离**：
    *   AI 更新不需要每秒钟 30 帧、60 帧，可以**相对低频更新**（一秒钟几次问题不大）。
    *   甚至一些较复杂的运算，**一秒钟更新一次策略**问题也不大。
    *   真实游戏引擎的 AI 系统架构分很多层：宏观的东西低频更新，底层的东西高频更新；**很多算法可以混合使用**。

#### (3) 能否用分布式系统把 AI 从客户端分离出去

*   **提问背景**：客户端做 AI 很费，能不能放到服务器甚至云端去做？
*   **现状**：这在现代游戏中已经是很多实践了——很多网游已把 AI 变成**独立的 AI 服务器**；完全可以把 AI 预置于游戏引擎之外变成一个服务，**通过 Python 接口调用**。
*   **这是未来较大的发展方向**，但难以一言以蔽之：
    *   **手游**：所有计算就在"方寸之间"，可能要用手游自身的 AI 推理芯片。
    *   **复杂的多人 MM 或网上虚拟世界**：确实可以把很多 AI 变成独立服务。
*   **好处**：AI 可以做得非常丰富和复杂。
*   **坏处**：AI 计算有个很大前提是 `perception`（不断从世界抓取各种状态），把这些状态序列化（`serialize`）传送到 AI 服务器、反序列化（`deserialize`）回来，这个过程**比较废**——计算本身还行，但世界状态的打包传输可能很麻烦；且分布式 AI 服务器需要同时传很多份。
*   **本质是 balance（权衡）**：如果 AI 计算本身足够昂贵（expensive），就值得这样做。
*   **老师个人观点**：**比较喜欢这种架构**，因为很符合引擎架构的 **decoupling（解耦）** 原则——把各种计算变成一种服务，每个服务独立维护，彼此之间通过数据协议交换。对于超复杂的虚拟世界架构，若某个 AI 服务器坏了，可以重新启动该服务并把整个链接重新建立起来（pick up），这是一种**很鲁棒（robust）**的架构。评价：提出这个问题的同学相当专业。

### 2. 工程实践与避坑经验

*   **行为树 tick 的代价（血泪教训）**：行为树每次 AI 被唤醒 tick 都要从 root 把整棵树跑一遍，而 90% 的时候从头 tick 没有意义（上次的 action 还没做完）。**整棵树的遍历本身可能吃掉 70%~80% 的计算 budget**——这是引擎团队自己做引擎时的血泪教训。HTN 除非世界改变或 task 失效，否则不用重新计算，因此更高效。
*   **HTN 的 World State 认知**：切勿把 world state 当成客观世界——它是 AI 大脑里的主观认知，二者混淆会导致算法实现出错。
*   **HTN 的静态检查工具**：几十上百个 primitive task 形成逻辑链路时，设计师极易犯错（如忘了给 task 加 `effect`，导致该任务永远生成不了——可行性检查总发现某个 state 满足不了而被跳过）。**需要静态检查工具帮助设计师及早发现这类错误**。
*   **务必配置 default task**：构建 root task 时，千万要设置足够鲁棒的 `default task`（如 `default idle`），不要把所有 task 都设计得那么有挑战、有意义。否则当世界条件不满足时，NPC 会傻站在那儿，看起来像 bug——其实系统没出 bug，只是没有环境变量满足、NPC 没有任何输出告诉它该干什么。
*   **长期计划不宜过长过密**：在高不确定性环境中，HTN 计划过密过长会导致频繁 replanning，AI 行为呈现震荡/不稳定性。
*   **GOAP 的状态定量化**：必须用一堆布尔值表达游戏状态，否则 goal 和 action 都无法定义。对高度复杂的游戏（如 RTS、星际争霸类）这几乎不可能，应谨慎选用 GOAP。
*   **UCB 常数 C 的调参（"炼丹"）**：C 大更 aggressive（偏向探索），C 小更保守。需要根据自身 scenario 反复调试，没有放之四海而皆准的值。
*   **MCTS 终止后的选择策略**：max child（Q 最大）、robust child（N 最大）、max-robust child（Q、N 都最大）、LCB（下置信界公式）。可各自尝试，**只要 work 就行**，不必向别人长篇证明合理性。
*   **算法混合使用**：真实项目中不要"一把梭"，**把每种算法放到它合适的位置**——高层策略用 MCTS/GOAP/HTN，底层动作执行可以配合行为树甚至 FSM；MOBA 等游戏直接硬用 MCTS 有问题，必须对世界进行转换。
