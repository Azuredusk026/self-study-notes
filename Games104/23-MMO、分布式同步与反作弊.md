# 网络游戏进阶架构：MMO 系统分层、分布式同步与反作弊

---

## 一、 核心知识点与原理剖析

### 1. MMOG 概述：从 MUD 到虚拟世界

*   **核心概念**：`MMOG`（Massive Multiplayer Online Gaming，大型多人在线游戏）指**海量玩家在同一世界中通过互联网彼此连接**的游戏类型。注意：MMO 并不等于 `MMORPG`，如今大量 `FPS`（第一人称射击）游戏用户量同样巨大，也属于 MMO 范畴。
*   历史上最早的联网游戏是课程组找到的"多人一起走迷宫、互相竞技"的联网小游戏；而最早的多人角色扮演游戏则是**文字游戏 `MUD`**（Multi-User Dungeon，多用户地牢，纯文本交互的多人游戏），玩家通过文字描述（"进入房间""在桌上捡起一个碗""选择与某人对话"）进行互动。
*   现代 MMO 已经演化为一个**小型的虚拟世界**：玩家可以星空探索、一起挖矿、在主城互相看见、对话、交易。老师引述 Gabe Newell（"鸡胖"）的观点：**"你们这些讲元宇宙的人，还不如打打 MMO 游戏"**——因为 MMO 里已经实现了大量元宇宙设想的功能。
*   **做单局 Gameplay 与做 MMO 的差异**：单局（一个 session、一场战斗）只需关注战斗玩法本身；而真正构建一个让几十万甚至上百万人彼此连接、一起下战场的虚拟世界时，会**一下子多出大量子系统**，包括：
    *   `User Management` 系统：管理大量玩家数据；
    *   `Matchmaking` 系统：匹配对战、一起下副本；
    *   交易系统：部分交易会牵扯到真实世界货币，具有**经济属性**，若道具被偷甚至可能产生**法律责任**，因此系统必须做得非常严格、保护好玩家安全；
    *   社交系统：交友、聊天、社群、公告；
    *   数据（Data）系统：海量数据的存储。

### 2. 网游整体架构：经典三层架构

*   **核心概念**：一个网游服务器的大致架构分为**三层**（这是最核心的三层）：
    *   **顶层——玩家**：各种客户端连接到世界；
    *   **连接层（Link 层）**：把用户的所有链接管理好，包含 `login server`（登录服务器）与 `gateway`（网关）；
    *   **服务层（Service 层）**：提供各种服务——账号/房间大厅服务、每一局对战的服务、社交服务、存储服务等等；
    *   **数据存储层**：以数据库为核心构建的数据存储与服务层，有各种各样的 `DB`（数据库）。

### 3. 连接层：Login Server 与 Gateway

#### (1) Login Server（登录服务器）
*   **核心概念**：MMO 的服务器本体是一个**必须被保护起来**的对象，因此**所有用户不能直接连接游戏服务器**，而是先连接 `login server`。
*   在 login server 上完成的工作：
    1.  完成链接与握手；真实场景中一般使用 **`HTTPS`**（超文本传输安全协议，即 HTTP + TLS 加密），通过更安全的加密信道连接；
    2.  验证账号密码；
    3.  验证通过后，**绝不直接允许客户端与各个业务 server 直接交互**，而是转交给 `gateway`。

#### (2) Gateway（网关）
*   **核心概念**：用户**永远只跟 gateway 对话**，由 gateway 负责与内部服务器（`character server` 角色服务器、`lobby` 大厅服务器、邮件服务器等）通信。
*   **本质就是一道防火墙**：即便用户拥有正确的账号密码，也可能是黑客在发送大量奇怪数据尝试破解服务器，gateway 会**验证所有信息的合法性与有效性**。
*   附加能力：游戏服务器常遭遇 **`DDoS`**（分布式拒绝服务攻击），gateway 具备一定拦截功能（更复杂的 DDoS 有更复杂的机制）；解压/压缩等操作也都在 gateway 内完成。
*   **部署方式**：gateway 工作任务很重，一般会**同时开多个实例**，随玩家数量增长不断增开。可将其理解为"**大厅接待员**"——像客服团队一样接待所有玩家。

### 4. 大厅（Lobby）

*   **核心概念**：通过 Link 层后玩家进入游戏大厅。大厅很多时候本身就是一个游戏场景，可以认为**大厅是一个特殊的游戏模式**——只是在该模式里通常不能放技能、不能打架（但有的游戏允许玩家在主城决斗，即保留一定 Gameplay 功能）。
*   **作用**：大厅常作为**缓冲池**，让玩家在等待 `matchmaking`（匹配）期间被管理起来。
*   注意：大厅**不一定是真实场景**，也可能是纯虚拟的 UI 大厅（如游戏开战前玩家在虚拟大厅里互动）。

### 5. 服务层核心子系统

#### (1) Character Server（角色服务器）
*   **核心概念**：网游中用户的数据量远超想象——**一个角色的数据可达几兆甚至几十兆**（包括所有获得的道具、完成的任务、经历的事件等，随游戏时间增长而膨胀）。
*   **为什么需要独立角色服务器**：这些数据会被各类 server 反复查询。如果数据分散在战斗 server、交易 server、聊天 server 里，就会"七零八落、谁也管不了"。因此由 `character server` **集中管理所有玩家真正的属性数据**。
*   职责示例：装备查询、交易成功后道具归属、战斗重伤后的数据更新（有些不会立即同步到 character server）、发邮件等，都是 character server 要完成的任务。

#### (2) 交易系统
*   **核心概念**：交易系统有非常重的**金融属性**，写它时**安全性要求极高**。
*   **硬性要求**：
    *   每一笔交易保证**绝对原子性**（transaction 要么全部成功、要么全部失败，不存在中间状态）与安全性；
    *   全部交易都要可以 **`rollback`**（回滚）；
    *   当客户端交易中途断线或服务器异常时，每个 `transaction` 都能被准确记录，不会出现异常数据。

#### (3) 社交系统（Social System）
*   **核心概念**：涵盖聊天、邮件、拉黑别人、组队开小群聊天、分频道等，写起来并不简单。
*   **必须拆分服务器**：如果所有社交功能写进单一 server，当大量玩家同时互发邮件、聊天时**单一 server 会"炸掉"**。因此社交系统要分成**若干种不同的 server**——例如邮件甚至有专门的邮件 server（分得特别细）。

#### (4) Match Making（匹配系统）
*   **核心概念**：把 **ranking 值（天梯分/skill 技能分）差不多**的玩家匹配到一起，保证对战相对公平。对 MOBA（如英雄联盟）类游戏而言，**匹配系统常是最核心的系统**。
*   匹配时还需考虑**玩家彼此的网络延迟**，尽量把延迟相近、差异不大的玩家匹配到一起，否则体验不佳。
*   **开黑的特殊处理**：远程与队友开黑时无法按延迟匹配，系统会把**开黑玩家扔到一个单独的池子里匹配**（开黑打单排对散人不公平）。
*   对全球联合匹配的射击游戏，matchmaking 尤其复杂：既要平衡 rank 又要考虑延迟。

### 6. 数据存储层：四类存储服务

*   **核心概念**：在线游戏世界必须一直存在——玩家的电脑/游戏可以关，但**服务器不能关**，数据随时随地产生，必须有人存、保管、调用。因此**数据存储设计是 online game 的核心设计**。

#### (1) 关系数据库（Relational Database）
*   如大名鼎鼎的 `MySQL`（有钱可用 `Oracle`，但网游中很少用）。
*   游戏中**核心数据**用关系数据库存储。
*   面对网游海量数据，实际采用**分布式数据库架构**：同时写入多个**并行表**，确保写入/查询效率足够高，且某个服务器挂掉后数据不丢失、不损坏。
*   相关技术：**冷热表**（把高频访问的"热数据"与低频访问的"冷数据"分表存放）、**灾难备份**等。

#### (2) 非关系数据库（NoSQL）
*   **为什么需要**：关系数据库存储负载重——每条数据要建立索引关系表/哈希，才能被各种组合查询命中。而很多数据（如游戏最重要的 log 日志，一天可达 **TB 级别**）需要查询但**不需要特别及时**。
*   非关系数据库**访问速度更快、更轻量**，如 `MongoDB`（芒果 DB）。
*   用途：存储大量**临时性的 `game state`（游戏状态）**、`logging` 信息等。这类数据集不需要高效率、复杂查询，但依然有分析价值。

#### (3) 数据仓库（Data Warehouse）
*   **核心概念**：用于处理 MMO 产生的**海量数据**。举例：玩家道具丢失后打电话给客服，客服凭角色 ID 说明事件，过一段时间真的能找回道具——就是因为客服在巨量的 log / game state 数据中验证了玩家所述属实后返还道具。

#### (4) 内存数据库（In-Memory Storage）
*   **核心概念**：一款网游跑起来可能有**几百个 server** 分散在内存中，产生大量游戏**中间数据、公共数据**；若随便乱扔，查询和管理会非常复杂。
*   内存数据库**效率高、能把数据管理起来，但又不用重地读写磁盘**（读磁盘慢）。
*   老师**个人很推崇内存数据库**，认为它是服务器端各服务之间中间/公共数据更整洁的处理方法；在游戏服务器端架构中正越来越流行。

*   **方法论**：如同做游戏引擎要先从**数据结构**思考，架构 MMO 网络服务器时**建议从数据开始思考**——把数据想清楚，上层各个系统的结构也就清晰了。

### 7. 分布式系统架构

*   **核心概念**：当游戏成功、玩家越来越多——面对 1 万玩家一台服务器还行，**10 万玩家同时在线单台服务器就扛不住了**（无论怎么优化），此时解法就是**分布式系统**：把服务器的各个服务拆成**多个进程**同时工作，且服务**可加可减**，让架构具备**弹性**。
*   **技术原理看似简单**：例如 character server 管理 1 万玩家属性只需一个进程（一个 CPU）；管理 10 万玩家数据则一个 CPU 会吃爆，必须**拆成十个服务**。
*   **分布式化后必须解决的新问题**：
    *   **数据冲突/竞争/死锁**：多服务访问同一份数据时彼此不冲突、不产生竞争、不产生死锁；
    *   **幂等性（Idempotency）**：网络不稳定导致消息**冗余发送**时，系统能自动过滤重复信息、执行正常逻辑而不出现异常；
    *   **容错**：系统里总会有某个地方挂掉，挂掉后不影响整体逻辑；
    *   **数据一致性**：同样一个业务处理完后，服务 A 与服务 B 的结果必须一致，才能保证业务绝对安全。
*   **复杂度陡增**：把简单系统变为分布式系统后，对代码的**安全性、鲁棒性要求高很多**，但也换来可负载均衡等好处。
*   **注意**：即使设计正确，服务器的业务逻辑、网络链接问题层出不穷——**这就是分布式系统的"日常"**（老师借此为"某大厂土豆服务器"稍作辩解：真正做一个鲁棒服务器，要考虑的东西非常多）。

### 8. 负载均衡与一致性哈希（Consistent Hashing）

*   **背景问题**：例如 character server 要管理 10 万个玩家，拆成 10 个服务（$S_1, S_2, \dots, S_{10}$），每个管 1 万。当一局战斗中玩家（如角色 ID `104`）捡到道具要写入数据库时，**game server 怎么快速知道该玩家的数据在哪个服务上**？
*   **朴素方案不可行**：
    *   逐个 RPC 轮询所有 server（"我在不在你这？"）效率极低——一次调用约两次 RPC，且对方大概率要做 $O(\log n)$ 的查询才能回答；
    *   按 ID 范围等分也不可行：角色 ID **不重用、只递增**，登录/退出会制造空洞；server 数量也会动态变化（2 万玩家 2 个 server，3 万变 3 个……），以及用户减少时要**释放 server**——范围约定会被打破。
*   **一致性哈希的核心思想**：
    1. 为服务器与玩家**分别设计不同的哈希算法**：服务器用 `ip:端口` 哈希到一个值，玩家用 `player id` 哈希到一个值；
    2. 两值都映射到环形空间 $[0, 2^{32}-1]$（假设用 `int` 管理上限，$2^{32}-1$ 即 32 位整型最大值）；
    3. 将服务器节点布在环上，所有数据（角色）也落在环上；
    4. 定义简单规则（如**逆时针**）：每个数据逆时针找到**最近的服务器节点**，即为其归属/存储服务器；由于 server 数量不多、key 已知，查找代价极小。
*   **增删节点的行为（极其简单）**：
    *   **删除 server**：例如删除 $S_2$，则落在 $S_1$ 与 $S_3$ 之间的原属 $S_2$ 的数据按逆时针找到下一个服务器 $S_3$，全部迁移到 $S_3$ 即可——**只影响相邻节点**；
    *   **新增 server**：相当于在环中间插入一个节点，把"珍珠串"在中间又切分一次（即珍珠串无限细分问题）。
*   **为什么叫"一致性"**：只要 player 与 server 的哈希函数定下来，**无需任何 RPC 调用**即可直接算知每个 player 属于哪个 server，把一个复杂问题变得非常简单。
*   **前提与优化——哈希函数必须认真设计**：若哈希设计不佳或玩家分布过于集中，负载仍会不均衡。优化方法是 **`virtual server node`（虚拟节点）方法**：在环上**再随机哈希出若干虚拟 server**，对数据进行更细的划分，虚拟 server 再映射回原始 server，从而让负载相对均衡。
*   老师建议：刚入学做基础项目时**不要一上来写这么复杂的分布式架构**——分布式系统"初步想想简单，真把复杂逻辑放进去后，一个简单功能写一两个月很正常"（写起来容易，但上线测试、处理各种边界情况的周期非常漫长）。

### 9. 服务管理与服务发现（Service Discovery）

*   **核心概念**：分布式系统会产生**太多太多的服务**（上百、上千个），而服务本身需要被管理，因为：
    *   服务会被**不断创生与销毁**：玩家登录多了就创建新的 character server / game server；半夜玩家走了又要关闭服务；
    *   服务可能**自行崩溃**：某个服务产生逻辑错误挂掉后别人不知道，可能导致其他服务跟着**雪崩式连锁崩溃**；
    *   这么多服务需要**互相找到彼此**——真实 MMO 中服务间连接"像一团乱麻"（老师称之为 `spaghetti` 意大利面效应：搅在一起，想抽出一根是不可能的）。
*   **实现工具**：
    *   **Apache ZooKeeper**；
    *   **etcd**（`etcd` 名字很有意思，`etc` 类似 Linux 下放配置的分布式目录 `/etc`，可理解为 "distributed etc"）。
*   **工作流程**：
    1. 服务创建好后，通过**简单的注册流程**注册到服务发现系统（老师团队喜欢用 etcd），记录其**标识与地址**；
    2. 其他服务想调用某服务时，用标识即可 **query** 找到地址；
    3. 可以**注册监听（watch）**：服务挂了或有异常变化，服务发现系统**主动通知**所有观察者；
    4. 发现某服务内存爆掉/进程被杀后，通知相关方**重启服务**（service recovery）。
*   **重要性**：这是一款 MMO 引擎**未来必须做**的部分，否则服务器很难架起来——一款网游跑起来至少上百个服务；如房间服务器随玩家开房不停创生/回收（部分房间可复用），管理相当复杂。

### 10. 带宽优化

*   **核心概念**：带宽优化与**游戏运营成本**息息相关（大场景 MMO 数据量特别大）；即便不在乎钱，**数据量过大**也会引发网络协议层面的**拥塞** → 产生 **latency（延迟）**，甚至某些网关（如小区策略）会**主动掐断连接**以保护其他用户。
*   **带宽计算三要素**（优化即对这三个点下手）：
    1.  传输的**玩家数量**；
    2.  每次与用户**通信的频率**；
    3.  每次通信的**数据量大小**。
*   **方法一：数据压缩——浮点数转定点数（Quantization，量化）**（网游中最常用）：
    *   表达位置通常用 `Vector3(x, y, z)`，三个 `float`，一个 `float` 4 字节，共 **12 字节**；速度 `velocity` 又是一个 Vector3。
    *   优化 1：若是 2D 游戏或角色贴地行走，**只传 `xy` 两个分量**，少一个 channel；
    *   优化 2：世界不大时，用 **16 位定点数**即可把位置精确到**厘米**级别；
    *   优化 3：表达朝向（`orientation`）只需用 **1 个字节（8 位）**；
    *   配合方法：对游戏地图**分区**，每个区做小，定点数就能表达得非常精确。
    *   **实战效果非常好**，很容易让带宽**下降一半以上**，对网络游戏体验与稳定性帮助巨大——这是老师最想强调的压缩方法。
*   **方法二：兴趣管理 `AOI`（Area of Interest，兴趣区域）**：
    *   **核心概念**：世界很大（几百平方公里），但玩家只关心**以自己为中心的一定范围**——如射击游戏关心方圆 300~500 米（游戏内空间被扭曲，射程 500 米已很远）；近战游戏范围更小。**只把相关物体同步给玩家**，即可做本地 Gameplay。
    *   **实现方式 A——静态 Zone（分区）**：把世界分成一个个静态 zone（区域），用传送门（portal）连接；城外的消息与城内隔绝，有效屏蔽大量不必要的状态同步。
    *   **实现方式 B——AOI 半径 + 空间画格子**：以每个玩家为中心划半径；半径内对象多时暴力 query 会出问题，于是**在空间中画格子**——早期网游最常用 **100 米 × 100 米**的格子，并以其定义一个 `zone` / `region`。玩家站在一个 zone 里，感知范围扩 2 格，即 **3 × 3 的 zone 区域**都是其 AOI。实体进入/离开 zone 时**给对方发 event 更新 AOI 列表**；玩家进出 zone 也 notify 他人。进/出 zone 是**相对低频**事件（100 米 × 100 米跑完需几秒），通常只需处理几十个消息，不会太高频。
    *   **方法本质**：空间换时间，通过点状分布快速查询 AOI。
    *   **实现方式 C——十字链表法（Cross Linked List）**：将空间简化为 2D 分布，沿 **x 轴**给所有对象排序，沿 **y 轴**再排一次；已知自己在两个轴上的位置后，沿 x 轴前后走 $R$（如 AOI 半径 150 米）得到一圈 entity ID，沿 y 轴同样得到另一圈 ID，**两个集合的交集即自己的 AOI**。对象移动时 notify 别人、更新各自 AOI。十字链表非常高效，但当大量物体高速移动时有维护需求。
    *   **实现方式 D——PVS（Potentially Visible Set，潜在可见集）**：根据玩家所在位置，使用**预先生成好的可见性集合**，不在 PVS 里的东西不关注——适合空间分割感更强的游戏，帮我们宏观地 filter out 不关注的对象。
    *   **AOI 的收益（不止降带宽）**：AOI 不仅降低带宽，还**节约服务器端和客户端的算力**——服务器端不需要更新/传送不相关对象的逻辑状态。
*   **方法三：降低服务器同步频率（按距离分级）**：
    *   近处的对象（如身边疾驰的车、跑过的人）**同步频率略高**；
    *   稍远（50 米外）降为每秒 2~3 次；100 米外、100~200 米外**每秒同步一次**。
    *   前提：配合前面课程讲的**插值（Interpolation）/外插（Extrapolation）算法**，保证运动平滑；远距离的变化玩家也不易察觉。
    *   **核心理念**：根据对象离主体（玩家）的远近**动态调整信息同步频率**，让带宽被最大效率地利用。
*   老师提醒：带宽优化这部分虽枯燥但**非常实战**，做网游能真正节约运营成本。

### 11. 反作弊（Anti-Cheat）

*   **重要性（数据）**：Steam 调研显示 **70% 的玩家**发现别人作弊后就不想玩这个游戏。玩家的典型心态：单机游戏自己可以改血量、改金钱，但**网游里自己作弊可以、受不了别人作弊**。因此反作弊是任何 online game 的**核心系统**。
*   **为什么脆弱（vulnerable）**：online 化后黑客攻击面极广——直接修改游戏内存、注入代码、破解客户端、破解系统底层 SDK（`D3D` 渲染 SDK 函数入口被重载后所有画面变线框，即"**透明挂**"）、用第三台机器**劫持网络通讯**发送假消息等，防不胜防。

#### (1) 作弊途径与对应防护
*   **A. 内存修改**：定位内存中敏感数据（如血量）并持续改写（单机游戏常见）。
    *   防护 1：**客户端加壳**——把客户端加密，运行时在内存中实时解壳运转。注意（悲观的现实）：**几乎所有客户端加壳服务据老师所知都已被攻破**。
    *   防护 2：**内存混淆（Memory Obfuscation）**——把高度敏感的 Gameplay 数据在内存中加密，只在使用的瞬间解密读取，写回时再次变换。针对"帧同步游戏防偷窥"问题，这是一种策略，但"好像也有人能破"。
*   **B. 修改本地文件资源**：例如把射击游戏本地贴图全改成发光材质，敌人目标一目了然（穿迷彩趴地上也无视），等同**地图透视挂**。
    *   防护：**本地文件哈希值校验**——客户端不断计算本地资源文件的哈希值并上传服务器比对，哈希值不对即判定篡改，**直接踢下线**。这是现代 online gaming 引擎都会做的事，因为篡改本地文件是最常见的外挂方式之一。
*   **C. 网络通讯劫持**：通过第三方机器劫持网络通讯并注入假消息。
    *   防护：**网络流量加密**。加密算法分两类：
        *   **对称加密**：客户端与服务器共享同一密钥。问题在于密钥存在客户端，客户端被破解则密钥暴露，通讯将"透明大白于天下"（像打电话被旁人旁听）。
        *   **非对称加密**：客户端只持**公钥**，服务器持有**私钥**，两者不对称；客户端被破解只知道公钥，没有私钥解不开数据。
    *   **网游建连的标准流程**：先通过 `SSL` 这样的高度安全链接（走非对称加密）建立连接——非对称加密慢、成本高，但只在**登录时用一次**；安全信道建立后，**用非对称加密把一把"一次性对称密钥"传下去**，之后客户端与服务器的通讯使用**一次性对称密钥**。这样即便密钥被破解，也只破坏一个客户端，不影响后续所有链接；必要时还可**不停更换密钥**。
    *   结论：**网游的网络 traffic 必须加密**，老师建议把加密作为引擎底层提供的一项服务。
*   **D. 软件注入（Hook）**：通过钩子注入引擎代码。
    *   防护：反作弊软件扫描。如大名鼎鼎的 **`VAC`**（Valve Anti-Cheat，Steam 平台）、**`EasyAntiCheat`（EAC）**。核心工作原理大同小异：
        *   扫描内存中游戏的**签名（signature）**；
        *   若发现游戏被注入奇怪代码、`checksum`/哈希值不对，即判定被外挂挂载或被修改；
        *   检测可疑进程/软件（如常见的内存修改器）并报警；
        *   对**已知商业外挂**，用其**特征签名**在内存中扫描匹配，命中即判定作弊——由于外挂多为牟利、必然在网络上叫卖，此法对**所有商业性外挂非常有效**。

#### (2) AI 作弊——最难防范的作弊
*   **原理**：用 AI 图像识别直接识别敌人在哪里，再模拟鼠标键盘操作（训练机器人）。没有任何传统作弊手段可查——因为对方的"操作"是真实、自然的。
*   **检测难度**：可以检测虚拟的鼠标键盘操作，但已经很困难；AI 枪法"行云流水、见面爆头"，老师笑言看 AI 作弊视频"看得挺爽"，甚至怀疑以后游戏可以交给 AI 打、自己在旁边吃泡面看 AI 相爱相杀。
*   **门槛越来越低**：像 YOLO 已经出到 v5、v7，能自动在图片中识别目标，甚至通过 skeleton（骨骼关键点）识别关节与头部，做到枪枪爆头。
*   **应对思路（均在早期阶段）**：
    *   **用 AI 检测 AI（以魔法打魔法）**：还在非常早期；
    *   **基于统计数据的模型**：正常玩家的操作有 pattern，开挂用户的信用模型是另一 pattern；从浩如烟海的战局数据中检测作弊，不纠结单次操作。局限：假设写 AI 作弊器的人"比较笨"；若 AI 只做**辅助瞄准**、大部分操作仍由人完成，发挥"稍微好一丢丢"，深度学习算法要求就很高；
    *   **玩家打分/人工判断**：玩家给可疑行为打分。风险是**高玩常被误判为作弊**并被封号——对大佬无所谓，但对一般游戏/引擎来说"有点狠"，未必是好方法；
    *   注意：**靠人力判断是这节课唯一与技术无关的反作弊方法**。
*   **cloud gaming 能否解决反作弊**：云游戏能防传统客户端作弊，但**防不了 AI 作弊**——对方模拟鼠标键盘、读取的是屏幕信息，依然无解。
*   **中外差异趣闻**：老师与某国开发者合作时发现，中国开发者非常关注反作弊，而该国开发者认为"写那么多反作弊代码会降低游戏体验"。原因：**在那个国家游戏中作弊是违法行为**，没人作弊，自然不需要大量反作弊代码。老师感叹若全球如此，反作弊压力会小很多，但短期内各国法律基础不同、难以落地。
*   **总结**：想做一个玩家不弃坑的 online game，**反外挂是长期战、持久战**——每天要忍受用户指责，但这是下一代 online gaming 必然要面对的问题。

### 12. 无缝开放大世界的构建

*   **核心概念**：构建真正开放世界，首先要把世界做得足够大、能容纳足够多角色，即构建一个 **scalable（可扩展）** 的数据/服务器架构。
*   **三种基础世界模型**：
    *   **`Instancing`（副本实例）**：把世界分成副本——一个服务器有几万人，但同时下副本的只有十几个人，每个副本内只有十几人，最简单；
    *   **`Zone`（分区）**：把世界按空间分块（zone），角色在 zone 之间来往；
    *   **`Replication`（复制/分层）**：把世界分多个**虚拟层**，成千上万玩家分到不同层处理，每层 hosting 例如 1 万人，10 万玩家就分 10 层——与前面负载均衡的思想类似。

#### (1) Zone 方案：如何构建无缝 Zone
*   **角色归属**：每个 character 属于哪个 zone 就放在哪个 zone（单个 zone 内人数不会太多）。
*   **自适应划分**：玩家在世界上分布不均——几千平方公里内几十万玩家撒上去，很多 zone 没人、主城 zone 塞爆。Zone 可以**动态创建/添加**，一般用**四叉树不断细分**，细分到一定程度就停止（细节后续课程会讲）。
*   **跨边界问题与 Ghost（幽灵实体）**：唯一要处理的问题是角色跨边界（从 Zone A 到 Zone B）。利用 AOI 概念：每个角色关注自己半径内的区域，于是**在两个 zone 之间做 border（边界带）**：
    *   角色进入边界区域时，虽然仍在 Zone A，但 **Zone B 的服务器为其创建一个 `ghost`**，Zone B 的玩家就能看到它；它真正的逻辑/行为仍由原 Zone A 的 server hosting；
    *   实际跨越边界线的一瞬间，执行一个简单的 **flip（翻转/迁移）**：把数据迁移，原 Zone A 中的实体变成 ghost、Zone B 的 ghost 变成实体；
    *   **防抖阈值**：有的玩家会反复在边界来回抖动，导致数据被拷来拷去。因此迁移要设置**阈值**——穿过边界 20~30 米才迁移过去；从 B 后悔往回跑、跑过一段距离才切回来，避免高频震荡。
    *   **核心思想记住一条：Ghost**——两边感觉彼此"真的存在"，但实际上并不在一个服务器里。由于只处理边界带内的情况，假设 ghost 数量不会太多。

#### (2) Replication 方案
*   理解了 ghost 后 replication 就好懂了：每个 character 被扔到**多个世界镜像层**里处理。例如把一座城市分成很多层，每个玩家被扔到不同层处理，每层平均处理 1 万个"市民"；其他九层的市民在我这一层上是 **ghost（虚拟的）**——渲染时取一下它的数据即可。
*   用这种 replication 思想也能处理大量用户。

#### (3) 推荐方案：自适应空间划分 + Replication 结合
*   **核心概念**：真实构建大世界时，老师个人推荐**两种方法结合**：
    *   既要用空间划分思想，且划分最好**自适应（adaptive）**——因为玩家喜欢在主城聚集、野外空置，zone 定多大都不合适：用户聚集时划分变密；但**不能切得过密**（动态切割会导致数据在各服务器间来回跑），zone 也不能太小（**AOI 一般要 100~200 米**左右，zone 太小数据会频繁搬来搬去）；
    *   当 100 × 100 平方米区域内角色数量已超过**单台服务器的 hosting 能力**时，再用 **replication 分担压力**。
*   这两者的结合是相对完整的解决方案，也是开放大世界游戏可以尝试的结构。
*   **愿景**：这就是 online gaming 的未来——像"绿洲"（《头号玩家》）那样的世界；老师表示地平线上已有很多产品在研发，是令人激动的游戏类型，也是本节课程架构部分的收尾。

## 二、 重点术语与概念解析

### 1. MMOG
*   **定义**：Massive Multiplayer Online Gaming，大型多人在线游戏；大量玩家在一个世界内在线连接。
*   **应用/注意点**：并不专指 MMORPG，大量 FPS 也属 MMO；对服务器架构而言意味着海量并发与海量数据。

### 2. MUD
*   **定义**：Multi-User Dungeon，多用户地牢，最早的多人文字角色扮演游戏。
*   **应用/注意点**：纯文本交互（捡起碗、推门而出等），是 online 游戏最早的雏形。

### 3. Login Server（登录服务器）
*   **定义**：处理用户登录、握手、账号密码验证的服务器，是保护游戏服务器的第一道入口。
*   **应用/注意点**：一般走 HTTPS 安全信道；验证通过后不直接连业务 server，而转交 gateway。

### 4. Gateway（网关）
*   **定义**：用户唯一直接通信的对象，负责与内部各业务服务器通信。
*   **应用/注意点**：本质是防火墙，验证信息合法性，具备 DDoS 拦截、解压缩等功能；需部署多个实例（"大厅接待员"）。

### 5. Lobby（大厅）
*   **定义**：玩家登录后进入的等待/缓冲场景，可视为一个不允许战斗的特殊游戏模式。
*   **应用/注意点**：作为 matchmaking 等待时的缓冲池；不一定是真实场景，可以是虚拟大厅。

### 6. Character Server（角色服务器）
*   **定义**：集中管理所有玩家属性数据（道具、任务、装备等，可达几十兆）的服务器。
*   **应用/注意点**：被各类业务 server 频繁查询；数据不分散，避免"七零八落"。

### 7. Match Making（匹配系统）
*   **定义**：按天梯分/技能分、网络延迟等因素把玩家匹配进对局的系统。
*   **应用/注意点**：MOBA 类游戏最核心系统；开黑玩家单独池子匹配。

### 8. 原子性 / 回滚（Atomicity / Rollback）
*   **定义**：交易的原子性指一笔交易要么全部成功要么全部失败；回滚指失败时可恢复到操作前状态。
*   **应用/注意点**：交易系统具有金融属性，必须保证每笔交易的原子性、安全性、可回滚，防止断线/异常导致数据异常。

### 9. 幂等性（Idempotency）
*   **定义**：同一个消息被冗余发送多次时，系统只执行一次正常逻辑、自动过滤重复信息。
*   **应用/注意点**：分布式系统网络不稳定时消息可能重复到达，必须保证处理的幂等性。

### 10. 分布式系统（Distributed System）
*   **定义**：将服务器各服务拆分为多个进程并行工作、可动态加减的架构。
*   **应用/注意点**：解决海量玩家在线问题，具备弹性；但引入数据一致性、幂等性、bug 震荡放大等复杂问题。

### 11. 一致性哈希（Consistent Hashing）
*   **定义**：把服务器与数据（如 player id）分别哈希到 $[0, 2^{32}-1]$ 的环形空间，数据逆时针找到最近服务器节点作为归属的算法。
*   **应用/注意点**：哈希函数定下后无需 RPC 即可确定归属，增删节点只影响相邻节点；哈希需认真设计，可用虚拟节点解决负载不均。

### 12. 虚拟节点（Virtual Server Node）
*   **定义**：在哈希环上为每个真实服务器随机哈希出若干虚拟节点，再映射回原服务器。
*   **应用/注意点**：解决哈希分布不均导致负载不均衡的问题。

### 13. 服务发现（Service Discovery）
*   **定义**：让服务创建后注册自身标识与地址、其他服务可查询并监听其变化的机制。
*   **应用/注意点**：代表工具 ZooKeeper、etcd；负责通知服务崩溃、重启服务，防止雪崩。

### 14. ZooKeeper / etcd
*   **定义**：服务注册与发现的开源工具（etcd 名字有 "distributed /etc" 之意）。
*   **应用/注意点**：服务注册、query、watch 通知，是大型分布式系统基础设施。

### 15. 量化（Quantization）
*   **定义**：把浮点数转成定点数的数据压缩方法。
*   **应用/注意点**：网游中最常用压缩手段，如位置用 16 位定点数到厘米精度、朝向用 1 字节、2D 只传 xy，可让带宽下降一半以上。

### 16. AOI（Area of Interest，兴趣区域）
*   **定义**：以玩家（主体）为中心、只需同步其周围对象的区域范围。
*   **应用/注意点**：实现方式有静态 zone、空间画格子（如 100m×100m，3×3 邻域）、十字链表、PVS；不仅降带宽，还省客户端与服务器算力。

### 17. 十字链表（Cross Linked List）
*   **定义**：把对象分别按 x 轴、y 轴排序成两个链表，两轴上前 $R$ 范围集合的交集即 AOI。
*   **应用/注意点**：高效，但大量物体高速移动时有维护成本。

### 18. PVS（Potentially Visible Set，潜在可见集）
*   **定义**：预生成好的、按位置划分的可见性集合。
*   **应用/注意点**：不在 PVS 内的对象不关注，宏观过滤掉不关心的对象；适合空间分割感强的游戏。

### 19. Ghost（幽灵实体）
*   **定义**：实体跨 zone 边界前，在目标 zone 服务器上创建的"影子"实体。
*   **应用/注意点**：Zone B 的玩家能"看到"仍在 Zone A 的实体；实体真实逻辑仍由原 zone hosting；配合 flip 完成迁移。

### 20. Instancing / Zone / Replication
*   **定义**：开放世界三种承载模型——副本实例、空间分区、分层复制。
*   **应用/注意点**：实例最简单；分区横向分割空间；复制纵向分层分担负载；实际推荐自适应划分 + replication 结合。

### 21. 对称加密 / 非对称加密
*   **定义**：对称加密使用同一密钥加解密；非对称加密使用公钥/私钥对（公钥加密、私钥解密）。
*   **应用/注意点**：对称加密快但密钥存客户端易泄露；非对称加密慢但安全。网游登录用 SSL（非对称）握手后下发一次性对称密钥，之后用对称加密通讯。

### 22. 透明挂
*   **定义**：通过重载渲染 SDK（如 D3D）底层函数入口，把画面全部渲染成线框的外挂。
*   **应用/注意点**：线框世界里所有物体一目了然，属于"破解系统底层 SDK"型作弊，防不胜防。

### 23. 内存混淆（Memory Obfuscation）
*   **定义**：把高度敏感数据在内存中加密，使用时瞬间解密、写回时再变换。
*   **应用/注意点**：针对内存扫描/偷窥类外挂（如帧同步防窥屏）的防护手段，难度较高但"也有人能破"。

### 24. VAC / EasyAntiCheat（EAC）
*   **定义**：Steam 平台的 Valve Anti-Cheat 与 EasyAntiCheat 反作弊软件。
*   **应用/注意点**：扫描内存中游戏签名、checksum/哈希值，检测可疑进程与已知外挂特征，命中即判定作弊。

### 25. DDoS（分布式拒绝服务攻击）
*   **定义**：Distributed Denial of Service，通过海量请求使目标服务器瘫痪的攻击。
*   **应用/注意点**：gateway 需具备一定拦截功能；更复杂的 DDoS 有更复杂的防御机制。

### 26. Hit Registration（命中判定）
*   **定义**：判定射击/攻击是否命中的机制，可分为客户端判定与服务器端判定。
*   **应用/注意点**：服务器端判定更可信，但也受插值/外插算法影响；参考资料方向之一。

## 三、 工程经验与避坑指南

### 1. 架构方法论
*   像做游戏引擎"先从数据结构思考"一样，**架构 MMO 服务器从数据开始思考**：数据想清楚了，上层各系统的结构就清楚了。
*   先做对战游戏没问题；但做 MMO 还需要补大量其他技术细节与知识体系——"听完这一节千万不要觉得就能做网游了，里面每一页都有很多小细节"。

### 2. 分布式系统的血泪经验
*   **"简单功能写一两个月很正常"**：分布式系统写起来容易，但上线测试、边界情况处理周期漫长。
*   **最恐惧的是"抓不住 bug"**：线上跑三天偶然出现一次、无法重现的恶劣 bug，是分布式程序员最痛苦的——**"能确定重现的 bug 一定能解决；无法重现的 bug 最难"**。
*   **bug 会震荡放大**：一个低频、难以检测的 bug 若没在第一个服务内被拦截，错误数据会经 RPC 传递到其他服务被再次放大，甚至无限震荡，导致服务器性能急剧下降——实战团队只能把 RPC dump 下来分析，发现某些 RPC 被诡异调用无穷多次。这正是"复杂系统"（老师推荐书籍《复杂系统》）中震荡现象：**构建分布式系统就是在用复杂系统的思维方式架构**。
*   **鲁棒性**：业务逻辑可以写对，但健壮性未必达标——"土豆服务器"背后是海量的可靠性考量，不必一味嘲笑大厂。
*   给初学者：学 104 刚入学打基础时，**不建议一上来写一致性哈希这类复杂分布式架构**。

### 3. 服务管理与弹性
*   服务随玩家增减被不停创建/销毁，半夜玩家走了要关服务；**服务挂掉别人不知道会雪崩**。必须做服务发现（ZooKeeper/etcd），这是未来做 MMO 引擎的必做项。

### 4. 带宽优化经验
*   **量化先行**：先做浮点转定点的简单压缩，很容易降一半以上带宽；配合地图分区效果更好。
*   **AOI 必做**：做状态同步/消息 RPC 前首先要考虑 AOI 范围；游戏服务器新人一上来接触最多的概念就是 AOI。
*   **按距离分级同步频率**：近处高频、远处低频，配合插值/外插算法保证平滑。
*   **格子尺寸权衡**：格子太密 zone 多，太稀疏 zone 内角色多、效果达不到；早期网游常用 100m×100m。画格子与十字链表各有取舍，无绝对优劣。
*   比喻：服务器端像**快递公司**，每个客户端是家庭住址，服务器要把包（数据）挨个投递给不同地址——非常辛苦；玩家"能跳能看"的体验背后是大量底层细节。

### 5. 反作弊避坑与运营
*   **反作弊是长期战、持久战**：每天要忍受用户的指责，但这是做不弃坑 online game 的必然。
*   **悲观现实**：几乎所有客户端加壳服务都已被攻破；内存混淆"好像也有人能破"——民间高手太多。
*   **封号须谨慎**：靠玩家打分/人工判定可能**误伤高玩**（一通行云流水的操作被误判作弊），对一般游戏/引擎"有点狠"；数据统计法假设写外挂的人"比较笨"。
*   **有效手段**：对商业外挂做**已知特征签名扫描**非常有效（外挂要牟利就会叫卖）。
*   **云游戏也防不了 AI 作弊**：对方模拟鼠标键盘、读取屏幕信息，传统手段无解。
*   彩蛋：某国因为**作弊是违法行为**，开发者几乎不写反作弊代码；老师希望游戏作弊未来能成为违法行为。

### 6. 无缝大世界避坑
*   **边界抖动**：玩家在 zone 边界来回抖动会导致数据反复搬运，必须设置**迁移阈值**（如穿过边界 20~30 米才迁、回来要跑过一段距离才切回）。
*   **划分粒度权衡**：zone 切得过密 → 数据在各服务器来回跑；zone 太小 → AOI（一般 100~200 米）覆盖不到、数据频繁搬移；局部超载时用 replication 分担。
*   世界模型推荐：**自适应空间划分 + replication 结合**。

## 四、 课堂答疑（Q&A）

### 1. Q：玩家在服务器端做微调（命中判定），服务器能不能判定出来？
*   **A**：取决于判定方式：
    *   若是**客户端判定**（如守望先锋案例——打中那么大的判定盒都算命中），前提假设是客户端**不会被 compromise、不会被 hack**，此时微调确实判定不出来；
    *   若是**服务器端 hit registration（命中判定）**：射线真的命中目标，且服务器做 lockstep composition 结果一致，就认为真的击中；
    *   **微调对象很关键**：若微调的是**靶子位置**（把对方位置按与差值算法不一致的方式移动），服务器端算法与服务器上的结果不一致，**能判定出来**；若微调的是**枪口位置**（用外挂把枪真对准人打），服务器端**判定不出来**。

### 2. Q：分布式系统在游戏行业应用广泛吗？
*   **A**：早期网游服务器架构没那么复杂——有非常厉害的游戏**整个服务在一台物理机上跑完**，产品是"常青树"；随着现代网游复杂度提高，越来越多服务器引擎底层采用分布式系统架构，但**整个行业仍处于过渡阶段**；老师预计 **3~5 年（而非五到十年）内逐渐成熟，并成为行业标配**。

### 3. Q：无缝大世界 MMO 实现的难点有哪些？
*   **A**：老师谦虚表示"我自己还没做出来，不敢说知道什么难点"（自谦为"吴桐大师的 MMO"）。但初步看：
    *   第一步是做出**足够大的世界**让玩家在其中走动——这涉及 server hosting 能力；
    *   难点在于玩家不只是"互相看见"：还要**开枪打到远处的敌人、摧毁墙、进行大量交易/行为**，复杂度会变成 **$O(n^2)$（n 平方）级别**——静态世界里走来走去、say hi、跳个舞、简单战斗是简单的；但要几十万人同世界战斗+移动+交易+对话，则**所有 server（包括聊天）都要按分布式、负载均衡架构重新架构一遍，且叠在一起还能正常工作**——极其挑战；
    *   这也是为什么**目前商业引擎**中（如 Epic 的 Tim Sweeney 讲 metaverse）虽都在往这个方向努力，但**还没有人敢说交付了这样的技术平台**；这是下一代游戏引擎最值得努力的方向，也是老师的终身职业梦想，预计还需要 **5~10 年**才能交付这样的世界。
