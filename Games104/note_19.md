# 网络游戏的架构基础：网络协议、时钟同步与 RPC 通信机制

---

## 一、 核心知识点与原理剖析

### 1. 网络游戏的定义与五大核心挑战

*   **核心概念**：网络游戏（Online Game，讲师称其翻译困难，也可叫"联网游戏"）是相对于单机游戏（Single Player，单人游戏）而言的。早期游戏只需在一台电脑上自己玩；网络游戏的核心目标是**让玩家在任何时候、任何地方，与任何人一起玩**——从街机时代物理性地站在一起打游戏，到 NDS 联机，最终演变为"只要有一套设备、只要有网络，就能与任意小伙伴连在一起并肩战斗"。
*   **游戏引擎复杂度的本质区别**：传统游戏引擎的所有复杂逻辑只考虑了一个人的情况；一旦考虑多人，就引入了"**平行宇宙（multiverse）**"问题——**我看到的世界和你看到的世界不是一个世界**，100 个人联网进入一个虚拟世界，每个人看到的世界都不一样，但他们以为彼此看到的是同一个世界。讲师笑称游戏引擎研发者研究深了都会变成"物理民科"，因为网络游戏生动地验证了相对论与客观性的讨论。
*   **挑战一：事件一致性（最大的挑战）**
    *   **核心概念**：在存在网络延迟、信息不完整传递的前提下，让多个"宇宙"之间的世界实现同步，保证彼此世界发生的事件一致——不能出现"在我的世界里玻璃瓶是完好的，在你的世界里玻璃瓶已打碎"，否则就会像《黑客帝国》（Matrix）中的角色意识到自己活在虚拟世界一样穿帮。
*   **挑战二：传输不可靠**
    *   **核心概念**：网络世界最恐怖的事情不仅仅是延迟，而是**传输是不可靠的**：存在丢包、大面积延迟（delay）、拥塞（congestion），甚至断线、重连。玩家会看到对方突然"傻在那、动不了"，这就是掉线的表现。上帝之间不会丢包、没有延迟，但在游戏世界里连接经常丢包。
*   **挑战三：反作弊与信息安全**
    *   **核心概念**：Online Game 本质上是一个**巨大的经济系统**，反作弊、反信息泄露是重要责任。玩家登录后，个人 IP、全部信息、能否被陌生人加为好友、是否会被黑客入侵（hack）电脑、是否有作弊行为，都需要防范。
    *   **与单机游戏的对比**：单机游戏被 hack 无可奈何——以前打不过去时可以用内存修改工具搜索血量等数值，锁定内存地址，小怪怎么打都不掉血直接过关；但 Online Game 绝对不可接受"对面的人被我打了一通，血却动都没动"，玩家会当场摔键盘。
*   **挑战四：多样性**
    *   **设备多样性**：Online Game 面对的设备极其复杂——iPad、iPhone、Android、iOS、PC 客户端，服务器则可能是 Linux 服务器，这么多不同设备要能连接在一起，且运行完全一样的逻辑。
    *   **热更新**：游戏上线后，可能有很多玩家正在游玩，甚至"打的正嗨"。修复 bug、快速迭代逻辑与规则时，必须有一种办法让玩家"神不知鬼不觉"地完成更新，而不是强制推新版本打断他们。像《新世界》《最终幻想》《魔兽世界》这类大型网游，拥有海量系统与玩法，全部都要塞进网络数据包中彼此连接，这种多样性非常"恐怖"。
*   **挑战五：复杂度（大规模并发）**
    *   **核心概念**：要构建像《头号玩家》中"绿洲"那样的世界，上万人在同一个世界战斗，连接复杂度以 **N 平方** 急剧扩张。两个人的连接操作比较简单，但 200 人、2000 人、2 万人时，网络连接会越来越复杂。这是下一代游戏引擎非常重要的挑战——"无限进、无限出、看到无数人在一起的虚拟世界"。

### 2. 网络协议基础：OSI 七层模型与 Socket

*   **核心概念**：协议（Protocol）解决的核心问题是"**如何在两台电脑之间传递数据**"。物理层传输非常"粗暴"：多少电压算 0、多少算 1，传输的 0101 中哪个算收、哪个算伪？若没有协议层，要处理大量奇怪情况。
*   **历史背景**：互联网概念与 TCP/IP 协议由 Vint Cerf 与 Robert Kahn 创立，源自美国军方项目，最早通过电话线、卫星链接实验室。讲师感慨军事推动人类科技发展，"前人挖井，后人吃水"。
*   **OSI 七层模型**：从最底层的**物理层（Physics）**、**数据链路层**、**网络层**、**传输层**，到**会话层**、**表示层**、**应用层**。中间加了一层 layer，将硬件复杂性全部隔绝，上层协议只需直接写数据、由下层负责分发。
    *   **实用观点**：做游戏通常不需要用到那么深，一般都在**应用层**"各种鬼混"；但做 CDN（内容分发网络）这类提供下载服务的应用，必须深刻理解七层协议，因为七层存在大量冗余数据拷贝，可以针对协议底层做优化——这是非常高端的能力。
*   **Socket 编程**：对大部分游戏引擎开发者，用 Socket 编程即可。只需提供 **IP 地址** 与 **端口号（Port）**，就能与对方建立连接，确定协议后持续传输数据。所有网游的本质都是：客户端写死服务器的 IP 与 Port，下载客户端后连过去。
    *   **安全警示**：如果服务器地址必须开放，但不具备抗 DDOS 攻击（分布式拒绝服务攻击）的能力，很容易被写个程序把运行良好的游戏打掉；现代网游已做大量相应处理。讲师提醒这是违法行为。
*   **IPv4 与 IPv6**：
    *   在中国做在线应用一般多用 **IPv4**。
    *   做真正的通用游戏引擎，**建议一定要考虑 IPv6**——全球很多国家（如德国）已大面积使用 IPv6，若服务器不支持 IPv6，很多用户会连不上你的服务器。

### 3. TCP：可靠的传输控制协议

*   **核心概念**：TCP 是最经典的互联网协议，互联网上绝大部分信息通过 TCP 传输。中文全称"传输控制协议"，是**面向连接的、可靠的**字节流协议。
*   **主要特性**：
    1.  **三次握手建立连接**：通过三次握手建立"牢靠"的连接，连接比较稳定。
    2.  **顺序保证**：确保发出的包**有顺序**地到达，前面的包不会与后面的包冲突。
    3.  **流量控制（Flow Control）**：当网络发生拥塞或阻塞时，自动降低发送效率。
    4.  **拥塞控制（Congestion Control）**：防止网络被过量数据"炸掉"。
*   **TCP 包头**：较长，约 **20 字节**，有些"重"。
*   **确认机制（Acknowledgment Mechanism）**：TCP 的核心原理非常简单——接收者每收到一个信息，就给发送者发回一个 ACK（Acknowledgment，确认告知）；发送者只有在收到 ACK 后才会继续发下一个包；若没有收到确认，就持续重发。这也是可能引发网络拥塞的原因之一。
*   **拥塞控制的滑窗思想**：
    *   发包不是一个个散发的，而是**一批批按窗口（Window）发送**。
    *   一开始窗口很小，随后开始传输；如果每次都很顺利收到 ACK，就**把窗口变大一点**（一次性多传一些）；一旦发现 ACK 出现丢包，就把窗口往下滑，少发一点。
    *   在不稳定的网络下（例如小区里热播大电影导致全小区抢带宽），TCP 链接的带宽波动呈"一会儿快、一会儿慢"的锯齿状，这正是 TCP 导致延迟的原因，但同时也是互联网没有"炸掉"的保障——就像马路上开车，前面车多时自觉减速、不上高架，高架就能通行；所有人不管不顾往上冲，高架很快堵死，谁都走不了。
*   **与游戏的关系**：TCP 的确认机制意味着"前面消息没收到确认，后面的消息就不发"，这在游戏中很致命——玩家想打出一个输出操作，却因为前一个移动消息没传过去而被卡住，体验极差。

### 4. UDP：轻量的用户数据报协议

*   **核心概念**：UDP（中文"用户数据报协议"）由 TCP 的发明者之一在 10 年后发明。其设计初衷是：只有两个设备之间传数据，越简单越好，不要那么多复杂的约束。
*   **主要特性**：
    1.  **无需建立长连接**：不需要"没事握手"，"看顺眼就直接发，你爱收不收"。
    2.  **不要求稳定**：不保证数据一定到达，也不保证顺序（order）。就像发邮件，早几分钟晚几分钟"死不了人"。
    3.  **无流量控制、无拥塞控制**：没有 flow control 和 congestion control，"你就往上塞就好了"，因此也容易用来"干坏事"。
    4.  **包头轻**：包头约 **4 字节（32 位）**，比 TCP 包头轻了约 5 倍。
*   **游戏协议选型**：
    *   **炉石传说选用 TCP**：对延迟不敏感（0.2 秒、0.3 秒并不介意），连接稳定更重要。
    *   **守望先锋等快速射击游戏用 UDP**：要求响应特别快（responsive），尤其在不稳定的公网环境下。
    *   **大型 MMO 使用组合协议**：一般不用单一协议，而是按需选择通道——用 TCP 做**签名认证、登录、建立账号连接、维持心跳包**；用 **UDP 传输真正的战斗数据**；聊天、邮件等可能又走回 TCP 通道。
*   **本质总结**：TCP 稳健但"磨磨唧唧"，带宽上下波动、阻塞后续消息；UDP 快速但完全不可靠，客户端与服务器之间连"最基本的信任"都没有。于是聪明人把两者优点结合——这正是现代游戏引擎的做法。

### 5. 可靠 UDP 的构建：ARQ 与 FEC 前向纠错

*   **核心概念**：做自己的游戏引擎尤其是做在线联机时，非常推荐采用第三方或自己定制一个**基于 UDP 的可靠连接协议**，难度并不像想象中那么大，且蕴含很多有趣的数学原理。游戏服务器与标准 Web 服务器开发有很大区别：游戏要**始终保持活着的连接**、最好保证消息传递**有一定顺序**（例如先喝药回蓝再放技能，乱序受不了），又要**非常高响应、最好没有延迟**，还经常需要**群发广播（broadcast / send all）**——这些需求恰好一半像 TCP、一半像 UDP，因此要定制协议把两者优点结合。
*   **构建可靠连接的三大基础概念**：
    *   **ACK**：收到一个包后告诉对方"确认收到"。
    *   **NACK（Negative ACK）**：ACK 的孪生兄弟，除了告诉对方"我收到了某某包"，还能告诉对方"什么包我没收到"，同样具有信息量。做网络与信息学中的信息论思想很接近——**在彼此不可靠的连接下，建立可靠的彼此信任的通讯**。讲师用古代两位指挥官协同作战类比：传信者可能被截杀、被俘获叛变（compromise）、存在延迟，如何在两军间建立可靠通讯，与网络问题同构。
    *   **序列号（Sequence Number）**：给每个包编号，用于识别与排序。
    *   **超时（Time out）**：超过一定时间没确认的包就"不理他了"。
*   **ARQ：自动重传请求（Automatic Repeat reQuest）**
    *   **定义**：在建立网络连接传输时，若丢包或未收到，接收方能告知发送方"自动给我重新传发包"。所有可靠算法都要实现 ARQ 的效果。
    *   **滑动窗口协议（Sliding Window Protocol）**：当传输大量数据时，有一个窗口；一次性把窗口内的数据全部传出，收到接收方返回的 ACK（比如确认了 2 号包），就知道 2 号及以前（1、2）都已到位，于是把窗口往前滑，继续传后续的包（3、4、5、6……），直到收到后续 ACK 继续滑动。
    *   **Stop-and-Wait ARQ（停等 ARQ）**：窗口大小为 1，每发完一个包都要等确认再往前走。最古典但也最笨，从没被实际使用过——因为每个包都要等一个来回（RTT 约一两百毫秒），上行带宽完全没被利用。
    *   **Go-Back-N ARQ（回退 N 步）**：若发现窗口里有一个包丢了，就把整个窗口里的包重新传一遍。非常实用，**讲师推荐在做自己的 reliable UDP 协议时优先用这个策略**。
    *   **Selective Repeat ARQ（选择性重传）**：使用 NACK，告诉发送方"哪个包（如 2 号包）丢了"，发送方只需重传那一个包。连接更稳定，也能节约不必要的带宽浪费，但需要额外的 NACK 消息类型。细节非常多，但不是本课重点。
*   **FEC：前向纠错（Forward Error Correction）**
    *   **核心概念**：UDP 丢包"不管"，但我们必须管。如果靠重传：要等 ACK 收到，再翻出老早以前的包重传；滑动窗口方式下后面所有包都得卡住。因此聪明的人类想到——**即使知道数据丢了，也能把正确数据找出来**。思路是"空间换时间"：用额外数据传输量解决丢包问题。把数据传两遍可以但太笨，要用更高明的方法。在丢包率仅 5%~10% 时，可极大减少重发概率；但丢包率接近 10%~20% 时会浪费约 20% 带宽，可能"救不了命"，需要严格概率运算。
    *   **方法一：异或（XOR）校验算法**
        *   异或运算规则：两个 bit 相同则结果为 0，不同则结果为 1（0⊕1=1，1⊕0=1，0⊕0=0，1⊕1=0）。
        *   原理：假设有 A、B、C、D 四个数据，把它们全部异或得到校验值 $E = A \oplus B \oplus C \oplus D$。$E$ 不仅能校验数据，更厉害的是：**当 A、B、C、D 中任意一个丢失时，用剩下的数据与 $E$ 做异或，就能恢复出丢失的原值**。例如 A 丢失时：$A = B \oplus C \oplus D \oplus E$。该定理可被严格证明。若 $E$ 本身丢失则无所谓，因为真正信息是 A、B、C、D。
        *   实际应用：硬盘 RAID 5 存储阵列的数据冗余正是此原理——5 块硬盘中 4 块存数据、1 块存异或值，任何一块坏了都能迅速把数据恢复（pick up）。
    *   **方法二：Reed-Solomon 编码算法（里德-所罗门码）**
        *   这是计算机体系结构中很重要的算法，不仅用于网络重传。其思想非常巧妙：
        *   对任意数据 $D$，构造一个**范德蒙德矩阵（Vandermonde matrix）** $B$：上半部分是单位对角阵（全 1），下半部分是构造出的冗余矩阵。
        *   **关键性质**：从 $B$ 中**任意抽掉若干行**（例如抽 3 行），剩下的矩阵**依然可逆**。
        *   编码：用矩阵乘信息 $C = B \times D$。$C$ 的上半部分与原始数据一模一样，下半部分出现冗余信息（例如 5 个信息加 3 个冗余，共 8 个包）。
        *   解码恢复：假设传输中非常不幸丢了 3 个包（丢包率接近 30%~35%），把丢失信息对应的行从矩阵中删掉，$B$ 收缩成 $B'$，$B'$ 仍是长宽一致的方阵。此时拿到的是 $C' = B' \times D$，只要 $B'$ 可逆，就有 $D = B'^{-1} \times C'$，**通过一步矩阵逆运算就把原始数据重建出来**。
        *   应用价值：**网络传输中应用极多**。尤其是手游/移动端，网络链接常常不稳定（WIFI + 手游切换），手机端丢包率甚至可超过 10%~20%。用 Reed-Solomon 能很好解决丢包问题，避免"每次等 ACK 就过去 200ms"导致游戏没法玩。数学并不抽象，本质就是"构造一个任意抽掉若干行仍可逆的矩阵"。
*   **可靠 UDP 的自由组合策略**：
    *   只要理解 ARQ 基本算法，就能选择性使用：用 sliding window 分批传输，自定义 retransmit（重传）策略（可有大量小技巧），再加上 FEC 算法，保证在一定的丢包率下包体仍能正确收到，使 ACK 尽量成功。
    *   游戏引擎底层用 UDP 包装时，客户端与服务器会建立**很多条连接**，每条连接可挑选不同策略：对稳定性要求高、延迟不敏感的，策略偏向稳定；对响应速度要求极高（low latency）、丢几个包无所谓的（如玩家左右移动的操作丢了也无妨），追求 highly responsive。
    *   结论：不直接用"包装好的"TCP，而用自己的 UDP 自由组合，**特别适合游戏这种复杂情况**，可自由组合各种想要的体验，"定制化 DIY 总是开心的"。做更复杂的网络游戏，甚至可能连底层协议栈都要去改。

### 6. 时钟同步：NTP 算法原理与工程实践

*   **核心概念**：做对战游戏前，第一件事是**把彼此的时钟对准**。原因很简单：玩家 A 说"我在 13 秒零五打出了一发子弹"，玩家 B 说"我在 13 秒零六做了一个躲闪动作"，B 到底算躲过还是没躲过？如果彼此时间没对准，就无法判断。这正是"多重宇宙"概念在时间维度的体现——**不同宇宙中时间不同步**；相对论讲的"每个人都是相对的、以自我为中心的参考系"在游戏里都会遇到，多个 universe 之间第一步就是要**把时钟对齐（时钟同步）**。
*   **网络时延基础概念**：
    *   **RTT（Round Trip Time，往返时间）**：从发一个包给对方，到收到回报，共需多久。很多是**应用层自己写的**——客户端发个包给服务器，服务器多久回，就能测出 RTT 与当前网络延迟（latency）。
    *   **ping 值**：更底层，由网络协议 / OS 更底层（可能在传输层）做的自我检测。与 RTT 非常接近，但严格抠起来有细微差别。游戏引擎中两者不必区分太严格，RTT 更有用。
*   **对时的普遍需求**：GPS 的本质原理就是在天上飞 24 颗卫星，每颗装有极准的电子钟（原子钟），GPS 接收装置与原子钟对时，通过精准的时间相位差用三角定位法算出与各卫星的距离差，从而确定地球表面位置。**对时最大的难点是：任何信息传输不能超过光速**——北京说"现在七点整"，消息传到手里时已过了几百毫秒；生活场景无所谓，但对 GPS 这类精密仪器影响巨大。
*   **NTP：网络时间协议（Network Time Protocol）**
    *   **分层结构（stratum）**：对时是一层层的，像地层一样。例如南京紫金山天文台有最精准的天文钟，往下逐层对时；**原则上超过 15 层之后钟就对不准了**。而在网络游戏中，stratum 通常只有一层——**你只要跟服务器对就好了**。
    *   **NTP 基础算法（四个时间戳）**：
        1. 客户端在本地的 $T_{0C}$ 时刻发出请求（C 代表 Client）。
        2. 服务器根据自身时钟在 $T_{1S}$ 时刻收到（S 代表 Server）。
        3. 服务器在 $T_{2S}$ 时刻把回包发出（包内记录 $T_{1S}$、$T_{2S}$）。
        4. 客户端在本地 $T_{3C}$ 时刻收到回包。
        *   客户端手里同时握有 $T_{0C}$、$T_{1S}$、$T_{2S}$、$T_{3C}$ 四个时间。
    *   **核心公式（offset 时差）**：
        $$\theta = \frac{(T_{1S} - T_{0C}) + (T_{2S} - T_{3C})}{2}$$
        即"服务器处理前后的两个时差取平均"，估算客户端与服务器之间的时差 offset。
    *   **RTT 估算**：$RTT = (T_{3C} - T_{0C}) - (T_{2S} - T_{1S})$，把服务器在两端消耗的时间剪掉，即得出路上往返延迟。
    *   **数值示例**：客户端 17:01:00 发出，服务器收到时是 17:01:32（显然客户端与服务器钟差 30 秒）；服务器 1 秒后在 17:01:33 发出回包；客户端在 17:01:05 收到。路上延迟 = 5 秒 - 1 秒 = 4 秒（RTT 约 4 秒）。按 RTT=4 秒估算，收到包的正确时间应为"服务器时间 33 + 4÷2 = 35 秒"，而客户端显示 05 秒，于是得出"我的钟比你慢了 30 秒，得赶快往前拨"，offset 计算结果正好是 30 秒。
    *   **算法的危险假设（两大不成立的前提）**：
        1. 认为**网络环境整体稳定**，不会一会儿快一会儿慢。
        2. 认为**上行与下行延迟对等**，可以用 RTT÷2 估算单向延迟。现实中大概率不成立——家庭网络下行带宽很高（下载快），上行带宽较窄，且延迟大小不定，上下两路不一定对等。因此 NTP 基础算法不准确，但"肯定比没对时好很多"。
*   **游戏引擎中的工程实践（对时技巧）**：
    *   信息论告诉我们：在不可靠连接前提下，**无论校对多少次都无法把时钟完全对准**（可用数学证明），但可以尝试去猜、去逼近。
    *   **第一步**：把 NTP 算法跑一遍，算出客户端与服务器的差别，快速调整客户端时钟。
    *   **第二步**：继续多跑几次 NTP 算法（3 次、5 次、10 次都可以），得到一系列 offset 值，同时也能算出相应的 RTT 值。
    *   **第三步（统计学思路，很 hack）**：把 **RTT 高于平均值 50%** 的那些校准样本**直接扔掉**——因为这说明当时网络在波动，算出的 offset 不可信。
    *   **第四步**：把剩余"可靠 RTT"情况下算出的 offset 值**取平均**，用这个平均值对钟做最终调整，完成一次对表。
    *   重要经验：**客户端与服务器建立链接、握手成功后的第一件事，就是要把钟对起来**。以前做游戏引擎时，很多 bug 是"钟没对好"导致的，处理时间敏感业务逻辑时尤其重要。
*   **实践结论**：用 NTP 算法加上述简单策略，能得到基本可靠的对时；但实践下来仍存在误差，有时不易去除，因为真实世界的网络链接远比想象复杂。

### 7. RPC：远程过程调用与 IDL 接口定义

*   **为什么要 RPC（Socket 写业务逻辑的痛点）**：
    *   有了 Socket，只需找到 IP 与端口，塞数据就行；但真正写游戏业务逻辑时发现"真的不好使"。表达游戏业务逻辑就像人与人的对话：服务器想做一件事 → 服务器说好 → 做完后告知。
    *   **痛点一：消息定义复杂**。游戏逻辑中一会儿一个 `float`、一会儿一个空间 `vector4`、一会儿一个颜色、一会儿一个矩阵、一会儿是怪物的血量值、一会儿是怪物类型……要把这些五花八门的数据打包成网络协议发给别人并定义好协议，程序员写到这一趴会很痛苦。古老的做法是定义"巨长无比的消息列表"，**极难维护**。
    *   **痛点二：跨平台与字节序问题**。客户端与服务器操作系统不同（客户端是 Android/iOS，服务器是 Linux），做主机联网游戏时，Xbox 与 PlayStation 平台最反人类的地方就是 **big endian / small endian（大端/小端）**问题——数据到底是高位在前还是低位在前，packing 都不一样，网络传输的数据也就不一样。
    *   **痛点三：对齐与 packing**。网络传输时希望数据按 4 字节对齐，若只是顺序压数据会"像狗啃的一样"一会长一会短；传变长的 `array` 时消息怎么定义也很麻烦。
    *   **痛点四：易出错且危害大**。让写业务逻辑的程序员去定义消息、解决传输困难，是"他特别不喜欢做、特别容易做错"的事——**一个消息定义错了，对端整个解析就乱七八糟，底层逻辑全部炸掉**。还存在一种攻击：向服务器发各种乱码数据，服务器要解码（decode）、解密（decrypt）却解析出无效信息，浪费大量算力。
*   **RPC：远程过程调用（Remote Procedure Call）**
    *   **核心思想**：让程序员**像写自己的日常代码一样做函数调用**——只需写函数名、把参数传进去，剩下的一切（把参数打包成消息、序列化、网络路由到对方服务器、对方接消息、入队排队处理、反序列化、回调结果）全部透明，程序员"该干嘛干嘛去了"，做完后被 call 回来处理结果即可。这是一个"非常了不起的发明"。
    *   **优势**：极大释放程序员的开发效率，同时**不会出错**——最怕逻辑写错、数据 packing 错，而 RPC 把这些都封装好；无需再手写复杂的网络报文结构体（struct），不用操心序列化/反序列化（serialization / deserialization）、加密解密过程，后台处理完全透明，让程序员专注写游戏逻辑。RPC 是现代引擎**最标准的实践（practice）**。
    *   **Go 语言示例**：RPC 调用很简单——告诉对方"我要调用 server 的某函数，参数是什么"，server 那边有相应函数，调用后通过一系列消息的数据准备与传输，最终该函数被激活执行。
*   **IDL：接口定义语言（Interface Definition Language）**
    *   **定义**：用一种独立语言描述接口，如 Google 的 **protobuf（Protocol Buffers）**。它非常像工具链中的 **schema 定义**——小引擎里 component 的接口与这种语言特别相似，都是共通的东西。
    *   **与反射的关系**：这解释了**反射（reflection）为何如此重要**——它不仅对工具侧、数据序列化/反序列化有用，对 component 有用，**对网络也极为有用**。所有网络通讯都通过 IDL 定义好后，用一整套东西解决函数指针存储、数据 packing、序列化与反序列化。
*   **RPC Stub（票据存根）**：
    *   **定义**：客户端或服务器启动后，彼此告知存在，并**注册一大堆 RPC**；于是函数侧知道"我有这么多 RPC 可以被调用"。
    *   **作用**：每次调用 RPC 时在存根里查询；若调用了不存在的 RPC，系统可以**报错而不让系统崩溃（crush）**——游戏引擎通常不允许系统 crash，只报错"你 call 了一个不存在的 RPC，回去查查"，其他业务逻辑照常运行。因为大型游戏 RPC 动辄**几百个以上**，且游戏版本一直在更新，很容易出现旧脚本/旧代码调用了错误的 RPC，若因此崩溃就太糟糕了；某特定业务没发生不算是大问题。
*   **Stub Compiler（存根编译器）**：定义一堆 RPC 接口后，通过 IDL 用 stub compiler 进行编译生成代码。小引擎中的 schema 系统本身也可以作为 stub compiler；若用 protobuf 这类开源方案，compiler 是现成的。这是一个被解决得很好的系统，设计思想是通用的——**游戏引擎学到后面会发现很多设计思想、方法都是相通的**。
*   **真实 RPC 的完整路径**：
    1. 调用 RPC 后，把**所有参数进行序列化（serialization）**。
    2. 进行**压缩（compression）**——网络带宽很珍贵，必须压缩。
    3. 进行**加密（encryption）**——客户端与服务器通讯不加密，黑客很容易攻击、注入想要的逻辑。
    4. 通过网络传输（可能是基于 UDP 的可靠通道，也可能是 TCP 连接）。
    5. 服务器端收到后**解密 → 解压缩 → 反序列化（deserialization）**，对应函数被调用。
    *   有些 RPC 走 reliable UDP（如游戏业务相关），有些走 TCP（如**账号登录、保证客户端与服务器端握手成功**等场景）。
*   **总结**：讲这么多基础内容，是因为这些就是网游最基础的东西——**首先怎么建立一个网络链接**。游戏引擎连底层传输协议都需要自己定义定制；做更复杂的网络游戏甚至要改底层协议栈。没有这些基础，online gaming 游戏引擎确实做不了。

## 二、 重点术语与概念解析

### 1. TCP（Transmission Control Protocol，传输控制协议）
*   **定义**：互联网最经典的可靠传输协议，通过三次握手建立连接，保证数据有序、可靠到达，具备流量控制与拥塞控制；包头约 20 字节。
*   **应用/注意点**：核心是 ACK 确认机制——没收到确认就持续发，可能引起拥塞；带宽随拥塞控制呈锯齿波动。适合炉石传说这类对延迟不敏感、需要稳定连接的场景。

### 2. UDP（User Datagram Protocol，用户数据报协议）
*   **定义**：由 TCP 发明者之一在 10 年后发明的轻量端到端协议，无连接、不保证顺序与可靠、无流量/拥塞控制，包头轻（约 4 字节/32 位）。
*   **应用/注意点**：响应快，适合快速射击游戏（如守望先锋）；但不可靠，需在其上构建可靠层。

### 3. ACK / NACK
*   **定义**：ACK（Acknowledgment）是接收方对收到数据包的确认；NACK（Negative ACK）是接收方明确告知发送方"哪个包没收到"。
*   **应用/注意点**：ACK 是 TCP 可靠性的基石；NACK 是 Selective Repeat ARQ 的基础，能节省不必要的带宽。

### 4. ARQ（Automatic Repeat reQuest，自动重传请求）
*   **定义**：丢包或未收到时，接收方让发送方自动重传的机制，是所有可靠传输算法的核心目标。
*   **应用/注意点**：三种典型策略——Stop-and-Wait（窗口为 1，最笨）、Go-Back-N（丢包重传整个窗口，讲师推荐）、Selective Repeat（用 NACK 只重传丢失的包）。

### 5. 滑动窗口协议（Sliding Window Protocol）
*   **定义**：维护一个可滑动的发送窗口，一次性发送窗口内所有包，收到 ACK 后窗口前移，继续发送后续数据。
*   **应用/注意点**：充分利用带宽，是 TCP 及可靠 UDP 的常用底层机制。

### 6. FEC（Forward Error Correction，前向纠错）
*   **定义**：通过携带冗余信息，使接收方在丢包时无需重传就能重建原始数据的编码技术（"空间换时间"）。
*   **应用/注意点**：包括异或（XOR）校验与 Reed-Solomon 编码；适合丢包率不太高的场景，丢包率过高（接近 10%~20%）时冗余开销反而浪费带宽。

### 7. Reed-Solomon Codec（里德-所罗门编码）
*   **定义**：基于范德蒙德矩阵的纠错编码算法：用矩阵乘数据产生冗余，矩阵任意删去若干行仍可逆，通过逆运算恢复丢失数据。
*   **应用/注意点**：计算机体系结构中的经典算法，广泛用于网络传输与存储，尤其适合手游/移动端高丢包（10%~20%）环境。

### 8. RTT（Round Trip Time，往返时间）
*   **定义**：一个包发出去到收到回报的总时间，通常由应用层自行测量。
*   **应用/注意点**：与更底层的 ping 值接近但有细微差别；游戏引擎中用于测延迟，二者不必严格区分。

### 9. NTP（Network Time Protocol，网络时间协议）
*   **定义**：用于网络时钟同步的协议，通过对四个时间戳 $T_{0C}$、$T_{1S}$、$T_{2S}$、$T_{3C}$ 计算 offset 来对齐时钟。
*   **应用/注意点**：假设网络稳定且上下行对称（现实不成立）；游戏中对时通常只有一层 stratum（只跟服务器对），配合多次采样+丢弃高 RTT 样本的统计方法逼近真实时差。

### 10. stratum（对时层级）
*   **定义**：NTP 中对时源的层次，类似地层结构，由原子钟等最高精度时钟逐层向下同步。
*   **应用/注意点**：超过 15 层后钟就对不准了；游戏引擎一般只用一层。

### 11. RPC（Remote Procedure Call，远程过程调用）
*   **定义**：让程序员像调用本地函数一样调用远端服务器函数的机制，序列化/压缩/加密/传输/反序列化全部透明。
*   **应用/注意点**：现代游戏引擎最标准实践，极大提升开发效率并避免消息打包出错。

### 12. IDL（Interface Definition Language，接口定义语言）
*   **定义**：独立于编程语言的接口描述语言，如 Google protobuf。
*   **应用/注意点**：与引擎 schema 定义、component 接口设计思想相通，借助反射（reflection）实现通用序列化与 RPC 代码生成。

### 13. RPC Stub（票据存根）
*   **定义**：RPC 注册表/存根，记录客户端与服务器注册的全部可调用 RPC。
*   **应用/注意点**：调用不存在的 RPC 时报错而非崩溃，保证游戏主逻辑不受影响。

### 14. Stub Compiler（存根编译器）
*   **定义**：把 IDL 定义编译成序列化/调用代码的工具。
*   **应用/注意点**：小引擎的 schema 系统可作为 stub compiler；开源方案（如 protobuf）自带现成 compiler。

### 15. OSI 七层模型
*   **定义**：物理层、数据链路层、网络层、传输层、会话层、表示层、应用层的分层网络模型。
*   **应用/注意点**：隔离硬件复杂性，让上层只需写数据；游戏开发一般只在应用层"鬼混"，但做 CDN 等需要深入理解并做底层优化。

### 16. Socket
*   **定义**：网络编程接口，通过 IP 地址 + 端口号建立连接并传输数据。
*   **应用/注意点**：网游客户端写死服务器 IP 与端口；但由此暴露的服务器地址需要抗 DDOS 能力。

### 17. IPv4 / IPv6
*   **定义**：第四代/第六代互联网协议地址版本。
*   **应用/注意点**：国内多用 IPv4；做通用引擎务必支持 IPv6，否则德国等已大面积使用 IPv6 国家的用户无法连接。

### 18. big endian / small endian（大端/小端）
*   **定义**：数据字节序——高位在前（大端）还是低位在前（小端）。
*   **应用/注意点**：Xbox、PlayStation 等主机平台字节序不同，网络传输数据时 packing 不同，是跨平台通讯的主要麻烦之一，也是 RPC/IDL 要解决的序列化问题。

### 19. 热更新
*   **定义**：游戏在线运行期间无感推送 bug 修复、逻辑与规则更新的机制。
*   **应用/注意点**：玩家正在游玩时不能强制更新，需要"神不知鬼不觉"地完成迭代。

### 20. DDOS 攻击（Distributed Denial of Service，分布式拒绝服务攻击）
*   **定义**：通过海量请求淹没服务器使其瘫痪的攻击手段。
*   **应用/注意点**：服务器地址必须开放，必须具备抗 DDOS 能力；实施此类攻击违法。

### 21. DLSS（Deep Learning Super Sampling，深度学习超采样）
*   **定义**：基于深度学习的图像超采样技术，用低分辨率（720P/1080P）画面 upscale 成 4K/8K 画面。
*   **应用/注意点**：结合空间域与时域（temporal）采样重建细节；依赖显卡 tensor core 算力；DLSS 2.0 已做到与特定游戏解耦、通用化。

### 22. NeRF（Neural Radiance Fields，神经辐射场）
*   **定义**：基于深度学习的视图重建渲染技术，用少量照片重建整个环境。
*   **应用/注意点**：Google Earth 已应用，讲师认为"基于 deep learning 的渲染算法"是未来渲染方向。

### 23. 反射（Reflection）
*   **定义**：程序在运行时检查和操作自身结构（类型、属性、方法）的机制。
*   **应用/注意点**：对工具侧、数据序列化、component 系统与网络 RPC 均有重要价值，是 IDL/schema 系统的底层支撑。

## 三、 工程经验与避坑指南

### 1. 协议选型要"实用主义"，不要教条
*   游戏引擎是没有任何教条主义的工程科学——一切人类智慧成果都是工具，目标是构建像"黑客帝国"那样的世界。
*   炉石等延迟不敏感的游戏用 TCP；快节奏射击游戏用 UDP；**大型 MMO 通常走组合协议**：TCP 负责签名认证、登录、账号链接、心跳维持，UDP 负责战斗数据，聊天/邮件走 TCP 通道，按"哪个通道更合适走哪个"。
*   真正做联网引擎时，非常推荐**自己定制或采用第三方基于 UDP 的可靠连接协议**，难度不大且可自由组合 ARQ + FEC 策略，适配不同数据的不同需求（高稳定 vs 低延迟）。

### 2. 可靠 UDP 的搭建要点
*   基础三件套：ACK/NACK、序列号、超时（timeout）。
*   重传策略优先推荐 **Go-Back-N ARQ**；对带宽敏感的场景考虑 **Selective Repeat ARQ（用 NACK）**。
*   在丢包率不高（5%~10%）时叠加 **FEC 前向纠错**（XOR 或 Reed-Solomon）可显著减少重传；注意丢包率过高时冗余带宽开销大，需做严格概率评估。
*   客户端与服务器之间建议**建立多条连接**，每条连接按数据特性配置不同策略：左移右移等操作可丢包、追求 highly responsive；喝药、放技能等有顺序依赖的操作走稳定通道。

### 3. 时钟对不齐是大量 bug 的根源
*   **客户端与服务器握手成功后的第一件事就是对齐时钟**。以前做游戏引擎时很多 bug 是"钟没对好"导致的。
*   对时技巧：NTP 算法跑一次后调整时钟，再多次采样（3/5/10 次），**丢弃 RTT 高于平均值 50% 的样本**（网络波动时算出的 offset 不可信），对剩余可靠 offset 取平均做最终调整。
*   牢记 NTP 的两大不成立假设（网络稳定、上下行对称），对时只能"逼近"无法"完全对准"——信息论保证在不可靠连接下不可能完美对时。

### 4. RPC 系统设计经验
*   用 IDL（如 protobuf）定义接口，让程序员像写本地代码一样写网络逻辑，**避免手写消息定义、packing、字节序、序列化这些极易出错的工作**。
*   RPC 底层要走完整链路：序列化 → 压缩 → 加密 → 传输 → 解密 → 解压缩 → 反序列化，加密必不可少（否则黑客可注入逻辑）。
*   调用了不存在的 RPC 时**报错而非让游戏崩溃**——大型游戏 RPC 动辄几百个且版本迭代快，旧脚本调错 RPC 只导致特定业务不发声，不应拖垮整个游戏。

### 5. 服务器与安全
*   服务器地址必须开放，**必须具备抗 DDOS 能力**，否则很容易被攻击打掉。
*   客户端与服务器的通讯必须加密，否则黑客可注入任意逻辑。
*   小心乱码数据攻击：服务器 decode/decrypt 无意义数据会浪费算力，需要设计手段识别无效信息。

### 6. 通用引擎要考虑 IPv6
*   中国在线应用多用 IPv4，但做**通用游戏引擎一定要支持 IPv6**——德国等国家已大面积使用 IPv6，不支持就会丢用户。

### 7. 其他工程感悟
*   做游戏引擎"连底层传输协议都要自己定义定制"，做更复杂的网游甚至要改协议栈——这是引擎开发者的常态，不要惊讶。
*   讲师对机房 IT 同学盘线缆（cable）手艺印象深刻——1cm 的线都要编号，接上很粗的电缆柱，无数比特在其中交换，而现代开发者完全不需要操心这些硬件复杂度，这是 OSI 分层与前人智慧的功劳。
*   课程强调：网络游戏本质是巨大的经济系统，反作弊（如锁定内存血量作弊在网游中不可接受）与信息安全是必须长期投入的责任。

## 四、 社区问答专题（课程开场 Q&A）

### 1. 深度学习（Deep Learning）与强化学习（Reinforcement Learning）的未来
*   **老师的观点**：深度学习只是一种方法；问题的实质是监督学习 vs 无监督学习/强化学习之争。
*   举例：DeepMind（如 AlphaGo/AlphaZero 类工作）偏监督学习多一些；OpenAI 更偏向强化学习。
*   类比人类智能：早期智力很大程度上靠"监督"形成——做错事父母的表情、不开心的脸就是负反馈，开心脸就是正反馈；后期学会下围棋后更多靠自我摸索（类似无监督/自我强化）。所以未来是否转向无监督还很难判断。
*   **给同学的建议**：对此保持开放性，不要"押宝"单一方法；游戏引擎课的特点是**实用主义**——对具体问题哪个方法最好最快就用哪个。很多游戏问题用最基础的 AI 算法和工具就能解决，不需要上复杂花哨的东西。

### 2. 游戏版本更新时，AI 模块是否也要跟着更新？
*   **不一定**。AI 确实与游戏逻辑/业务深度绑定，原则上逻辑变化时 AI 部分需要变化。
*   但 AI 与世界的连接主要通过 **perception（感知/对世界的认知）**：你观察世界的变量（state）没有变化，决策依据就不会大变；反过来，AI 能做的动作集合（如还是那 70 种动作）不变的话，AI 原则上可以不更新。
*   现代引擎中 AI 常由**数据/脚本配置**驱动，这些配置不需要随每次版本升级而更新，除非世界 state 的表达变了或可行动作增删了。
*   若用深度学习方法，只有当**实质性战场策略发生变化**时，AI 系统本身才需要升级。
*   游戏上线后的常态：一边用 AI 指导电脑打游戏，一边**不停抓取真实游戏数据用来训练（training）AI**。

### 3. DLSS 算法到底是怎么回事？
*   **定义**：Deep Learning Super Sampling，即**基于深度学习的超采样**。
*   **为什么有用**：4K/8K 屏幕像素接近上亿，逐个渲染显卡会崩掉；DLSS 可以用 720P/1080P 渲染再 upscale 成 4K/8K 画面。
*   **技术原理**：类似 B 站上很火的"老照片/黑白照片高清 AI 修复"——有经验的画师拿到模糊老照片能想象和修补光影、细节（皮肤肌理、衣服肌理、动作细节），这正是深度学习最擅长的事。它不仅在**空间域（spatial）**上采样（从周边像素推断这是树叶、人脸皮肤还是大理石纹理），还在**时域（temporal）**上采样——在帧与帧之间寻找关联关系。
*   **版本演进**：DLSS 已发展到 2.0。第一代算法很多人能模拟出相近效果；**DLSS 2.0 做到了与特定游戏解耦**——不用再为花里胡哨的 FPS（如《守望先锋》）或写实风的 RPG（如《上古卷轴》）分别调参，通用性极强。
*   **硬件基础**：现代硬件自带大量 **tensor core**（张量核心），算力在核心上就位，深度学习算法越来越强。
*   **资料现状**：最基础算法有公开论文讨论，但最新算法尚无公开资料，老师也无法讲太多。
*   **老师展望**：非常看好该方向——**未来的渲染不应是逐像素渲染**（太慢），基于 deep learning 的算法会有很多了不起的应用，如 Google Earth 用 **NeRF** 把整个环境用几张照片重建出来，这就是"人脑能做的事，未来深度学习也能做"。
