# 游戏引擎中的粒子系统与声效系统：从基础原理到工程实现

## 一、 核心知识点与原理剖析

### 1. 特效系统总览与粒子系统的历史

*   **两大组成部分**：游戏中的特效系统（FX）由两大部分构成——**粒子系统（Particle System）**与**声音系统（Audio System）**。两者在工程上往往"不分家"：很多效果系统到最后一定要挂上声音，否则粒子效果看上去非常假。
*   **粒子系统的地位**：对科幻类（SF）游戏而言粒子系统是**最关键的成就游戏整体质感的系统**，打击感、效果感全靠它"拉满"；对角色表现力、打击感与 `gameplay` 影响极大。《鬼泣》《艾尔登法环》（老头环）《对马岛之魂》等 3A 游戏都重度依赖粒子系统。
*   **变现能力**：行业里常开玩笑说粒子系统是游戏中**变现能力最强的系统**——"付费为特效付费"，角色变强的本质往往只是把原来一柄大剑砍出去的粒子再做大一倍、两倍。
*   **起源**：粒子系统最早并非来自游戏行业，而是**电影行业**。1982 年电影《星际迷航2：可汗之怒》首次引入粒子系统的概念，将所有这种 **fuzzy object（模糊对象）** 定义为一种 **procedural system（程序化系统）**，负责其产生、生命周期中的动画以及整个生命周期的管理。次年（1983 年）相关论文发表于图形学领域最权威的杂志 **ACM Transactions on Graphics（SIGGRAPH）** 上，正式定义了 **particle system** 这一概念。3D 游戏时代之后，粒子系统在游戏行业逐渐普及。

### 2. 粒子系统的基础构成：Particle、Emitter 与 System

#### (1) Particle（粒子）
*   **核心概念**：粒子是粒子系统最基础的构建元素，可以理解成空间中一个**小点或一个小面片**。
*   **基本属性**：位置（position）、速度（velocity）、尺寸（size）、颜色（color），以及**当前生命周期状态**（如已产生 5 秒还是 6 秒）。
*   **直观例子**：锤子打下去会蹦出很多火花，每个火花就是一个粒子。
*   **生命周期（lifespan）**：
    1. 粒子被 **spawn（创生）** 出来；
    2. 拥有运动属性（速度）；
    3. 颜色随时间变化；
    4. 与**环境互动**（撞到东西反弹、受风力影响、受重力影响）；
    5. 寿命到期后**自动消灭**。
*   **易踩的坑**：粒子系统最容易写出的 bug 就是**生命周期没管理好**——若粒子只产生不死亡，游戏环境中的粒子会越来越多，最终导致系统资源消耗殆尽、整个系统崩溃跑不动。

#### (2) Emitter（发射器）
*   **核心概念**：发射器不断地往外"扔"出各种各样的粒子小球，每个小球拥有各自的属性并形成自己的运动轨迹。
*   **随机初始值**：发射器常给粒子赋予**随机初始值**。例如要表现一个喷泉，粒子的**初速度大小**必须带一点随机、**方向**带一点偏差（cg/偏差），才能呈现出喷泉发散的效果。
*   **发射形态（Spawn 区域）**：
    *   最常见的是**点发射器**（在单个点上发射）。
    *   可限定空间区域，在 **box（长方体）**、**sphere（球体）**、**capsule（胶囊体）** 区域内生成粒子，形成各种复杂形状。
    *   可直接拿一个 **mesh** 在其表面上采样随机点来生成粒子（例如在一个挖洞的人形 mesh 上采样），形成更酷炫的效果。
*   **行为模型**：发射器可以设置不同的行为模式——**连续随机喷射**（如喷泉），或 **periodic（周期性爆发）**，即到了一定时间随机突然爆发一批粒子。

#### (3) System（粒子系统）
*   **核心概念**：多个 emitter 放在一起构成一个 system。严格来说，system 是**多个 emitter 与其发射出来的所有正在活着（或仍在管理中）的 particle 的总和**。
*   **为什么要定义 system**：游戏里真正表达一个效果，需要**多种不同的 particle 组合**。以火焰燃烧为例：
    *   火焰本体粒子（体积大、颜色亮暗变化：从根部暗红 → 中间最亮 → 上方逐渐暗淡）；
    *   飞起的**火星**粒子（轨道与本体不同）；
    *   **烟**粒子。
    *   三种粒子合在一起才能形成真实逼真的火效果。再如弹药击中石头的爆炸：冲击烟尘 + 向四周四散炸开的东西 + **debris（碎片）**。
*   **特效艺术家（Effect Artist）**：其最核心的工作就是研究**组合方式**——在真实世界中观察到效果后，如何用一个个简单的系统组合生成想要的效果。粒子系统做得好的地方效果增益、真实有感觉；做得不好就是"一群简单的面片满天飞"，即俗称的"五毛钱特效"。

### 3. 粒子模拟（Simulation）

*   **核心概念**：粒子从发射器 spawn 出来之后，在空间中的所有行为统称为 **simulation（模拟）**。
*   **受力的模拟**：每个粒子可看作一个**非常小的物理质点**，最常见受到三类力的影响：
    1. **重力**；
    2. **空气阻力**；
    3. **风的扰动**（如《对马岛之魂》的"信仰之风"，即模拟粒子沿风吹方向流动来指引方向）。
*   **积分方法**：粒子系统**不需要严格物理准确**，一般使用最简单的**显式积分（forward Euler）**即可——每帧根据当前速度与受力决定下一帧的速度与位移，逐步推进。
*   **可扰动的参数**：simulation 不仅扰动位置与速度，还包括：
    *   **旋转**：让粒子转起来显得更真实；
    *   **颜色**：如火焰粒子从暗红（产生时）→ 发亮（温度最高时）→ 变暗（飞高后温度损失），这与**黑体辐射**规律一致——不同温度的辐射体颜色不同；
    *   **尺寸**：如烟的粒子一开始浓密而小，随后不断扩散变大、变淡，覆盖空间越来越大。
*   **环境互动（碰撞）**：现代粒子系统还要求粒子在 simulation 过程中**与环境互动**。若直接调用物理引擎做碰撞会非常慢（一个系统动辄撒出几百上千个粒子），需要一种**高效的碰撞检测算法**；与整个世界的碰撞（collision）是粒子系统非常重要的属性要求。

### 4. 粒子的视觉形态：Billboard、Mesh 与 Ribbon

#### A. Billboard（公告板）粒子
*   **核心概念**：一张始终朝向 camera 的面（quad）。无论 camera 怎么转，该面始终"盯着"你。它是粒子系统**最经典、最古老**的形态，早期粒子系统基本就是 billboard particle。
*   **关键 trick（防穿帮）**：若 billboard 是一张**静态图、内容不变化**，用户很容易意识到"它是一群永远朝向 camera 的面片"。因此：
    *   粒子尺寸小 → 可以用简单颜色表达，没关系；
    *   **粒子尺寸大 → 强烈建议使用 animated texture（动画贴图）**，让外观随时间不断变化，用户就不会注意到它是用很多小面片去模拟空间中的体量感。

#### B. Mesh 粒子
*   **核心概念**：当要表现各种小的碎屑、碎片、钢铁等时，直接用 mesh 作为粒子。
*   **随机性要求**：mesh 粒子一般需要具备随机性，避免重复感：
    *   最简单：把每个 mesh **转一个随机角度**、**放缩大小**；
    *   更复杂：做 **XYZ 三个方向的随机放缩**。
*   **设计原则**：设计引擎粒子系统时，最重要的一点是**给 artist 提供各种随机的、可调整的量**。艺术家特别偏好"把所有变量都允许我随机一下"，这样做出的效果才自然真实。

#### C. Ribbon / Beam 粒子（光带粒子）
*   **核心概念**：粒子飞行的过程中不断拉出一个一个**额外的控制节点**，以一定的宽度把这些控制点连接起来，形成一条**绶带状的光带**。典型应用：
    *   魔法剑/箭矢飞行的**尾迹抛物线丝带**；
    *   刀剑划过的弧度轨迹；
    *   气功波（气功弹）打出去的轨迹；
    *   表现空间的"时空滞留感"。
*   **实现挑战**：若只把离散的点直接连起来，得到的是一条**一折一折的折线**。因此在实现 ribbon particle 时一般要采用**样条曲线插值**。
*   **为什么用 Catmull-Rom 曲线**：
    1. 实现简单，用二阶/三阶的多项式公式即可直接插出；
    2. **严格保证插值曲线通过所有控制点**；
    3. 只要在控制点之间再插入若干点，形成一小节一小节的 transition（过渡段），整个特效看上去就圆滑很多。
*   **引擎提供三类粒子的总结**：billboard、mesh、ribbon 这三类粒子，配合尽可能多的随机扰动；ribbon 必须加入 Catmull-Rom 插值让形状平滑。十几年前做粒子系统，基本有这些东西就够用了。

### 5. 透明物排序（Transparency Sorting）问题

*   **核心概念**：透明物排序是游戏渲染中"挥之不去的一个噩梦"。透明物必须**从最远的画到最近的**，一层层覆盖，alpha blending 的结果才正确；若顺序混乱，结果就是乱的，人眼一眼就能看出来。
*   **粒子场景的排序难度**：场景里几十块玻璃墙排序尚可，但粒子系统动辄产生**几百上千个 billboard**，排序难度剧增。排序有两大流派：
    *   **全局排序（Global Sorting）**：把所有粒子系统、所有 emitter 产生的全部粒子（如 200 多个）合在一起按距离统一排序，结果最正确；但排序元素越多成本越高，且各粒子系统绘制时参数设置要求一致，来回跳转绘制（draw state 切换）成本很高。
    *   **Per-Emitter 排序**：很多粒子系统只能按 emitter 为单位排序（谁前谁后）。两个靠得很近的 emitter 会产生问题：例如绿色 emitter 与红色 emitter 的粒子本有大量交叠，但因绿色 emitter 距相机稍近，所有绿色粒子都会被画在红色之前——这是粒子系统**非常常见的问题**。
*   **典型 bug 现象**：早期游戏里，当相机移动时，一些**烟柱（smoke column）**等特效会突然"闪动"，多半就是 particle sorting 出了问题。
*   **入门建议**：**先写最简单的 per-emitter sorting**，可解决部分问题；global sorting 写起来麻烦，且需要更复杂的 GPU 算法。
*   **Ribbon 穿帮案例**：一条光带（ribbon）本应穿过一堆粒子中间，但由于其 **bounding volume（包围盒）** 总是更靠近相机，会被排到所有粒子之后，看起来像是浮在所有的烟之上；若采用 global sorting，把 ribbon 的每一节与粒子逐一排序，结果就正确了。
*   **环境粒子（Ambient）**：现代游戏的气氛感来自海量环境粒子——脚下几千上万个微微扰动的大气粒子在流动，让人感觉"空气是活的"；再加上每一步带起的尘土、风吹过的落叶、天空飞过的鸟雀，才让人觉得世界是真实的。**好游戏与坏游戏对粒子系统的依赖度差别非常大**。

### 6. 性能问题：Overdraw 与 Half Resolution 渲染

*   **为什么粒子是性能杀手**：
    *   绘制不透明物体时，无论世界多复杂，一根视线只需绘制**最后一个像素**——z buffer 会把所有被遮挡的几何滤掉，只留下离眼睛最近的点进行 shading，100 万像素只画一次。
    *   但透明物不同：一根视线顶多看到七八个环境透明物，而粒子系统堪称 **trouble maker**——面前一个烟的爆炸瞬间可以怼出**几十个甚至上百个整个屏幕大小的粒子**。
*   **Overdraw**：指同一个像素被重复绘制的次数。一个屏幕大小的粒子就有 **1100 多万像素点**，几十上百个就是**几亿到十几亿的计算量级**，游戏帧率会迅速下降。
*   **Half Resolution（半分辨率渲染）技术**：
    1. 把渲染分辨率**整体减少一半**（X、Y 都缩小一半），总像素量只有原来的 $1/4$，z buffer 也相应缩小一半；
    2. 所有透明物（尤其 particle）在 1/4 像素量的半分辨率缓冲上渲染；
    3. 两个细节要求：
       * 若粒子的 Z 已经在 opaque（不透明）物体之后（被遮挡），就不需要绘制；
       * 所有粒子/透明物算出的结果要**集体算一个 alpha**，再与前面 opaque 物体的结果进行 blending。blending 是一个 **upscale（上采样）** 的过程，做一些简单的差值、变化与扰动，即可得到非常不错的效果。
*   **行业趋势**：随着显示器分辨率越来越高（1080P 约 200 多万像素，4K 接近 1000 万像素，8K 更大），即使超强 GPU 也难以做到全尺寸渲染，因此**游戏引擎中越来越多渲染开始使用 half resolution**。
*   **相关技术**：大力水手 **DLSS** 就是 up sampling / down sampling 的典型应用——先用低精度绘制，再用算法放大回原分辨率，这是现代渲染里非常常用的技术。
*   **其他优化**：当粒子离相机特别近时，**cut 掉（剔除）一些粒子**，或用其他方法降低同一像素点上被重复覆盖的粒子数量。

### 7. GPU 粒子系统：Particle Pool 与 Alive/Dead List

*   **动机**：现代游戏场景很容易达到**几万甚至上十万**的粒子数量，每帧都做各种计算处理，对 CPU 是重大负载。GPU 天然善于处理海量并发运算，很自然想到把粒子系统搬到 GPU 上管理。
*   **难点**：粒子有**生命周期**——每时每刻都有新粒子产生、也有粒子死亡，在 GPU 这种简单硬件上实现动态分配并不容易。
*   **学习建议**：自己写粒子系统时写两套——先写一个 CPU particle，再按课程思路写一个 **GPU 版本**。
*   **GPU 粒子系统的两大好处**：
    1. 利用 GPU 的**并行化算力**；
    2. 读取 z buffer、处理 frame buffer 时**不用再把数据读回 CPU**，全程留在 GPU 内完成。
*   **核心框架（Particle Pool + 双列表）**：
    1. 定义 **particle pool（粒子池）**：用一串标准的数据结构描述所有粒子的描述数据，如位置、速度、颜色、尺寸、其他 meta 信息（例如 texture uv）等；同时假定整个系统的**容量上限**（例如 10 万个粒子）。
    2. 维护一个 **dead list（空位列表）** 及计数 `dead list count`：初始时没有粒子，所有空位都在 dead list 中。
    3. 维护一个 **alive list（存活粒子列表）**：初始为空，记录存活的粒子索引。
    4. **产生粒子**：emitter 在 GPU 中产生 N 个粒子时，从 dead list **尾部取 N 个空位**（类似栈结构，从尾巴取数据），填入数据，dead list 相应减少，alive list 增加。
    5. **模拟与淘汰**：每个 tick 对所有活着的粒子做一次 simulation。采用**双 buffer 策略**（alive list0 / alive list1）：遍历 alive list0 的同时写 alive list1——仍然存活的粒子（如 3、4、5 号）依次写入 alive list1；发现已死亡的粒子（如 6 号）则把它 append 到 dead list，同时跳过不写入 alive list1。
    6. 之后做一次 **buffer swapping（缓冲交换）**，就得到下一帧要绘制的粒子列表。
*   **Compute Shader 的作用**：上述"从死列表取空位 + 追加到死列表"的操作在 CPU 上很好写，但在旧式 GPU 上很难实现；**自从有了 compute shader（计算着色器）之后就变得非常简单**——compute shader 提供**原子操作（atomic operation）**：在一组并行计算中可以设置一个全局（局部）变量，无论多少线程并行运行，读写该变量都保证原子性。
*   **GPU 上进一步的优势操作**：
    *   **View Frustum Culling（视锥剔除）**：得到一个所有可见粒子的列表，进一步减少绘制量。这是非常适合 GPU 的简单计算。
    *   **关键细节**：视锥剔除**不会反向修改 alive list**。因为一个粒子是死是活与你看不看它无关——烟火射出去后不看你它也在空中飞，回头再看它应该还在；若因上一帧看不见就把它从存活列表中干掉，回头时粒子就凭空消失了，产生奇怪的效果。
    *   因此：**particle simulation 是 view-independent（与视图无关）**的，simulation 产生所有活跃粒子后，再单独做一次 view frustum culling 取出可见粒子；随后做 depth buffer 比较、**sorting（排序）**，全部在 GPU 内完成。
    *   最后基于可见且排序完成的 alive particle 生成渲染用的 **vertex buffer 和 index buffer**。
*   **通用性**：这套思想可用于一切**集群性运算**——一上来构建一个 pool 明确计算上限，用 alive list 指向活动数据的 index，用 dead list 记录被 recycle（回收）的条目，两个列表的 index 来回 swap，即可完成对一个高度动态系统的管理。这是一套非常常用且好用的结构。

### 8. GPU 上的并行排序：Merge Sort 与缓存一致性

*   **背景**：粒子系统最难的是排序（sorting），且理想情况是 **global sorting**。数据在 CPU 内存中时，可以用数据结构课上的快速排序等实现；但数据搬到 GPU 后，需要能在 GPU 上运行的排序算法。
*   **经典思路：Merge Sort（归并排序）**：
    *   把一个大的数列排序分解成**无数个已经排好序的数列的整合**过程。
    *   第一步把所有相邻的两个元素排好，得到无数个小的有序数列；
    *   每两个一组，二进四、四进八……因为双方都已有序，合并非常快——合并时每个元素**不需要和自己数列的其余元素比较**（后面的数据一定更大），只需要在另一个数列中用**二分查找**找出有多少数据在自己前面即可；
    *   每步计算复杂度为 $\log n$，整体计算复杂度为 $n \log n$，是一个非常快速的方法。
*   **GPU 上的两种实现策略**：
    *   **方法一（符合直觉，效率低）**：把两个已经排好序的 source 数组都遍历一遍得到结果。问题在于**写入时地址一直跳来跳去**，导致 memory/cache coherence（缓存一致性）非常低。对几十 K 量级的数据排序时内存跳变巨大，效率极低。
    *   **方法二（行业主流，作者推荐）**：**反向计算**——对目标矩阵上的任何一个点，在两个 source 数列上反向去寻找该位置上应放置的元素（在别人的数列中做二分查找，判断前一个游标节点与本节点之间无冲突即可放入）。这样每次写入的顺序是 1、2、3、4、5 一路写下来，**cache coherence 高**。作者对两种方法做了详细对比（参考文献课后在 PDF 上补上）。
*   **核心思想总结**：给两个已排好序的数组，如何合并成一个排好序的数组，是归并排序法的核心思路；在 GPU 上必须额外考虑**硬件实现的可行性**。方法二因能顺序写入目标数组，成为行业里 GPU 粒子系统实现的重要技术细节。

### 9. 基于深度缓冲的 GPU 粒子碰撞

*   **动机**：让每个粒子都和物理引擎真实结算一遍会非常慢，行业中通常不这样做。
*   **常用方法**：用 **depth buffer（深度缓冲，view-dependent 的 screen space 深度）** 模拟出空间的几何形状，让粒子与它碰撞——直接从 depth buffer 中取值与粒子进行碰撞判定。
*   **效果评估**：该方案效果不错，远好于完全没有碰撞的粒子（collision detection in particle）；典型应用案例即 screen space depth buffer 碰撞结果。
*   **系统本质**：粒子系统永远是**在效果与计算效率之间做 trade off（权衡）** 的系统。GPU particle 现在已经基本成为现代引擎的标配。

### 10. 高级应用：Crowd 人群模拟与状态机粒子

*   **Crowd 模拟的本质**：游戏引擎中展现大量人群、鸟、动物，很多时候并非物体系统，而是**粒子系统的能力**（如星战 demo 中跑来跑去的人群，本质是粒子系统）。
*   **实现原理**：
    1. 把角色变成一个个 **mesh，mesh 即一个 particle**；
    2. 该 mesh 还可以动：在每个顶点上存储**它受控于哪个 bone（骨骼）**。因为是粒子系统，采用最简单的绑定即可——**每个顶点只受一根骨骼控制**（不用复杂的 skinning）。缺点是没有 skinning 时骨骼转起来顶点处会出现断裂，但由于粒子很小，玩家注意不到这种小裂缝；
    3. 有了 skeleton 和最简单的 skinning 信息后，把该粒子**所有可能状态下的动画**（如 1~7 个状态）以及**该状态对速度的影响**（往前走、往后走、还是停止）全部 **codec（编码）成一个 texture（纹理）**；
    4. 每个粒子的 simulation 从简单的加减乘除（速度、位移、重力）**升级为一个状态机**：每个时间点粒子在自己的状态机之间来回切换。
*   **沿场景流动**：
    *   最简单做法是给一个统一速度 + 随机量，所有人朝一个方向走；
    *   更真实的需求是"沿道路走、不走进建筑物"，这需要一个**场（field）**：
        *   **SDF（Signed Distance Field，带正负号的距离场）**：告诉你当前点是在空间内部（inner）还是外部；值越接近零，说明越接近某个障碍物。
        *   有了 SDF 后，可以算出整个场景任一位置的空间**导向图（directional field）**，只需存储两个量即可。
        *   给任意一个 particle（角色）一个指引性：在某点 spawn 后指示它该去的方向，它就会像受到一股力一样向该方向"飘动"。
    *   在 state machine 中加入**随机量**：走到一半时产生随机的状态切换，观众会觉得人群行为非常真实。
    *   可以进一步加入"感知到其他 particle 就避开"的状态，实现人群避让。
*   **结论**：crowd 模拟最核心的底层系统就是**粒子系统**。现代粒子系统比大家理解的复杂得多——从古典到现代，复杂度已远超最初的理解。

### 11. 古典粒子系统与现代粒子系统（以 Niagara 为例）

*   **古典粒子系统（简单模型）**：
    *   预先设定好几种 **emitter 造型**，开放各种参数让 artist 控制；
    *   预先设定好各种 particle 类型（mesh particle：选哪个几何、对哪些属性做扰动；ribbon particle：颜色如何变化、拖尾怎么拖等）；
    *   通过 emitter 与 particle 的组合，就能定义出各种各样的效果。
*   **现代粒子系统（复杂模型）**：
    *   从**每一个 particle 的 simulation** 开始定制：粒子被打出去后在生命周期内到底发生哪些变化（如通过 **UV 变化**让粒子持续变形；读取**环境变量**判断周围有无扰动；查询**最近的 neighbor particle** 等）；
    *   emitter 本身也**允许用户自定义**；
    *   现代粒子系统还会与影视特效系统深度结合，如 Houdini（胡迪尼）的很多表现越来越多地集成进游戏引擎，**数据之间实现互通**。
*   **行业标杆：虚幻引擎 Niagara**：
    *   个人认为做得最好的是虚幻引擎最新一代粒子系统 **Niagara**，它把过去基于 **stack base（栈结构）** 的粒子系统和**完全基于脚本化可视化图**的粒子系统全部结合起来；
    *   Niagara 非常复杂——整个 Unreal 代码中 Niagara 一个系统就有**将近 100 多万行代码**；
    *   若想精专于粒子系统，**以 Niagara 为蓝本，花几个月甚至半年深度钻研，收获会非常大**。
*   **Games104 的课程精神**：既把最基础、最基本的概念讲清楚，又告诉大家行业最前沿的发展方向。
*   **Technical Artist（技术美术）**：在游戏公司承担重要研发角色，用聪明才智与想象力使工程师意识到底层系统的可行性与可能性。粒子系统从 1982 年提出至今 40 年发展得庞大而复杂，其中有很多 technical artist 的贡献。

### 12. 声学基础：音量、音调、音色与分贝

*   **声音为何重要**：
    *   声音决定了用户对世界的感知、互动性与情绪带入。TGA（游戏颁奖典礼）上的最佳音乐奖、最佳声效奖非常考验团队水平；《死亡空间》《死亡搁浅》以及大量恐怖游戏证明了 sound engineer（音效工程师）与 sound designer（声音设计师）是游戏的真正灵魂。
    *   **进化论解释**：人的大脑从**脑干**开始发育，脑干在远古时代并非思维器官，而是**感应周围环境振动的器官**——所以我们对震动的感知从脑干开始，**声音对情绪的影响最直觉**。关掉电影画面只听声音，大脑反而能构建画面感；关掉声音看电影则完全无感。因此声音对人的认知影响是 **more fundamental（更根本）** 的。
    *   游戏引擎设计常常对 audio 不够重视，但实际上声音是**事半功倍**的东西（如陈星汉《Journey》（风之旅人）的音乐）。
*   **Volume（音量）**：本质是声音的**振幅**，也就是你感受到的**空气压强变化**。声音主体是一个**纵波**（空气被压缩、弹开），同时也导致一定的横波；在单位面积上产生压强，这个压强就是你感受到的音量大小。
*   **分贝（dB）**：
    *   0 dB 定义为人类能感觉到的最小压强——约为**一只蚊子离你 3 米处发出声音**产生的压强（约 $P_0 \approx 20 \mu Pa$）；
    *   其他声音以它做 **log（对数）对比**：每十倍为一个台阶，乘以系数 20，即
        $$dB = 20 \log_{10} \frac{P}{P_0}$$
    *   即 10 dB 为压强的 10 倍、20 dB 为 100 倍、60 dB 为 1000 倍，到人类容忍极限约 120 dB 时，约为基数的 **100 万倍**；
    *   所以音量感知**不是线性的，而是 log 基的**，与地震烈度"每差一级能量差很多"是同一类概念；
    *   **引擎设计要点**：游戏引擎开放给 audio designer 的所有工具**不直接调节 volume**，而是全部用**分贝（或类分贝）数值**表达，即以 $20 \log_{10}$ 次幂表达，符合人对声音的自然认知。
*   **Pitch（音调）**：决定声音尖锐与否，本质是**频率**——频率越高声音越尖。人耳能听到的频率范围约为 **20 Hz ~ 20 kHz**。
*   **Timbre（音色）**：由大量谐波（overtone，即基频的整数倍分量）叠加形成。同样的音调，钢琴与小提琴演奏出来完全不同——频率都差不多，但**叠加的谐波不同、每个谐波的权重不同**，听感就截然不同。
*   **降噪耳机原理（顺带科普）**：声音是纵波，压缩波与舒张波相遇会**互相抵消**。降噪耳机先侦测空气中声波的**相位与强度**，再发出一个**反向位移**的波打过去，两波抵消，从而实现降噪。此原理在游戏中用处不大。
*   **听觉范围的工程细节**：虽然人耳能识别的频率是 20 Hz ~ 20 kHz，但高于此范围（如 1 万赫兹以上）的声音人仍有所感知——虽然"听不见"，但会**扰动你听到的音色**。因此做电影或高水平声音录制时，**表达/采样的声音频率要高于 5 kHz**。听觉本质上是一种很敏感的心理感受。

### 13. 数字音频：PCM、采样定理与音频格式

*   **数字化的必要性**：声音在空气中是无限连续的信号，计算机中必须**离散化（digitalize）**。
*   **PCM（Pulse Code Modulation，脉冲编码调制）**——计算机上表达声音的基础方法，分三步：
    1. **采样（sampling）**：对波动的模拟信号按时间间隔采样，采样出来的数据还是浮点型（无限精度）；
    2. **量化（quantization）**：把浮点值变为可存储的定点型数据（也可用浮点存储），这一精度称为 **bit depth（位深）**，现代音频常用 14 bit 或 24 bit 存储；
    3. **编码（encoding）**：压缩、表达，便于存储与传输。
*   **香农采样定理**：对任何一个频率的信号，只要**采样密度达到其频率的两倍**，就能无损表示。人耳可分辨的频率上限约 20 kHz，因此采样率只需超过其两倍即可；实际采样率会**略高一点**（因为更高频的声音会影响音质）。
*   **量化流派**：有的用**线性量化**（老老实实 1、2、3…存到 100 万）；有的 codec 用**对数量化**（以对数/指数方式传达），能**最大效率利用存储空间**。各有利弊，工程上有大量比较与分析。
*   **早期音频历史**：早期电脑不能播放音乐，只能发出 8 位质量的音，非常差；早期游戏用 **MIDI** 音编写（如超级玛丽、魂斗罗的音乐）。之后才出现真正的电脑音乐播放器与各种格式。
*   **常见音频格式对比**：
    *   **无损**：WAVE、FLAC；
    *   **有损**：MP3、OGG——以损失一定质量为代价，极大节约存储空间。
    *   **游戏中几乎不用无损格式**（数据量太大），一般用有损格式。
    *   **为什么不用 MP3**：
        1. MP3 格式设计时有瑕疵，**只支持立体声（左右两个声道）**，不支持 5.1 环绕声音源的采样，而游戏中常需要环绕音；
        2. MP3 **有非常重的专利保护**，引擎支持 MP3 需要**支付专利费**（专利墙，类似芯片/操作系统领域）。
    *   **为什么越来越多用 OGG**：**OGG 没有专利保护**，谁都可以用。有趣的是：花心思设计并申请专利的格式反而没人用，不申请专利的格式用的人非常多——这就是开源精神的体现（小引擎同样是开源引擎）。
*   **工程提醒**：做引擎时一定要**区分清楚各种音频格式的利弊**，知道该用什么东西。

### 14. 3D 声音渲染：Listener 与声场空间感

*   **背景**：理解了声强、音色、存储格式并数字化，只是开始。游戏引擎最难的是**在三维空间中构建一个声音的场**，让人感觉世界里发生着各种事情。
*   **声音的"渲染"**：3D 空间渲染声音是一套**非常独立的渲染系统**（与光学渲染是两个概念），复杂度与专业度很深，很多算法非常深。
*   **Listener（听者）**——声学渲染中的"camera"：
    *   **位置（position）**：
        *   FPS（第一人称）游戏：一般绑定在角色身上；
        *   TPS（第三人称射击）游戏：位置很讲究——放在相机上会奇怪（视觉上人已进入某处但声音没到），放在角色身上也有问题（视觉上觉得离角色有距离）；一般放在**观察者视点与角色之间的某个点**，具体位置很多游戏自行调整，"比较玄学"。
    *   **速度（velocity）**：光学渲染里做 motion blur 时才考虑速度，声学渲染中**必须考虑**——用于计算多普勒效应。
    *   **朝向（orientation）**：侧过耳朵听还是正对着听，听到的东西不一样。
*   **声音空间感（仅靠左右耳如何定位）**：
    1. **左右耳音量差**：声源靠近左边，左耳音量略大、右耳因隔着整个头部略小；
    2. **到达左右耳的时间差**：仅十几毫秒的差距，人就能感知空间位置关系的变化；
    3. **左右耳音色微变**：同一个声音到达左右耳时相位/音色产生细微变化，同样形成空间感知。
    *   人的大脑与耳朵经过百万年进化，能够通过这些微小的变化**反向绘制出音源的空间位置**——"听声辨位"确有科学原理。
*   **Panning（声像定位）**：
    *   定义：当 speaker 有很多 channel（通道）时，通过调整各通道上**声音的大小、音色、latency（延迟）**，让听众产生虚拟空间的感觉。
    *   最简实现（左到右线性移动）：直接用线性插值移动声像。
    *   **关键细节（功率平方效应）**：人对声音的感知是**音强（power）的平方**——当声源处于正中间时，由于左右功率都按平方计算，你会觉得声音**小了一半的感觉**（实际总音量未变）。解决办法是**归一化**：保证左右功率的平方和始终为 1.0，即用最简单的 $\sin$ / $\cos$ 函数（如 ease in / ease out 等插值方法，前面插值章节讲过）进行能量分配。
    *   **更复杂的空间方位**：当声源处于前后左右上下不同位置时，每个左右声道所需的变化来自**大量的采集与测算**，是**符合人体心理学认知的经验变化**，不是简单的数学运算。音频公司做了大量实验，计算机渲染时把数据搬过来（调整音量、相位/位向移、甚至频率），形成空间定位感。
    *   类比：高级音箱（5.1）安装时技师上门**校正与定位**，就是为了让前后左右上下的空间感准确；家中沙发位置变了听感就不同。
    *   **游戏中的主力方案**：目前游戏音效主力的还是 **stereo display（立体声/双耳渲染）**，把两个耳朵的双耳渲染效果做到最优。

### 15. 声音衰减（Attenuation）与遮蔽（Occlusion）

*   **Attenuation（衰减）**：不只是"越远声音越小"，引擎中的实现要复杂得多：
    *   同一音源在不同距离处，**高频与低频的衰减各不相同**：高频声音稍远一点就听不清，而"轰隆轰隆"的低频能传得很远；
    *   游戏中为表达效果，会在某一区域**强化高频**，随后逐渐回到很低频的 bass 区域。
    *   **吃鸡游戏案例**：根据枪声判断开枪者远近——中等距离时高频回响、混响变重；距离更远时高频混响逐渐消失，听到的多是低频声音。audio engineer / sound designer 会**单独制作近、中、远三份音频**，运行时在它们之间插值。
*   **衰减形状（构建空间感）**：
    *   **Sphere（球形）**：最简单，随距离向各个方向均匀衰减；
    *   **Capsule（胶囊体）**：模拟长条状声源，如**小溪流水**——靠近越大、越远越小，但沿小溪方向走声音不会特别变化；
    *   **Box（盒状空间域）**：模拟**声音被墙阻隔**——出了某个范围声音迅速衰减；
    *   **Cone shape（锥形）**：模拟**高音喇叭的定向性**——站在喇叭正前方很吵很刺耳，跑开一点点就小很多。
    *   引擎无法在游戏世界里做真实的物理声学模拟，就用 attenuation 制造空间感。
*   **Occlusion（遮蔽）/ 声音被阻挡的两种机制**：
    *   **Absorption（吸收）**：声音是波，被障碍物阻挡时，在障碍物**边缘**会产生**波的衍射**——每个拐角处又形成一个新的波源，声音绕过来；
    *   隔墙听声：声音推动墙震动，墙再把震动传给另一侧的空气，所以隔墙仍能听到声音。
    *   两种机制的处理方法完全不同。
*   **Ray Casting 近似方案**：从声源发射一些 ray（射线）发散、采样，类似渲染中蒙特卡罗积分的随机采样方法。这个方法非常耗时，但**对重要事件值得做**——例如近处手雷爆炸：这是已知的重要 event，listener 只有玩家一个，此时加入 ray casting 计算即可大致模拟效果。
*   **对 gameplay 的重要性**：射击游戏中，根据手雷爆炸声是"闷闷的"还是"明显在拐角那边"，能判断战斗发生在哪。吃鸡、CS 玩家摘下耳机后"基本站立（胜率）就没了"——声音对现代游戏的 gameplay 极为重要。

### 16. 混响（Reverb）与多普勒效应（Doppler Effect）

#### A. 混响（Reverb）
*   **作用**：混响对游戏空间感影响特别大。典型场景：在教堂里与 NPC 对话、骑马穿过桥洞时马蹄声发生变化。
*   **构成（三部分）**：
    1. **干音（Dry）**：真实发出、未经任何反射直接到达耳朵的声音；
    2. **回声（Echo）**：声音打到一面墙再反射到另一材质后到达耳朵（对着大水泥墙/空腔喊一嗓子能听到自己的回音）；
    3. **尾音（Tail）**：声音在两个面之间来回弹射形成的近乎无限的循环，每次都有能量衰减。
    *   回音 + 尾音合称 **湿音（Wet）**。audio designer 仅用 dry 与 wet 两个词就能定义出完全不同的空间容积感。
*   **关键量**：
    *   **材质吸音**：不同材质对不同波段声音的吸收率不同——有的材质特别擅长吸收高频，有的擅长吸收低频（如办公室的消音板、专门的声音采集室/录音室的声学设计都基于此）；材质吸收率有对应的经验表格。
    *   **空间大小 → 延迟**：空间越大，声音来回的 latency/delay 越大。
    *   **听感经验**：完全没有回音、只有干音的声音会让人非常难受——人说话或放音乐一定要听到一些 reverb；浴室唱歌最好听，正是因为浴室的混响（混音）效果最好。
*   **引擎中的简化参数（四个量）**：
    1. **干音/湿音分量比例**；
    2. **Pre-delay（预延迟）**：以秒为单位，延迟 0.5 秒左右表达非常空旷的空间（如山谷），0.16 秒左右则较轻；
    3. **High Ratio（高低频混响比例）**：值大约在 0.5 到 10 之间，统一定义"对高频的混音效果更强还是对低频的混音效果更强"；
    *   仅凭这四个量，artist 就能做出大量想要的空间效果。混音（reverb）是现代 audio engine 非常重要的基础功能。

#### B. 多普勒效应（Doppler Effect）
*   **定义**：在运动介质中运动的波源持续产生波，波以波源为圆心扩散，导致观察者感受到的**振动频率发生变化**。当飞机扑面而来时，飞机本身的声音不变，但因与你的距离和相对速度不断变化，听感频率持续改变。
*   **普遍性**：多普勒效应不仅存在于声学，光学中也有（如超高速宇宙射线打中大气层、粒子速度大于介质中光速时会产生特殊辐射，原理类似）。
*   **游戏中的价值**：多普勒效应是**打击感与速度感的重要来源**——高速开车、空中追击作战、子弹从身边掠过时，引擎对多普勒效果的处理非常重要。
*   **实现前提**：需要 listener 的速度（velocity）参与计算。

### 17. 声音中间件与游戏音频架构

*   **行业现状**：很少有游戏引擎团队自己写声音引擎，一般使用**中间件（Middleware）**。两大主流：
    *   **FMOD**：目前维护有点"拉胯"；
    *   **Wwise（WWISE）**：越来越受重视。
    *   最新的游戏引擎也意识到可能需要自己直接写声音引擎（如一些最新引擎已开始自研音频）。
*   **中间件的价值**：
    *   为 **audio designer** 提供一个非常符合他们工作习惯的**调音环境**（如对音效添加效果器、加 reverb、调节干湿音效果与空间效果）；
    *   让 **audio engineer（引擎工程师）** 只需专注如何在 3D 世界中完成声音的组合渲染，而把声音的生产与管理全部交给 audio designer——连渲染的一部分也由中间件完成。
*   **复杂世界的声音**（以《蜘蛛侠》曼哈顿为例）：
    *   城市中每个点、每个区域的混响效果都不一样；
    *   制作方专门做了一套算法，把曼哈顿**每个区域的混响效果归纳成不同的类型**，形成一张不同颜色的分布图，从而实现蜘蛛侠在曼哈顿穿梭时听到整个城市的声音感觉在变化（视频中每个蓝色点代表一个音源）。
    *   **开放世界**游戏引擎的技术要求非常高（如果要做得很高质量）。
*   **音效数据的组织（资源管理）**：
    *   实战引擎一般接入 audio middleware（FMOD 或 Wwise）；
    *   audio designer 只放入很多 **clips（音频片段）**（类似动画的原始数据）；
    *   游戏引擎触发各种 **event（事件）**，事件触发声音的混合需求，混合器（mixer）从 clips 中选出声音，按混音方法或播放规则生成声音；
    *   游戏中做**资源上限控制（budget 控制）**：同一时刻最多播放的音源数量有上限；
    *   资源加载更像场景/网格/动画的资源管理：**用到了才调用（按需加载/different loading）**——很多音乐和效果确定用不到就不加载，否则光加载音乐音效就可能吃掉几百兆甚至上 GB 内存，而内存是游戏中最稀缺的资源；
    *   典型做法：**以关卡为单位**——记录本关卡用到的音效表格并加载；切换关卡时保留可重用的部分、移除不需要的部分，再加载两边差值（difference）所需的新资源。

## 二、 重点术语与概念解析

### 1. Particle（粒子）
*   **定义**：粒子系统最基础的构建元素，空间中一个小点或小面片。
*   **应用/注意点**：拥有位置、速度、尺寸、颜色、生命周期等属性；生命周期若不管理好，粒子无限累积会导致系统资源耗尽。

### 2. Emitter（发射器）
*   **定义**：不断生成并发射粒子的部件，可为粒子提供随机的初始位置、初速度、方向等。
*   **应用/注意点**：支持点发射、区域发射（box/sphere/capsule）与 mesh 表面采样发射；行为模式有连续喷射与周期爆发。

### 3. System（粒子系统）
*   **定义**：多个 emitter 与其发射出的所有存活/管理中的粒子的总和。
*   **应用/注意点**：游戏中一个完整效果（火焰、爆炸）通常由多种粒子系统组合而成，组合方式是特效艺术家研究的核心。

### 4. Billboard（公告板）
*   **定义**：始终朝向 camera 的四边形面片粒子。
*   **应用/注意点**：大尺寸 billboard 必须配 animated texture（动画贴图），否则会被看穿是面片。

### 5. Mesh Particle（网格粒子）
*   **定义**：直接以 mesh 作为形态的粒子。
*   **应用/注意点**：用于碎屑、人群等；必须加随机旋转、随机缩放，避免重复感。

### 6. Ribbon / Beam Particle（光带粒子）
*   **定义**：飞行过程中拉出控制节点、连成有宽度丝带的粒子。
*   **应用/注意点**：用 Catmull-Rom 曲线插值保证曲线过所有控制点且平滑，适合表现尾迹、剑气、气功波。

### 7. Catmull-Rom Curve（卡特莫尔-罗姆曲线）
*   **定义**：一种通过所有控制点的样条插值曲线，实现简单。
*   **应用/注意点**：ribbon particle 中在控制点间插入过渡点，使特效圆滑。

### 8. Overdraw（过度绘制）
*   **定义**：同一像素被重复绘制的次数。
*   **应用/注意点**：粒子系统是 overdraw 大户，可用 half resolution 渲染降低开销。

### 9. Half Resolution（半分辨率渲染）
*   **定义**：把渲染分辨率在 X/Y 各缩小一半（总像素为 1/4）进行透明物渲染，再 upscale 回全分辨率。
*   **应用/注意点**：z buffer 同步减半；被 opaque 遮挡的粒子跳过；全体透明物统一计算 alpha 后再与 opaque 结果 blending。

### 10. DLSS
*   **定义**：以低精度绘制再用算法上采样放大回原分辨率的技术。
*   **应用/注意点**：up sampling / down sampling 在现代渲染中非常常用。

### 11. Particle Pool（粒子池）
*   **定义**：预分配、容量上限固定的粒子数据存储（位置、速度、颜色、尺寸、texture uv 等）。
*   **应用/注意点**：配合 alive list 与 dead list 管理粒子生命周期，是 GPU 粒子系统的核心结构。

### 12. Alive List / Dead List（存活列表 / 死亡列表）
*   **定义**：分别记录当前存活粒子的索引与可回收空位的索引。
*   **应用/注意点**：两个列表的 index 来回 swap（双 buffer 策略）即可管理高度动态的集群系统。

### 13. Compute Shader（计算着色器）
*   **定义**：GPU 上执行通用并行计算的着色器阶段。
*   **应用/注意点**：提供原子操作（atomic operation），使粒子池的分配/回收在并行环境下安全实现。

### 14. View Frustum Culling（视锥剔除）
*   **定义**：剔除视锥体之外对象的操作。
*   **应用/注意点**：适合在 GPU 上并行执行；但不会改变 alive list——粒子死活与是否可见无关。

### 15. Merge Sort（归并排序）
*   **定义**：把大数列分解为若干有序子数列再逐级合并的排序算法，复杂度 $O(n \log n)$。
*   **应用/注意点**：GPU 上实现时优先采用"反向查找、顺序写入"的策略以提升 cache coherence。

### 16. SDF（Signed Distance Field，带符号距离场）
*   **定义**：记录空间每一点到最近表面的带正负距离的场；正值在外、负值在内，接近 0 表示贴近表面。
*   **应用/注意点**：可用于粒子防穿透、沿表面流动、crowd 人群导航（配合 directional field），也是多种全局光照算法的基础输入；现代 GPU 上可实时计算。

### 17. State Machine（状态机）粒子
*   **定义**：把粒子 simulation 从简单物理积分升级为状态机，粒子在各状态间切换。
*   **应用/注意点**：用于 crowd 模拟等复杂行为；动画状态与速度影响可编码进 texture。

### 18. Niagara
*   **定义**：虚幻引擎最新一代粒子系统，融合 stack-based 与脚本化可视化图编程。
*   **应用/注意点**：非常复杂（Unreal 中 Niagara 代码近 100 多万行），是现代粒子系统的行业标杆。

### 19. Technical Artist（技术美术）
*   **定义**：兼具技术与美术能力的岗位，承担重要研发角色。
*   **应用/注意点**：用想象力和聪明才智挖掘底层系统的可能性，推动粒子系统 40 年发展。

### 20. Decibel（分贝，dB）
*   **定义**：以人类可感知最小压强为基准的对数声强单位，$dB = 20 \log_{10}(P/P_0)$，$P_0 \approx 20\mu Pa$。
*   **应用/注意点**：游戏引擎向 audio designer 暴露音量时一律使用分贝/类分贝数值，符合人耳对数感知。

### 21. Pitch（音调）
*   **定义**：决定声音尖锐程度的主观量，本质为频率。
*   **应用/注意点**：人耳可听范围约 20 Hz ~ 20 kHz。

### 22. Timbre（音色）
*   **定义**：由不同谐波（overtone）及其权重叠加形成的听感差异。
*   **应用/注意点**：相同频率的音高，不同乐器因谐波构成不同而听感不同。

### 23. PCM（Pulse Code Modulation，脉冲编码调制）
*   **定义**：对模拟信号依次采样、量化、编码得到数字音频的方法。
*   **应用/注意点**：位深（bit depth）常用 14/24 bit；量化有线性与对数两大流派。

### 24. 香农采样定理（Shannon Sampling Theorem）
*   **定义**：采样率 ≥ 信号最高频率的 2 倍即可无损重建。
*   **应用/注意点**：实际采样率会略高于理论值，以保留影响音质的高频成分。

### 25. WAVE / FLAC / MP3 / OGG
*   **定义**：常见音频容器/编码格式。WAVE、FLAC 无损；MP3、OGG 有损。
*   **应用/注意点**：MP3 只支持立体声且有专利费，游戏引擎普遍改用无专利的 OGG；游戏中不用无损格式（数据量太大）。

### 26. Listener（听者）
*   **定义**：声学渲染中的观察者，具有位置、速度、朝向三个属性。
*   **应用/注意点**：TPS 游戏中 listener 位置放在观察点与角色之间的某处较合理；速度用于多普勒效应。

### 27. Panning（声像定位）
*   **定义**：通过多声道间音量、音色、延迟的调节产生虚拟声源方位感的过程。
*   **应用/注意点**：注意"功率平方效应"（声源居中时听感变小），需用 $\sin$ / $\cos$ 归一化保证 $L^2 + R^2 = 1$。

### 28. Attenuation（声音衰减）
*   **定义**：声音随距离/环境变化的强度衰减。
*   **应用/注意点**：不同频率衰减不同；用 Sphere/Capsule/Box/Cone 等形状定义衰减区域以构建空间感。

### 29. Occlusion（遮蔽）
*   **定义**：声音被障碍物阻挡的现象。
*   **应用/注意点**：包含吸收（衍射绕行）与墙体传导两类机制，处理方式不同；对重要事件用 ray casting 近似。

### 30. Reverb（混响）
*   **定义**：声音在空间中经多次反射形成的余响，由干音（Dry）、回声（Echo）、尾音（Tail）构成（后两者合称湿音 Wet）。
*   **应用/注意点**：引擎中用干湿比例、pre-delay、high ratio 等少量参数即可表达空间感。

### 31. Doppler Effect（多普勒效应）
*   **定义**：波源与观察者相对运动导致观察频率变化的现象。
*   **应用/注意点**：游戏打击感与速度感的重要来源，需要 listener 速度参与计算。

### 32. Middleware（中间件）
*   **定义**：介于游戏引擎与音频制作之间的第三方音频工具（FMOD、Wwise）。
*   **应用/注意点**：提供符合 audio designer 习惯的调音环境与渲染 SDK；引擎工程师专注 3D 声音组合渲染。

## 三、 工程经验与避坑指南

### 1. 新引擎命名与品牌（PICO）
*   引擎正式定名为 **PICO**（意大利语"短笛"，一种非常小但音域特别广的乐器，寓意小引擎也能越做越丰富）。
*   icon 设计理念：孔洞代表 **0**，短笛形状代表 **1**，一和零构成计算机世界。
*   后续工作：代码命名、文件名、GitHub 工程名都要随之变更，预计持续一周左右完成更名。

### 2. 上期作业（动画系统）常见踩坑
*   **动画插值权重必须归一化**：当有三个甚至四个以上动画同时插值时（控制状态较多），**总权重一定要归一化**，否则会出现非常奇怪的 bug。
*   **动画 blending 要用 Slerp 而非简单 Lerp**：简单线性插值在旋转角度为钝角（卡特兰角问题/COTAN 问题）时，会在某一瞬间出现不自然的效果，那一瞬间插值就"插过去了"。
*   **滑步问题不必焦虑**：本次作业提供的动画素材量不够（真正做到脚部无滑步需要大量素材，如斜向移动、横向移动等），素材充足时插值误差更小。小引擎没有做得很复杂，在"跑→跳→落地带前移""加上斜向移动"等复杂组合下确实可能产生滑步——这不是代码写错了。**动画系统想做到尽善尽美本身就非常难**。
*   若能把前几节课的作业都做完，基本就能对基础引擎架构有整体的了解。

### 3. 粒子系统设计经验
*   **生命周期管理是第一要务**：粒子必须能在 lifespan 到期后自动消灭，否则不断产生的粒子会拖垮整个系统。
*   **随机感优先于一切**：做粒子系统一定要给 artist 提供**尽可能多的可随机扰动量**（位置、速度、方向、旋转、尺寸、颜色、XYZ 随机放缩等），避免重复感——艺术家最喜欢"所有变量都允许我随机一下"。
*   **大 billboard 必须动画化**：尺寸大的 billboard 若用静态贴图，用户极易看穿它是"永远朝向 camera 的面片"；务必使用 animated texture。
*   **排序先做 per-emitter，再考虑 global**：入门阶段先写最简单的 per-emitter sorting，能解决部分问题；global sorting 写起来麻烦且依赖更复杂的 GPU 算法。
*   **注意 overdraw 陷阱**：一个"很简单的效果"可能瞬间把游戏帧率拉下来——粒子离相机近时考虑 cut 掉部分粒子，或降低同一像素上的重复覆盖。
*   **half resolution 的细节**：被 opaque 遮挡（Z 在后）的粒子不用绘制；所有透明粒子要**集体算一个 alpha** 再与 opaque 结果混合，混合过程要做上采样与扰动。

### 4. GPU 粒子系统实现要点
*   **建议写两套**：先写 CPU particle，再按课程思路写 GPU 版本（GPU 版本很有趣）。
*   **死列表用"从尾巴取"的栈式操作**：emitter 产生粒子时从 dead list 尾部取空位，死亡粒子 append 回 dead list。
*   **双 buffer 管理生命周期**：遍历 alive list0 同时写 alive list1，死亡粒子跳过写入并加入 dead list，随后 buffer swap。
*   **compute shader 原子操作**是 GPU 上安全做分配/回收的关键。
*   **视锥剔除不修改 alive list**：粒子死活与是否可见无关（看不见的烟火还在飞，回头应该还在）。
*   **GPU 排序选"反向查找 + 顺序写入"策略**：正向遍历两个有序数组写入时地址跳跃，cache coherence 极差；反向为每个目标位置在 source 中二分查找，写入顺序连续，效率高。
*   **粒子碰撞用 depth buffer 而不是物理引擎**：直接读 screen space depth 与粒子碰撞，效果远好于无碰撞，且开销可控。粒子系统本质是在效果与效率间做 trade off。

### 5. 音频工程经验
*   **引擎对外暴露音量一律用分贝**：直接给 audio designer 的 volume 数值全部以 $20\log_{10}$ 分贝/类分贝表达，符合人耳对数感知。
*   **音频格式选择**：游戏中不用无损格式；**不要选 MP3**（只支持立体声 + 专利费），**选 OGG**（无专利、谁都能用）。
*   **混响参数化**：用干/湿比例、pre-delay、high ratio 等少量参数即可让 artist 做出大量空间效果。
*   **衰减形状即空间感**：用 Sphere/Capsule/Box/Cone 等衰减形状近似模拟真实声学，避免昂贵的真实声学模拟。
*   **重要事件才做 ray casting**：只有关键事件（如手雷爆炸）且 listener 唯一时才值得做射线采样近似遮蔽。
*   **音频资源按需加载**：音乐/音效按关卡为单位加载与卸载，切换关卡时保留复用部分、只加载差值，避免音频吃光内存（几百兆甚至上 GB）。
*   **音频用中间件**：引擎不自研音频，接 FMOD / Wwise；中间件提供调音环境与渲染 SDK，引擎工程师专注 3D 声音组合渲染。

## 四、 Q&A 实战答疑

### 1. CPU 上写粒子系统是否适合用 ECS？
*   **大方向正确**：用最简单的编程模型（数据一块块分散存储）访问与处理效率一定很低。
*   **核心思想**：用 ECS 思想把粒子数据**全部集中在一起**，一类 particle 交给一个 process 处理，效率很高。
*   **不需要完整的 ECS 框架**：实际就是一个简单的 **DOP（Data Oriented Programming，面向数据编程）** 概念，不必引入复杂 ECS 完整体系。
*   **可配合 SIMD**：一条主指令同时进行 4 条浮点数的 vector 运算，速度很快，这套架构已经非常成熟。
*   **与 GPU 的关系**：CPU 上优化得再好也比 GPU 慢；但两者都有存在价值——GPU particle 即便 compute shader 很强大，仍有不少局限（有些复杂行为的粒子做不了），而 CPU 上高性能粒子系统对现代游戏引擎**仍有实战价值**。

### 2. 粒子系统能否与动画系统、物理系统结合？
*   **完全可以（Yes）**，特别是对现代粒子系统而言。
*   **与物理结合**：复杂的粒子系统有大量环境互动，会用到物理系统；最前沿的粒子系统甚至加入了物理解算，保证粒子行为符合物理规律——如表现悬挂的锁链、多个小球之间刚性结算（彼此不穿插）。
*   **与动画结合**：
    *   crowd 模拟本质就是在粒子系统内部实现了一个**非常轻量的动画系统**（把轻量动画系统 embed 进粒子系统）；
    *   反向融合：粒子系统也可以直接从动画系统获取输入，如表现"角色走着走着突然变成漫天沙尘"的效果。
*   **与影视特效结合**：现代粒子系统与影视特效系统深度绑定，如 **Houdini** 的许多表现越来越多地集成进现代游戏引擎，数据之间实现互通。

### 3. Crowd 粒子系统中用到的 SDF 是预计算的吗？
*   **早期引擎中确实预计算**：给一个巨大的城市，有设计图、城市不会变化，SDF 与 directional field 都可以提前算好。
*   **现代引擎中可实时计算**：由于越来越多 **global illumination（全局光照）** 算法上来就需要对空间计算 SDF，SDF 在现代 GPU 上**实时计算已经不是特别难**；可以算得 **view-dependent**——离眼睛近的地方精度高、远的地方精度低。
*   **SDF 是很多系统的标配**：
    *   用于**扰动粒子**：粒子在空中乱飞时不穿进物体内部，GPU 粒子用 SDF 算出的效果非常好，感觉粒子沿物体表面流动；
    *   也可用于 **GI（全局光照）** 计算。
