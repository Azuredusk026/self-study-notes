# 现代游戏引擎架构：面向数据编程（DOP）与任务系统

## 一、 核心知识点与原理剖析

### 1. 编程范式总览：从面向过程到面向对象

#### (1) 编程范式（Programming Paradigm）的概念

*   **核心概念**：编程范式即编程模式，指编写代码时组织逻辑与数据的总体风格。在游戏引擎开发中，各种编程范式都会被用到，常见的有面向过程、面向对象、面向函数（函数式）等。
*   **老师的反思**：进入游戏引擎行业后才意识到，面对几百万行代码的复杂系统，仅凭"小聪明"写代码是不够的，**必须系统学习各种 Design Pattern（设计模式）**，例如 GoF 经典《设计模式》一书中讲的 `Listener`、`Publisher`、`Subscriber` 等模式。这就是做引擎"要读书"的原因。
*   **关键决策点**：采用面向过程还是面向对象，是引擎立项时一开始就要想清楚的重要问题。

#### (2) 面向过程编程（Procedural Programming）

*   **适用场景**：早期的简单游戏，例如"小乌龟吃豆子"这种小游戏，用一个函数处理各种输入、输出和数据，逻辑非常简单，用面向过程就够了。

#### (3) 面向对象编程（Object-Oriented Programming, OOP）

*   **核心概念**：以"对象"为中心组织代码，把数据（变量）和动作（函数）封装在类中，通过派生（继承）复用。
*   **典型体现**：引擎中"万物皆 GO（Game Object）"的思想——从 GameObject 可以派生出 Vehicle（载具）、飞机、武器、人物等一切东西，与前述 Component-Based 系统/数据集成思想一脉相承。
*   **优点**：自诞生至今，OOP 非常符合人类对世界的认知，写代码时感觉很舒服，因此同学们学得最多的就是 OOP。
*   **本节立场**：为了引出主角 DOP，本节会系统性地"黑"一遍 OOP，指出其在大规模高性能系统上的固有缺陷。

### 2. 面向对象编程（OOP）的固有缺陷

> 以下缺陷是老师在实际商业引擎开发中总结的，也是 DOP 诞生的直接动因。

#### (1) 动作归属的二义性（Ambiguity）

*   **核心问题**：一个动作到底属于哪个对象，存在二义性。以"人攻击怪物"为例：
    *   **攻击者视角**：人（Actor）调用 `attack` / `apply damage to`，传入目标 Actor；
    *   **受益者视角**：怪物（Actor）调用 `onDamaged` / `been damaged`，询问谁打我、造成多少伤害。
*   **实际表现**：打开商业级游戏的逻辑代码会发现，不同程序员写法不同——有人从攻击者角度写，有人从数据（被攻击者）角度写。**同一动作归属不定，代码一致性被破坏**，令"强迫症"开发者十分痛苦。

#### (2) 深继承树导致查找困难

*   **核心问题**：OOP 系统往往是一棵很深的继承树。例如"对某个东西造成魔法伤害"这个逻辑，你无法直观知道它实现在：
    *   基类 `Base Class`（如 `UObject` 层）：所有对象都能受到魔法伤害；
    *   `Actor` 层：所有 Actor 都能受到魔法伤害；
    *   `Monster` 派生类层：所有 Monster 受到魔法伤害；
    *   更深层的 `Flying Monster`（飞行/可变形怪物）层：仅特殊怪物受到魔法伤害。
*   **实际痛点**：面对几百万行真实引擎代码产生新需求时，需要在"深不见底的继承树"中定位某个函数的实现，非常头疼。
*   **日常纠结**：OOP 程序员经常纠结"这个功能属于基础服务还是特殊服务"——有人觉得是通用需求应写到基类，有人觉得是特殊需求应写到派生类，最后发现共用了又要挪回基类。这是程序员之间的日常对话。

#### (3) 基类（Base Class）臃肿，形成"全家桶"

*   **核心问题**：大系统的基类会做得极其繁复。以某商业引擎的 `Actor` 基类为例（老师强调不点名、大家可以自行研究），里面放了无数功能，连 `Debug` 功能都在里面。
*   **通俗解释**：当你只想要几个功能而派生 `Actor` 时，基类却给了你一个"全家桶"——类比商业销售捆绑销售套路。
*   **结论**：**Base Class 的臃肿是 OO 大型系统做到后来大概率会发生的通病**，打开任何商业引擎源码即可切身体会。

#### (4) 性能低下

*   **原因一：内存碎片化**。OOP 数据分散到各个 Object 中，通过派生继承后数据全是异构的（不同类型混杂），每个对象的分配/释放都分散进行。抓取一个 OO 系统的内存布局来看是"东一块西一块"，CPU 访问效率极低。
*   **原因二：虚函数指针跳转**。OOP 中有大量函数重载与虚函数。**虚函数本质是指针**，导致代码执行在内存中跳来跳去：本来一段 `execution` 代码在一个地方，执行到某处突然跳到另一处执行另一个函数。
*   **profiling 表现**：用 profile 工具看 OO 系统的性能图，图形非常"丑"、非常不稳定，一眼可知该高性能系统性能做得不好。
*   **通俗解释**：一个工厂里没有管理者，所有"师傅"凭感觉干活：做鞋做到一半缺原料就从库房拿，只会做鞋底就把半成品递给做鞋面的师傅……整个任务调度完全无序。

#### (5) 可测试性差（Unit Test 难写）

*   **核心问题**：测试某段业务逻辑（如伤害结算公式）时，必须把整个环境的全部对象创建起来才能测到中间那个函数。
*   **理想目标**：现代软件工程中的 Unit Test 理想状态是——代码可以一直改，但几十上百个测试只测特定模块的数据。
*   **现实困境**：OO 世界对象"一层套一层"，很难把某个元素单独提取出来测试。**重度 OO 系统的单元测试代码非常难写**。
*   **备注**：克服可测试性问题并不只有 DOP 一条路，面向函数（函数式）编程也能解决，本节不展开。不同编程范式存在的深层原因，正与超大型软件工程对可测试性的高要求密切相关。

### 3. 面向数据编程（DOP）的动机：CPU 与内存的性能鸿沟

#### (1) CPU 与内存增速差距

*   **核心事实**：过去约 20 年里，CPU 处理速度提升接近 **上千倍（约 $10^3$）**，而内存访问速度只提高了约 **一个数量级（约 $10^1$）**，两者差距被拉开到 **2~3 个数量级以上（$10^2\sim10^3$ 倍）**。
*   **注意**：与"CPU 已到瓶颈、必须多核"的说法并不矛盾——一切都是相对的，瓶颈描述与增速对比是两个层面的事实。
*   **直接后果**：CPU 与内存速度差距直接催生了现代计算机复杂的 **Cache（缓存）机制**，并最终催生了面向数据编程（DOP）思想。

#### (2) 分级缓存（Cache）机制

*   **核心概念**：Cache 像一个分级"水泵"，把数据从主内存一级一级抽到 CPU 附近。CPU 在最上面，各层关系如下：
    1.  **L1 Cache**：最靠近 CPU，最快也最小；
    2.  **L2 Cache**：一般十几 MB（老师回忆早期电脑只有 2MB L2，现在能买到十几 MB），速度比 L1 慢一个数量级；
    3.  **L3 Cache**：十几 MB 到上百 MB，速度比 L2 再慢一个数量级；
    4.  **主内存（Main Memory）**：比 L3 再慢一个数量级。
*   **成本累计**：L1、L2、L3、主内存逐级慢一个数量级，**最坏情况从主内存取数据比 L1 命中慢约 $10^3$（1000）倍**。
*   **访问流程**：CPU 处理时先找 L1，没有就问 L2，L2 没有问 L3，L3 没有才从主内存调，一路问完一旦决定从内存调数据，成本就是千倍级别的。
*   **对高性能编程的启示**：做高性能编程时脑中要始终有这个层级图，时刻自问"我的代码/数据对这个 Cache 是 friendly 还是 not friendly"。

#### (3) Cache 替换策略：LRU 与随机丢弃

*   **核心概念**：Cache 满了之后需要淘汰数据。有两种经典策略：
    *   **LRU（Least Recently Used，最近最少使用）**：保留最近一直使用的数据，扔掉最近最没用的数据。
    *   **随机丢弃**：每次随机扔掉一小块（例如 64B / 128B，相对大容量存储约千分之一）。看似不合理，但**从概率角度，最久没被访问的数据被随机扔掉的概率最大，恰好符合数学期望**——因此随机丢弃在统计意义上是近似 LRU 的，且实现更简单。
*   **实际意义**：这也是我们打包数据和代码时要"尽可能放在一起"的原因。

#### (4) Cache Line 与访问顺序

*   **核心概念**：内存中管理数据有 **Cache Line（缓存行）** 概念。每次从 L2/L3 往 L1 取数据，是 **一次取一个 Cache Line（约 64 字节）**，按 line 为单位进行读写。
*   **一致性保证**：CPU 必须保证 L1/L2/L3 与主内存中同一份数据最终一致；数据一旦改变，写回主内存也是一级一级按 line 写。
*   **通俗解释**：你在 L1 里有一段数字，L2、L3、内存里也各有一段，所有副本要保证一致。

#### (5) 行优先 vs 列优先的矩阵访问

*   **核心实验**：同一个矩阵，若按行优先存储，**逐行读取比逐列读取效率高几百倍甚至上千倍**。
*   **原因**：矩阵按行连续存放；若按列读取，坐标只加一个 1（y 方向），但物理地址跳过了大量 Cache Line，每次被迫从主内存一层层往上搬数据。
*   **结论**：**数据访问的 order（顺序）极其重要**，它直接决定 Cache 命中率。同学们有兴趣可以自己写代码测一下这个差距。

### 4. 面向数据编程（DOP）的核心思想

#### (1) 一切皆数据

*   **核心概念**：DOP（Data Oriented Programming）认为，游戏里所有事件、所有事情的表达都是数据，代码和对应的数据放在一起看。
*   **核心目标**：把数据与代码作为一个整体，在 CPU 中尽可能降低 **Cache Miss（缓存未命中）**——不仅是数据访问会 Miss，代码加载同样会 Miss。

#### (2) 数据与代码共同优化

*   **核心事实**：profile 数据显示，**时间消耗中近 7% 的损耗来自"代码执行完被迫加载新代码"的指令 Cache Miss**。这一数字远超一般人的直觉——大家总以为慢在数据访问，其实代码优化同样重要。
*   **实践原则**：
    *   数据与代码在内存中可以分开，但**在 Cache 里要尽可能在一起**；
    *   保证这一段代码执行完，刚好能处理完对应的这批数据；
    *   然后整体 swap 出，再换下一批"数据+代码"。

#### (3) 鞋厂流水线比喻（理解 DOP 的关键）

*   **理想状态**：处理鞋子的工人和要处理的鞋料、工艺全部放在一起，一次处理完后把工人和成品一起 swap 出去，再换下一个工人和他的原料——效率极高。
*   **要避免的两种情况**（也是 DOP 想避免的核心问题）：
    1.  工人只能做一道工序，做一半要切换另一个工种，就得从内存把另一个工人调出来，数据空等；
    2.  工人确实能处理这些鞋，但鞋的原料四散在各处，做一半得去别的地方取原料。

#### (4) 性能收益

*   **核心结论**：同样逻辑下，DOP 比传统 OOP 快 **1~2 个数量级（10~100 倍）是很正常的**。
*   **佐证**：Unity 用 DOTS 系统实现同样的东西，性能提升接近 **100 倍以上**。前提是系统与代码必须从架构层面按此方式组织。

### 5. DOP 实践要点

#### (1) 避免执行顺序依赖（Order Dependency）

*   **核心概念**：任务之间应尽可能 Order Independent（执行顺序无关）。这与前文讲 Job System 时强调的一致。
*   **重要性**：顺序无关是并行化与高效调度的前提。

#### (2) 伪共享（False Sharing）

*   **核心概念**：两个函数（线程）各自读写不同的变量，但这两个变量恰好落在**同一条 Cache Line（64 字节）**内，就会发生伪共享。
*   **危害**：系统为了保证数据一致，对同一条 Cache Line 的读/写过程要专门做两遍同步，**内存 swap 成本大幅上升**。即使双方写的是不同地址，仅仅因为地址在同一个 64 字节范围内，性能就会受到严重拖累。
*   **实践原则**：**超高性能系统中，尽量避免两个线程同时读写同一条 Cache Line**；不要把一个线程访问的数据切得太碎，**一个线程访问的数据基本就是自己的那一块，双方尽量无交集**。

#### (3) 分支预测（Branch Prediction）与减少 if/else

*   **核心概念**：现代 CPU 追求极高性能，会做 **Branch Prediction（分支预测）**：程序 100 次进入某判断时可能有 99 次走同一分支，CPU 会提前把该分支的代码（比如 100 行）加载进 L1 Cache 直接执行。
*   **失败代价**：当下一次进入时条件突然不满足，原来预加载的分支代码在 L1 中失效被 swap 出，再调入 else 分支的代码；若该代码既不在 L2 也不在 L3（是"冷代码"，还在主内存里），系统就要等很久。
*   **实验对比**：用随机数据测试复杂的 if/else 判断，性能会非常低，因为分支预测频繁出错。
*   **经典解法**：
    1.  **先排序再遍历**：例如对数组判断"大于 10 做工作一，否则做工作二"，先对数据排序，只在边界处切换一次分支，后面全是同一分支——排除排序开销后，该函数性能显著高于乱序版本；
    2.  **提前把数据分好类**：创建每个数据时直接放入不同的数据容器，**一个容器只处理一种逻辑**，保证整个逻辑高度一致，避免复杂 if/else。
*   **结论**：写高性能高频代码时**尽量少用分支**。分支预测出错时，即使数据在 Cache 里也没用，因为代码本身要 swap，代码 swap 又会导致数据失效。

#### (4) 内存布局：AoS 与 SoA

*   **核心概念**：超高性能开发中，数据怎么摆放非常讲究，需要理解汇编、C 语言等底层知识。两个核心概念：
    *   **AoS（Array of Structures，结构体数组）**：按 OO 思想定义一个结构（如 `Particle` 包含 position、velocity、color、age），100 个粒子自然排布为"第 1 个粒子的 position、velocity、color、age，第 2 个粒子……"。
    *   **SoA（Structure of Arrays，数组结构体）**：把同类数据拆出来，各自排成超长数组（所有 position 一个数组、所有 velocity 一个数组……）。
*   **对比分析**：以更新粒子 position 为例，只需读 velocity 和 position；AoS 布局下每个粒子都要跳过 color、age，**Cache coherence（缓存一致性/局部性）不好**；而 SoA 布局下连续读取连续处理，配合 SIMD 效果极佳。
*   **类比 GPU**：理解现代高性能编程可以参考 GPU Compute Shader——显卡骨子里就是**以数据为驱动的编程**，每个 shader 可理解为一个函数，数据紧凑排列，这也是同样运算上 GPU 后飞快的原因。
*   **结论**：**追求高性能时按 SoA 方式组织数据**。

### 6. ECS（Entity Component System，实体组件系统）架构

#### (1) Component-Based + OOP 的困境

*   **背景**：构建游戏引擎时天然会想到用 Component-Based（基于组件）系统搭出想要的东西，最自然的实现方式是用 OO——构建大量对象、层层派生继承。
*   **问题**：代码分散在各个类里，虚函数/虚指针一团糟，数据非常分散；当场景中 Component 变多、对象变多时，每帧 tick 性能比想象中慢很多。明明没做复杂运算，系统却慢——其实大量时间浪费在**等指令加载、等数据加载、执行到一半找数据、虚函数指针跳转找实现、再加载那段代码**的无谓倒腾上。
*   **结论**：Component-Based + OOP 导致"任务调度完全无序"，ECS 就是为了彻底解决这个问题而生。

#### (2) ECS 三大概念

*   **Entity（实体）**：
    *   在 Component-Based 系统里 GO 是一个类，可装很多 Component；
    *   在 ECS 里 **Entity 非常轻量，只是一个 ID（iD），指向一组 Component**。
*   **Component（组件）**：
    *   在 ECS 中 Component 就是**一块纯数据**（如位移数据、速度数据）；
    *   **不允许包含任何业务逻辑**——这与传统 Component-Based 系统（每个 Component 有 tick、get/set property 等一堆接口函数）截然不同，是特别容易弄混的点；
    *   可以对它读、写，但它本身不知道自己的意义。
*   **System（系统）**：
    *   System 是**对 Component 进行处理的函数**，例如 `MoveSystem` 根据速度改位置、`HealthSystem` 根据受到的 damage 调整 health 值。
    *   关键点：**System 往往同时处理好几类 Component 的数据**（因为单位被拆得非常细），而不是一次只处理一个。

#### (3) ECS 为什么快

*   **数据打平**：把数据全部"打平"，从以前一个个 GO（owner）中剥离开，**每一类数据集中在一起存储**，再通过 ID 建立离散的关联关系（如"我用了多少号 transform、多少号 velocity"）。
*   **Cache 友好**：System 处理时操作极其简单，数据连续紧凑，**能充分利用数据的 Cache Coherence，充分压榨面向数据编程的性能**。
*   **天然可并行**：System 的运算很容易分散到很多核上并行执行，这是 ECS 系统一个很大的优势。

### 7. Unity DOTS 系统剖析

#### (1) 三大支柱

*   **核心概念**：Unity 提出的 Data Oriented Tech Stack（面向数据技术栈，DOTS）有三个支柱系统共同工作：
    1.  **ECS**：重新面向数据组织整个计算的引擎框架；
    2.  **C# Job System**：数据已切成 Component/System，非常容易批量化并行处理；
    3.  **Burst Compiler**：把 C# 编译成 Native Code（等价于汇编），解决性能问题。
*   **备注**：Unity 目前已决定放弃 DOTS 项目（老师提到"没关系，不妨碍拿它来分析 ECS 应用"）。

#### (2) Archetype（原型 / 泛型）

*   **核心概念**：Unity ECS 在 Component 之上抽象了一层 **Archetype**，可理解为"type of GO（某一类 GameObject）"——某一类对象所需 Component 的集合。
    *   做一个 NPC 大概需要固定的几个 Component；
    *   能战斗的 Monster 会多一些攻击属性、伤害属性、行为属性 Component；
    *   做 Vehicle 也有相应的一套 Components。
*   **作用**：游戏中有几百上千个 Entity，每个 Entity 挂的 Component 不一致；**有了 Archetype，System 就知道哪些 Entity 需要处理，处理速度变快，也方便他人理解**，避免了逐个询问"你有没有这个 Component"的低效过程。

#### (3) Chunk（块）内存布局

*   **核心概念**：Unity ECS 最经典的一张图：把内存定义成一个个 **Chunk（块）**，**一类 Archetype 的所有 Component 按 Component 类型放在同一个 Chunk 里**。
*   **两大好处**：
    1.  一个 Chunk 内一定是同一类 Archetype。当 System 需要处理时，只需问这个 Chunk 的 Archetype——例如要做对话 System，就知道 NPC 的 Archetype 里必然有对话需要的 Component，直接处理；而载具 Archetype 的几十个实体完全不需要考虑；
    2.  代码 + 一小块数据正好能塞进 Cache，处理完整个把下一个 System 和它的 Chunk 切进去，数据整体处理效率最高。
*   **Chunk 大小**：早期架构一般设 **16KB**，主要考虑 Cache Line 与 L1 Cache 的 swap 方式；最新资料显示 Chunk 变大了，**UE（虚幻）把它提到了 128KB 或更大**——这是一个可调的量，具体数据大家可自行查询。
*   **为什么不把所有同类 Component 全放一起**：如果所有 Transform Component 全放一起数据量太大，反而不符合 Locality（局部性）要求。

#### (4) System 的运算

*   **实现**：一个"Update Position"的系统非常简单——拿到 Velocity Component 和 Translation Component，做一个运算（ECS 里的 System 可理解成一个运算），算完整个 Chunk 里所有物体的 Translation Component 都被更新一遍；因为读和写的数据都在一起，效率非常高。

#### (5) 100 倍性能提升

*   **核心结论**：Unity 用 DOTS 实现同样东西，性能提升接近 **100 倍以上**。

#### (6) Burst Compiler 为什么存在

*   **背景**：如果整个系统用 C# 写，你申请一个 Array、定义一个数据结构，它在硬件上到底对应什么完全是**黑盒**——C# 跑在虚拟机（.NET）上，并非 Native Code。C# 中定义一个变量"根本不是一个变量"，除了很小的一块数据，还带很多反射数据等附加信息。
*   **矛盾**：高性能 DOP 开发需要和硬件一对一对抗，最需要的是 Native 的东西。
*   **Unity 的解法**：
    *   在 ECS 里虽然看着写 C#，但定义 Array 时要明确写 **Native Container**——很像 C 语言里定义的一段裸指针，分配一段内存，与物理内存一一对应，数据访问才能连续映射；
    *   因为非常 Native 了，**必须加大量安全检查**（如内存释放管理），并在编译器层面、Job System 层面确保所有无用资源被释放——这非常困难；
    *   因此必须写自己的编译器 **Burst**，把 C# 语言（只借用了 C# 语法）编译成非常底层的语言（等价汇编），并完成必要检查。
*   **DOTS 的本质**：把复杂性全部藏在自身，对上层业务开发者，只需按它的规则写 C#，无需理解 Cache 等底层概念，即可获得高性能。
*   **对 C# 的评价**：C# 是非常了不起的语言，但在高性能开发（尤其是 DOP 类型开发）上确实存在这个弊端。

### 8. UE5 Mass 系统剖析

#### (1) 背景

*   **核心概念**：UE5 最新的 **Mass 系统** 实现了一套类似 ECS 的东西（老师怀疑它与 Unity DOTS"互相抄作业"，但不下定论）。典型应用是 UE5 的 **Matrix Demo**（矩阵觉醒演示，非刺客信条），其中的曼哈顿街景有成百上千上万的汽车、行人，就是用这套系统实现的——这是 ECS 系统的典型应用案例。

#### (2) Entity 与 Serial

*   **核心概念**：Mass 中 Entity 同样只是一个 ID；每个 ID 带一个 **Serial（序列号）**，单调递增、永不重用，保证 ID 永远不会被重用。
*   **类比**：这很像之前课程教大家做 Handles（句柄）时用 **Salt** 保证 ID 可重用——两者用两个数字区分新旧身份，是小细节但很重要。

#### (3) Fragment

*   **核心概念**：Mass 把 Component 命名为 **Fragment（碎片）**——一小块内存碎片、一小块数据。
*   **命名动机**：UE 已有 1000 多万行代码、定义了无数 Component，再做 ECS 时若也叫 Component 会造成概念冲突（此 Component 非彼 Component）；且老师认为 **"Component" 这个名字取得不好**——容易让人联想到 COM 接口、数据服务绑在一起的东西，而 ECS 架构中 Component 就是 **pure data（纯数据）**；"Fragment" 这个名字更贴切。
*   **组织方式**：整个 Component 实际就是存放很多 Fragment 数据；每个 Entity 拥有若干类型的 Fragments。

#### (4) Processor（处理器）

*   **核心概念**：Mass 把 System 命名为 **Processor（处理器）**——"你给我这么多数据，我一个 processor 全部处理完"，命名非常贴切。Processor 有两大核心功能：
    1.  **Query（查询）**：
        *   Processor 先声明自己需要哪些 Fragment、对每个 Fragment 是读还是写（像写数据库查询函数一样）；
        *   通过一段描述执行 query，把所有满足条件的 Entity 扫一遍，把数据拿出来；
        *   Mass 也用了 Archetype 概念来加速扫描；
        *   **Query 有缓存**——上一次 query 完，如果本次没有变化，基本不用动，直接用缓存结果。
    2.  **Execute（执行）**：
        *   Query 之后所有需要的 Fragment 都拿到了，**注意这里只是引用（引用），并没有把数据搬过来**；
        *   因为每类 Archetype 的数据集中存储在 Chunk 里，Processor 处理完一个 Chunk，下一个依次切换也是整个 Chunk 切过去，后续处理相对简单。

### 9. 架构取舍：OOP 与 DOP 的辩证关系

*   **不要理想主义**：游戏是非常复杂的系统，业务依赖关系非常乱、复杂，**几乎不可能把整个引擎变成纯 ECS**。
*   **ECS 的正确用法**：**在合适的地方用 ECS 非常棒，但用不到的地方千万不要到处用**——它极大增加代码维护复杂度，开发难度大，抽象度高（很多人很难理解为什么数据和业务分开；现实中 90% 以上的游戏逻辑都是"数据 A + 数据 B + 数据 C，问自己问别人，然后怎么办"这种写法）。
*   **工程现实**：强如 UE5，其 ECS（Mass）也只用于非常特别的场景，主体引擎仍是**面向对象的 Component-Based 架构**（即本节前面被"黑出翔"的架构）。
*   **老师的澄清**：今天把 OO 黑得一无是处只是为了烘托气氛、引出 DOP。**实战型游戏引擎中 OOP 与 DOP 同等重要，甚至 OOP 的重要性还要大一点，基于 DOP 的 ECS 稍小一点**。

### 10. 总结：高性能编程的本质

*   **核心结论**：今天所有内容本质上是**高性能编程（High Performance Programming）**。当面对游戏引擎这种对性能极其敏感的系统时，被迫理解操作系统和硬件——CPU、内存、Cache 是如何协作的。
*   **关键图表（延迟数量级表）**：老师展示了一张经典表格，同学们应逐行研读：一条 ALU 指令要花多少、硬件级中断要花多少、线程上下文切换（thread context switching）要花多少、C++ 里一次函数调用/虚函数调用/一次栈的 swap 要花多少。
*   **数量级差异**：表中各操作的代价差异**不是线性的，而是数量级的**——从 $10^0$、$10^1$、$10^2$ 一直到 $10^4$、$10^5$，最高达 **100 万倍**。因此一个系统写不好，同样的逻辑、同样的代码慢 100 倍是**很正常**的事。
*   **本节所有解决方案本质上都是对着这张表做优化**。
*   **人才观**：我们并不缺 Programmer，但**非常缺 Architect（架构师）**。有志于底层系统架构的同学，这节课的内容非常值得深入研究——钻研的路径就是把这张表每一行看明白，弄懂"为什么这里更慢"。

## 二、 重点术语与概念解析

### 1. DOP（Data Oriented Programming，面向数据编程）
*   **定义**：一种编程思想，认为游戏中所有事件/事物的表达都是数据；把数据与代码视为整体，核心目标是尽量降低 CPU 的 Cache Miss，充分利用数据局部性。
*   **应用/注意点**：性能上比传统 OOP 高 1~2 个数量级（10~100 倍）；实践时需注意避免执行顺序依赖、伪共享、复杂分支，并使用 SoA 内存布局。

### 2. OOP（Object-Oriented Programming，面向对象编程）
*   **定义**：以对象/类为中心，把数据与行为封装在一起，通过继承/多态复用代码的编程范式。
*   **应用/注意点**：符合人类认知、写起来舒服，但存在动作归属二义性、深继承树查找困难、基类臃肿、性能低、可测试性差等大系统通病。

### 3. Design Pattern（设计模式）
*   **定义**：针对软件设计中反复出现的常见问题的、经过验证的解决方案模板，如 `Listener`、`Publisher`、`Subscriber` 等。
*   **应用/注意点**：做大型软件系统时**要 follow 已有范式，千万不要发明创造**（"太阳底下没新鲜事"）。

### 4. Cache（高速缓存）
*   **定义**：位于 CPU 与主内存之间、速度远快于内存的小容量存储，用于弥合 CPU 与内存的速度鸿沟，分 L1/L2/L3 三级。
*   **应用/注意点**：逐级慢一个数量级，最坏情况下从主内存取数比 L1 命中慢约 1000 倍；高性能编程始终要自问代码/数据是否 Cache-friendly。

### 5. Cache Line（缓存行）
*   **定义**：CPU 与缓存之间以约 64 字节为单位的读写数据块；CPU 按行读写并保证各级缓存与主内存数据一致。
*   **应用/注意点**：矩阵按列访问会跳过多条 Cache Line，效率比按行访问低几百上千倍；两个线程写同一 Cache Line 内不同变量会引发伪共享。

### 6. Cache Miss（缓存未命中）
*   **定义**：CPU 需要的数据/代码不在当前级缓存中，必须向更低级缓存或主内存请求。
*   **应用/注意点**：不仅数据访问会产生 Miss，代码加载也会（profile 显示约 7% 的时间消耗在指令 Cache Miss）。

### 7. LRU（Least Recently Used，最近最少使用）
*   **定义**：缓存满时优先淘汰最近最少使用的数据的替换策略。
*   **应用/注意点**：随机丢弃策略在概率意义上是其近似实现——最久未被访问的数据被随机扔掉的概率最大。

### 8. Locality（局部性）
*   **定义**：程序倾向于在较短时间内访问内存中相近位置的数据/代码的特性。
*   **应用/注意点**：DOP 的核心追求之一；数据处理尽量一次性连续完成。

### 9. False Sharing（伪共享）
*   **定义**：两个线程修改同一条 Cache Line 内不同变量，导致缓存一致性协议反复同步、性能骤降的现象。
*   **应用/注意点**：超高性能系统中应让一个线程访问的数据独占一块，避免与其他线程的数据落在同一 Cache Line。

### 10. Branch Prediction（分支预测）
*   **定义**：CPU 猜测分支走向并预加载对应分支代码的硬件优化机制。
*   **应用/注意点**：数据随机、分支结果不可预测时频繁失败，性能大幅下降；解决方法是先排序，或按数据类别预先分流到不同容器、每个容器只跑一种逻辑，尽量减少 if/else。

### 11. SIMD（Single Instruction Multiple Data，单指令多数据）
*   **定义**：一条指令同时对多个数据（如 4 个 float 组成的 vector）进行同一运算的并行机制；现代 CPU 基本全部实现 SIMD。
*   **应用/注意点**：打包数据时应尽量打包成 SIMD 友好的 16 字节等对齐空间，配合 SoA 布局使用。

### 12. AoS（Array of Structures，结构体数组）
*   **定义**：按对象为单位连续存储，一个对象的所有字段相邻，然后是下一个对象的所有字段。
*   **应用/注意点**：符合 OO 直觉，但处理单个字段（如只更新 position）时需跳过无关字段，Cache Coherence 差。

### 13. SoA（Structure of Arrays，数组结构体）
*   **定义**：按字段为单位连续存储，所有对象的同一字段排成一个超长数组。
*   **应用/注意点**：追求高性能时的推荐布局，连续读写配合 SIMD 效果极佳；GPU 渲染本质就是数据驱动、紧凑排列。

### 14. ECS（Entity Component System，实体组件系统）
*   **定义**：一种以数据为中心的架构模式，由轻量 ID（Entity）、纯数据块（Component）、处理函数（System）三部分组成。
*   **应用/注意点**：性能高、易并行，但抽象、维护成本高，适合确定性的批量场景（如 Mass 中的海量车辆行人），不应在引擎中到处使用。

### 15. Entity（实体）
*   **定义**：ECS 中非常轻量的存在，只是一个 ID，指向一组 Component。
*   **应用/注意点**：不同于传统 GO（类），Entity 本身不含任何数据与逻辑。

### 16. Component（组件）
*   **定义**：ECS 中的一块纯数据（如位移、速度），**不允许有业务逻辑**。
*   **应用/注意点**：与传统 Component-Based 系统中带 tick/get/set 接口的组件完全不同，是 ECS 学习中特别容易弄混的点。

### 17. System（系统）
*   **定义**：对 Component 进行处理的函数（如 MoveSystem、HealthSystem）。
*   **应用/注意点**：往往同时处理多类 Component 的数据，运算简单、易并行化。

### 18. Archetype（原型 / 泛型）
*   **定义**：Unity ECS 中"type of GO"的概念，描述某一类对象所需 Component 的集合。
*   **应用/注意点**：让 System 快速定位需要处理的 Entity，避免逐实体询问；同类型数据集中存储在 Chunk 中。

### 19. Chunk（块）
*   **定义**：Unity ECS 内存组织单位，一类 Archetype 的所有 Component 按类型存放于其中。
*   **应用/注意点**：早期约 16KB，UE 最新提到 128KB 或更大；让"一段代码 + 一小块数据"整体塞进 Cache。

### 20. DOTS（Data Oriented Tech Stack，面向数据技术栈）
*   **定义**：Unity 面向数据的完整技术栈，由 ECS + C# Job System + Burst Compiler 三大支柱组成。
*   **应用/注意点**：性能提升接近 100 倍；Unity 已宣布放弃，但仍是分析 ECS 应用的最佳样本。

### 21. Burst Compiler（Burst 编译器）
*   **定义**：Unity 自研编译器，将 C# 语法代码编译成 Native Code（等价汇编）并完成必要的安全检查。
*   **应用/注意点**：因为 C# 跑在虚拟机上，数据结构在硬件上不可控（黑盒），DOP 开发必须依靠它获得与硬件一对一对抗的能力。

### 22. Native Container（原生容器）
*   **定义**：DOTS 中与物理内存一一对应的底层容器，类似 C 语言裸指针分配的一段内存。
*   **应用/注意点**：数据访问能够连续映射；因过于底层，必须在编译器与 Job System 层面做好安全检查与资源释放。

### 23. Mass 系统（UE5）
*   **定义**：UE5 实现的一套类 ECS 系统，用于海量实体（如 Matrix Demo 中的曼哈顿车辆与行人）。
*   **应用/注意点**：Entity 带永不重用的 Serial；Component 更名为 Fragment；System 更名为 Processor。

### 24. Fragment（碎片）
*   **定义**：Mass 中对 ECS Component 的称呼——一小块数据/内存碎片。
*   **应用/注意点**：强调其"纯数据"本质，避免与 UE 既有海量 Component 概念冲突。

### 25. Processor（处理器）
*   **定义**：Mass 中对 System 的称呼，含两大功能 Query（查询所需 Fragment 及其读写属性）与 Execute（处理引用到的数据）。
*   **应用/注意点**：Query 有缓存，结构不变则结果复用；Execute 拿到的是引用而非拷贝，配合 Chunk 整体切换。

### 26. Job System（任务系统）
*   **定义**：将任务拆分为可并行执行的 Job，由调度器分配到多线程执行的任务调度框架。
*   **应用/注意点**：Fiber-Based Job System 是高层任务调度，与 ECS（面向数据组织运算）有交集但非完全一致；Unity DOTS 与 UE Mass 实际基于 Dependency Graph 构建任务 fork，效果同样很好。

### 27. Fiber（纤程）
*   **定义**：比线程更轻量级的用户态任务执行单元，支持快速切换。
*   **应用/注意点**：Fiber-Based Job System 常提供"一键降级为单线程"的调试功能，按依赖依次执行以验证业务逻辑。

### 28. Unit Test（单元测试）
*   **定义**：针对代码中某个特定模块/函数的自动化测试。
*   **应用/注意点**：重度 OO 系统因对象层层嵌套难以单独提取元素，单元测试极难编写；DOP 与函数式编程有助于改善可测试性。

### 29. Compute Shader（计算着色器）
*   **定义**：在 GPU 上执行通用并行计算的着色器程序。
*   **应用/注意点**：是"以数据为驱动的编程"的代表，与 CPU 端 DOP 思想一致。

### 30. False Sharing / Order Dependency / Cache Coherence
*   **定义**：
    *   False Sharing：见上文第 9 条；
    *   Order Dependency（顺序依赖）：任务执行结果依赖任务间的先后顺序；
    *   Cache Coherence（缓存一致性/局部性）：数据在缓存中紧密、连续的特性。
*   **应用/注意点**：DOP 实践要尽量让任务顺序无关、线程数据不共享同一条 Cache Line、数据排布紧凑连续。

## 三、 工程经验与避坑指南

### 1. 架构取舍：不要有"技术执念"

*   **实事求是**：做游戏引擎架构**千万不要执念于某种技术方案，一定要实事求是**——关键是把技术用对地方。
*   **不要好高骛远**：学了前沿知识后容易陷入理想主义冲动，想搭一个"彻底基于 DOP/彻底基于 ECS 的下一代引擎"。真要落地做实战引擎，面临的问题与挑战远比想象复杂、抽象。
*   **规模认知**：一个真正达到可用规模的游戏引擎通常是**几百万行以上**的代码，此时可测试性要求非常高。
*   **混合架构**：引擎中 OOP 与 DOP 同等重要，甚至 OOP 更重要；ECS 只应在确定合适的场景使用（如 UE5 的 Mass），主体引擎仍是 OO 的 Component-Based 架构。

### 2. ECS 使用的边界与成本

*   **不要到处用**：ECS 会极大增加代码维护复杂度，开发难度大，抽象度高——很多人天然难以理解"数据和业务分离"。
*   **适合的场景**：强如 UE5，ECS 也只在 Mass 这种非常特别的场景中彻底使用；实体数量巨大、行为模式统一的批量计算场景最合适。
*   **成本意识**：写 ECS 时注意区分 Component 与 System 的职责——Component 纯数据、System 处理逻辑，两者极易混淆。

### 3. Job System 与 ECS 的关系澄清

*   **关系**：Fiber-Based Job System 更多是 **high level（高层）任务之间的调度**；ECS 则是大量运算时**面向数据组织运算**。两者有交集，但并非完全高度一致。
*   **误区**：**并不是用了 ECS 就一定要实现 Fiber-Based Job System**——用 Join 的 Pattern（如生成静态的 Dependency Graph：任务 fork 出去、完成后做下一件事）一样可以运行得很好。
*   **事实**：Unity DOTS 与 UE Mass 都不是完整的 Fiber-Based Job System，而是基于 **Dependency Graph** 构建任务依赖，效果同样非常好。
*   **工程结论**：Job System 虽高大上，但真实引擎**不太可能把整个引擎全部扔进 Job System**，可能只有 **50%~60% 的 workload** 能被并行化；物理等子系统还需要特殊处理才能真正跑得好。

### 4. 并行编程的团队协作模式

*   **少人接触多线程**：多线程 Debug 极其困难，正确解法是**让尽可能少的程序员接触到多线程编程**。
*   **底座化**：由团队中技术最扎实、思维最缜密的少数同学，把原子操作、锁机制等底层机制做成一个稳定的"底座"；上层程序员只做简单逻辑开发，访问的数据、可调用的函数都要约束好——**最好上层同学只写脚本，不用关心底层真正发生的事情**。
*   **好处**：现代游戏引擎被迫支持多线程，这种"底层底座 + 上层简单开发"的模式是推荐的开发模式。

### 5. 高性能开发通用经验

*   **要懂底层**：做高性能开发需要理解汇编、C 语言等底层知识，才能在 arrange memory 时非常讲究。
*   **数据访问顺序**：数组/矩阵遍历的 order 极其重要，按内存连续顺序访问可差几百上千倍。
*   **少用分支**：高频代码尽量减小分支计算（先排序 / 按类别分流容器）。
*   **警惕伪共享**：不要让两个线程同时读写同一条 Cache Line 内的数据。
*   **CPU 占用管理**：Job System 应持续监控每个核的占用情况，超过阈值（如 80%~90%）就不再塞入新 Job（Job 挂起但不启动），避免 CPU 跑满引发行为变化。

### 6. 参考资源与学习路径

*   **课程组资料**：课程组分享了大量资料，包括 Cache 系统到底如何工作、各种 **Blocking / Non-Blocking 方法**系列文章。
*   **不要"土法炼钢"**：写并行程序时千万不要自己发明创造——"太阳底下没新鲜事"，你拍脑袋想出的解法，别人可能 10 年、20 年前就遇到过无数次，**行业提炼总结的 Paradigm（范式）是经过实践验证成功的，直接 follow 它**。这是做大型软件系统的一个重要觉悟。

### 7. 课堂问答（Q&A）

#### Q1：自旋锁把 CPU 跑满怎么办？

*   **老师的判断**：可能是任务的安排不太合理。CPU 跑满后，可能触发一系列连锁反应——线程被迫 swap 出去、很多进程/线程拥塞在那里。
*   **坦言**：目前没有一个好的办法能彻底解决它。
*   **工程实践**：自己实现的 Job System 会**一直监控每个核的占用情况**；当某个核使用率超过阈值（80%~90%）时，不再给它塞任何 Job——**Job 挂在队列里但不启动**，尽量避免跑满；因为跑满之后很多行为会发生变化。

#### Q2：并行编程有没有比较好的 Debug 方法？

*   **坦言**：老师自认并非非常好的并行编程开发者，因为并行编程真的非常难。
*   **方法一：Log 抓取**。通过 log 观察数据问题；但 **log 本身很慢**（写文件速度慢），会导致程序时序发生变化，这是 log 调试的重大局限。
*   **方法二：一键降级单线程**。做 Fiber 系统时，会做一个功能：**一键把 Fiber 变成 Single Thread**，让所有 Job 依次按依赖顺序执行——先确认业务逻辑基本正确，再排查多线程问题（如某个资源竞争）。
*   **现状**：新一代 IDE（如 VS）在这方面已做得越来越好，能展示很多状态；但最难的仍是"出了问题断不下来、不知道在哪个线程断下"。
*   **团队血泪史**：自己团队写 Job System 时，前期同学遇到大量极难的 Debug 问题，**一个问题很可能花一两个星期才能找到**。

#### Q3：渲染线程和逻辑线程的同步怎么做？

*   **常见做法：Ring Buffer（环形缓冲）**。逻辑线程算完所有值，一股脑扔给渲染线程——逻辑线程每帧形成一个 **Frame（逻辑帧）** 交给渲染，渲染自己去做。
*   **代价**：这会导致**渲染线程总是比逻辑线程慢一帧**（渲染要等逻辑全部算完数据才到）。
*   **现状**：业界也在探讨其他架构避免此问题；但**目前成熟商业引擎很多时候仍被迫让渲染线程等逻辑线程算完**，否则数据会产生很多奇怪的二义性。
*   **分界线原则**：面对 DOTS 这种复杂系统，每类任务必须有一条清晰的分界线；采用固定线程法架构时，任务不能轻易在渲染线程、逻辑线程、模拟（simulation，如物理）线程之间来回跳——它们做的事情完全不同，且有数据依赖关系。
*   **理论 vs 实际**：讲理论很简单，但面对引擎实际情况时，**一般都要对算法做定制**，为特殊 Scenario（场景）进行针对性优化。
