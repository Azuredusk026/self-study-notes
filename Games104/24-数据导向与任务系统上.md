# 现代游戏引擎架构：面向数据编程（DOP）与任务系统

---

## 一、 核心知识点与原理剖析

### 1. 为什么要做：性能极限压榨与多核趋势

*   **核心概念**：现代游戏引擎跑在操作系统之上，操作系统跑在硬件之上；游戏引擎最大的特点是对 **performance（性能）要求非常高**，而**带宽有限、算力有限**。
*   每一帧（1/30 秒）内要完成大量物理逻辑运算、物理模拟，还要瞬间渲染出几百万乃至上千万像素里无数光的反射积分。
*   玩家需求还在不断提升：30 帧不够，要 60 帧；60 帧不够，电竞要 120 帧。
*   因此设计游戏引擎时，**必须把操作系统和硬件的所有性能几乎压榨到极限**——这正是重型游戏团队或引擎团队基本都是硬件与操作系统性能大师的原因。

**为什么必须转向并行（多核）**：

*   晶体管/集成电路工艺已经 **almost hit 到量子力学的上限**：当前在突破 22nm，理论极限约 0.5nm，1nm 以下几乎不可能再往下走。
*   主频也已触顶：现在基本停在 **3.x GHz** 上不去（团队里有一块英特尔赠送的 CPU 主频可冲到 4.x，但噪音已经"有点吓人"）；无论是散热还是功耗都有很大问题。
*   于是硬件厂商转向**堆核**：四核、八核、十六核已成为常态。
*   结论：**既然不能把单个核做得更快，就用更多的核解决问题**，必须想办法把所有这些核的算力全部利用起来。

### 2. 进程、线程与多任务模型

#### (1) 进程与线程的区别

*   **进程**：有独立的存储单元，存储完全独立，由系统管理。
*   **线程**：存在于进程之内，**共享进程的存储 memory**，memory 本质上是线程间的数据交换通道。
*   线程写不好会互相"内存打架"；线程比进程轻量很多（Windows 下；Linux 下进程也可以做得很轻量）。
*   进程之间必须通过特殊机制才能彼此交换信息。
*   这是**所有并行化编程的 foundation（基础）**。

#### (2) 游戏引擎天然的 Multi-Tasking

*   游戏要做动画、物理、逻辑、rendering 表现等大量事情，天然是多任务（multi-tasking）的。
*   有四核、八核、十六核时，应尽量把核都用起来。

#### (3) 抢占式多任务（Preemptive Multitasking）

*   **核心概念**：任务/线程在跑的时候，**调度者（scheduler）自己决定**什么时候把你调出去、过一会儿再调回来。
*   例如高优先级任务来了，就打断当前任务、触发中断，让当前任务出去、高优先级任务进来。
*   **Windows 操作系统就是抢占式的**：不可能让一个进程把所有系统资源吃光，否则操作系统本身没法跑。

#### (4) 非抢占式多任务（Non-Preemptive Multitasking）

*   **核心概念**：任务在干活时**不会被主动打断，除非它自己声明结束**（协作式）。
*   优点：如果所有任务都是你给的，对运行节奏的**控制能力非常强**。
*   缺点：一旦任务写坏了、一直占着不放，其他人全部被迫等待。
*   普通操作系统中很少用；但在**实时性（real-time）要求非常高的操作系统**中会采用这种模型。

### 3. 线程切换的代价（为什么线程切换"很贵"）

*   场景：启动 20 个线程但只有 4 个核，就必须在线程之间来回切换。
*   一次线程被打断要**触发一个中断（interrupt）**，该中断至少耗费 **2000 多个 CPU cycle**；对比之下，最快的 ALU 指令只要 1 个 cycle。
*   更糟的是：切回来的线程，其数据**并不在各级缓存（cache）里**，需要从内存重新调入，此时延迟可能从 **1 万到 100 万个 cycle**。
*   **重难点：线程之间的切换极其昂贵**——这正是后面 job system 选择 **fiber-based（基于协程/光纤）** 设计的原因：设计者意识到了线程切换非常 expensive。

### 4. 并行化编程的两类问题

*   **第一类：独立任务（简单问题）**——"这些线程我不打断你，该做就做完"，没有 thread interaction / thread swapping 问题；一堆独立任务各自算完、一起收口。
    *   最简单案例：**蒙特卡罗积分**。每个线程负责撒 1000 个采样点，总共采 100 万个采样点就完成了（$N$ 个线程各自独立采样 $\frac{10^6}{N}$ 个点），不会遇到线程切换瓶颈。
*   **第二类：相互依赖的任务（真实游戏场景）**——无法把一个游戏要做的模拟切分得那么干净：
    *   各个子系统（surprise/system）之间有很多**数据依赖**；
    *   还存在一种特殊依赖叫 **dependency**：**"我得等你这件事做完之后，才能启动我的事情"**。
    *   正是依赖关系使 parallel programming 变得非常复杂。

### 5. 数据竞争（Data Racing）与阻断式同步

#### (1) 数据竞争（Data Racing）

*   **核心概念**：同一个数据，**一个线程在读它的时候，另一个线程正在改变它**。
*   典型逻辑：读到一个值，基于该值做后续操作——很可能读的时候是一个值，等操作时那个值已被修改成另一个值，逻辑就出问题了。
*   类比：三四个小伙伴轮流在墙/黑板上写东西，你看到的和你写的东西完全不一样。
*   **data racing 是围绕所有并行化编程的核心问题**：死锁等一系列问题本质上都以它为核心。

#### (2) Critical Section（临界区）与阻塞式编程

*   **核心概念**：critical section 指的是一段代码——"我进去了直到我出来，你们不要捣乱，必须让我完整执行完；其他线程里这段代码不能被同时重复执行"。
*   例子：每个学生注册、把学生塞入数据库表、计数器 count 递增；若数据库是单线程的，用 `mutex` 把所有操作控制住即可。
*   现代编程语言中的实现方法：显式定义的 `critical section`、`mutex`（互斥锁）、`semaphore`（信号量）等。
*   本质：**阻断式（blocking）编程**。

#### (3) 阻断式编程的严重缺陷

*   **缺陷一：死锁**——在一个变量上等待、写变量，很容易产生死锁。
*   **缺陷二：单个任务失败拖垮全系统**——同时启动几十上百个任务时，无法保证每个 task 一定成功，有些 task 会自己死掉；一旦有 task failure 甚至 crash，会导致整个系统死锁，写代码不小心时极易出现且难排查。
*   **缺陷三：高优先级任务难以打断它**——进入 critical section 后它被彻底保护住，即使更高优先级任务进来，按现有调度算法也不会被打断。
*   工程结论：**lock 在大型系统里能不用就不用、越少越好**；后面讲的 job system 会用 lock，但会**用得极其少**。

### 6. Lock-Free 编程与原子操作

*   **核心概念**：有些量非常敏感、怕所有人去改它，于是把它变成**原子性操作（atomic operation）**——由硬件和底层支持，CPU 在硬件底层保证：**对某个变量的读写操作不会被多个任务同时侵占**。
*   两个核心概念：**Load**（从内存读出数据看一眼）与 **Store/Save**（往内存写入）——是原子性操作的核心。
*   相关指令族：**ARM**（Read-Modify-Write，读-改-写）、**CAS（Compare And Swap，比较并交换，即 check and set 检查并设置）** 等一整套原子性指令。
*   核心思想：**不需要锁住一整段代码**（一段代码里若有崩溃控制不住），只在**一个绝对保证能执行下去的指令**里，保证对**一个内存数值**（如 integer、boolean，一般是 integer）的操作具有原子性。
*   观察方法：用 profiling 工具抓多核跑动图，若看到很多**空洞（gap）**，说明那段时间 CPU 在 **idle（空闲）**、正等着其他任务启动。
*   优点：**尽可能避免死锁**。
*   缺点：原子变量之间彼此等待、依赖，会产生很多空洞。
*   适用范围：对性能极其 critical 的应用（如**高频通讯协议**）需要这种结构，但要**严格的数学和推演证明**其不会产生异常。
*   **做引擎时掌握到 lock-free 这一层就够了**——剩下的 gap 在 job system 里能相对较好地解决。

### 7. Wait-Free 编程

*   **核心概念**：等待几乎为零的编程，通过一套**数学方法**保证在多线程研发中尽可能把全部 CPU 资源占掉。
*   现状：非常复杂（老师自己也没有完全搞清楚）；对一个复杂系统保证 CPU 利用率 100% **几乎不可能**，目前没有看到理论架构。
*   但针对**具体的对象**（如对战、一个队列）把操作变成 wait-free，行业内已有解法。
*   性能极其 critical 的应用（高频通讯协议）可能必须用这种结构，且需要严格的数学推演证明其不会产生各种异常。

### 8. 编译器乱序（Out-of-Order Execution）与内存一致性

*   **核心概念**：写代码时我们天然认为代码会**顺序执行**；解释执行语言（如最早的 BASIC、部分脚本语言）确实一行行执行，但高级语言（C/C++）交给现代编译器后，**完全不知道最终汇编是怎么实现的**。
*   编译器只要保证"顺序执行下来的最终结果一致"，就认为编译有效，因此**可能把代码重排成无序的两段**——单线程没问题，**多线程下会出大问题**。

**经典例子（断言失败）**：

1. 初始：`a = 0`，`b = 1`。
2. 线程 1：执行 `a = b + 1`（则 $a=2$），随后把 `b` 设为 0。
3. 线程 2：循环 `while (b != 0);` 直到 $b=0$，然后 `assert(a == 2)`。

*   人按书写顺序理解：当看到 $b=0$ 时，$a$ 一定已经等于 2。
*   但编译器认为 `a`、`b` 是两个无关变量：可能先把 `b` 用临时寄存器设为 0，稍后才写回；而 `a` 却**抢先**用旧的 $b=1$ 算出了 2——于是看到 $b=0$ 时 $a$ 已完成 $=2$ 的假设**不成立**。
*   **这就是编译器乱序在并行开发中特别容易出问题的地方**。

**硬件层面的乱序执行**：

*   不同 CPU 架构（PC 的 x86、PowerPC、ARM）很多**并不能保证按代码顺序依次执行**。
*   **ARM 特别追求功耗和性能、尽量简单**：会把一个 100 行的函数切分成几大段、变量一通乱替代，最终保证结果一致。
*   人天然认为第一个 section 做完才做第二个，但在另一个线程里 section 的执行顺序可能错乱——"那你就完蛋了"。
*   **移动端开发典型症状**：在 PC 模拟器上代码完全正常，一到真机就 down 得死去活来，正是这个原因。

**为什么编译器要乱序**：

*   现代 CPU 要从内存反复读出数据和指令，CPU 速度快、内存慢，CPU 总是"饥饿地等着数据"。
*   因此 CPU/编译器不等待指令一条条执行，而是把一大段函数切成很多块**一股脑扔进去**，让指令和数据同时在里面运行——这样结果才快。现代编译器基本按此原理优化。

**Debug 版与 Release 版的差异**：

*   Debug 版函数执行顺序基本可以认为是正确的；
*   到了 **Release 版，最终编译出的汇编和执行逻辑可能跟你想的完全不一样**。
*   惨痛经验：多线程代码在 Debug 版逻辑成立，**一编译成 Release 版就莫名其妙挂掉，且这种 bug 极难排查**——因为你根本不知道编译器的优化是什么样的。

**重难点（必须建立的基本常识）**：一段函数在 CPU 中执行是**乱序**的，**不能假设变量的值符合你书写下来的顺序**；C++11 开始可以显式要求编译器保证执行顺序一致，但代价是执行性能变差。

### 9. 游戏引擎并行架构的演进

#### (1) 固定线程架构（Fixed Thread）

*   **做法**：把每一项任务分到一个线程——rendering 一个、simulation（物理）一个、逻辑一个，各干各的、井水不犯河水；彼此通讯在每个 frame 开始交换数据。
*   这是最古典、也是当时大部分游戏引擎的架构，在 **2~4 核**场景下分得清楚、挺好使。
*   **问题一：负载不均衡（木桶效应）**——很难保证各线程 workload 一致：有的 thread 很轻很快结束，有的很重，所有人只能**等着最慢的那个 worker 完成**这一帧。
*   能否把重 workload 拆开分给轻的？很难，因为：
    1. **数据访问的 locality（局部性）**：应尽可能让一个 thread 访问的数据集中在一块地方（如 rendering 数据集中）；若看到 simulation thread 空闲就把 rendering 数据挪过去，会引发 data racing。
    2. **不同场景负载分布完全不同**：有的场景渲染特别慢，有的场景角色敌人多、逻辑忙不过来；不可能根据游戏阶段动态调整 thread 分工——那会引入更多 bug。
*   经验数据：固定作用架构的 profiling 图里，**大约有 1/3 左右的计算资源被浪费掉**（经验值，不一定准）。
*   **致命短板**：
    *   遇到**双核电脑**：分好的 4 个 thread 只能两个挤在一个核上来回竞争（来回切换很慢）。
    *   遇到**八核/十六核的"幸福烦恼"**：引擎无法根据机器动态改制线程分布，只能眼睁睁看着大量算力用不上——**高配电脑游戏照样卡、但 CPU 很多资源没被占用**，就是这个原因。

#### (2) Fork-Join 模型

*   **核心概念**：游戏计算中有些模块**一致性高但计算量大**（如动画），这类运算是复杂重复的线性代数、矩阵运算，**可以完全切分开**。
*   **做法**：到某一时刻，把固定线程上的任务**fork** 出去，扔到**预先申请好的 worker thread** 上；做完之后 **join** 收回线程、把结果合回。
*   **现代基于 Unreal、Unity 的游戏基本都用 fork-join 方法**。
*   优点：能相对充分利用多核算力（4 核、8 核、6 核都能用到）；worker thread 数量通常**跟随操作系统报告的核数**，相当于"有这些工人，不用白不用"。
*   缺点：仍有很多工作**非常难以 balance**，中间产生很多 gap。
*   **Unreal 的实践**：有两种线程——**named thread**（明确指定，如 for 游戏逻辑、for rendering，循环体里看得很清楚）与**working thread**（物理等可扔上去展开）；用 profiler 抓 Unreal 游戏可看到大致这样的图。
*   评价：比较清晰也比较鲁棒（robust）的架构；**如果对多线程要求没那么高，这是非常好的架构**。

#### (3) Task Graph（任务图）

*   **核心概念**：任务不写死在某个线程上，而是先创建大量任务、设置好它们之间的 dependency，一次性扔给所有核；核**自动根据 dependency 决定哪个先执行、哪个后执行、哪个能并行**。
*   著名的 SDK：**TBB（Intel Threading Building Blocks）**。
*   对游戏尤其重要：**游戏创建的大量计算任务是有 dependency 的**，又不想把任务写死（如 task2 固定扔给某 thread、task3 固定扔给 animation thread），所以必须构建 dependency graph。
*   **实现非常淳朴**：在代码里一个一个 link 构建——"task1 的依赖/下一个是 task3"，逐条标记；依赖关系全部做好后就形成一张图，系统拿到图即可执行。
*   **两个大问题**：
    1. **task 树构建不透明**；
    2. 它假设"task1 执行完才能执行 task2"，但**真实游戏引擎里经常是任务执行到一半才发现还要做很多事**：例如做角色动画做到一半，意识到得先做完它的物理，甚至会 fork 出伤害检测等任务，这些任务完成后才能回到自身继续——任务在运行中**不断创建、不断设置越来越复杂的 dependency**。
    *   静态的 task graph 在**动态不断增删节点时非常复杂**；早期版本也没有实现"做到一半要等其他任务做完才能继续走"的机制（必须靠后面更动态的系统解决）。

### 10. 协程（Coroutine）

*   **核心概念**：一种非常轻量的多线程执行上下文方式。一个函数执行到一半，可以调一条指令 **yield（让道）** 把执行权让出去；过一会儿别人再 **invoke（激活）** 它，它就能**从刚才的位置继续执行下去**。
*   生活类比：学生去学校报名，办到一半发现缺材料，把报名流程"让"一下，先去打印店把材料打印完，再回来继续后面的流程。
*   语言支持：**Go 语言原生态支持**，C# 里这类概念用得特别多；有了这种结构，写并行化编程会非常方便。**遗憾的是 C++ 里协程很"蛋疼"**（见下文）。

**协程与线程的本质区别（换座位比喻）**：

*   线程切换要**调硬件中断**，整个中断栈、所有环境 context 全部重置，是 **kernel（内核）级**的操作，操作系统成本极高。
*   协程**由程序自己定义**，一般在一个 thread 内让多个协程来回切换；从 CPU 视角看这还是**同一个线程、从没掉过中断**，只是我们的程序逻辑让它们换来换去——**根本没有激活 kernel 的 switch**。
*   类比：线程换座位要惊动"教导主任"（系统报备），协程则是同桌私下商量自己换，不需要报备、随需求调整，**overhead 大幅下降**。

#### (1) 有状态协程（Stackful Coroutine）

*   **核心概念**：函数执行到一半时，函数里有大量 **local variable（局部变量）与寄存器状态**。yield 出去再回来时，**所有这些变量、寄存器、堆栈都必须完整恢复（resume）**。
*   难度所在：函数跳出去后，栈空间可能被其他函数占用，恢复上下文非常难。
*   程序员的天然预期：从 yield 回来时所有 local variable、所有寄存器**都不应该被污染**，否则代码逻辑极难书写——这与 RPC 存在的道理一致（人脑对业务逻辑的理解天然是"一次记录、顺序执行"）。
*   报名例子：先要来了学号和班级号（本地变量），去打印时 yield，表格拿回来后大脑 **resume 整个 coroutine**，自然知道学号和班级号继续填写。
*   **关键点：能否恢复函数执行时的所有 context**。

#### (2) 无状态协程（Stackless Coroutine）

*   **核心概念**：回来时"不管了"，**认为前面所有 local variable、所有寄存器全部被清掉**。
*   实现举例：C/C++ 里写一个 `goto` 直接跳出函数，再想跳回来，状态就全错掉了——简单但问题很多，不建议轻易做。
*   优点：**实施相对简单**，且**不需要保存和恢复整个栈与 local register 状态**。
*   缺点：**对协程开发者要求非常高**，一旦写不好会产生大量 bug。
*   **重难点（游戏引擎开发的核心理念）**：一个游戏引擎只是基座，大量开发者会基于它的接口做不同游戏产品；如果引擎**对开发者要求过高**（要求清晰理解并行编程的各种坑），这个引擎基本没人能用。因此**引擎的职责是把困难留给自己、把最难的东西留给自己**；对开发者则尽量提供简单方案——能用简单代码解决就用简单代码，能用脚本写完最好，能连几张图（graph）完成更好。
*   使用建议：**stackless 协程除非在很底层自己用，否则尽量不用**；它适合**非常高频、底层、只有少数核心同学维护的代码**（甚至可以直接写汇编），但写的人水平要求非常高。
*   引擎选型结论：要做高度并行化的引擎、让普通游戏开发者也能享受并行化乐趣，**强烈推荐有状态协程（stackful）**；无状态协程（stackless）用在非常底层、少数人控制、native code 甚至汇编的场景。

#### (3) C++ 中实现协程的难点

*   C/C++（及汇编等底层语言）在不同操作系统下**并不原生支持 coroutine 机制**。
*   Windows 下实现方案：**boost** 提供一套底层机制，但仔细读它的代码会发现**内部其实调用的是汇编**——需要把寄存器、堆栈全部导出，还要**设置栈空间大小**（一上来就要告诉系统每个函数的栈有多大）。
*   **栈设置小的后果**：函数写着写着栈空间就"炸掉"（**堆栈空间爆炸 / stack overflow**）；写递归代码、或局部变量申请太大时会遇到。Python、JS 等很少遇到，但写 C++ 常遇到。栈小则每次拷贝保存、恢复快，性能高。
*   **栈设置大的后果**：每次 coroutine 的 yield 和 resume 成本变高。
*   写这类系统要求对**操作系统调度底层、内存如何分配、数据如何存放、代码如何存放**理解得非常清楚。
*   平台现状：PlayStation 似乎 native 支持 coroutine（老师表示属保密信息不便细讲）；**ARM base 芯片需要自己通过一段汇编实现类似 coroutine 的机制**。
*   好消息：实现方法网上有很多很好的样例；实在不行参考 boost 也能知道怎么做。
*   **stackful coroutine 是构建游戏引擎很多基础组件时的 foundation（基础）**。

### 11. Fiber Based Job System（基于协程的任务系统）

#### (1) Fiber 的概念与核心思想

*   **fiber**（光纤/管道）是 **Windows 的一个概念**；老师十几年前在美国学习架构下一代引擎（design 引擎）时，为加入多线程高度并行化而研究过 fiber 技术。
*   可以理解为：**架构一个非常高速的"进程管一个线程的管道"**，往里面高速塞入大量 task，task 内部可以自由进行各种 coroutine 切换。
*   塞进 fiber 的任务就叫做 **job**；job 可以设置 **dependency（依赖）** 和 **priority（优先级）**。
*   **最朴素的理想模型**：有 100 个、1000 个不同任务、10 个核时，按每个任务的长短**像搭积木一样凑在一起**，尽量确保所有 fiber 的任务在同一时间进来、也在相近的时间完成。

#### (2) Worker Thread 数量与"一个核对应一个 worker"原则

*   fiber 可以想象成一个 worker thread；问题在于：**到底申请多少个 worker thread？**（4 核机器几个？16 核机器几个？）
*   **核心 trick：尽可能一个 worker thread 对应一个核**——核可以是逻辑核也可以是物理核，一般对应**逻辑核**。
*   逻辑核概念：现代 CPU 都是 **hyper thread（超线程）**，一个物理核逻辑上分成两个核；通常一个 hyper thread 配一个 worker thread。
*   好处：当不停往里面加各种各样的 job 时，**并不需要线程间 swap**。
*   **fiber 系统最核心的思想：thread 的 swap 几乎为零**——这一点至关重要，因为前面已反复强调每次线程切换都极其昂贵。
*   简化落地：**有多少个核，就生成多少个 worker thread**。

#### (3) Job Scheduler（任务调度器）

*   用户生成一个个 job，压进 fiber，worker thread（"可怜的工人"）依次执行。
*   job 有两个核心概念：**优先级（priority）** 与 **dependency（依赖）**；一个 job 可以 **fork** 出很多其他 job。
*   调度方式：存在一个 **global 调度系统 job scheduler**。**job 并不是直接递给 worker thread**，而是由 scheduler 根据**每个 worker thread 的饱和状态**决定把任务扔给谁。
*   **与 fork-join 模型的本质区别**：fork-join 本质上还是**单线程**的——只是运行到某一段后突然生成一大批类似任务、做完再合回；它并不是真正的全面并行化模型。
*   真正的全面并行化模型是：有一个 scheduler，**所有硬件计算资源只是它的 resource/worker**，由 scheduler 决定"任务大一点就扔这儿做得长一点、任务小一点就多塞几个小任务"，**尽量保证各 worker 任务基本均衡**。

#### (4) 任务队列策略：FIFO 还是 LIFO？

*   问题：worker 是**先认领的任务先完成（FIFO，先进先出，像队列）**，还是**最后扔进去的任务先执行（LIFO，后进先出，像堆栈）**？
*   人的天然理解是 FIFO（先生成的任务先做完，后续才能做）。
*   **重难点（工程实践中的关键点）**：实现 job system 时，一般（"一般"不一定对）会采用 **LIFO（Last Thing First Out）**，即**像堆栈一样后进先出**。
*   原因：游戏引擎中很多 job 是**前一个 job 做到一半突然产生四五个不同 job**，新 job 执行到一半又产生新 job，彼此是 dependency 关系——**fork 出来的任务不完成，自身就完不成**，因此后生成（更依赖前者）的任务应该优先执行。
*   这正是企业里做并行开发（OPL）时**特别容易犯的错误**。

#### (5) 依赖处理与等待队列（Waiting List）

*   当 worker 执行时**发现当前 job 被 yield 掉**，就把这些被让道的任务扔到一个 **waiting list** 里——这件事由 **scheduler** 负责。
*   worker thread 里的任务**并不是永久占位**：一旦发现某个 job 被 yield，就把它搁置，**立刻执行下一个可以执行的任务**。
*   这样就能把 CPU 尽可能利用起来：被依赖的任务完成后，等待者才能回来继续执行。

#### (6) Work Stealing（任务窃取）

*   **为什么需要**：无论 scheduler 做得再好，它**都无法准确估计每个任务要跑多久**，因为存在三种情况：
    1. 任务的计算本身太复杂（看起来是个函数壳，里面算了一大堆东西）；
    2. 任务要等待 **I/O**；
    3. 任务本身不复杂，但过程中产生了一大堆 dependency。
*   因此必然出现：**有些 worker thread 活已做完、有些还剩很多**。
*   **做法**：空闲的 worker thread 向 scheduler 请求，**把没做完的线程里剩余的任务"偷"过来**，放进自己空闲的队列里执行。
*   工厂经理类比：job system 像一个工厂，有一个经理时刻看着每个工人手上的活儿；工人任务相对独立但彼此有依赖（造鞋：有人刷鞋底、有人做鞋面、有人穿鞋带，还有皮鞋、凉鞋混在一起）；经理不停把部件堆到工人面前、观察工人状态，**尽量保证每个人手上都有活干**，并用 LIFO 方法保证**前导工序做完后再去做后面的工序**。
*   job system 听起来高大上，实际实现（尤其针对游戏这种 case）是蛮复杂的，但最核心的思想就是上述这些。

#### (7) Job System 的价值、优势与挑战

*   **本质**：一种更彻底地运用多线程/并行化编程思想的方式，**充分压榨利用所有 CPU 资源**。
*   **未来趋势**：核会越来越多——x86 架构的 8 核、16 核、32 核一定会发生；ARM base 芯片核也越来越多（因为"不能做得太快、要降低功耗"），job system 会是未来的一个重要实施方式。
*   **优势**：
    *   非常容易实现任务的 schedule（调度）；
    *   很容易处理任务之间的 dependency；
    *   不像 task graph 需要在程序启动前傻傻地不断定义 task 和 dependency（写起来很难受）；
    *   当然 task graph 也有用——现代引擎/平台中**一些大模块之间的 dependency 还真得用它来定义**；
    *   但**一帧之内产生几百、上千、上万个 job 时，只有 job system 能高效解决**；
    *   每个 job 的堆栈独立、彼此不干扰；
    *   基于 coroutine 架构，每个 worker thread 对应一个物理核，**不存在 context switching**——只要不触发硬件中断，效率非常高。
*   **挑战**：
    *   C++ 原生不支持 fiber，**必须自己实现一套 coroutine 机制**；可以用 boost，嫌 boost 太大就把它的代码抠出来，不同平台实现方法不一样；
    *   真正实现（尤其实现 job system 底层）挑战非常大；
    *   对上层业务逻辑开发者完全透明：开发者觉得"任务扔进去、中间 fork 一个 job 就出来了、结果就拿到了"，可以尽情写；跑起来用 profiler 一看，**CPU 像小砖头一样垒得整整齐齐**，job system 的 profiling 特别"满足强迫症患者"（如老师本人），有种拼花拼图的快感；
    *   但实现一个**非常鲁棒、稳健**的 job system，要求对**多线程硬件的底层开发**非常了解。

### 12. ABA 问题（ABA Case）

*   **核心概念**：硬件/底层开发中会产生很多 data racing 挑战，甚至出现非常难以发现和 debug 的问题，ABA 就是典型。
*   **场景还原**：
    1. 内存中分配了一段空间；线程 A 认为该空间无效，要释放它，之后检测释放是否成功——若不成功就按成功处理、后面把这块东西干掉；若数据没被释放就继续原逻辑。
    2. 但另一个线程发现这段内存空了，发起新的分配任务；**heap（堆）很可能把那段内存地址重新分配出去并复用**，而且"好死不死的"在那个位置放的数值又恰好一模一样。
    3. 于是后续检测时发现"数据其实没有变化"，没有检测到它已经被改动过。
*   **定义**：在一个线程里，前一段代码对数据做了一些修改，后面检测时发现它"没变"、逻辑走向完全另一个方向；**但实际上在两次访问之间，另一个线程已经把这个数据改过去一遍、再改了回来**。
*   **危害**：产生非常深刻、非常难以发现的 bug——**可能跑几天几夜，突然系统异常挂掉，几乎无法复现**（内存分配是随机过程，还得随机到数据恰好被写回原状态），导致**大量检测函数全部失效**。

## 二、 重点术语与概念解析

### 1. DOP（Data Oriented Programming，面向数据编程）

*   **定义**：本节课主题之一，强调以数据的组织、访问方式为中心设计程序，配合 job system 提高并行度与 cache 利用率。
*   **应用/注意点**：课程实际讲述顺序与标题相反（先讲 job system 相关的并行基础，DOP 留待后续）；本节主要打基础。

### 2. Job System（任务系统）

*   **定义**：现代游戏引擎的并行执行框架：把任务（job）塞入 fiber/worker，由 job scheduler 统一调度，按 dependency、priority 与 LIFO 策略执行，并支持 work stealing。
*   **应用/注意点**：适合一帧内几百~上万个 job 的场景；实现底层要求极强的并行与硬件功底。

### 3. Preemptive Multitasking（抢占式多任务）

*   **定义**：调度者自行决定随时把运行中的任务调出/调入，高优先级任务可打断当前任务（需触发中断）。
*   **应用/注意点**：Windows 等通用操作系统采用；代价是上下文切换开销。

### 4. Non-Preemptive Multitasking（非抢占式/协作式多任务）

*   **定义**：任务不被主动打断，除非它自己让出执行权。
*   **应用/注意点**：控制力强；任务写坏会卡死全体；常见于实时性要求极高的系统。

### 5. Thread 切换 / Context Switch（线程切换 / 上下文切换）

*   **定义**：操作系统在多个线程间切换执行上下文的过程，涉及中断（约 2000+ CPU cycle）与缓存失效（1 万~100 万 cycle 的内存重载延迟）。
*   **应用/注意点**：代价极高，是 fiber/job system 想方设法避免的对象。

### 6. Data Racing（数据竞争）

*   **定义**：多个线程对同一数据并发读写，导致读到的值与判断/操作时不一致。
*   **应用/注意点**：一切并行问题的核心根源；须通过同步、原子操作或任务依赖规避。

### 7. Critical Section（临界区）

*   **定义**：一段不允许被其他线程同时执行的代码区域，进入后须完整执行完毕。
*   **应用/注意点**：实现手段有 `critical section`、`mutex`、`semaphore` 等；属于阻断式编程，易引发死锁与任务失败连锁问题，大型系统应少用 lock。

### 8. 原子操作（Atomic Operation）/ Lock-Free

*   **定义**：由硬件保证对单个内存值（integer/boolean）的 Load/Store 等操作不可被并发侵占。
*   **应用/注意点**：相关指令包括 ARM（Read-Modify-Write）、CAS（Compare And Swap）等；可避免死锁，但原子变量间的等待会造成 CPU 空洞。

### 9. Wait-Free

*   **定义**：通过严格数学证明保证所有线程在有限步内完成的并行结构，等待几乎为零。
*   **应用/注意点**：实现复杂，行业仅对特定对象（如队列）有成熟解法；用于高频通讯协议等性能 critical 场景。

### 10. 编译器乱序（Out-of-Order）/ Release 与 Debug 差异

*   **定义**：编译器/CPU 在不改变单线程最终结果的前提下重排指令执行顺序。
*   **应用/注意点**：多线程下破坏"按书写顺序"的直觉；Debug 版近似顺序、Release 版可能完全不同；C++11 可显式要求排序但牺牲性能；移动端"模拟器正常、真机崩"常因此而起。

### 11. Locality（数据局部性）

*   **定义**：一个线程访问的数据应尽量集中在同一块内存区域，以利缓存。
*   **应用/注意点**：固定线程架构中拆分重任务时会破坏 locality 并引发 data racing，故难以动态均衡负载。

### 12. Fork-Join

*   **定义**：单线程把一批相似任务 fork 到 worker thread 执行，完成后 join 回收结果。
*   **应用/注意点**：Unreal、Unity 等引擎普遍采用；非彻底并行模型，仍有负载不均与 gap。

### 13. Task Graph（任务图）/ TBB

*   **定义**：以静态图描述任务间 dependency，交给多核自动调度；TBB（Intel Threading Building Blocks）是著名 SDK。
*   **应用/注意点**：适合大型模块间固定依赖；不适合一帧内动态大量产生/等待的子任务。

### 14. Coroutine（协程）

*   **定义**：可让道（yield）、再被激活（resume）继续执行的轻量执行上下文；切换不经过内核。
*   **应用/注意点**：Go、C# 支持良好；C++ 不原生支持，需自己用汇编/boost 实现；分 stackful（有状态，推荐用于引擎）与 stackless（无状态，仅限底层高手使用）。

### 15. Yield / Resume / Invoke

*   **定义**：yield 指协程把执行权让出；resume/invoke 指重新激活协程，从上次让道处继续执行。
*   **应用/注意点**：其正确性依赖 context 的完整保存与恢复。

### 16. Fiber（光纤/纤程）

*   **定义**：Windows 提出的轻量执行单元概念，可作为承载多个协程/job 的"高速管道"。
*   **应用/注意点**：fiber-based job system 通过让每个 fiber/worker 对应一个逻辑核，使线程 swap 几乎为零。

### 17. Job Scheduler（任务调度器）

*   **定义**：全局调度系统，根据各 worker thread 饱和状态分发 job，处理优先级与依赖。
*   **应用/注意点**：job 不直接交给 worker，而是由 scheduler 统一分配，以追求负载均衡。

### 18. FIFO 与 LIFO

*   **定义**：FIFO（First In First Out）先进先出（队列）；LIFO（Last In First Out）后进先出（堆栈）。
*   **应用/注意点**：游戏 job system 工程实践一般用 **LIFO**，因为后 fork 出的任务依赖前者、需优先完成。

### 19. Work Stealing（任务窃取）

*   **定义**：空闲 worker 从其他繁忙 worker 的队列中偷取任务执行。
*   **应用/注意点**：缓解 scheduler 无法预估任务耗时的缺陷，尽量保持所有核满载。

### 20. ABA Problem（ABA 问题）

*   **定义**：两次检测之间数据被另一线程"改过去又改回来"，导致检测函数误判"数据未变"。
*   **应用/注意点**：伴随内存重用出现，bug 极难复现、可能数天后才爆发。

### 21. Mutex / Semaphore（互斥锁 / 信号量）

*   **定义**：同步原语，用于保护临界区/限制并发访问。
*   **应用/注意点**：属于阻断式方案；大型系统中应尽量少用。

### 22. Hyper Thread（超线程）

*   **定义**：一个物理核在逻辑上分为两个核（逻辑核）。
*   **应用/注意点**：一般一个逻辑核对应一个 worker thread。

### 23. Heap（堆）

*   **定义**：操作系统管理的动态内存区域。
*   **应用/注意点**：内存分配/释放/复用过程中可能引发 ABA 类问题。

### 24. Stack Overflow（堆栈空间爆炸）

*   **定义**：函数栈空间不足（递归过深、局部变量过大、协程栈设置过小）导致的崩溃。
*   **应用/注意点**：C++ 常遇到，Python/JS 等很少；设置协程栈大小时需在性能与安全性间权衡。

### 25. VAC（Valve Anti-Cheat）

*   **定义**：Steam 平台的反作弊系统。
*   **应用/注意点**：作弊一旦被报到 VAC，整个 Steam 账号可能受影响——属于"社交化"反作弊手段的典型例子。

### 26. Microservice（微服务）

*   **定义**：把后台业务拆成尽可能干净、单一、尽量无状态的服务单元（邮件、聊天、登录、房间匹配等），基于容器部署。
*   **应用/注意点**：是分布式服务器架构的一种实现方式/设计理念，支持弹性扩容、服务发现与故障隔离；现代 online game 并不完全微服务化，部分服务仍需全局自管理。

### 27. TBB（Intel Threading Building Blocks）

*   **定义**：Intel 提供的多线程并行编程库，task graph 是其核心模型之一。

### 28. Profiling / Profiler（性能剖析）

*   **定义**：抓取程序运行期各线程/CPU 占用情况的工具。
*   **应用/注意点**：多核图上的"空洞"即 CPU idle；job system 的 profiling 呈"砖块整齐"效果。

## 三、 工程经验与避坑指南

### 1. 并行开发的总体心法

*   **线程切换极贵**：一切并行框架设计都要围绕"减少线程切换"展开；job system 选 fiber-based、worker 与核一一对应，都是为了 thread swap 几乎为零。
*   **lock 越少越好**：大型系统里 lock 尽量不用、用得越少越好；job system 中会用到 lock 但极少。
*   **掌握 lock-free 即可**：做引擎不必追求 wait-free（太难、需数学证明），能到 lock-free 层就够了，剩余 gap 交给 job system。
*   **必须建立"乱序"常识**：不要假设变量值符合书写顺序；多线程代码 Debug 正常、Release 崩溃的问题极难排查，要在设计时就防范。

### 2. 并行架构选型建议

*   **固定线程架构**：2~4 核小机器上好使、分得清；但存在木桶效应、无法动态拆任务（locality 与 data racing 限制）、无法适配不同机器核数（双核尴尬 / 八核浪费），经验上浪费约 1/3 算力。
*   **Fork-Join**：清晰、鲁棒，对多线程要求不高时是很好选择；Unreal 用 named thread + working thread 的组合。
*   **Task Graph（TBB）**：适合描述大模块间固定依赖；不适合一帧内动态产生、中途等待的大量子任务。
*   **Job System**：适合现代高核数平台与"一帧上千上万 job"的重负载场景，是未来方向（x86 32 核、ARM 多核）。

### 3. Job System 实现要点与坑

*   **队列用 LIFO**：游戏 job 多为"做到一半 fork 出新 job"的依赖链，后进先出才能保证前导工序优先完成；这是企业做并行开发（OPL）特别容易犯的错误。
*   **依赖与等待**：被 yield 的 job 交由 scheduler 放入 waiting list，worker 立刻执行下一个可执行任务，避免 CPU 空转。
*   **Work Stealing**：scheduler 无法预估任务耗时（计算复杂 / 等 IO / 依赖多），空闲 worker 应主动偷取繁忙 worker 的任务。
*   **底层必须防范所有并行异常**：包括 data racing、死锁、ABA 等；否则系统上线后会在各种奇怪的地方挂掉。
*   **ABA 问题**：与内存分配/复用相关，可能跑几天几夜才随机爆发、几乎无法复现、检测函数全部失效——是底层 job system 实现者最该警惕的问题。

### 4. 排查 bug 的心态与优先级

*   **100% 复现的 crash 是"好 bug"**：QA 能 100% 复现，就一定能修好，不用怕。
*   **最怕"概率性崩溃"**：如"服务器开服三天后有概率挂掉"，几乎无法复现、非常惨。
*   因此写底层并行系统前，**务必把理论功底、基本功练扎实**；否则容易搭出一个"看上去很酷"但业务一压就四处漏风的系统。

### 5. 学习方法建议

*   对并行底层核心系统，**多做形式化推导**——从理论上证明其安全，而不是仅凭经验判断"合理不合理"。
*   多查网上资料：国外开发网站上有大量程序员总结的并行化 pattern，能提前知道在哪些地方会遇到问题。
*   实现协程机制时，实在不行就参考 **boost** 的底层代码（本质是汇编级的寄存器/堆栈保存恢复）。

### 6. C++/协程专项避坑

*   C++ 不原生支持协程/fiber，需自实现或借助 boost。
*   协程栈大小设置是双刃剑：小了性能好但易 stack overflow（递归/大局部变量），大了每次 yield/resume 成本高；需对操作系统调度、内存布局理解透彻。
*   ARM base 平台通常要自己用汇编实现协程；PlayStation 有 native 支持（保密细节）。

### 7. 移动端与跨平台经验

*   "PC 模拟器一切正常、真机崩"大概率是**编译器/CPU 乱序**问题（ARM 尤甚）——不要假设代码按书写顺序执行。

## 四、 Q&A 答疑：上节课问题解答

### 1. 游戏反作弊能不能彻底解决？

*   **答案：不能**（至少老师目前所知是 No，"搞不定"）。
*   这是**全世界所有 online gaming 极其头疼的问题**，本质是"道高一尺、魔高一丈"的动态斗争。
*   常用手段：
    *   **技术层面**：加密等各种方法——但无论用什么方法总有人能破解；
    *   **设计层面**：从设计上尽量避免"作弊能获益"（例如把判定逻辑彻底放服务器，但会影响手感，不再用本地物理等机制）；
    *   **社交化方法（很有意思）**：如 Steam 的 **VAC**——只要在一个游戏里被认定作弊并报到 VAC，整个 Steam 账号都可能受影响；一想到一个作弊导致自己几十上百个游戏不能玩，大部分人就不敢作弊了。
*   结论：反作弊是**长期、艰苦卓绝的斗争**，需要持续不断更新；它**不是纯技术问题**，还需要与社区、玩家联动去解决和发现问题，永远是动态平衡。

### 2. 微服务与分布式服务器架构有什么区别？

*   两者**不是并列的"区别关系"**，而是"概念范畴"的关系：
    *   **分布式服务器架构**：一种标准的、最经典的服务端选型方法。相对于"把所有业务写进一个进程"（那就不是分布式），它是在**多台物理机上用多个进程/线程协同工作、各司其职**。架构形式可以很多：数据库访问与游戏逻辑分离；每个战局形成独立的 game server；把整个游戏世界业务拆成一个一个独立进程/线程——即分布式游戏 server architecture。
    *   **Microservice（微服务）**：一种**设计理念**，是分布式服务器架构的**一种实现方法**。思想是把服务器后台的东西拆成**尽可能干净、单一的业务实施单元**（如邮件、聊天、用户登录、房间匹配都变成独立服务）；早期微服务**尽量争取无状态**（便于扩容、减负、支持弹性变化）；一旦某个服务出问题，可通过**服务发现**发现问题并 spawn 出更多服务；本质是**基于容器**的一种分布式服务器系统实现方式。
*   二者**无所谓高下**：现代 online game 的服务器架构**并不是完全的微服务**——有些服务用微服务架构，有些仍要全局自己管理服务。
*   忠告：真正开始做生产（有性情/上线）系统时，**不要纠结于概念之争**（"甜豆浆 vs 咸豆浆哪个好"），**适合你的场景的方案就是最好的方案**。

### 3. 如何构建一个全球联网对战的战斗系统？

*   **难度**：这个问题若能回答清楚，基本可以到游戏大厂申请**资深开发者职位**了。
*   **核心挑战：全球物理连接延迟**。
*   关键手段：
    1. **分布式部署**：在世界各地都放置服务器；
    2. **服务器间高速通讯**：建设/租用**高速干线（high speed 主干线）**，让全球各机房之间走**专线**、通讯速度足够快；
    3. **认清物理极限**：光速无法超越——中国连美国/欧洲，光传播本身约 **100ms 左右甚至不到**；**真正的延迟大头是无数次的网关路由转发**（不停转发转发）；
    4. **很花钱**：要在世界各地购买或自建专用机房，机房之间用光纤尽可能直连（也有通讯服务商提供的**虚拟专用通道**服务）；
    5. **本地节点**：区域用户不要直接连你的服务器，应提供本地更方便的节点；
    6. **区域网络图谱差异**：举例南美——南美西侧智利沿安第斯山脉（全世界最长、约 1 万多公里，从北美洲一路贯穿到南美洲）东西两侧网络非常隔绝；某些南美国家连亚洲可能比连大陆另一侧还快。所以服务南美要做专门处理：**服务器架在墨西哥还是阿根廷？千万不要放在智利**；与北美是直连还是走其他方式——需要掌握**全球高速光纤分布图**。
*   总结：概念层面并不复杂，但真正实施时需要对全球网络拓扑有深入了解。
