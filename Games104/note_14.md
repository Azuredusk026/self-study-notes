# 游戏引擎 Gameplay 玩法系统基础：事件系统、脚本系统、可视化脚本与 3C 系统

---

## 一、 核心知识点与原理剖析

### 1. Gameplay 玩法系统的定位与挑战

*   **核心概念**：Gameplay（玩法系统）是一个边界模糊、几乎涵盖游戏中一切交互内容的庞杂系统。正如课程组讨论的结论——**"Gameplay 就是一个 everything"**，几乎所有与游戏体验相关的内容都可算作玩法系统，它不像物理、渲染那样有清晰的边界。
*   **为什么玩法系统难做**：做 Gameplay 的工程师是"杂学家"，需要与动画、特效、音效、UI、渲染等所有系统对接，才能满足设计师的需求，典型场景是"**设计师动动嘴，程序员跑断腿**"。

#### (1) 挑战一：需要与各个系统协作（系统 Talk 能力）
*   一个简单的"有打击感的战斗玩法"就需要联动：
    *   **动画系统**：动作与打击感的动作表现；
    *   **特效系统（Particle/VFX）**：打击感的视觉核心；
    *   **音效系统（Sound Effect）**：命中音效；
    *   **控制（Control）系统**：手柄、鼠标键盘输入；
    *   **UI 系统**：暴击、"Double Kill"等屏幕提示；
    *   **渲染系统**：实现"卡帧 / 打击帧"（Hit Stop）——把画面瞬间卡住以强化打击感。
*   **Gameplay Engineer 的角色**：不必亲自实现上述每个系统（各有专职工程师），但必须能调用它们、与所有人沟通，才能满足设计师需求。

#### (2) 挑战二：玩法多样性带来的可扩展性要求
*   游戏类型多样：RTS、FPS、ACT 各不相同；同一款游戏中玩法也极其丰富，如《巫师》里的核心战斗、昆特牌、《荒野大镖客》的丰富机制；网游中更有抛绣球、踢足球、吃鸡、打牌下五子棋、科举考状元等玩法。
*   因此**玩法系统的架构可扩展性要求极高**，引擎侧不能写死具体玩法。

#### (3) 挑战三：快速迭代
*   例证：**堡垒之夜（Fortnite）**最初是末世题材生存类 MMO（PvE），EPIC 老大 Tim Sweeney 决定转型吃鸡（Battle Royale）后，团队**两个月**就做出了新模式。
*   对比：Rendering / Animation 的一个 feature 往往要半年到一年以上（算法复杂、需与美术反复打磨流程），而 Gameplay 通常以几天、几周为迭代周期，少数极复杂的玩法才做数月，且通常拆成很多个小 Sprint（突击）迭代。
*   **结论**：引擎侧必须支持玩法系统的快速迭代，总结为"**要便宜、量又足**"，才能支撑丰富游戏体验。

### 2. 事件系统（Event System）：GameObject 间通信的基础

*   **核心概念**：玩法的基础是游戏世界中的 Game Object 之间能够相互通信（"互相写信"）。如果通信被写死为 `if else if else` / `switch case` 分支循环，代码将无法维护，因此引入 **Event / Message 机制**（老师强调：虽然常叫 Event 系统，但引擎里经常写成 `Message`，更有物理实体感）。
*   **设计范式**：**Publish–Subscribe Pattern（发布—订阅模式）**，即"发行者与订阅者"模式：有人负责发布信息，一群人注册订阅感兴趣的信息。比喻：每个人都出校园小报，读者订阅自己喜欢的小报。
*   **三个核心组件（Key Component）**：
    1. **Event Definition（消息/事件定义）**：消息的类型与数据结构；
    2. **Callback（回调函数）**：消息到来时的处理函数，需预先注册；
    3. **Event Dispatcher（事件分发器）**：相当于物流公司，负责消息的分拣与派送，把事件送到各接收者（Listener / Subscriber）。

#### (1) Event 的定义
*   **Event Type**：最简单方式是枚举类型（看起来像字符串，本质是唯一标识号）。早期引擎由程序员手打定义 100 种 event；但到后期 **event 的 type 也需交给设计师创建**（因为 90% 情况下玩法不是程序员决定的，如"大 Boss 残血进入第二段状态"这类消息无法预知）。
*   **Event Arguments / Payload**：事件携带的数据，如爆炸事件需要"爆炸地点、伤害数值、伤害类型"。
*   **最简单的实现（面向对象派生）**：定义一个 Event 基类，其他事件继承它并定义各自数据类型。如果整个玩法层都用 C++（或纯面向对象语言）写是可以的，但真实场景中——**设计师每改一次 event，引擎代码就要重新编译一遍，非常麻烦**。
*   **可扩展的 Event 定义**：真实引擎必须允许设计师在**核心引擎代码之外**扩展 event 定义。实现途径包括：
    *   用纯数据方式定义（在工具链与玩法系统中）；
    *   可视化方式定义（如 UE 蓝图），实际生成 C++ 代码，引擎运行时（Runtime）可以把新编译的 C++ 代码当作 DLL **注入**引擎；
    *   在上层包一层其他语言接口（如 C#，易于动态挂载扩展）；
    *   用脚本语言定义 event。
*   **要点**：**Event 定义的可扩展性本身就是一件不简单的事情**，值得深入设计，且与后续系统（脚本、可视化脚本）密切相关。

#### (2) Callback 注册与对象生命周期
*   **命名注解**：Callback 直译"回调函数"，老师更喜欢 `invoke`（激活/触发）的感觉——提前准备一堆小的功能模块（piece of code），当某类消息来了就把对应处理段"激活"。注册即建立"某类消息 → 某个 handler"的对应关系，如收到 `Damage` 事件就调用伤害处理 handler；收到 `Reloading` 消息就触发装弹操作。
*   **最大的坑：回调的注册与执行在时间上分离**。先注册后执行，中间间隔内可能发生各种问题，核心是**对象生命周期（Lifecycle）与回调函数安全性**。典型故障：
    *   一个注册了伤害处理回调的对象，在下一帧已被销毁，此时旁边手雷爆炸触发回调，就可能调用到**野指针（Dangling Pointer）**，导致系统出错甚至崩溃。
*   **两种引用（Reference）解决生命周期问题**（现代语言中 `weak pointer`、`shared_ptr` 等 smart pointer 都在解决同一问题）：
    *   **强引用（Strong Reference）**：回调注册后，被引用对象不能被删除，否则下次调用会崩溃。保证引用安全性，但**对象真正该销毁时因被引用而无法释放，内存会越来越大（泄漏）**，现已少用。适用场景：**拥有 / 包含关系**，如父物体（房间）不销毁，子物体就不能销毁——表达一种内存锁定关系；老师当年学习时把它理解为 `persisted`（拥有控制权）。
    *   **弱引用（Weak Reference）**：对象可以被删除；当调用引用时，只需额外加一步**判断对象是否已被删除（是否失效）**。若 owner 已消失，则指针无效，直接跳过处理并把自己置为无效，方便资源释放。适用场景：**非拥有关系**，如"当前所有可见敌人"的缓存列表——敌人可能在几帧内已死亡并被 GC 回收，攻击目标引用用弱引用最合适。
*   **工程要点**：游戏中 GO 之间、Callback 与 GO 之间的强/弱引用两种都很有用，**必须用对，千万不能混淆**；Callback 注册尤其多用弱引用。
*   **两难问题**：真实引擎中一个游戏对象由几十个系统用不同逻辑操作（一会儿生一会儿死），任何系统使用时都不能假设对象一定有效；但每次都做大量有效性判断又会让引擎变慢。

#### (3) Event Dispatcher 与消息分发策略
*   **最朴素的分发方式（不可取）**：每帧产生 N 个消息，每个 GO 有 M 个 callback，共 K 个 GO，则每帧扫一遍的复杂度为 $N \times M \times K$，效率极低；且消息分配/释放内存反复扫描很慢。
*   **立即执行（Immediate Dispatch）的问题**：
    *   **嵌套调用 / 调用栈过深**：如手雷爆炸触发附近手雷爆炸，一层层链式反应，调用栈"深不见底"，debug 时同一名字的函数因对象不同被疯狂重复调用，极难排查；
    *   **长操作阻塞**：如果回调中创建几百个粒子并渲染（粒子系统很费），其他游戏逻辑都在等它做完，导致**帧率突然不稳定**；
    *   **无法并行化**：调用一层套一层，无法在多核（8 核、16 核）机器上并行处理（对比后续的面向数据编程架构）。
*   **现代架构：Event Queue（事件队列）**：把本帧产生的所有事件全部收集（catch）到一个队列，下一帧开始由各机构依次处理。
*   **序列化与反序列化**：每个 event 类型不同、数据不同，存储时希望放到一块连续内存（block of memory），把几百个 event 拍成一块内存块，再用反射描述（上节课讲的代码生成/反射）反向拆成一个个 C++ 结构。**反射在 event 系统中的应用非常多**——拿到反射描述就知道每个数据结构的内存大小。
*   **内存管理：Ring Buffer（环形缓冲区）**：
    *   预先假设每帧最多同时存 1000~5000 个 event，分配固定大小的 ring buffer，**避免每次申请新内存**，持续重用。
    *   处理完一个事件就把 head 前移；添加新事件把 tail 后移；**head 与 tail 重合即表示 buffer overflow（溢出）**。
    *   溢出通常是"某个对象错误地不停发事件"这类 bug 的标志；此时可对事件流**截断（truncate）**，代价是游戏逻辑可能错误几帧，但**整个引擎不会崩溃**。
*   **消息分类（分而治之）**：现代引擎把 event 按大类分开，各自用独立 ring buffer 和独立 dispatcher：
    *   **网络事件（Network）**：数量多且与其他事件处理无关；
    *   **战斗相关事件（Combat）**；
    *   **动画系统事件（Animation）**：动画常是独立系统。
    *   好处：提升效率；**大幅提升 Debugability（可调试性）**——出错时直接去对应分类队列找（如"此处动画消息怎么没产生"），而不是翻整个 event queue。
    *   原则：理想上不分类也可以，但会导致效率大幅下降，**强烈推荐分类**。

### 3. Event Queue 的固有缺陷与对策

*   **缺陷一：执行顺序无法保证**。引擎中动画、AI、战斗系统的执行顺序常是固定的，但某些业务逻辑希望"先动画后物理再战斗"，或"战斗行为决定动画行为"。统一延迟到下一帧、同类消息集中处理，无法保证执行顺序。写逻辑时必须保证健壮性——**这是游戏 bug 的高发点，至今仍是难题**，有时会为此 hard code 一些东西。
*   **对策：保留多种处理时机（三种方法）**，现代引擎要全部支持：
    1. **Immediate（立即处理）**：真正常见的也有，需要精心设计（如故意塞在某个位置、安全地改数据）；
    2. **Pre-Tick 处理**：下一帧一上来就处理；
    3. **Post-Tick 处理**：本帧 tick 完之后处理。
    *   何时用哪种，要求程序员非常理解系统调用方式，**特别容易产生 bug**；更难的是如何把这种选择"告诉设计师"而让设计师不犯错。
*   **缺陷二：延迟（Latency）**：Event 机制大部分行为在下一帧处理，复杂的递进逻辑（事件 A 触发事件 B 触发事件 C）**每一步慢一帧**。
    *   **打击感反例**：这一帧检测到砍中敌人，按 event 方式下一帧 health 系统结算、粒子飙血才出现，再下一帧屏幕抖动，总共 2 帧≈**100ms** 延迟，打击感明显不对。
    *   **对策**：对实时性要求高、讲究同步的场合，**需要 hard code 直接绕过去**（绕过 event queue），如打击帧反馈必须几乎同一帧渲染到屏幕。
*   **定位总结**：Event Queue 仍是 Gameplay 玩法系统最重要的基础系统（foundation），把第二节课提出的"消息分发处理"概念彻底讲清楚了。

### 4. 脚本系统（Scripting System）：玩法的书写方式

#### (1) 为什么需要脚本：C++ 直接写玩法的三大痛点
*   早期游戏（如用汇编写俄罗斯方块）可以 C++ 硬写，效率最高，但难以为继：
    1. **每改一点玩法，整个引擎必须重新编译一次**（开发效率噩梦，link 半小时）；
    2. **难以热更新（Hot Update）**：游戏发布后出 bug（如"跳起来暴击打不到""装备掉落错误"），推新版本代价巨大，而**热更新**是几乎所有网游的刚需；编译型语言（C++）热更新非常困难，硬 hack 极麻烦；
    3. **玩法最大的用户是设计师而非程序员**：设计师没受过良好编程训练，艺术家也要定制玩法功能，让他们直接改 C++ 极其痛苦。

#### (2) 脚本语言的优势
*   **简单易学易上手**；
*   **热更新方便**：多为解释执行语言，代码更新后逻辑立刻变化（"走到一步看一步"，类似早期 BASIC 语言的解释执行，函数执行前换掉它即可按新逻辑运转）；
*   **沙箱隔离、崩溃自愈**：脚本运行在虚拟机（VM）上，相当于沙箱，脚本崩溃不会搞崩引擎本体，大不了重启该脚本逻辑。典型场景：大型 MMO 服务器端几百个进程（聊天、邮件等）随时可能挂掉，靠"发现服务挂掉→用脚本重新启动并接入"的系统保证玩家几乎无感知，这就是脚本"不会把本体 crush 掉"的核心好处。

#### (3) 脚本的工作原理
*   脚本本质是文本 → 通过自带编译器编译成自定义的 **bytecode（字节码）**，每条 instruction 描述"做了什么操作、哪些数字相加相乘、内存怎么移动"，非常简单 → 形成一段二进制 blob → 由 **虚拟机（VM）** 执行 bytecode → 整体 run 起来。
*   比喻：**在游戏操作系统之上又跑了一个虚拟机**，所以鲁棒；代价是**执行速度较慢**。

#### (4) 核心难点：对象（GO）管理权之争
*   关键问题：**脚本里的对象与引擎里的对象，生命周期（创建与销毁）到底归谁管？** 例如进主城刷出几十个 NPC，交完任务离开后 NPC 是否销毁、由谁销毁，否则内存一直被占用。
*   **流派一：引擎管理对象生命周期**
    *   思路：C++ 引擎效率最高、安全性测试充分，GO 全部由引擎内核管理；脚本访问时需询问对象是否销毁。
    *   问题：C++ 引擎内存管理做不好易内存泄漏；且玩法越复杂，**对象创建/消亡越多由玩法决定**（如扔出道具变成三个小怪物、小怪物砸出的石头），每个对象都要到引擎绕一圈，非常麻烦。
*   **流派二：脚本管理对象生命周期（配合 GC）**
    *   思路：玩法丰富复杂的游戏把 GO 创建与管理交给脚本系统，引擎只引用脚本创建的对象，不负责其生命周期管理。
    *   **GC（Garbage Collection，垃圾回收器）**：几乎所有脚本系统都有，发现对象没人需要就找时间清掉。
        *   **爱它**：省事，不担心野指针、内存泄漏，无脑创建、用完就扔；
        *   **恨它**：算法慢，每次要扫描整个 context 里的引用关系；复杂 Lua 脚本 GC 效率很低，**在复杂游戏产品里 GC 本身可能吃掉整个游戏时间的约 1/10**；与重度脚本型复杂 MMO 团队交流时，核心话题就是"如何优化 GC"。
*   **选择依据（取决于游戏类型）**：
    *   对象数量少但角色细节表现丰富（几十个对象、大量动作和 AI 细节，如欧美单机动作游戏）→ **引擎管理生命周期**；
    *   业务特别复杂、玩法大量产生新 GO（典型如 MMORPG）→ **脚本管理生命周期**，便于创建销毁各类物体。
    *   老师直言：**很难说哪个方法好，各有利弊**，希望下一代引擎设计能彻底解决"对象到底归谁管"这个拉扯问题。

#### (5) 引擎与脚本的两种架构
*   **架构一：引擎调用脚本**：引擎每帧 tick，到特定业务逻辑（如某 component、某玩法）时调用脚本处理。示例：Unity 原生态做法——每个 Component 可以扩展成用 C# 写的脚本。
*   **架构二：脚本包裹引擎（用脚本反向包引擎）**：把引擎变成 SDK 库，提供各种基础服务，**由脚本控制整个 tick 的 flow**。例如脚本对引擎说"这些物体不用 tick animation 了，休息/干掉"，引擎按名单执行。早期著名大作有此架构，现已较少见。
*   **要点**：走架构二必须**认真设计引擎暴露的接口**；两种思路都可考虑。

#### (6) 热更新的实现原理
*   **本质极简单**：修改函数指针。老的函数有函数指针，调用时执行该指针指向的实现；来了新函数，把指针**重新指向新实现**即完成热更新。
*   **注意点（大坑）**：脚本中有大量 local variable、函数局部变量、全局变量（upvalue/global），**热更新时这些变量必须重置或做必要的数据处理**，否则热更不当会导致游戏崩塌。
*   **商业级引擎的残酷现实**：个人开发时"写错大不了重启"，但商业级游戏有上百万玩家同时在线（正在充值、开时装宝箱、打关键 Boss），**热更搞坏可能几千上万人同时追讨**，因此引擎架构必须特别考虑工程上的**鲁棒性（Robustness）**。

#### (7) 脚本语言的选型
*   **游戏引擎是"多语言复合体"**：一个现代引擎会用到十几种语言，每种场景选最合适的——服务器用 Go、脚本层用 Lua、扩展可能用 C#、服务器管理用 Python、底层用 C++，还可能用 Java，前端还要用一些语言。
*   **选型考量维度**：内置库/生态是否丰富（一行指令处理完复杂操作）、执行效率与轻量性（内存占用低）、面向对象封装是否好（免自己管理复杂数据结构）。
*   **Lua**：因《魔兽世界》一己之力带入中国游戏行业。优点：**轻量**、虚拟机非常轻、省内存、效率高、与 C++ 接口效率高；缺点：基本没有内置库、扩展少，很多东西要自己写。
*   **Python**：优点：**库极其强大丰富**、天然面向对象；缺点：**非常重**，虚拟机跑起来可能占几百 MB 内存。
*   **C#**：借助 `Mono` 库与 .NET 官方支持，可将编译型语言用作脚本语言。优点：学起来成本低（会 C/C++ 就易理解）、社区与库支撑强大；越来越多的团队将其作为扩展语言，**Unity 完全依托 C# 的可扩展性，是很 smart 的选择**。
*   **性能对比**：Lua 通常最慢（原生态），Python 也好不到哪去；C# 执行效率高很多。**内存占用**：Lua 最省，Python 最费，C# 相对居中（找到平衡）。
*   **踩坑教训**：老师团队早期接 Lua 时犯过错误——认为 Lua 弱类型难管理，把它改造成面向对象，结果 **Lua 的 GC 变得特别慢**；上了 LuaJIT 后因没按原生态方式写，GC 基本无法加速。**弱类型（Weak Type）语言的问题**：对象无类型，什么东西都能塞、都能调，但反射真正数据时很麻烦，要抠内部结构，效率低。
*   **JIT（Just-In-Time，即时编译）**：如 LuaJIT 非常著名——虽是解释执行，但可一边解释一边编译，下次直接运行机器码。**JIT 理论上可能超过编译语言**：运行时能知道代码执行路径，若存在 99% 情况都不走的分支，JIT 可把这些分支直接优化掉。LuaJIT 比原生 Lua 快约一个数量级。
*   **结论**：设计引擎时需仔细寻找合适的脚本语言（Pillow 引擎未来或将由社区投票选 Lua / Python / C#）。

### 5. 可视化脚本（Visual Scripting）：面向设计师与艺术家的编程

*   **核心概念**：用图形化方式表达逻辑，代表作是 Unreal 的 **Blueprint（蓝图）**、Unity 的 Visual Scripting，现代引擎基本都提供此类功能。
*   **为什么需要**：对非程序背景的开发者（设计师、艺术家）而言，编程成本极高——他们不懂变量声明、生命周期管理，写几行能编译通过的代码都"哭爹喊娘"；且写代码常犯的错（对象类型用错、函数调错）**只有运行时才知道**。可视化脚本通过**各种提示、关系锁定把错误提前屏蔽掉**，极大方便艺术家与设计师创造玩法。

#### (1) 可视化脚本的构成要素（对应编程语言要素）
*   一门编程语言通常包含：**变量定义、函数、表达式（加减乘除、调用函数）、语句（执行动作）、控制流（if/else）、函数（打包操作复用）、类（数据+处理打成闭包）**。设计可视化编程系统就要对应实现这些要素。
*   **变量**：
    *   **类型**：布尔、int、颜色、向量等；几乎所有可视化编程语言都用**不同形状或颜色的引脚（Pin）**定义数据类型，避免错误数据接入输出——这是对艺术家最友好的点，"看到绿色就接绿色"即可。
    *   **作用域（Scope）**：变量是本地临时计算用，还是来自外部（角色的血量跟角色相关、世界温度跟整个世界相关），角色的血量变化不影响其他角色，更不影响世界温度。
    *   **类型转换**：float 与 int 等可直接转换的类型，系统会自动加类型转换器。
    *   **调试辅助**：运行时鼠标悬停可看到节点数值。
*   **语句 / 动作（Statement）**：几乎所有可视化语法（state machine、蓝图）都用**三角形符号**表示要执行的语句/动作，执行完再走下一个 flow。例：`Print as a string` 在控制面板打印一行字；更复杂如"让屏幕相机抖三抖"。**真正的执行 flow 靠语句走**。
*   **表达式**：加减乘除、大小比较、乘法等，都有巨大符号明显显示（highlight）。
*   **控制流（Control Flow）**：比较大小、依次执行等；需区分**数据的比较**与**执行的比较**两种。
*   **函数**：高级语言引入函数前代码从头写到尾；函数把一系列操作打包，抽象出输入，**执行入口只有一个、出口可以有多个**，形成"接电单元"。可视化系统同样支持。
*   **类（闭包）**：数据与处理打包在一起的体验对应类概念。**一个 Blueprint 非常像一个类**：内部定义 local variable，可设为 private（只能自己看到）或对外可见。
*   **结构理解**：Unreal 深受 C++ 思想影响，其 Blueprint 体系结构**就是 C++ 概念用图形化方法表达**；一旦理解这个基础结构，做一个简单的类 Blueprint 系统难度并不大（有 WPF 方便做 UI、又懂脚本语言，就能搭简易可视化编程语言；如叙事结构的 Story Flow 系统也可用此法实现）。

#### (2) 可视化脚本的辅助功能（生产力工具的本质）
*   **快速节点测试**：鼠标移上去快速测试节点；拖出一个点后直接给出提示（补全）。
*   老师强调：**引擎的本质是生产力工具**——引擎好坏不由功能多少决定，而是**由别人用起来的效率决定**，让人用起来效率高是门槛很高的事。做完基础功能再补这些辅助功能，非常必要，能极大提高使用者效率。
*   **Debug 优势**：对象在什么状态时对应节点会被 highlight，鼠标悬停显示各种值。程序员习惯断点+print 数值，对艺术家很难；可视化后调试变得直觉化——老师观察发现，程序员觉得 Blueprint 麻烦，但对无编程基础的人，它**符合所有直觉**。

#### (3) 可视化脚本的缺点（工程实践中的问题）
*   **多人协作 merge 困难**：大型产品若脚本/图由多人同时修改，merge 会变成痛苦问题。代码 merge 相对简单（可用 Beyond Compare 之类工具，语义变化清晰），但**图的节点增删、移动后的 merge，即使能 merge，语义已没人能讲清楚**。
*   **可读性差**：代码是线性的、可分块（函数定义、类定义、分文件），清晰易读；而商业级游戏的图"像一团乱麻"，除非创作者本人，接手者根本看不清怎么用。
*   **工程实践共识**：国内大型商业产品团队用带可视化编程的引擎（如 Unreal）时——**原型（Prototype）阶段用 Visual Scripting 极快**；**一旦进入产业化生产，工程师一定把它改成 C++ 原生代码或换其他脚本语言**，原因：(1) 便于管理和 merge；(2) 早期可视化脚本语言执行效率低，希望用更快的语言。

#### (4) Visual Script 的本质
*   **记住一个概念：Visual Script 与脚本是同一回事（一模一样的东西）**。图（Visual Graph）可以直接编译成一个脚本代码（Lua 脚本或 C# 脚本），前面所有逻辑不用动，即可执行。
*   现代引擎很多不再走脚本一步，而是**图 → 机器码 / bytecode**，效率更高；但若想增加中间层的 Debug 能力、少写代码，可走"**图 → 脚本 → 机器码**"，效果完全一样。
*   **复杂度认知**：实现一个**简单**可视化编程系统，一个人几个月能做出；做一个**商业级可用**的，一群人干一两年很正常（如 Unreal Blueprint 迭代多年仍在快速演进）。
*   **扩展性挑战**：要在可视化系统里定义新 event、扩展游戏功能、兼容其他脚本，要求系统做得非常复杂。

### 6. 3C 系统：Character（角色）、Control（控制）、Camera（相机）

*   **核心概念**：3C = **Character, Control, Camera**（角色控制与相机）。它是玩家对游戏世界感知的最直接来源，决定游戏体验的最直接部分（不是所有玩法的核心，而是体验最直接的来源）。最佳学习案例是《双人成行（It Takes Two）》，老师认为其 3C 比很多 3A 大作做得还到位。

#### (1) Character 角色系统
*   **不是指角色模型/动画**，而是角色的**移动、战斗、血量（Health）、技能魔法体系**等反馈系统。
*   **移动的细节**：小引擎里移动就是前进/左右/加速/减速，但 3A 游戏角色移动细节极多——障碍物、上坡下坡、走着突然停下、穿过门、面前小坎，都要响应，否则角色像机器人一样僵。
*   **与环境互动**：走到冰面变滑冰、跳入水中行为改变、在沙地/雪地产生不同音效与粒子效果；与地形（Terrain）系统、音效、粒子系统交互。
*   **与物理系统关系**：如滑翔时模拟空气流动（airflow），既要有控制又要有物理输出。
*   **实现方式：状态机（State Machine）**。动画系统里的 **ASM（Animation State Machine，动画状态机）** 的每个节点内部又可以是一段脚本系统——动画切换时上面挂载很多复杂业务逻辑。好游戏的 Character 系统是用大量动画脚本/图（Script Graph）内嵌大量逻辑形成的综合结果。
*   **引擎侧的做法**：引擎能提供物理、动画、脚本系统，但**关键是设计时允许这些系统之间的状态互相通讯，具体通讯逻辑开放给设计师定义**，才能产生丰富的角色行为系统。

#### (2) Control 控制系统
*   **核心任务一：处理各种各样的输入设备**：方向盘、手柄、鼠标键盘、飞行模拟器设备、VR 手势等。输入设备与游戏并不直接关联，Control 系统要把设备 input **翻译成真正的 Gameplay 行为**，不同玩法感受不同。
*   **细节在魔鬼中：瞄准（Aim）与射击的完整链路**：
    *   右键按下瞄准 → 状态改变 → 相机 UI 聚焦（渲染课讲过望远镜效果：**把 FOV 变小**，相机位置变化）；
    *   左键按下射击 → 产生 `Aim` / `Shoot` 事件 → 行为变化。
    *   **吸附效果（Aim Assist / Magnet）**：准星移动到目标点附近时触发吸附。引擎侧需开放编辑器交给设计师/艺术家配置：**定义哪些东西是目标、脚本判断准星与目标夹角小于多少度时触发吸附，且吸附不是一瞬间而是一个过程**。
    *   **为什么需要吸附**：主机射击游戏大多带或多或少的吸附系统。眼睛看到目标 → 反应到手 → 手柄传输到主机 → 主机处理，**中间 latency 可达一两百毫秒**，且移动有惯性，不做吸附基本套不中任何人，更别提枪枪爆头。吸附系统是 Control 系统非常核心的设计。
*   **核心任务二：反馈（Feedback）**：
    *   手柄**震动（Haptic / Vibration）**：如《双人成行》的打击感；高级飞行摇杆、赛车方向盘有力反馈（Force Feedback）。
    *   鼠标键盘的反馈：**RGB 背光**——游戏紧张/残血时键盘背光变红，用光效提供代入感。
    *   **游戏是主动媒体（Proactive Media）**：电影是被动媒体（Passive Media），做啥看啥无反馈；游戏精髓在于**游戏世界与玩家行为之间的互动反馈**，Control 正是解决互动最核心的系统。
*   **多态输入**：同一按键在不同环境下产生的操作可能完全不同，程序员无法控制，只能在引擎提供接口，让设计师/艺术家用**可视化脚本或脚本系统**定义不同行为。用户输入一定是多态的：可以是**组合键（Chord）**、也可以是一串按键序列（街霸的搓招序列）。
*   **地位认知**：Control 系统常被低估——不是"按下什么键做什么事"的直译，**真正的 3A 手感（丝滑手感）正是源于 Control 系统**，它决定整个游戏的手感。现代设备越来越注重对用户的多生态反馈（如 PS5 手柄自带小喇叭和麦克风，恐怖游戏里突然响起吓人一跳，还能与其他玩家语音）。
*   **引擎侧支撑**：吸附、反馈等都需要工具系统、脚本系统提供相应数据编辑功能，交给艺术家配置。

#### (3) Camera 相机系统
*   **朴素认知**：相机系统=设定位置 POV + 张角 FOV，确实就这么简单；但好的游戏相机**并不是固定死绑在角色身后某固定长度**，跑动/行走时相机距离远近都会变化——这才是精妙之处。
*   **弹簧臂（Spring Arm）**：第三人称视角左右动时保证相机尽量不穿墙。处理麻烦：有时不能穿墙，有时可以穿墙但墙变透明，各种小细节。
*   **聚焦模式（Focus）**：进入聚焦时相机更聚焦（FOV 变化）。
*   **Camera Cage / Camera Track（相机笼/相机轨道）**：设计师精心定义角色在什么状态下相机的参数与位置，空间上可视化出来像一个奇怪形状的笼子。**相机表达一种非常强的人的主观感受**：恐惧时瞳孔放大、FOV 变小更聚焦眼前敌人；放松时视野更宽泛。Camera Cage 让设计师有能力精准表达人的主观感受，隔着屏幕传递身临其境的紧张感与代入感。
*   **相机效果（Camera Effect）**：打击感用到很多相机技术——屏幕震动（抖屏）、打中瞬间全屏白闪/黑闪等，需开放给设计师。
*   **相机管理（Camera Manager）**：真实游戏里有很多相机，同一时刻看似只有一个，其实在多个相机间来回切换：
    *   端枪进入 FPS 模式 → 第一人称相机；
    *   收枪走路 → 第三人称相机；
    *   拎加特林重机枪 → 相机位置变化，左右看视角变化；
    *   急喷（冲刺）、开车、开狙击镜、进入赛车 → 各切换一套相机。
    *   如此简单的过程中已切换三套以上相机；Camera Manager 的**另一重要任务是在相机之间做插值（lerp/interpolate）**。
*   **主观感受（Subjective Feeling）**：表达滑道速度感时通过 **Motion Blur（运动模糊）**、相机抖动、视野放缩，形成身临其境的代入感。角色跑动时相机不是机械绑定，而是**有自己的惯性与逻辑**，否则角色显得很僵。
*   **性价比结论**：渲染课讲过 LUT（Look Up Table）后处理是性价比很高的提升档次手段；**相机系统同样是对提升"大作感"性价比非常高的系统**。
*   **引擎侧支撑**：相机行为定义有很多功能——读取角色速度、调用各种相机效果、调整 FOV、让相机抖动。**引擎必须允许用脚本系统或可视化图（Blueprint 之类）编辑相机行为**，并提供 Camera 系统功能，别人才能在上面开发高质量游戏。

### 7. 玩法系统全景总结

*   行业多年总结提炼出的 Gameplay 骨架：
    1. **Event 系统**：用发布—订阅模式统一游戏内对象之间的通信，让通信有序可管理；
    2. **Scripting 系统**：引擎无法写死的逻辑开放出来，让设计师/艺术家定制玩法；
    3. **Visual Scripting 系统**：脚本太难学时，用可视化系统降低门槛；
    4. **3C 系统**：角色、控制、相机，直接决定体验。
*   **敬畏之心**：要做 SG（卡牌）、FPS、RTS，gameplay 差异非常大，很多上层代码甚至引擎部件都要改。**很难找到一个"一招鲜"的架构覆盖所有游戏**，每个优秀作品在玩法系统上都有自己的想法和突破。这也是为什么游戏引擎并非万能——不同游戏类型有各自的引擎偏好（preference）。

## 二、 重点术语与概念解析

### 1. Publish–Subscribe Pattern（发布—订阅模式）
*   **定义**：一种设计范式，发布者（Publisher）发布信息，订阅者（Subscriber）注册订阅自己感兴趣的信息，双方解耦。是 Event 系统的底层范式。
*   **应用/注意点**：游戏内所有对象通过发布/订阅进行通信，而不是写死的 `if/else` 或 `switch case` 分支。

### 2. Event / Message（事件 / 消息）
*   **定义**：世界中发生的一件事被封装成事件对象，含类型（Type）与数据（Event Arguments / Payload）。
*   **应用/注意点**：类型常用枚举/唯一标识号；数据如爆炸的地点、伤害数值、伤害类型；引擎实现中常写作 `Message`。

### 3. Event Dispatcher（事件分发器）
*   **定义**：负责事件分拣与派送的系统，类似物流公司。
*   **应用/注意点**：配合分类的 ring buffer 将消息高效送至各 Listener；错误时可按类别快速定位问题。

### 4. Callback / Handler（回调函数 / 处理函数）
*   **定义**：提前注册好、当某类消息到来时被"激活"（invoke）的处理代码块。
*   **应用/注意点**：注册与执行分离；必须通过强/弱引用解决对象生命周期安全问题；Callback 注册多用弱引用。

### 5. Strong Reference / Weak Reference（强引用 / 弱引用）
*   **定义**：强引用=被引用对象不能被销毁（拥有/锁定关系，如父物体与子物体）；弱引用=对象可被销毁，调用时先判断对象是否失效。
*   **应用/注意点**：对应 C++ 的 `shared_ptr` / `weak_ptr` 等智能指针；GO 间与回调中两种都要用对；回调场景多用弱引用，否则可能内存泄漏或野指针崩溃。

### 6. Ring Buffer（环形缓冲区）
*   **定义**：固定大小的循环缓冲区，head 前移消费、tail 后移生产。
*   **应用/注意点**：用于管理 event 池，避免频繁申请释放内存；head 与 tail 重合表示 overflow，应截断事件流保护引擎不崩溃。

### 7. Serialization / Deserialization（序列化 / 反序列化）
*   **定义**：把多个事件拍成一块连续内存块 / 从内存块反向还原为事件结构。
*   **应用/注意点**：依赖反射系统知道每个数据结构的内存大小。

### 8. Reflection（反射）
*   **定义**：运行时获取类型结构（字段、内存布局）的能力。
*   **应用/注意点**：Event 序列化/反序列化大量依赖反射；也是小引擎每次编译都要重新生成代码的原因。

### 9. Pre-Tick / Post-Tick / Immediate（三种事件处理时机）
*   **定义**：事件处理的三类时机——下一帧开头处理、本帧 tick 结束后处理、立即处理。
*   **应用/注意点**：现代引擎需全部支持；用错时机是最易产生 bug 的地方；实时性要求高的反馈（如打击帧）需绕过 event queue 立即处理。

### 10. Latency（延迟）
*   **定义**：事件在队列中等待导致的处理时延，事件链每步慢一帧。
*   **应用/注意点**：Event Queue 固有缺陷，打击感等实时反馈场景会因此"掉手感"（两帧约 100ms）。

### 11. Hot Update（热更新）
*   **定义**：游戏运行时动态替换逻辑代码（如修复 bug、更新玩法），无需重新发布版本。
*   **应用/注意点**：网游刚需；实现本质是函数指针重定向；热更时必须重置全局/局部变量状态；平台（iOS 审核、PlayStation 加密）可能限制热更。

### 12. Bytecode / VM（字节码 / 虚拟机）
*   **定义**：脚本文本经编译器生成的自定义指令序列（二进制），由虚拟机执行。
*   **应用/注意点**：虚拟机即沙箱，脚本崩溃不拖垮引擎本体；代价是执行速度较慢。

### 13. GC（Garbage Collection，垃圾回收器）
*   **定义**：自动回收"没人再需要"的对象内存的机制。
*   **应用/注意点**：几乎覆盖所有脚本系统；省事但慢，复杂产品中 GC 可能占用约 1/10 游戏时间；优化 GC 是重度脚本型 MMO 团队的核心话题；把 Lua 改成面向对象写法会让 GC 无法加速。

### 14. JIT（Just-In-Time，即时编译）
*   **定义**：运行时一边解释一边编译，热点路径下次直接执行机器码。
*   **应用/注意点**：如 LuaJIT；能根据实际执行路径优化掉不走的冷分支，理论上可超过编译语言；LuaJIT 比原生 Lua 快约一个数量级。

### 15. Visual Scripting（可视化脚本）
*   **定义**：用图形化节点、连线（图）表达逻辑的编程方式，如 Unreal Blueprint、Unity Visual Scripting。
*   **应用/注意点**：面向设计师/艺术家，通过引脚颜色形状与关系锁定提前屏蔽错误；merge 困难、图可读性差，产业化为可维护代码时通常替换为原生代码/脚本；本质=脚本（图可编译成脚本代码）。

### 16. Blueprint（蓝图）
*   **定义**：Unreal 的可视化脚本系统，被公认为最成熟、最老牌的可视化脚本语言。
*   **应用/注意点**：一个 Blueprint 像一个类；深受 C++ 思想影响，是 C++ 概念的图形化表达；包含变量（类型/作用域）、表达式、语句（三角形符号）、控制流、函数等要素。

### 17. 3C（Character, Control, Camera）
*   **定义**：角色、控制、相机，游戏体验最直接来源的三件套。
*   **应用/注意点**：最佳案例《双人成行》；现代引擎必须提供充分支撑（状态机通讯、输入映射与吸附、相机 Cage / Manager / 效果编辑）。

### 18. ASM（Animation State Machine，动画状态机）
*   **定义**：动画系统内以状态节点与转移条件组织动画切换的机制。
*   **应用/注意点**：每个节点内部又可挂一段脚本系统/业务逻辑；Character 系统常由大量动画脚本/图内嵌逻辑形成。

### 19. Spring Arm（弹簧臂）
*   **定义**：第三人称相机防穿墙的机制，相机与角色之间像有弹簧连接。
*   **应用/注意点**：左右移动时保证相机不穿墙；有时需墙变透明等细节处理。

### 20. Camera Cage / Camera Track（相机笼 / 相机轨道）
*   **定义**：设计师在空间上可视化定义相机在不同状态下位置与参数的方式。
*   **应用/注意点**：用于精准表达"主观感受"（恐惧聚焦、放松开阔）。

### 21. Camera Manager（相机管理器）
*   **定义**：管理游戏内多套相机并根据状态切换、在相机间插值的系统。
*   **应用/注意点**：FPS/第三人称/重机枪/开车/狙击镜等状态各有相机，切换时做插值过渡。

### 22. Aim Assist（瞄准吸附）
*   **定义**：准星接近目标时自动轻微吸附的辅助瞄准机制。
*   **应用/注意点**：主机射击游戏标配，用于抵消约一两百毫秒的输入延迟与惯性；吸附是过程而非瞬间；需引擎提供可配置数据。

### 23. FOV（Field of View，视场角）
*   **定义**：相机张角，决定视野范围。
*   **应用/注意点**：瞄准/聚焦时减小 FOV（如望远镜效果）；放松时 FOV 增大视野更宽。

### 24. Motion Blur（运动模糊）
*   **定义**：物体快速运动时产生拖影的渲染效果。
*   **应用/注意点**：相机系统用运动模糊+抖动+视野放缩表达速度感与代入感。

### 25. SDK / 脚本包裹引擎架构
*   **定义**：把引擎做成 SDK 库，由脚本控制整个 tick flow 的架构。
*   **应用/注意点**：与"引擎调脚本"相对；早期著名大作采用过；需精心设计引擎暴露的接口。

### 26. Passive Media / Proactive Media（被动媒体 / 主动媒体）
*   **定义**：电影等单向输出的媒体 vs 根据用户输入互动反馈的媒体。
*   **应用/注意点**：游戏是主动媒体，Control 系统是"游戏世界与行为互动"的核心系统。

## 三、 工程经验与避坑指南

### 1. 事件系统设计
*   **回调生命周期是头号坑**：回调注册与执行分离，对象销毁后触发回调会命野指针。务必用弱引用并加有效性判断；对象间拥有关系（父子）用强引用，缓存/临时目标（可见敌人列表）用弱引用，**不要用错**。
*   **不要立即分发所有事件**：立即执行会导致调用栈深不见底（手雷链式爆炸）、长操作阻塞（粒子创建拖累帧率）、无法并行化。用 Event Queue 收集后下一帧统一处理。
*   **消息务必分类**：网络、战斗、动画等各用独立 ring buffer 与 dispatcher，既提效又极大提升可调试性（出错直奔对应队列）。
*   **Ring Buffer 溢出要截断**：head/tail 重合通常标志"某对象错误地不停发事件"的 bug；截断可保证引擎不崩溃，代价只是逻辑错几帧。
*   **理解三种处理时机**：Immediate / Pre-Tick / Post-Tick 都要支持，程序员必须深刻理解调用方式，此处特别容易产生 bug。
*   **实时反馈绕过队列**：打击感（飙血、屏幕抖动）等要求几乎同帧呈现的效果，若走 event queue 会慢 1~2 帧（约 100ms），手感明显不对，需要 hard code 直接处理。

### 2. 脚本系统实践
*   **对象生命周期归属要按游戏类型选**：角色少而精（欧美单机动作）→ 引擎管理；玩法复杂、对象海量（MMORPG）→ 脚本管理配 GC。
*   **不要违背脚本语言原生范式**：把 Lua 改造成面向对象后，GC 慢且 LuaJIT 无法加速——**用脚本就要按它的原生态写法写**。
*   **热更前必须重置变量**：函数指针重定向只是第一步，全局/局部变量不重置会引发游戏崩塌；商业级引擎热更必须考虑鲁棒性（上百万玩家在线，出错后果严重）。
*   **选脚本语言看四个维度**：内置库丰富度、执行效率/内存占用、面向对象封装、与 C++ 的接口效率。Lua 轻但库少、Python 强但重、C# 平衡且生态强（Unity 的选择）。
*   **脚本沙箱的实用价值**：复杂 MMO 服务端几百个进程随时可能挂，靠"发现挂掉→脚本重启接入"保证几乎无宕机感知。

### 3. 可视化脚本实践
*   **定位是原型工具**：Visual Scripting 做 Prototype 极快，但进入产业化生产后应替换为原生 C++ 或脚本——图 merge 困难、可读性差，多人协作与管理都成问题。
*   **先做脚本系统再做可视化脚本**：Q&A 建议，支持可视化脚本前第一步先把脚本系统支持好；有了可视化脚本也不要"喜新厌旧"，两套系统都保留。
*   **重视生产力辅助**：引擎的本质是生产力工具，好坏由使用者效率决定；节点拖拽提示、快速测试、悬停看值等辅助功能非常必要。
*   **复杂度预期**：简单可视化编程一人几个月可成；商业级要一群人一两年，且仍在快速演进（如 Blueprint）。

### 4. 3C 系统实践
*   **角色移动细节决定"活"与"僵"**：上坡下坡、小坎、过门、冰面、水面都要响应，否则像机器人。
*   **吸附系统是主机射击手感的关键**：不配置 Aim Assist，一两百毫秒的输入延迟+惯性会让你根本瞄不中人；吸附要设计成"过程"而非瞬移。
*   **反馈不止于手柄**：鼠标键盘可用 RGB 光效；高级外设有力反馈；现代设备（PS5 手柄喇叭/麦克风）注重多生态反馈。
*   **相机不要机械绑定角色**：相机要有自己的惯性与逻辑，否则角色显僵；相机远近距离、FOV 随状态（速度、模式、朝向）变化。
*   **相机是高性价比"大作感"来源**：与渲染课的 LUT 同理；屏幕震动、白闪/黑闪、运动模糊、FOV 放缩都是打击感与代入感的核心手段。
*   **引擎要开放 3C 编辑能力**：状态互相通讯、输入映射、吸附参数、相机 Cage、相机效果，都要用脚本/可视化图开放给设计师编辑。

### 5. 工程管理与组织
*   **玩法迭代要快**：Gameplay 迭代周期是"几天/几周"，一个 feature 两月落地（堡垒之夜转型案例）；设计引擎必须支持快速迭代。
*   **逻辑与表现分离要看游戏类型**：MMORPG（数值结算型）逻辑表现分得开、团队可以很大、效率高（decoupling 越好效率越高）；3A 动作/主机游戏玩家对细节要求越来越高（捡装备、看两眼、发光、走路姿态变化），**逻辑与表现高度耦合难以分开**。
*   **多语言混合是常态**：一个现代引擎会用十几种语言（Go 服务器、Lua 脚本、C# 扩展、Python 管理、C++ 底层、Java、前端语言），各取所长。

### 6. 小引擎（Pillow）相关
*   **每次编译都要全量编译的原因**：反射系统每次编译先调反射 compiler 生成大量 generate code，编译器视为脏代码重新编译；若 schema 定义未变可不触发重编（实现复杂，需时间）。
*   **大型引擎编译是重要工程问题**：百万~千万行代码时分布式 incremental 编译至关重要；老师当年 Hero 引擎编译 30 分钟，找牛人花一年降到 10 分钟（根因：include 一堆类，某些文件一编译就被处理几百上千次）。
*   **选型 CMake 的理由**：开源社区最 popular 的构建工具，功能强大、文档多、支持跨平台；XMake 更简单但暂不更换，先集中精力做好一个版本。

## 四、 课堂互动与 Q&A

### 1. 课程作业通知与提交提醒
*   **作业延期**：第二节课作业（用 LUT 做各种后期效果、"音节模式"视觉特效）与第三节课作业（动画简单混合实现走→跑、简单 control 效果）因同学进入课程时间有先有后、难度较大，**提交时间统一到 8 月 31 日**，与第四节课作业一起收。
*   **建议**：不需要做全部作业，可选自己能上手的题材（做 rendering 的、做动画的，选感兴趣的方向），"很少有人能写全部的游戏引擎"。
*   **提交失败原因**：games 课程提交网站在上传附件后**还要单独点一下提交按钮**，很多同学只传附件没点按钮导致失败；课程官网文档第 9 页有专门教提交作业的说明；课程组小姐姐可通过微信帮提交失败的同学代传。
*   **Pillow 引擎是否做脚本系统**：游戏引擎一定要有脚本系统否则难以扩展；课程组 9 月前专注把课程和引擎做完善，之后可能由课程组或与社区一起为 Pillow 设计脚本系统。
*   **引擎语言构成**：现代引擎是复合体，用十几种语言混合编程，接入脚本系统是第一次感受"混合编程做大型系统"。

### 2. Q&A：接入可视化脚本后是否就不需要传统脚本了
*   原则上可以，但开发者很少这么做。实践中可视化脚本作为**早期 Prototype**，开放给艺术家/设计师；**脚本系统一定会保留**——用 Unreal（可视化脚本做的最好的引擎）的团队也一定会再开发一套自己的脚本系统。
*   两者**不是替代关系**：脚本在有些时候效率更高、更好维护；可视化脚本在有些时候够用且方便非程序员使用。
*   **建议**：先支持脚本系统，再支持可视化脚本；有了可视化脚本也建议两套都保留。

### 3. Q&A：未来平台是不是趋向于禁止热更
*   传统 PC 时代可方便热更一切，尤其 MMO（魔兽世界等）没有热更基本没法运行——复杂产品一定会有想象不到的问题。
*   但现有平台限制明显：**iOS 平台**为防止审核后注入不受审核的新内容而禁止热更，做 online game 的开发者非常痛苦；**主机平台**（PlayStation、Xbox）因游戏加密过程只受平台控制、存在安全性问题，热更困难——老师团队曾花很久与平台方沟通"online gaming 非常需要热更"。
*   未来有两种可能：平台越来越封闭，或大家逐渐明白超复杂游戏离不开热更而开放授权。**作为游戏/引擎开发者，老师希望平台开放、热更越来越方便**，因为热更对游戏非常重要。

### 4. Q&A：有可能采取"逻辑与表现分离"的方法开发游戏吗
*   游戏开发中大部分时候逻辑和表现是分离的，取决于游戏类型：
    *   **传统 MMORPG（修仙练级打怪）**：表现相对简单（技能打出去、伤害结算），逻辑由设计师团队单独写，表现与逻辑分得非常开；策划像给艺术家下订单——"要这几个特效、每个特效打多远、从低级到高级"，然后配数值、配结算、配音效，数据配好后表现直接调用。**团队规模可以很大，decoupling（解耦）越好开发效率越高**。
    *   **现代 3A / 主机游戏**：玩家要求打击感、动作表现、角色与环境的互动细节，**逻辑与表现关系越来越密切**。玩家不再满足于"递上装备就进背包"，而希望看到蹲下捡起、看两眼、放进背包、装备发光、身上有效果、走路姿态变化。
    *   客观要求引擎能让不同工种（设计师、艺术家、程序）合力把玩法与表现糅合在一起做，对团队和引擎都提出更高要求。
*   **老师个人观点**：未来这类游戏（尤其主机游戏）玩法和表现比较难以分开；3C 不仅是表现，与玩法也高度相关；如果有更好的架构能分开，非常乐意尝试，因为效率更高。引擎不是完美的理想架构，而是**大量妥协、保持各种可能性的工程基础平台**，按游戏类型选取模块强化。
