# 网格数据、缓存与几何处理

网格不是一组孤立的三角形。它是一套拓扑、顶点属性和索引数据。DCC 里的一个“点”进入引擎后，可能因为 UV 缝、硬边或材质边界拆成多个 GPU 顶点。

## Point、Vertex 与 Primitive

不同软件对这些词的定义不完全相同。理解时先看属性属于哪一层：

- **Point** 表示共享空间位置，Houdini 常把位置 `P` 和可共享属性放在这里；
- **Vertex** 是一个 Primitive 对 Point 的引用，适合存每个面角不同的 UV、法线；
- **Primitive** 表示三角形、多边形或曲线段，可保存材质 ID、组和面属性；
- **Detail** 是整份几何只有一份的数据，例如导出设置或管线元数据。

GPU Vertex Buffer 通常没有 Houdini 这种分层。导出器要把所需属性摊平成顶点记录。只要同一个位置对应的法线、切线、UV 或颜色不同，就必须复制顶点。

因此 DCC 显示的点数不等于引擎顶点数。检查资源预算时应看导入后的 Vertex Count，而不是只看建模软件里的面数。

## Vertex Buffer 与 Index Buffer

Vertex Buffer 以固定步长保存 Position、Normal、Tangent、UV、Color、Bone Index/Weight 等属性。Index Buffer 用索引组合三角形，使相邻三角形复用相同顶点。

没有索引时，两个共享边的三角形需要提交 6 个顶点。使用索引后，矩形通常只需要 4 个顶点和 6 个索引。复用能减少顶点数据和 Vertex Shader 重复执行，但前提是两个面角的全部顶点属性一致。

16 位索引能表示最多 65536 个不同索引值，占用和读取带宽更小。更大的网格需要 32 位索引或拆成多个 Section。拆分也会影响 Draw Call、剔除粒度和材质批次。

## 顶点布局

交错布局把同一顶点的属性连续存放，适合一次绘制读取完整属性。分离布局把位置、法线、UV 放入独立 Buffer，适合只读取部分属性的 Pass，例如仅位置的 Depth Prepass。

选择取决于使用方式：

- 主材质 Pass 通常需要大部分属性，交错布局读取直接；
- Shadow、Depth 或计算任务可能只需要 Position；
- 动态更新位置时，分离静态属性可减少上传量；
- 压缩 Normal、Tangent、UV 能省带宽，但 Shader 需要解码。

布局变化也会改变 Pipeline 输入状态。不要为了理论上的字节节省制造大量难以合批的格式。

## Post-transform Vertex Cache

GPU 处理一个索引后，会短暂缓存 Vertex Shader 输出。如果后续三角形很快再次引用这个索引，就能复用结果。

三角形顺序不影响最终拓扑，却会影响缓存命中。网格优化工具会重排三角形和顶点，使空间相邻的三角形在索引序列中也尽量相邻。常见观察指标是 ACMR，即平均每个三角形需要多少次新顶点变换。

顶点缓存优化与像素 Overdraw 的目标可能冲突：

- 按局部拓扑排序有利于顶点复用；
- 按 Front-to-back 或 Cluster 排序可能更有利于 Early-Z；
- 大场景还要考虑 Meshlet、剔除和流送粒度。

应按实际瓶颈选择，不存在对所有 Pass 都最优的唯一顺序。

## 法线、硬边与 UV 缝

平滑法线会在相邻面之间共享或平均方向。硬边需要同一位置保存不同法线，因此会拆顶点。UV 缝同理。

切线空间还依赖 UV 方向和手性。引擎与烘焙器应采用兼容的切线基，例如 MikkTSpace。否则即使 Normal Map 相同，也可能在接缝处出现明暗断裂。

硬边通常应配合 UV 缝。若一个顶点在几何上是硬边，却让两侧共享同一套烘焙纹理插值，Normal Map 很难稳定补偿突变。

## 网格简化

简化不是随机删三角形。目标是在减少几何的同时控制形状误差、轮廓、UV、法线和蒙皮误差。

Quadric Error Metrics（QEM）会为平面约束建立二次误差。边折叠时，把两个顶点合并到新位置，并估计新位置到相关平面的累计误差：

$$
E(\mathbf{v}) = \mathbf{v}^{T}\left(\sum_i \mathbf{K}_i\right)\mathbf{v}
$$

其中齐次位置 $\mathbf{v}=(x,y,z,1)^T$，$\mathbf{K}_i=\mathbf{p}_i\mathbf{p}_i^T$，$\mathbf{p}_i$ 是相邻平面的归一化平面方程。优先折叠误差较小的边，可以逐步得到低模。

实际工具还要保护：

- 外轮廓和明显折角；
- UV 岛边界与材质边界；
- 骨骼权重和关节附近形变；
- 需要保留的 Socket、Pivot 和碰撞关系；
- 植被枝干等影响剪影的结构。

## Retopology 与 Baking

Retopology 解决的是可变形拓扑、面密度和运行时预算。高模细节通常通过 Normal、Height、AO 或 ID Map 烘焙到低模。

Baking 本质是从低模表面沿 Cage 或投射方向查找高模表面，再把高模属性写入低模纹理。常见错误包括：

- Cage 穿入高模，投射到错误表面；
- UV 岛 Padding 不足，Mipmap 后串色；
- 高低模命名或分组错误，互相投射；
- 切线空间设置与引擎不一致；
- 镜像 UV 的切线手性处理错误。

## Bounds、Submesh 与碰撞

Bounds 是剔除、LOD、流送和空间查询的基础。静态网格通常可以离线计算紧致 AABB；蒙皮、顶点位移和 GPU 程序化动画若超出导入时 Bounds，物体会在仍可见时被错误剔除。

解决方法不是无限放大 Bounds。过大的范围会降低视锥和遮挡剔除效率。应根据动画极值、风动幅度或位移参数计算保守但有限的范围，并用运行时可视化检查。

一个网格按材质拆成多个 Submesh，通常意味着多个 Draw。把材质 ID 合并进同一 Shader 可以减少 Submesh，但会增加纹理数组、分支或实例数据复杂度。应同时看 Draw、材质变体和像素成本。

渲染网格也不应直接等同于碰撞网格：

- Hero Asset 可以使用手工低模碰撞体；
- 静态环境可使用简化 Mesh Collider；
- 动态刚体优先使用少量凸包组合；
- 复杂的逐三角形碰撞会增加构建、内存和查询成本。

Pivot、Bounds、Socket 与碰撞体必须共享明确的坐标和单位契约，否则导入后即使画面正确，放置、物理和工具批处理仍会出错。

## 程序化几何的属性契约

Houdini 节点网络的优势不是“节点比代码直观”，而是几何与属性可以经过可重复的数据流。一个可交付的 HDA 应明确：

- 输入几何、曲线和参数的单位与坐标系；
- 必需属性及其 Point/Vertex/Primitive/Detail 归属；
- 输出组、材质路径、碰撞和 LOD 命名；
- 随机种子和确定性；
- 非法输入的报错方式。

尽量用 Group、Attribute 和参数表达选择，避免依赖一次手工 Edit 的硬编码点号。拓扑变化后，点号会改变，后续节点就可能选错对象。

## 检查方法

- 在引擎导入器查看实际 Vertex/Index Count、Submesh 和 Index Format。
- 用 Frame Debugger 或 RenderDoc 检查绑定的 Buffer、Stride 和 Vertex Input。
- 对比 DCC 点数与引擎顶点数，定位硬边、UV 缝和材质边界产生的拆分。
- 检查简化前后的剪影、法线、UV、蒙皮和碰撞，不只比较面数。
- 用固定摄像机捕获不同 LOD，做差分图和 GPU 时间对照。
