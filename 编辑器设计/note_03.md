# 2D 地图编辑器 MVP、证据驱动调试与编辑运行桥接

## 一、核心知识点与原理剖析

### 1. AI 工具变化与可迁移工作流

课堂恢复后先讨论了代码智能体生态的变化。重点不是记住某个模型排名，而是：

- 国外服务可能存在账号风控、网络、付款和 KYC 等使用门槛；实际使用必须遵守服务条款。
- Cursor、Codex、Claude Code、国内模型等在能力、速度、上下文、价格和多模态上各有取舍。
- 不应把生产工作流绑定到一个 Agent 的专属功能。计划、Skill、规则和项目记忆应放在自己维护的工作区，具体 Agent 只做桥接。
- 某一服务不可用时，应能把同一套 Skill 和项目规则迁移到另一个智能体。

### 2. 高质量交付必须经过设计、执行和验证

```text
设计（Design） → 执行（Implementation） → 验证（Verification）
```

- 设计阶段先明确需求、架构和视觉标准。
- 执行阶段按计划实现，复杂任务持续监控。
- 验证阶段通过测试、日志、运行截图或 MCP 操作证明结果。
- 只“生成了代码”不等于完成；没有验证的交付不可认为可靠。

### 3. AI 搭建 UI 的正确约束

- 直接让 AI 在 Unity 中自由搭 Prefab，容易出现引用丢失、布局偏差和层级错误。
- 推荐先用 SVG 生成最终效果图：
  1. 反复修改 SVG，直到人类认可布局。
  2. 把 SVG 作为可比较的视觉标准。
  3. 使用专门 UI Skill 指导 AI 复刻。
  4. 对照截图或运行画面验收。
- UI Skill 需要持续沉淀：首次制作中发现的锚点、字体、Prefab 引用、分辨率和交互问题，都应写回 Skill。
- 如果按图复刻仍不可靠，应由人类完成关键 UI 结构，AI 负责逻辑和机械工作。

### 4. 证据驱动调试的进一步说明

- UI 交互 Bug 和逻辑 Bug 都需要复现证据。
- 复杂问题应清空旧日志，完整执行一遍复现步骤，再把运行日志保存到文件交给 AI。
- 网络联机项目更需要自动日志收集。课堂举例：一局结束后服务器收集同一局所有客户端的运行日志、游戏日志和网络状态，才能定位跨端问题。
- 如果问题简单且代码范围明确，可以静态检查；多次静态修复失败后必须加日志，不能继续猜 API 或猜状态。

### 5. 恢复并验收地图编辑器基础工程

课堂项目因为间隔较久，首先遇到并处理：

- 场景使用了错误相机或同时存在两个相机。
- Runtime 控制脚本丢失。
- Prefab/Scene 引用没有正确挂载。
- 运行一开始报错，导致所有交互看起来都失效。
- 2D 编辑视口却使用了不合适的 3D 相机设置。

恢复后的 MVP 要求：

- 从左侧预制件列表拖出对象。
- 拖拽期间显示 Ghost 预览。
- 在地图中生成对象。
- 选中对象后移动和旋转。
- 右侧 Inspector 显示并编辑属性。
- 保存工程与地图数据。
- 管理多张地图，而不是永远只编辑第一张。

### 6. 编辑工具栏与操作模式

课堂把原本混乱的操作句柄拆为清晰模式：

- Move：移动。
- Rotate：旋转。
- 模式切换按钮显示当前工具。
- 后续增加 Undo、Redo。

发现的问题包括：

- 句柄样式杂乱。
- 拖拽对象的世界坐标错误，曾生成到数万单位外。
- 选中对象后右侧没有属性。
- 点击 Inspector 会取消场景选择，UI 事件互斥错误。
- 撤销按钮存在但历史记录没有真正工作。
- Vector2、Vector3 Drawer 未配置，导致位置等字段不能显示。

### 7. 撤销系统必须贯穿所有编辑入口

课堂加入 Undo/Redo 时发现：AI 之前实现移动和旋转时直接修改 Transform/数据字段，没有通过 SerializedProperty 和 Transaction。

这说明撤销不是最后加两个按钮即可，而是架构约束：

```text
Move / Rotate / Inspector / Drag Create
              ↓
    SerializedProperty / Transaction
              ↓
        History Manager
```

- 所有编辑入口必须走统一修改 API。
- 连续拖动应在 Pointer Down 时 Begin Transaction，在拖动中更新预览，在 Pointer Up 时 Commit。
- 直接赋值会绕开 Patch，Undo 必然失效。

### 8. 多任务并行与模型切换的实践

- 课堂因某智能体额度耗尽而切换到其他模型，并并行修复交互、Ghost、Undo 等问题。
- 小修复可以先让 AI 输出根因；如果解释和人类观察一致，可简化完整计划审查。
- 大改动仍必须看计划。
- 较弱模型出现未读取真实 API 就猜方法名的问题，应在全局规则中要求“调用前先搜索代码/文档，禁止猜 API”。
- 多个 Agent 同时改互相关联文件会产生编译报错和冲突，应限制并行任务的文件范围。

### 9. 编辑器到游戏运行时的桥接

完成编辑端和一个简单 2D Player 运动 Demo 后，需要建立中间流程：

1. 编辑器工具栏增加 Play/运行按钮。
2. 把当前地图数据提交到全局临时上下文或持久数据。
3. 加载游戏运行场景。
4. 运行场景从全局上下文读取地图。
5. 按地图数据实例化所有对象。
6. 生成玩家并开始运行。
7. 后续应提供返回编辑器按钮。

这一步打通：

```text
编辑地图 → 保存/提交 → 切换场景 → 重建地图 → 实际游玩
```

课堂运行时曾出现玩家穿过或掉出平台，根因之一是 Collider 没有跟随图片缩放，需要手动修正或让生成逻辑同步几何和碰撞体。

### 10. 最小 2D 平台游戏底层

- 创建地面和 Player。
- Player 支持左右移动和跳跃。
- 地图数据实例化后，Player 能与地图 Collider 交互。
- 没有背景时移动不明显，但逻辑可先验收。
- 此底层与编辑器必须通过数据中间层连接，不能让运行场景直接依赖编辑器场景对象。

### 11. 验证、单元测试与归档

- AI 主动创建大量单元测试并非坏事，说明它试图形成自验证闭环。
- 测试数量不是核心，关键是覆盖真实行为、能稳定运行并能捕捉回归。
- 当 MCP/运行工具足够时，AI 可以直接启动 Unity、操作流程并验证；工具不足时会退回静态单元测试。
- 每个功能完成后应归档：
  - 更新计划状态。
  - 记录实现结果。
  - 更新项目日志和变更日志。
  - 把新架构或长期规则写入 Memory。
- 课堂演示项目与主项目共享工作区，为避免污染主项目记忆，没有把所有内容写入同一 Memory；实际独立项目必须维护自己的记忆。

## 二、重点术语与概念解析

- **Ghost Preview**：拖拽创建对象时跟随鼠标的半透明预览。
- **Gizmo / Handle（操作句柄）**：移动、旋转、缩放对象的可视控件。
- **Event Conflict（事件互斥）**：一个 UI 区域的点击意外取消另一个区域状态。
- **History Manager**：管理 Patch、Transaction、Undo 和 Redo 的历史系统。
- **Global Context**：跨场景暂存当前工程、地图和运行参数的全局上下文。
- **Scene Bridge**：把编辑器数据传给运行场景的桥接层。
- **Prefab**：Unity 中可复用的对象模板。
- **Collider**：参与物理碰撞的几何边界，可能与渲染图片尺寸不同。
- **Regression（回归）**：新增或修复功能导致旧功能再次出错。
- **Archive（归档）**：任务完成后整理计划、结果、日志和长期知识。

## 三、工程经验与避坑指南

### 1. 现场环境先恢复，再判断业务 Bug

- 相机错误、脚本丢失或启动时报错会让整个编辑器像是“全部坏了”。
- 调业务逻辑前先确保场景能无错误启动、唯一活动相机正确、核心控制器引用完整。

### 2. 不要让多个实现绕开序列化层

- Inspector 走序列化、Gizmo 直接改 Transform，会形成两套数据真相。
- 保存、撤销和运行时加载会彼此不一致。所有编辑必须收敛到同一命令或事务 API。

### 3. 小任务和大任务采用不同审查强度

- 小修复：先看根因说明，确认后快速执行。
- 架构变更：必须有完整计划、决策和验证方案。
- 灵活调整流程不等于省略证据。

### 4. 工具、额度和上下文不是质量保证

- 快模型可能猜 API；强模型也可能因上下文压缩丢失早期要求。
- 规则应要求真实检索、阶段测试和任务归档。
- 额度耗尽时可迁移 Agent，但核心工作流必须保持一致。

### 5. MVP 的完成标准

- 能创建工程与地图。
- 能拖入、选中、移动和旋转对象。
- 能编辑属性。
- 能保存、撤销和重做。
- 能把地图送入运行场景实际游玩。
- UI 美化、更多组件和高级关卡逻辑可后续迭代。
