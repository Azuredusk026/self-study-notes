# AI 智能体开发工作流与编辑器序列化基础

## 一、核心知识点与原理剖析

### 1. AI 编程智能体的组成

现代代码智能体并不只是一个大语言模型，而是由多个部分共同构成：

- **基础模型（Base Model）**：负责推理与生成，是智能体的“大脑”。课堂以 Codex、Claude Code 等产品为例，说明不同智能体会选用不同 GPT、Claude 系列模型。
- **工作流（Workflow）**：规定从需求分析、计划、执行、验证到收尾的步骤。模型能力相近时，工作流往往决定最终代码质量。
- **记忆（Memory）**：保存项目长期有效的规则、正确心智模型和架构事实，使新对话不必重新了解一切。
- **技能（Skill）**：把反复执行的开发流程、模板功能或领域知识封装成可复用指令。
- **工具（Tools / MCP）**：让智能体读取代码、运行 Unity、执行测试、查看日志或操作外部环境。
- **回调钩子（Hook）**：在对话结束、任务完成等事件发生时触发固定提示或检查，可用于自动沉淀经验。

智能体当前所谓的“自我进化”主要还是**被动进化**：人类必须主动审核结果，并把有效经验写回 Memory 或 Skill。

### 2. 用户级规则、项目级规则与记忆

- **用户级规则**位于本机用户配置目录，对所有项目生效，适合语言、通用安全要求和个人工作习惯。
- **项目级规则**存放在项目内部，只约束当前代码库，适合工具要求、代码规范、模块边界和固定工作流。
- Memory 文件通常保存多个主题文档的引用。当用户明确要求“记住某规则”或“以后不要再犯”时，应把结论沉淀为长期记忆。
- Codex 与 Claude Code 的文件名和默认启用策略不同，使用前应确认当前产品的实际规则加载机制；不能假设每个新对话天然继承历史信息。

### 3. 一套完整的 AI 开发工作流

#### 3.1 开启上下文

1. 使用架构级 Skill 加载项目或大型系统的背景。
2. 使用具体模板 Skill 加载当前功能的上下文。
3. 再描述新需求或 Bug。

小项目可直接读代码；大型项目包含十几个系统时，纯靠临时扫描很难建立准确上下文，必须主动分层。

#### 3.2 创建和审查计划

任何非简单任务都应先创建计划。AI 生成代码的速度会很快超过人类逐行 Review 的能力，因此人类主要审核：

- 架构与模块边界。
- 实现方案和数据流。
- 执行前的任务计划。
- 计划中的不确定项与决策。

推荐流程：

```text
描述需求
  → 创建计划
  → 完善计划
  → 处理待决策项
  → 审查最终计划
  → 执行
```

- 如果任务涉及架构升级，整体程序设计应由人类把控，并与 AI 反复讨论，而不是把最终决策完全交给模型。
- 计划不符合预期时，应回到需求描述重新规划，不应在错误计划上继续打补丁。
- 若缺少架构约束，代码会持续“熵增”：依赖越来越混乱，出现 Bug 后越来越难定位和维护。

#### 3.3 执行监控

- 简单任务可以让智能体自行运行。
- 大型任务要观察其思考摘要、文件修改方向和阶段检查是否仍符合原计划。
- 人类在此阶段承担“警察”角色：不代替 AI 写每行代码，但及时阻止偏离范围或架构的行为。

#### 3.4 功能验证与返工

- 结果符合预期后进入功能测试。
- 结果不符合预期且属于整体方向错误，回到需求与计划阶段。
- 只是实现细节出错，则进入 Bug 工作流。

### 4. 基于证据的 Bug 工作流

复杂项目不能只让 AI 静态阅读代码并猜测原因。课堂给出的流程：

1. **添加调试日志**，覆盖关键输入、状态变化和输出。
2. 由人类或 MCP 工具完整运行一次复现流程。
3. 保存无关日志已清理后的完整复现记录。
4. 结合日志和代码定位根因。
5. 输出修复计划并审查。
6. 执行修复。
7. 重新运行测试。
8. 测试通过后沉淀经验。

大型代码库中，增加上下文并不等于一定更准确；上下文过长还可能增加遗漏或幻觉。因此**事实日志比盲目扩大代码读取范围更可靠**。

### 5. Memory 与 Skill 的沉淀规则

#### 5.1 适合写入 Memory 的内容

- 新增或调整后的架构事实。
- 项目独有术语及其准确含义。
- 关键模块之间的依赖关系。
- 已确认的正确心智模型。
- 容易反复误解、每次对话都需要知道的约束。

#### 5.2 适合写成 Skill 的内容

- 重复出现的模板功能开发，例如卡牌、遗物、道具或编辑器组件。
- 稳定的排错、测试、发布或归档流程。
- 架构级上下文加载方法。
- 某一模块的固定开发步骤。

Skill 可以分层：

```text
项目架构 Skill
├── 编辑器系统 Skill
│   ├── 图片组件开发 Skill
│   ├── 文本组件开发 Skill
│   └── 手牌组件开发 Skill
└── 运行时构建系统 Skill
```

Skill 不应一次生成后永久不变；每次真实使用中发现的问题都应反馈进去，持续验证和打磨。

### 6. 编辑器的核心：统一数据编辑

无论地图编辑器、桌游编辑器还是 Unity Inspector，核心都是：

```text
用户 → GUI 控件 → 修改数据 → 保存变化 → 支持撤销/重做
```

问题在于不同对象的数据结构完全不同。如果每个字段都写一套 UI 回调，例如：

```csharp
player.Name = inputField.text;
```

那么换成另一个类或嵌套字段时，整套编辑逻辑都要重写。解决方案是建立**序列化层**。

### 7. 序列化对象与序列化属性

#### 7.1 统一树状结构

任意对象都可以表示为字段树。例如：

```text
Player
├── Name
├── Score
└── PlayerData
    └── Money
```

系统至少需要两个概念：

- **SerializedObject（序列化对象）**：某个原始对象的统一可编辑包装。
- **SerializedProperty（序列化属性）**：字段树中的一个节点，可包含子属性。

数组和字典也要映射到统一的节点规则，只是索引或键的寻址方式不同。

#### 7.2 属性路径读写

编辑器应通过字符串路径寻找嵌套属性并统一读写：

```csharp
serializedObject.SetValue("PlayerData.Money", 100);
object value = serializedObject.GetValue("PlayerData.Money");
```

它在效果上等同于直接赋值，但上层 UI 不再依赖具体类型，因此同一个输入框、滑块和 Inspector 可以编辑任意对象。

#### 7.3 序列化补丁与撤销

- 每次属性变化都生成一个**序列化变化补丁（Patch）**。
- 补丁至少记录：属性路径、旧值、新值和目标对象。
- Apply 使用新值，Undo 使用旧值，Redo 再次使用新值。
- 由于所有对象都使用统一规则，撤销系统不必为每个业务类型单独实现。

### 8. 第一阶段课程作业

借助 AI 完成一个通用序列化器：

- 输入任意普通 Class，不限制为 GameObject，初期不要求继承结构。
- 能转换为 SerializedObject。
- 类的字段转换为 SerializedProperty。
- 支持嵌套属性路径。
- 能统一读取和写入字符串等基础属性。
- 写入可以提交、撤销和重做。
- 更换数据结构后同一套编辑 API 仍生效。
- 用简单 Inspector 和按钮验证，不要求正式美术界面。
- 具体序列化底层可以使用成熟的 Microsoft/.NET 序列化库或 DLL，不建议从零实现完整格式解析。

## 二、重点术语与概念解析

- **Agent（智能体）**：以模型为推理核心，并能使用规则、记忆、技能和工具持续完成任务的系统。
- **Context（上下文）**：当前对话中模型能访问的信息，包括需求、代码、规则和工具结果。
- **Memory（记忆）**：跨对话长期保存的项目事实和心智模型。
- **Skill（技能）**：封装后的可复用流程与领域指令。
- **MCP**：Model Context Protocol，让模型通过标准接口访问 Unity、代码检索或其他外部工具。
- **Hook（钩子）**：在特定事件发生时自动运行的回调流程。
- **Serialization（序列化）**：把任意数据结构映射为统一、可存储或可操作的表示。
- **Property Path（属性路径）**：使用字符串定位嵌套字段的路径，如 `PlayerData.Money`。
- **Patch（补丁）**：描述一次数据修改前后差异的记录。
- **Undo / Redo**：撤销已经应用的变化，或重新应用已撤销的变化。
- **Inspector（检视面板）**：根据对象数据动态生成编辑控件的界面。

## 三、工程经验与避坑指南

### 1. 架构比逐行代码 Review 更重要

- AI 生成量很大时，不要把质量控制寄托在逐行检查；应把精力放在接口、数据流、程序集依赖、计划和验证。
- “让 AI 全权重写并靠自己维护”风险很高。人类不必亲自写完实现，但必须理解系统设计。
- 能交给 AI 的重复劳动尽量交给 AI，包括整理 Skill；人类负责需求、设计、判断和验收。

### 2. Unity 程序集必须明确

- 不要把所有脚本堆在默认程序集的一个 `Scripts` 文件夹中。
- 使用 Assembly Definition 划分模块，并保持程序集之间**单向依赖**。
- 明确依赖能天然限制耦合，避免 AI 随意跨模块引用，代码量增大后仍能维护。
- 双向依赖或所有代码共享默认程序集，会让人和 AI 都难以理解真实边界。

### 3. 序列化不是只用于存档

- JSON 存档也是序列化，但本课重点是把序列化表示程序化，用统一 UI 读写任意对象。
- 不经过序列化层直接绑定 `Player.Name` 等字段，虽然一开始快，但无法扩展为通用编辑器。

### 4. 工具与账号相关课堂说明

- 课堂比较了终端版、VS Code 插件版和桌面版智能体：终端通常能力完整，插件的会话管理更直观，选择取决于工作习惯。
- 老师提醒第三方账号、代理、代订阅和绕过平台限制存在封禁与合规风险；实际使用应遵守服务条款，不应把生产工作流建立在不稳定账号来源上。
- 工具会快速变化，课堂提到的具体模型名称、额度和界面仅代表当时体验，不是永久结论。

### 5. 学习重点

- AI 时代不意味着程序基础无意义，而是重点从“记住某个 API”转向：定义需求、设计架构、审核计划、提供证据、验证结果和沉淀工作流。
- 序列化器是后续属性绘制、历史记录和运行时编辑器的基础，必须真正理解，而不是只让 AI 生成一份无法解释的代码。
