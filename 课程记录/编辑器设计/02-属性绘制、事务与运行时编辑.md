# 属性绘制器、事务撤销与运行时编辑器架构

## 一、核心知识点与原理剖析

### 1. 序列化器作业的验收标准

上一课的序列化器至少应做到：

- 将任意普通 Class 转为 SerializedObject，而不是只扫描 GameObject。
- 将字段转为 SerializedProperty。
- 通过属性路径取得嵌套字段。
- 通过 SerializedProperty 修改原对象。
- 支持提交、撤销和重做。
- 换成另一种数据结构仍能使用相同 API。

初期可以不处理继承，但嵌套对象不能永远省略。具体实现应借助成熟库，并通过 AI 计划和验证完成，而不是纯手写所有底层。

### 2. 从序列化属性自动生成 Inspector

序列化层完成后，前端只需遍历属性树，并按属性信息生成控件：

```text
SerializedObject
  → 遍历 SerializedProperty
  → 匹配 Property Drawer
  → 生成输入框、滑块、枚举、资源选择器等 UI
  → 控件变化写回 SerializedProperty
```

#### 2.1 绘制器匹配优先级

1. **先按字段特性（Attribute）匹配**。
2. 没有专用特性时，再按字段类型匹配默认绘制器。

例如同为字符串：普通字符串使用输入框；带资源选择特性的字符串则弹出资源选择窗口。序列化属性必须能读取原字段上的 Attribute、字段类型、名称和其他元数据。

#### 2.2 基础与自定义绘制器

- 基础类型：String、Int、Float、Bool、Enum、Vector2、Vector3 等。
- 复杂类型：折叠后递归绘制子属性。
- 数组/列表：支持元素增删、重排和逐项绘制。
- 自定义 Attribute：图形化选择、资源引用、ID 下拉框、范围限制等。

把序列化后端与 UI 绘制前端分离后，新增数据类型只需扩展 Drawer，不应修改所有业务页面。

### 3. 从单属性撤销升级到事务

单个输入框变化可以产生一个 Patch，但图形化操作常同时影响多个属性。例如拖动节点可能修改位置、连线、父子关系和列表顺序。

解决方法是加入**事务（Transaction）**：

```text
Begin Transaction
  → 捕获多个属性补丁
  → Commit Transaction
  → 历史记录中只生成一项
```

- 一次 Modify 可以包装单个 Patch，也可以包装一个包含多个 Patch 的 Transaction。
- Undo 事务时按反向顺序撤销全部子补丁。
- Redo 时按原顺序重新应用。
- 事务使蓝图、图形化节点、批量移动和复杂编辑仍能被视为用户的一次操作。

### 4. 编辑器、运行时与逻辑注入层

以 Unity 为参照：

```text
开发者逻辑（C# 等）
          ↓
   中间逻辑抽象层
      ↙        ↘
Unity Editor   Unity Runtime
      ↓            ↑
   产出数据  →  读取并运行
```

自定义桌游或地图编辑器也应采用类似分层：

- **编辑器层**：提供 GUI，写入项目数据，支持撤销和保存。
- **运行时层**：读取编辑结果并运行游戏，不依赖编辑器 UI。
- **中间逻辑层**：定义编辑器和运行时共同理解的规则、组件、命令或脚本接口。

中间层非常重要：若业务逻辑直接依赖编辑器或运行时的具体实现，将来更换脚本语言、运行环境或注入方式时会非常困难。

### 5. 蓝图、脚本与 AI 时代的逻辑入口

- 蓝图/Scratch 式图形逻辑对不会编程的用户直观，但复杂逻辑会产生大量节点，阅读和编辑效率低。
- 运行时 C# 编译可以提供更高上限，但应用已经启动、Mod 已加载时，外部代码修改往往需要重新加载程序集或重启，热更新体验需要额外设计。
- 自创图形语言的数据不是纯文本。若希望 AI 操作它，必须通过 MCP/CLI 暴露创建节点、连线和修改参数等行为，中间存在信息损失。
- 对面向未来的编辑器，课堂更推荐优先提供 Lua、C# 或其他 AI 熟悉的文本逻辑入口，并把图形化作为低门槛补充。
- AI 是否能有效理解和修改逻辑层，应成为编辑器设计的约束之一。

### 6. 面向人类与 AI 的双入口

传统路径：

```text
用户 → GUI → 编辑数据
```

AI 时代可增加：

```text
AI → CLI / MCP → 编辑数据
```

- GUI 在当前阶段仍然重要，因为人类要设计、观察和验收。
- CLI/MCP 使 AI 能以稳定、可测试的命令修改编辑器数据，而不是模拟鼠标点击。
- 如果未来自动化能力继续提升，CLI 的价值会更高，但这不代表当前可以省略 GUI。

### 7. 2D 地图编辑器 MVP 需求拆解

课堂开始用 AI 搭建一个最小运行时地图编辑器，初始布局：

- 工程选择页面：创建工程、打开已有工程、删除工程。
- 每个工程拥有独立目录和数据。
- 进入工程后：
  - 左侧为可用预制件列表。
  - 中间为 2D 世界编辑视口。
  - 右侧为复用序列化器的 Inspector。
  - 顶部为工程、地图、保存和读取操作。
- 项目结构示例：

```text
ProjectFolder/
├── project.json       # 名称、修改时间等工程信息
└── Maps/
    ├── map_01.json
    └── map_02.json
```

### 8. 从宏观需求到可执行计划

课堂演示了完整计划迭代：

1. 描述布局和业务目标，不先拆实现。
2. 让 AI 输出阶段计划。
3. 检查其是否误解左侧资源列表、存储模块和入口页面。
4. 修正“进入程序直接编辑地图”的错误，增加类似 Unity Hub 的工程选择页。
5. 明确点击工程卡片进入编辑器。
6. 要求 AI 输出 SVG 或界面效果图，确认最终视觉和信息布局。
7. 再审查实施顺序：层级结构、存储、视口、Inspector、总结与验证。
8. 把所有决策写回计划后才能执行。

计划上层目标错误时，下面再详细也没有意义。必须先让“最终要做什么”与人类预期一致。

### 9. AI 执行与 UI 搭建试验

- 执行 Skill 应包含：读取计划、补全决策、执行前汇报、分阶段实现、逐阶段验证和收尾。
- AI 可通过 MCP 搭 Unity UI，也可直接编辑 Prefab/场景文件。
- 课堂实测中，MCP 工具缺少设置脚本引用等能力，导致 AI 转而编辑文件；Prefab 容易出现脚本丢失、字体丢失、引用未挂载和布局问题。
- UI Toolkit 使用 UXML/CSS 式纯文本，理论上更适合 AI 生成；旧版 Unity 的 Runtime 支持、美术介入和项目熟悉度仍需评估。
- 课堂项目先得到基础页面，但选择、编辑和运行仍有错误，留待下一课继续。

## 二、重点术语与概念解析

- **Property Drawer（属性绘制器）**：把某类 SerializedProperty 显示为特定 UI 控件的组件。
- **Attribute（特性）**：附加在字段上的元数据，用来改变序列化或绘制行为。
- **Transaction（事务）**：把多个相关修改作为一个不可分割的历史记录项。
- **Runtime Editor（运行时编辑器）**：在最终应用运行时提供给玩家、策划或用户的数据编辑工具。
- **Logic Injection（逻辑注入）**：让用户用脚本、蓝图或其他方式向运行时添加逻辑。
- **UGC**：User-Generated Content，用户生成内容。
- **CLI**：Command-Line Interface，以文本命令操作系统，适合作为 AI 的稳定入口。
- **GUI**：Graphical User Interface，供人类直接观察和交互的图形界面。
- **MVP**：Minimum Viable Product，能跑通核心价值的最小可行产品。
- **UI Toolkit**：Unity 的 UXML、USS/CSS 风格 UI 系统。

## 三、工程经验与避坑指南

### 1. 不要把绘制器和序列化器混在一起

- 后端只负责属性寻址、读取、写入、补丁和事务。
- 前端负责选择控件与用户交互。
- 混在一起会使新增类型、换 UI 框架和单元测试都变得困难。

### 2. 复杂操作必须用事务

- 图形化编辑如果逐字段进入历史记录，用户一次拖动可能需要撤销十几次。
- 事务开始和结束的边界应对应完整用户意图，而不是每帧鼠标移动。

### 3. AI 生成 UI 的限制

- 直接让 AI 操作 Unity Prefab 目前并不稳定，课堂速度甚至不如人工搭建。
- 更可靠的办法是先做 SVG 视觉标准，再让 AI 按图复刻；若仍不稳定，关键 Prefab 由人搭，AI 负责脚本和批量调整。
- 任何重复踩坑都应写入 UI Skill，让下一次生成有可验证标准。

### 4. 技术细节可交给 AI，架构不可失控

- 现在不一定要先学会 CLI 的所有技术栈才开始实现，但必须知道为什么需要 CLI、它处于哪个模块、依赖方向是什么。
- 后续能否维护，取决于接口、单向程序集依赖、日志、计划和测试，而不是代码是否由人亲手输入。

### 5. 课堂模型判断具有时效性

- 老师关于 Codex、Claude Code、Cursor、模型能力、额度和 UI Toolkit 版本的描述来自课堂当时环境。
- 工具选择应重新核对当前版本、许可、Runtime 支持和成本，不能把课堂即时体验当成固定标准。
