# 数据导向设计与任务系统

数据导向设计（Data-Oriented Design）关注“处理哪些数据、按什么顺序访问、如何并行”，而不是先建立对象继承关系。它不是对 OOP 的全面替代。稳定的工具接口可以保持对象化，帧内热点数据则更适合连续布局和批量处理。

## 从访问模式开始

CPU 执行速度和内存访问速度差距很大。一次 Cache Miss 可能让执行单元等待许多周期。优化前先回答：

- 一次更新真正需要哪些字段；
- 相邻迭代是否访问相邻地址；
- 数据是否被多个线程写入同一 Cache Line；
- 分支是否让同一批数据走完全不同的路径。

AoS 把一个对象的所有字段放在一起，适合整对象访问。SoA 把同类字段放在连续数组中，适合只处理位置、速度等少数字段的批量循环。实际系统常用混合布局，目标是贴合访问模式。

ECS 的 Archetype 会按组件组合分组，Chunk 内存放相同布局的 Entity。System 查询需要的组件集合后，可以顺序遍历匹配 Chunk。新增或删除组件会让 Entity 跨 Archetype 搬迁，因此结构变化不适合在热点循环中频繁发生。

## 任务图

任务系统把一帧工作拆成小任务，并显式记录依赖。A 写入位置、B 读取位置时，B 必须等待 A；两个只读任务可以并行。Task Graph 的边表达数据依赖，比按模块名称猜执行顺序可靠。

任务太大会浪费核心，任务太小会让调度和同步成本占主导。常见做法是把批量循环分块，并设置最小粒度。调度器可以给每个 Worker 一个双端队列：本线程从一端取任务，空闲线程从另一端窃取，减少争用。

Fiber 或 Coroutine 允许任务等待依赖时让出执行权，而不是阻塞整个 Worker 线程。它们仍然需要清晰的栈空间、恢复点和生命周期。等待期间保存了指向临时栈数据的引用，会产生难以复现的错误。

## 同步与内存顺序

Mutex 适合保护较长的复合操作，原子操作适合简单状态转换。Lock-Free 只保证系统整体持续前进，Wait-Free 才保证每个参与者在有限步骤内完成。无锁结构还要处理 ABA、内存回收和正确的 Memory Order，不能因为“没有锁”就默认更快。

Release 写和 Acquire 读可以建立 Happens-Before 关系。编译器和 CPU 都可能在规则允许时重排访问。Debug 版本偶然正常不能证明并发正确。

False Sharing 指多个线程修改同一 Cache Line 上不同变量。逻辑上没有共享，硬件仍会反复转移缓存行所有权。按线程分块、填充热点计数或改为局部累积后汇总可以缓解。

## 落地与验证

先用 Profiler 找到真实热点，再记录每个任务的耗时、等待、队列长度和工作窃取次数。验证内容应包括单线程结果对照、不同 Worker 数量、随机调度、长时间压力和关闭阶段。

DOP、ECS 和 Job System 可以独立采用。ECS 解决数据组织和查询，Job System 解决执行调度。把两者绑定为一个不可拆的框架，会增加工具链和调试成本。
