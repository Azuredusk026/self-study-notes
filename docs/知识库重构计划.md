# 个人游戏开发知识库重构计划

> 当前状态：P0、P1 和 P2 已全部完成。正式范围为 `知识库/00-21`，共 70 篇文章；89 份课程笔记的 350 个 H2 章节与 84 个高频概念组已经覆盖，全库审核与确定性复核通过。

## 1. 当前判断

当前正式文章已经完成图形与 TA 主体，公开课程笔记仍按课程顺序保存。C++、数据结构、编辑器设计、游戏 AI、网络和 ACT 等课程包含大量尚未进入正式知识的内容。

本轮保留课程笔记的学习语境，同时为每个有效章节建立正式文章映射。ignored 的 `文字记录/` 只保存在本机，不参与读取、审计、索引和覆盖统计。

## 2. 主要问题

### 2.1 文件粒度处在两个极端

旧百科把 Mipmap、Texture Sampling、UV、Texture Compression 等拆成独立页面，阅读时需要频繁跳转。课程笔记又把一整节课塞进一篇长文。新结构应当以“能完整解释一个自然主题”为单位。

### 2.2 模板反过来控制了内容

旧条目普遍使用“定义、核心原理、用途、区别、误区、相关条目、参考来源”。这些栏目本身没有错，但每篇都强制使用后，就产生了大量相似且空泛的段落。

新笔记不设置统一正文模板。纹理技术可以按采样流程组织，延迟渲染可以按帧流程组织，性能分析可以按诊断过程组织，工具管线可以按数据流和职责组织。

### 2.3 课程资料尚未真正融入知识体系

课程稿主要是独立整理，还需要回答“这段知识最终属于哪个长期主题”。新流程使用章节级覆盖记录，避免简单复制和重复总结。

### 2.4 基础概念之间缺少连接

例如 Deferred Rendering、GBuffer、Light Volume、Tiled Lighting、Bandwidth 和透明渲染应该形成一个连续解释。目前它们被拆开后，容易停留在“知道名词”的程度。

### 2.5 旧规则与新目标冲突

旧 `TA-Encyclopedia/AGENTS.md` 要求每个新增条目使用固定模板，并限制大规模重写。根目录原来没有 `AGENTS.md`。本次已建立根规则，并把旧目录改为迁移来源区。

## 3. 新知识库的结构原则

### 3.1 页面以主题聚合，不以关键词拆分

例如 `纹理技术` 可以自然包含：

- 纹理、Texel、UV 和采样器；
- Point、Bilinear、Trilinear 和 Anisotropic Filtering；
- Mipmap、LOD、`ddx` / `ddy`；
- Wrap、Clamp、Mirror 等寻址方式；
- BC、ASTC、ETC 等压缩格式；
- 常见错误和检查方法。

只有当其中某一部分已经形成独立学习目标或内容明显过大时才拆分。

### 3.2 每个领域有导航页，正文页数量保持克制

领域目录使用一个 README 或同名导航页说明：

- 这个领域解决什么问题；
- 推荐阅读顺序；
- 各文章之间的关系；
- 尚未覆盖的内容。

导航页不重复正文。

### 3.3 不用页数或字数作为硬指标

预计最终正文会显著少于旧百科的 191 页，但不设人为页数目标。判断标准是阅读和维护成本，而不是让目录看起来整齐。

### 3.4 正式知识、来源和过程分开

- 正式知识：按自然知识领域组织；
- 公开课程笔记：直接保存在课程根目录；
- `docs/`：保存审计、迁移表、术语决策、日志和审核报告；
- 私密课程原件：保存在 ignored 的 `文字记录/`，不进入公开流程。

## 6. 文章写法

每篇文章只需要选择适合自己的解释顺序。常见但不强制的组织方式包括：

- 从一帧或一个数据的流动过程展开；
- 从问题、机制、代价和替代方案展开；
- 对几种技术做并列对比；
- 从资产输入到引擎输出说明一条管线；
- 从一个错误现象反推底层原因。

重要主题需要能继续回答一到两层“为什么”。但不要机械生成问答列表。适合思考的位置可以加入少量 `[!question]`。

公式只辅助解释。例如 PCSS 的半影估计可以放在 Blocker Search 的说明旁边，不单独建立“公式”章节。

标题规则：

- 长英文概念优先使用中文加英文，如 `时域采样（Temporal Sampling）`；
- 已经稳定使用的缩写直接使用，如 `MSAA`、`TAA`、`BRDF`；
- 第一次出现时解释英文全称；
- 同一概念只保留一个主名称，其余名称进入别名或术语表。

## 7. 迁移执行阶段

完整执行分为 P0、P1、P2。三个优先级连续执行，中间不等待确认。原阶段 A-G 是每个优先级内部的工作步骤。

| 优先级 | 范围 | 完成条件 |
|---|---|---|
| P0 | 自治规则、完整审计、迁移台账、术语问题、架构定稿 | 每份旧资料都有初步处理结论，新目录和第一批文章清单确定 |
| P1 | 数学、GPU 管线、Shader、光照/PBR、阴影、纹理、颜色、引擎架构、性能分析 | 核心基础能够解释到机制、限制和验证方式，并通过模块审核 |
| P2 | 几何、动画、VFX、光追、工具、编程、AIGC、物理、Gameplay、AI、网络和全库审核 | 所有公开课程章节完成覆盖，正式导航、双链、术语和质量检查通过 |

### 阶段 A：完整资料审计

生成：

- `docs/资料清单与迁移表.md` 或结构化表格；
- `docs/现状诊断报告.md`；
- 重复主题和冲突术语清单；
- 内容缺口清单；
- 二进制课程资料的可读取性检查。

迁移表至少记录：来源路径、文件类型、主题、价值判断、目标文章、状态和备注。

### 阶段 B：架构定稿

根据完整审计复查 00-21 的边界。重点判断：

- 几何与动画是否需要保持独立；
- NPR 是否已经足够成为独立领域；
- 引擎资源系统和工具管线的边界；
- AIGC 是否保持独立；
- 课程内容最适合进入哪个长期主题。

这一阶段确定正式目录、第一批文章和阅读依赖图。

### 阶段 C：先修复核心基础

按依赖顺序重建：

1. 数学、采样与坐标空间；
2. GPU 与光栅化管线；
3. Shader 编译、Variant 和 GPU 执行；
4. 光照、PBR、阴影、纹理和颜色；
5. 引擎渲染架构与性能分析。

这组内容优先解决当前“知道概念，但无法继续解释机制”的问题。

### 阶段 D：扩展专业领域

继续重建几何、动画、VFX、NPR、实时光追、工具管线、编程、AIGC/Agent、物理、Gameplay、游戏 AI 和网络。

### 阶段 E：链接与术语统一

建立真正有意义的前置、对比和依赖关系。清理同义词、重复页面和断链。术语表只负责统一叫法，不重复正文定义。

### 阶段 F：旧结构退役

只有迁移表中相关来源全部有明确结论后，才删除或归档旧目录。每次删除前检查：

- 有价值内容是否已经进入目标文章；
- 目标文章是否记录或吸收了可靠来源；
- 旧链接是否需要更新；
- Git 中是否有清晰恢复点。

不建立大量旧页面跳转。新库直接以最新结构为准。

### 阶段 G：全库审核

检查分类、深度、准确性、文风、术语、链接、资料覆盖和未完成项。审核发现的问题直接修复，并形成 `docs/最终审核报告.md`。

## 8. 外部 skill 的使用方式

`llm-wiki-skill` 适合帮助完成：

- 多格式素材摄取；
- 来源缓存和重复检测；
- 批量处理状态；
- 断链、孤立页和索引一致性检查；
- 后续增量维护。

不直接采用它默认的 `entities/topics/sources` 页面模型，也不允许它自动决定正式目录。该模型偏向实体百科，和本项目“适度聚合的主题文章”目标冲突。

正式使用前执行以下检查：

1. 固定到经过检查的 commit，不直接追随远端最新版本；
2. 在临时目录执行 Windows dry-run；
3. 检查安装脚本、写入路径、缓存格式和删除行为；
4. 只启用素材摄取、来源记录和健康检查等需要的能力；
5. 如果无法与本项目目录规则解耦，则不安装，改用本地审计脚本。

## 9. 审核标准

每个模块完成时至少确认：

- 不存在明显的一词一页式碎片化；
- 不存在无法自然阅读的巨型课程稿；
- 核心主题能够解释问题、机制、限制和验证方式；
- 术语统一，链接有效，没有为了图谱密度强行加链接；
- 没有把不确定的底层行为写成确定事实；
- 文风像个人学习笔记，不像论文、百科生成器或固定模板填空；
- 对应公开课程章节已经在覆盖台账中得到处理。

全库完成时继续检查：

- 断链、孤立页和重复标题；
- 未处理来源和陈旧的 `待补充`；
- 同一概念在不同模块中的冲突解释；
- 课程资料是否真正吸收，而不是仅移动位置；
- Git 提交是否能清楚还原每个阶段。

## 10. Git 提交策略

审计、架构定稿和每个主要模块分别提交。提交信息说明完成了哪个知识责任，而不是使用 `update notes` 之类的模糊名称。

提交标题使用中文。建议形式：

```text
feat(P0-audit): 完成技术美术资料审计
feat(P0-architecture): 确定知识库目录与迁移边界
feat(P1-math): 重构图形数学与采样基础
feat(P1-pipeline): 重构 GPU 与光栅化管线
feat(P1-shader): 重构 Shader 编程基础
feat(P1-lighting): 重构光照、PBR 与阴影
feat(P1-texture): 重构纹理、颜色与后处理
feat(P1-engine): 重构引擎渲染与性能分析
feat(P2-content): 补齐游戏开发专业领域
feat(P2-sources): 完成课程资料迁移与旧结构退役
feat(P2-review): 完成知识库全量审核
```

提交只是恢复和审查边界，不按文件数量机械拆分。
