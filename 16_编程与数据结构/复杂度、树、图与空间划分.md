# 复杂度、树、图与空间划分

数据结构的目的不是背名称，而是让操作成本符合工作负载。TA 常见问题包括资产依赖、层级遍历、批处理调度、空间查询、路径搜索和 GPU 数据准备。

## 渐进复杂度

Big O 描述输入规模增大时的增长上界，忽略常数和低阶项。

常见：

- $O(1)$：数组索引、平均 Hash Lookup；
- $O(\log N)$：平衡树查询、Binary Search；
- $O(N)$：扫描列表；
- $O(N\log N)$：比较排序；
- $O(N^2)$：所有对象两两比较。

还要区分 Worst/Average/Amortized。Dynamic Array `push_back` 偶尔扩容为 $O(N)$，但按倍数增长时摊还通常是 $O(1)$。

复杂度不是实际时间。连续扫描一百万整数可能比随机访问十万个节点更快，因为 Cache、分支、分配和并行度不同。

## 先定义操作

选择结构前列出：

- 插入、删除、查找、遍历哪个最频繁；
- 是否需要稳定顺序；
- Key 是否唯一；
- 数据量和峰值；
- 是否多线程/GPU；
- 是否需要序列化、Diff 和确定性；
- 查询是精确、范围还是最近邻。

没有工作负载，“HashMap 比 List 快”没有意义。

## Array、List 与 Deque

连续 Array/Vector：

- Index $O(1)$；
- 尾部追加摊还 $O(1)$；
- 中间插删 $O(N)$；
- Cache Locality 好；
- Reallocation 会使 Pointer/Iterator 失效。

Linked List 已知节点时插删 $O(1)$，但查找是 $O(N)$，每节点分配与指针跳转对 Cache 不友好。现代实时代码中，它往往没有理论图上看起来那么便宜。

Deque 适合两端插删和 Queue。具体块布局与迭代性能取决于实现。

## Stack、Queue 与 Priority Queue

Stack 是 LIFO，适合 DFS、解析和撤销层级；Queue 是 FIFO，适合 BFS、Job 和事件顺序。

Priority Queue 通常由 Binary Heap 实现：

- 查看最小/最大：$O(1)$；
- 插入：$O(\log N)$；
- 弹出：$O(\log N)$。

A*、Dijkstra 和调度器会用它选择当前代价最小节点。若需要更新已有节点 Priority，要保存 Handle/Index 或允许重复插入并在弹出时跳过旧记录。

## Hash Table

Hash Table 平均查找/插入 $O(1)$，但碰撞、扩容和恶意 Key 可退化。

关键：

- Hash 与 Equality 必须一致；
- Mutable Key 放入后不能改变参与 Hash 的字段；
- Load Factor 影响内存与碰撞；
- Rehash 会产生峰值；
- 普通 Hash 遍历顺序不应作为确定性输出顺序。

资产构建需要稳定结果时，输出前按 Canonical Key 排序，或使用有序结构。不要依赖某次运行的 Dictionary 枚举顺序。

## Tree

Tree 表达层级：Scene Graph、Skeleton、UI、文件目录和 BVH。

Depth-first Search（DFS）适合递归处理子树、序列化和后序删除。Breadth-first Search（BFS）适合按层级处理和找最少边数路径。

Recursive DFS 简洁，但极深树可能 Stack Overflow。大型/不可信数据使用显式 Stack，并检测 Cycle。场景“应该是树”也可能因损坏引用形成环。

平衡 Binary Search Tree 保持查询、插入、删除 $O(\log N)$，并支持有序遍历。若只需要 Key Lookup，Hash 往往更直接；若需要 Range/Order，Tree 更合适。

## Graph

资产依赖、任务调度、Shader Node 和关卡连接常是 Graph，不是 Tree。一个节点可有多个 Parent，甚至存在 Cycle。

表示：

- Adjacency List：适合稀疏图，内存约 $O(V+E)$；
- Adjacency Matrix：查询边 $O(1)$，内存 $O(V^2)$，适合小而稠密；
- Edge List：交换/批处理简单，但邻居查询需索引。

Stable Node ID 与显示名称分开。重命名不应改变依赖身份。

## Topological Sort

有向无环图（DAG）可做拓扑排序，得到所有依赖先于使用者的执行顺序。

Kahn Algorithm：

1. 计算每个 Node In-degree；
2. 把 In-degree 为 0 的节点入队；
3. 弹出节点并减少其 Out-neighbor In-degree；
4. 新的 0 入队；
5. 输出数量小于节点总数说明存在 Cycle。

资产构建中，Texture/Source 先于 Material，Material 先于 Prefab/Level。Cycle 需要报告实际环路径，不能只说“排序失败”。

## Dijkstra

边权非负时，Dijkstra 从源点逐步确定最短距离。使用 Priority Queue 的复杂度常写为 $O((V+E)\log V)$。

它不只用于寻路，也可用于工具中的最小转换成本、依赖影响路径和图布局。所有边权相同时，BFS 更简单。

负权边需要其他算法；Dijkstra 得到错误结果时不一定会报错。

## A*

A* 使用：

$$
f(n)=g(n)+h(n)
$$

$g(n)$ 是已走成本，$h(n)$ 是到目标的启发估计。$h=0$ 时退化为 Dijkstra。

若 $h$ Admissible（不高估真实剩余成本），可以保持最优性。Consistent Heuristic 还能避免频繁重新打开节点。

网格中常用 Manhattan/Euclidean Distance，但要匹配允许的移动方式和边权。为了速度加权 $h$ 可能牺牲最优性，应显式记录取舍。

## 空间查询为什么需要结构

$N$ 个对象两两碰撞是 $O(N^2)$。空间结构先做 Broad Phase，把候选减少后再做精确 Narrow Phase。

结构选择取决于静态/动态、密度、对象大小、查询类型和维度。

## Uniform Grid 与 Spatial Hash

把空间分为固定 Cell，对象按 Bounds 插入覆盖的 Cell。范围查询只访问相交 Cell。

优点：实现简单、并行友好、动态更新直接。问题：

- Cell 太小，大对象跨很多 Cell；
- Cell 太大，每格候选过多；
- 密度极不均匀时浪费；
- 同一对象出现在多个 Cell，需要查询去重。

无限/稀疏世界可用 Cell Coordinate Hash，不分配空 Grid。Hash Key 要稳定处理负坐标和整数溢出。

## Quadtree 与 Octree

Quadtree 每节点分四块，用于二维/地形；Octree 分八块，用于三维。

它们适合空间密度自适应、LOD 和区域查询。但边界对象如何放置很关键：复制到所有 Child、保留 Parent，或使用 Loose Tree。

Loose Octree 扩大 Child Bounds，减少对象跨节点，但会增加重叠和查询候选。

树过深会产生大量小 Node 和 Pointer。可用 Linear Quadtree/Octree、Morton Code 和连续数组提高 Locality。

## BVH

BVH 按对象 Bounds 分组，而不是固定切空间。它适合 Ray、Collision、Culling 和不均匀几何。

静态 BVH 可用 SAH 构建高质量层级；动态对象可 Refit 或局部/整体 Rebuild。Bounds 重叠越多，遍历越容易访问两边分支。

在这个模块里，选择重点是：

- 构建与更新频率；
- Query 类型和数量；
- Node Layout 与 Cache；
- 动态变形导致的质量退化；
- 是否需要 GPU 并行遍历。

求交细节见 [[12_光追与现代渲染/光线、求交与加速结构]]。

## KD-Tree 与空间分割

KD-Tree 按轴向平面分割点或空间，适合静态最近邻、范围查询和部分 Ray Tracing。高维时剪枝效果下降，动态更新也不如 Grid 简单。

Point KD-Tree 与空间 KD-Tree 的数据归属不同。使用库前先确认节点保存点集合还是 Primitive 空间切分。

## Scene Graph 不是空间索引

Scene Graph 表达 Parent Transform 和语义层级。把同一层级直接用于可见性查询会出问题：一个空 Group 下面可能有横跨整张地图的对象。

运行时通常另建 Spatial Index。Transform Hierarchy 变化时更新对象 Bounds，再把它同步到 BVH/Grid/Octree。

## 复杂度与数据局部性

一个指针式 BVH 节点访问 $O(\log N)$，但每层 Cache Miss；一个连续数组的小范围扫描是 $O(N)$，实际可能更快。

优化步骤：

1. 用真实规模和查询记录 Baseline；
2. 检查算法增长；
3. 检查分配、Cache、Branch 和数据布局；
4. 批量查询并行化；
5. 再考虑更复杂结构。

结构越复杂，Build/Update 和 Debug 成本也越高。编辑器中每秒一次的 1000 项扫描不需要商业级 BVH。

## 常见 TA 应用

- 资产依赖：Graph + Reverse Edge + Topological Sort；
- 文件/场景层级：Tree + Stable ID；
- 批处理任务：DAG + Ready Queue；
- 最近资产/控件：KD-Tree 或 Spatial Hash；
- 大量实例范围查询：Grid/Quadtree/BVH；
- 撤销历史：Stack/Transaction Log；
- LRU Cache：Hash Map + Doubly Linked List；
- A* 调试：Priority Queue + Parent Map。

## 验证方法

- 为每个操作写规模测试，画 N 增长与时间/内存曲线。
- 使用随机、均匀、聚团、极端大对象和退化输入。
- 验证 Hash 冲突、Tree 深度、Graph Cycle 和 Queue 重复节点。
- 对空间结构比较 Build、Update、Query、Candidate Count 和 Memory。
- 检查输出确定性，尤其 CI、资产打包和程序化生成。
- Profile Cache Miss/Allocation，不只看 Big O 推断。
