# 帧捕获与性能分析工具

性能分析的目标是形成证据链：哪一帧慢、哪一侧慢、哪个事件占时间、它为什么慢、修改后是否改善。

## 稳定复现

先固定：

- 设备、分辨率和图形设置；
- 场景、相机路径和角色状态；
- VSync、帧率上限和动态分辨率；
- 是否开发构建；
- 冷启动还是缓存后；
- 温度和电量状态。

无法复现的“偶尔卡”要先记录 Trace，而不是直接猜优化方案。

## CPU与GPU时间线

### Unity Profiler

查看主线程、渲染线程、Job、GC、Loading 和 GPU Module。Timeline 比单一层级百分比更适合看线程等待关系。

注意：

- Editor Profiler 有编辑器开销；
- GPU 时间可能受平台和 Profiler 支持限制；
- `Gfx.WaitForPresent` 可能表示 CPU 等 GPU/VSync；
- Deep Profile 会严重改变性能。

### 平台工具

- PIX：Direct3D；
- Nsight Graphics：NVIDIA；
- Radeon GPU Profiler：AMD；
- Xcode GPU Tools：Apple；
- Android GPU Inspector：Android；
- Snapdragon Profiler、Arm Mobile Studio 等厂商工具。

引擎 Profiler 给系统视角，平台工具给硬件计数器和 API 细节。

## Frame Debugger事件

Frame Debugger 按引擎事件展示：

- Draw 顺序；
- Batcher 原因；
- 渲染目标变化；
- 着色器 Pass；
- 最终画面怎样逐步形成。

它适合理解引擎组织，但不一定显示真实 API 屏障、驱动工作和精确 GPU 时间。

## RenderDoc捕获

RenderDoc 捕获一个图形 API 帧，可以检查：

- 事件 Browser；
- 管线状态；
- 纹理/缓冲；
- 网格输入/输出；
- 着色器资源和 Constant；
- 像素历史；
- 着色器调试；
- Draw/派发时间（取决于计时支持）。

它主要回答“这一帧发生了什么”，不是长时间卡顿、温度和 CPU 调度工具。

## API 调试消息

图形 API 的验证层和调试回调适合在开发构建中尽早发现无效状态、资源绑定、同步和对象生命周期问题。OpenGL 调试输出的最小接入如下：

```cpp
void APIENTRY OnGlMessage(GLenum source, GLenum type, GLuint id,
                          GLenum severity, GLsizei length,
                          const GLchar* message, const void* user)
{
    if (severity == GL_DEBUG_SEVERITY_NOTIFICATION)
        return;
    LogGraphicsMessage(source, type, id, severity, message);
}

glEnable(GL_DEBUG_OUTPUT);
glEnable(GL_DEBUG_OUTPUT_SYNCHRONOUS);
glDebugMessageCallback(OnGlMessage, nullptr);
```

同步回调便于在调试器中定位触发调用，也会增加 CPU 开销。正式运行可以关闭同步或按来源、类型和 ID 过滤消息。

调试层只能报告 API 能识别的问题。合法但错误的矩阵、坐标空间、光照公式和性能设计仍需要帧捕获、可视化和对照实验定位。Vulkan Validation 层、D3D12 调试层和 GPU-based Validation 也遵循相同边界。

## 单帧分析顺序

### 1. 通道构成

列出阴影、深度、GBuffer/Forward、光照、Transparent、Post Process、UI。检查是否有意外重复相机、反射、场景捕获。

### 2. 分辨率与格式

检查每个渲染目标的宽高、Samples、Format 和 Mip。一个不必要的 Full-resolution RGBA16F 临时缓冲可能比着色器算术更贵。

### 3. 绘制与状态

检查 Draw 数、实例 Count、PSO/材质切换、顶点/索引数量和 Batcher。

### 4. 像素覆盖

检查全屏 Pass、透明层数、粒子包围范围和重复绘制。一个只在角落显示的效果不应运行全屏复杂着色器。

### 5. 着色器与资源

统计纹理采样、循环、分支、寄存器和指令。确认实际绑定的纹理尺寸、Mip 和压缩格式。

### 6. 同步与依赖

查找 Queue Wait、屏障、Readback、Resolve 和 Copy。判断 GPU 是否有空泡。

## 像素历史

像素历史可以显示某像素被哪些 Draw 修改、因深度/Stencil 失败或 Blend 后得到什么结果。

适合定位：

- 为什么物体没显示；
- 谁覆盖了颜色；
- 透明混合顺序；
- Stencil/深度状态；
- 重复绘制来源。

## GPU 计数器

不同硬件提供不同计数器，常见维度：

- 着色器 Core 利用率；
- 纹理/内存吞吐；
- 缓存命中与未命中；
- Wave 占用率；
- Raster/ROP；
- 图元 Culling；
- Tile Load/Store；
- 射线 Tracing Unit。

计数器高不是自动的问题。例如带宽利用高但帧时间达标，可能只是硬件被充分使用。需要结合瓶颈和修改实验。

## 引擎自带的追踪工具

通用图形调试器擅长单帧的 GPU 细节，但定位“哪个系统在什么时候消耗了多少”需要引擎侧的追踪工具。

### 追踪型 Profiler

Unreal Insights 一类的工具记录一段时间内的多通道数据——CPU 各线程的调用栈、GPU 时间、内存分配、加载事件、网络收发——并按同一时间轴对齐。

它与单帧捕获的分工很清楚：单帧捕获回答“这一帧的这次绘制为什么慢”，时间轴追踪回答“卡顿出现在哪一帧、由哪个系统引起”。长时间追踪适合定位偶发卡顿；具备触发捕获或环形记录能力的工具也可保留异常区间，具体能力按平台确认。

使用要点是先划定关注区间。一段几分钟的追踪数据量巨大，应当用自定义标记圈出关卡加载、战斗开始等关键区段，再逐层下钻。

### 内存分类报告

内存问题需要按类别归因而非只看总量。引擎通常提供两级手段：

- **全量报告**：某一时刻按资源类型、类、包分类的内存清单，适合回答“内存被谁占了”；
- **统计项埋点**：为自定义子系统声明统计项，持续采样其内存占用，适合回答“这个系统的内存是否随时间增长”。

前者是快照，后者是曲线。判断泄漏需要多次快照或持续曲线，单次快照无法区分占用大与持续增长。

### 构建配置影响测量结果

性能数据必须标注构建配置和实际编译开关。下面列出常见配置约定，项目可以覆盖这些设置，报告以构建日志为准：

| 配置 | 特点 | 适用 |
|---|---|---|
| 调试 | 无优化，可完整调试 | 定位逻辑错误，不用于性能测量 |
| 开发 | 优化开启，保留统计与控制台 | 日常性能分析 |
| 发布 | 全优化，剥离调试设施 | 最终性能验收 |

开发与发布的差距可能达到可观比例——统计埋点、日志、断言本身都有成本。开发与发布的执行路径也可能不同，不能仅按固定比例换算；反过来，发布缺少埋点，难以定位问题来源。

实践做法是用开发定位与迭代，用发布做最终验收，并在报告中始终标明配置。编辑器内运行则是第三种情况，其开销与独立包不同，适合分析编辑器自身；运行时性能验收应以目标平台独立构建为依据。

## 证据与假设

一个合格假设应写成：

> 透明粒子在 1440p 覆盖屏幕 6 层，Transparent Pass 占 4.2 ms，GPU 计数器显示颜色/纹理 Bandwidth 接近上限。把远景粒子降到半分辨率并收紧网格后，预计减少带宽和重复绘制。

而不是：

> 粒子很多，应该优化一下。

## 不同工具结果冲突

可能来自：

- 捕获帧不是同一场景状态；
- GPU Timestamp 粒度；
- Profiler 插桩改变执行；
- Dynamic Resolution/Exposure/Streaming 状态不同；
- 捕获禁用了某些异步或驱动优化；
- Editor 和播放器路径不同。

记录工具版本和捕获条件，再做交叉验证。

## 捕获结果的调查路径

事件列表说明 GPU 接到了什么命令，资源视图说明命令读写了什么。先找到第一份异常输出，再沿写入者和输入向前追踪，才能把最终黑屏缩到一个具体通道。时间线随后回答这个通道是否位于关键路径；状态正确与性能改善各用自己的证据确认。
