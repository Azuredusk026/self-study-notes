# PSO 缓存与运行时卡顿

现代图形 API 把一次绘制所需的 Shader 与渲染状态打包成 Pipeline State Object。驱动在创建 PSO 时解决硬件状态之间的依赖与冗余，算出最优的状态集合——这个过程称为编译，代价昂贵。

收益是绘制时几乎不再有状态切换开销，成本是首次遇到某个状态组合时的一次性编译。问题就出在这里：如果这次编译发生在玩家正在游玩的时刻，表现为一次明确的卡顿。而且它出现在特定场景的首次进入，恰好是最影响体验的时机。

## 卡顿的成因

PSO 编译卡顿有三个特征，决定了它比普通性能问题更难处理：

- **设备相关**。编译结果绑定具体 GPU 与驱动版本，无法在打包机上预先算好随包分发；
- **不可预测**。同一份内容在不同机型上的卡顿位置和严重程度不同；
- **首次出现**。开发者反复测试的场景早已缓存，恰恰不会复现问题。

治理思路由此确定：状态组合虽然编译结果无法预知，但**组合本身是可以预知的**——一个游戏用到的材质与渲染状态是有限且确定的。因此可以离线收集出完整的状态组合列表，随包分发，在设备上提前编译。

## 三个阶段

讨论 PSO 缓存必须区分三件性质完全不同的事：

| 阶段 | 发生时机 | 耗时 |
|---|---|---|
| 初次预编译 | 首次启动游戏 | 很长，需要真正编译全部 PSO 并生成驱动本地缓存 |
| 后续预编译 | 之后每次启动 | 快得多，驱动本地缓存已存在 |
| 运行时取用 | 提交绘制时 | 接近零，从内存或磁盘取已编译结果 |

混淆这三者会导致错误结论。看到"启动时要编译三分钟"就放弃方案是常见误判——那是初次预编译，只发生一次；而不用缓存的代价是在整个游戏周期中持续遭遇随机卡顿。

## 收集与打包

Unreal 的流程分三步：

**收集**：以特定参数启动游戏并跑遍场景，运行时记录遇到的每个 PSO，产出记录文件。项目需开启 Shared Code Library 与稳定 Shader Key，并在目标机型配置中启用管线缓存。

**打包**：用命令行工具把记录文件与 Shader 的稳定 Key 映射表合并，展开成稳定的 CSV 列表，放进项目的构建目录。重新打包时它会被转换成运行时格式并打进包里。

**运行**：启动时触发预编译。可以轮询剩余待编译数量，在 Loading 界面等待编译完成再进入游戏。

收集质量直接决定覆盖率。跑图必须覆盖所有材质、光照组合与画质档位，漏掉的组合会在玩家那里现场编译。

### 增量收集

逐版本从头跑图不现实。两级合并机制解决这个问题：

- 同一构建的多次运行产生的记录文件可以合并，允许多台设备、多个画质并行收集；
- 不同版本生成的稳定列表也可以合并，并用移动平均更新各 PSO 的出现频率。内容改动不大时，只需重跑变化的部分。

实践上值得把收集挂进功能测试与适配测试流程，持续积累覆盖率。但**不要在性能测试时收集**——记录本身有开销，会污染性能数据。

## 内存代价

全量预编译的内存开销常被低估。移动端实测中，Android 上每个 PSO 约占 0.1 至 0.16 MB。一千个 PSO 就是一百多兆，而单次运行实际用到的往往只是其中一小部分。

更棘手的是生命周期：Vulkan 与 OpenGL 下卸载关卡后，PSO 占用的内存不会释放。Metal 在这方面表现明显更好，内存占用与加载延迟都低得多。

两个机制用于控制内存。

### UsageMask

给每个 PSO 打标记，声明它属于哪种使用场景，运行时只加载相关标记的那部分。

最自然的划分维度是画质档位——低画质运行时不需要加载高画质的 PSO。还可以把机型、特性开关编入额外的掩码位。

典型策略是分两段：启动时只编译最低画质的基础 PSO，满足登录与更新界面；确定当前机型与画质后，再手动触发对应掩码的编译。这样既缩短了启动等待，又避免了全量加载的内存峰值。

按关卡划分是更细的思路：把 PSO 编译分摊到各关卡的加载过程中，用户感知的等待时间被自然吸收，内存压力也分散到各地图。

### LRU

限制常驻内存的 PSO 数量或总字节数，超限时回收最久未使用的。OpenGL 与 Vulkan 支持此机制，Metal 没有对应实现。

LRU 有明确的权衡：阈值设得过低会导致游戏中反复重建 PSO，把启动卡顿换成了游玩中的卡顿——后者体验更差。实测表明，在已启用 UsageMask 的基础上再开 LRU，内存收益不明显，却会拖慢加载。

## 编译策略

默认策略以较大批次持续编译，且**阻塞渲染线程**。低端机上默认批次可能让渲染线程完全停滞，用户看到的是彻底无响应的画面，容易被判断为崩溃。

因此需要限制每帧的编译数量与编译时间，保证进度条能够刷新。让用户看到进度，比缩短几秒总时长更重要。

引擎也提供后台编译模式：启动阶段耗时超过阈值后转入后台，每帧只编译一个。但对移动端不建议使用——后台持续编译本身产生卡顿，且一旦游戏中遇到尚未编译的 PSO，卡顿会直接暴露给玩家。在启动时间可接受的前提下，移动端应当在启动或切换画质时一次性编译完成。

配合后台编译还有排序选项：按首次出现顺序、按出现频率，或不排序（默认）。合适的排序能减少"用到时还没编译好"的概率。

## 各图形 API 的差异

| API | 索引信息 | 异步编译 | 本地缓存 |
|---|---|---|---|
| Metal | 完整 PSO | 支持 | 无 |
| Vulkan | 完整 PSO | 支持 | 有 |
| OpenGL | 仅 Bound Shader State | 不支持 | 有 |

OpenGL 值得单独说明。它本身没有 PSO 概念，真正起作用的是 Program 对象，所谓"PSO 编译"实际发生在 Program 链接时。由于 Program 只与 Shader 相关，其索引只包含 Bound Shader State。

这解释了一个实测现象：OpenGL 平台启用预载后的性能提升幅度**高于**其他平台。因为它在预编译与运行时使用了相同的索引，预热的命中率更高。

另一面是 OpenGL 缺乏异步编译机制，遇到未缓存的 Program 只能同步链接，卡顿无法掩盖。

### 本地缓存不更新

OpenGL 与 Vulkan 的二进制缓存只在预编译阶段生成，之后不再更新。这意味着收集阶段遗漏的组合，或运行时动态产生的新组合，每次启动都会重新编译、每次都会卡顿。

需要长期运行的项目应当考虑支持运行时增量更新本地缓存。

## PSO Precaching

UE 5.3 起提供了另一条路径：加载材质时就根据画质与材质用途推断可能需要的 PSO，提前异步编译。不再需要预先跑图收集，也不需要启动时统一预热。

特点与代价：

- 全部编译异步进行，但实际使用中通常仍在加载阶段等待完成；
- 用到某个 PSO 而它尚未就绪时，可选择跳过该次绘制或显示默认材质——两种降级都有视觉代价；
- Epic 在 Fortnite 上的数据是覆盖率超过 90%，代价是多编译约一倍数量的 PSO，对局加载时间增加数秒。

它用"多编译一些"换取"不必精确收集"，对迭代频繁的项目更友好。

> [!warning] 待补充
> 上述机制与控制台变量基于 UE4.26 至 UE5.3 的实测。PSO Precaching 在后续版本中仍在演进，移动端支持状态需按目标版本确认。具体阈值与批次大小必须在目标机型上实测，不能套用他人数值。

## 定位 PSO 卡顿

PSO 卡顿容易与资源加载、GC、Shader 编译混淆。几个区分特征：

- 只在某场景**首次**进入时出现，重进不再复现；
- 清除应用数据后重现，说明依赖驱动本地缓存；
- 卡顿发生在渲染线程而非游戏线程；
- 与新材质、新特效的首次出现时机吻合。

### 等待预编译完成

启动流程中轮询剩余数量，编译完成前停留在 Loading：

```cpp
// 渲染线程可查询剩余待编译数量
int32 Remaining = FShaderPipelineCache::NumPrecompilesRemaining();
if (Remaining > 0)
{
    UpdateLoadingProgress(Remaining, TotalPrecompileCount);
    return; // 保持在加载界面
}
EnterGameplay();
```

预编译在启动画面之后、加载 UObject 之前触发。只有这个数值归零才说明列表中的 PSO 已全部就绪；此时仍可能遇到未收集到的组合，那属于覆盖率问题而非时机问题。

验证方法是清除应用数据后冷启动，记录首次预编译总时长与内存峰值；再次启动记录后续预编译时长。两者差距应当在一个数量级左右，若无差距说明本地缓存没有正确生成。

## 验证方法

- 清除应用数据冷启动，测量初次预编译耗时与内存峰值，对比后续启动。
- 在低端目标机型上确认编译期间进度条仍在刷新，渲染线程未完全阻塞。
- 对比开启与关闭 UsageMask 的常驻内存，确认筛选确实生效。
- 关卡卸载后测量内存，Vulkan 与 OpenGL 上不应期待 PSO 内存被释放。
- 用跑图脚本统计 PSO 覆盖率，重点检查低频出现的材质与特效。
- 性能测试时确认 PSO 记录已关闭。
