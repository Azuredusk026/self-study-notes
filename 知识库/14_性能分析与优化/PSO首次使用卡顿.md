# PSO首次使用卡顿

一个特效第一次出现时卡一下，再出现就正常，可能是资源加载，也可能是管线创建触发了驱动编译。PSO 调查把首次请求、编译完成与首次绘制分开记录，再判断缓存缺失、预热过晚还是组合覆盖不足。机制与缓存键见 [[13_渲染架构/Pipeline State Object]]。

## 卡顿证据与缓存层次

同一着色器配上不同附件格式、样本数或顶点布局，会形成不同的完整管线状态。只预热材质名称无法证明这些组合都已准备。驱动还可能在创建或首次使用时完成设备相关工作，因此“着色器字节码已经打包”也不是无卡顿保证。

缓存要分层观察：

| 数据 | 保存内容 | 兼容与成本 |
|---|---|---|
| 组合描述列表 | 程序身份和渲染状态 | 可按目标配置随包发布，覆盖率取决于收集规则 |
| 驱动二进制缓存 | 特定实现准备的管线数据 | 按 API、设备与驱动兼容规则读取，更新后可能失效 |
| 内存管线对象 | 当前设备可使用的对象 | 占运行内存，回收后再次获取可能有成本 |

冷启动需要建立哪些层，决定启动工作量；热缓存只减少相应层的工作，不保证取用耗时为零。发布新着色器、修改状态或升级驱动，都可能再次触发准备。测试报告应写清清除了应用列表、驱动缓存还是内存对象，避免把不同条件都叫作“清缓存”。

## 组合收集与覆盖

运行记录捕获实际遇到的组合，适合沿功能用例、角色、特效、画质和渲染路径建立覆盖集合。收集路线需要触发低频材质、不同阴影通道和附件设置；只是走遍地图，未必触发全部组合。把组合键与首次出现的内容事件一起记录，才能补出缺失用例。

构建阶段把记录与稳定着色器身份合并，再生成目标平台可读的列表。稳定身份解决源码变化后的映射问题，实际工具参数与文件格式由锁定的引擎版本决定。日志至少保留原构建、目标平台、质量档位、记录数量、去重数量和无法映射的键。失去对应着色器的旧条目应明确丢弃或报错，不能继续当成有效覆盖。

准备过程本身会改变线程负载和缓存状态。收集运行用于发现组合，计时运行使用冻结列表并关闭记录，再按同一路线测量首次使用尖峰。

## 提前准备与加载边界

运行时可以从即将加载的材质、顶点工厂和组件状态推导候选组合。候选准备得足够早，编译就有机会与其他加载工作重叠；准备过晚，首次绘制仍要等待。自动推导与运行记录可以共同使用，覆盖范围由实际组件、全局着色器和 RHI 支持决定。

Epic 的 PSO Precaching 文档区分组件与资源收集：资源自身未必知道完整渲染状态，组件信息才能补齐部分状态。引擎还提供代理创建延迟等策略，用于处理管线尚未完成的情况。2026-10-22 核对的网页为 UE 5.8 文档；具体项目应锁定自己的引擎版本及 `GRHISupportsPSOPrecaching` 能力，不能直接沿用网页默认值。

下面是应用层算法伪代码。两种准备系统的进度来自各自接口，工作总量在内容加载期间可能增长，因此界面不应把一个瞬时计数当作永久总量。

```text
request required content and pipeline combinations
while loading:
    update content loading progress
    collect newly requested pipeline work
    poll completion of required pipeline requests
    keep loading UI responsive
    if contentReady and requiredPipelineRequestsFinished:
        enter target scene
```

这里的“完成”只覆盖已发现且被列为必需的请求。UE 5.8 文档说明 `FShaderPipelineCache::NumPrecompilesRemaining()` 可以查询组合缓存与 PSO Precaching 当前未完成的编译请求。计数归零后仍可能因后续内容加载新增请求，因此不能由此判断所有未来组合已经准备好。真正验证是在首次绘制时关联请求键与完成时间。

若等待时间超过产品预算，可以优先准备首屏组合，把其余工作限制在受控后台预算内。跳过对象、默认材质和现场同步创建分别牺牲画面完整性、外观或流畅度，策略必须按项目目标定义并记录触发次数。

### 请求状态与首次使用

应用为每个完整PSO键维护一条请求记录，状态按`Missing→Queued→Creating→Ready`推进；创建错误进入`Failed`并保存错误码。再次请求同一键时，Queued或Creating返回同一请求，避免多个加载线程重复创建；Ready返回持有所有权的对象，使用者按GPU完成条件释放引用；Failed按明确重试次数或回退策略处理，不能当作“等待计数已经归零”。缓存键的程序与状态字段见[[13_渲染架构/Pipeline State Object]]，记录里同时保存构建和目标设备兼容身份。

首屏所需键集合在对应内容完成发现后封闭。进入场景的条件是这组键全部Ready，并且对应内容可用；只检查全局剩余数为零，可能把尚未发现的请求或已失败的请求误当作准备完成。需要在预算到期后继续时，渲染端对每次首用显式选择等待、占位或暂缓绘制，并记下键与发生时刻；后台创建完成后再在帧边界发布真实对象，避免记录命令期间替换仍在使用的对象。

### 请求时间与首用期限

设必需组合K在加载开始后的20毫秒被请求，创建在80毫秒完成，首个绘制在60毫秒需要它；即使列表覆盖了K，仍有20毫秒缺口。把请求提前到0毫秒且创建耗时不变，可在60毫秒完成，但并发争用也可能延长创建，必须比较实际完成时刻。若首用时查询不到K，先比对完整状态键；同材质的四倍MSAA版本不是单样本版本的缓存命中。

回收也能制造再次首次使用：K在80毫秒完成、100毫秒被LRU删除，200毫秒再次请求时需要重新取得对象。记录请求、完成、回收、使用四类事件，才能将覆盖缺失、准备过晚和回收重建区分开。

## 内存与编译预算

并行编译会占 CPU 和临时内存，更多工作线程不一定更快。测量编译墙钟时间、峰值内存、加载界面帧时间和关键请求的等待时间，再设并发上限。帧数预算或毫秒预算限制的是调度策略，驱动的一次调用可能仍然耗时较长。

按质量档位或内容集合筛选候选，可以避免同时准备当前不需要的组合。LRU 回收内存对象则减少常驻量，但对象再次使用时仍可能重建；驱动缓存是否保留以及重建成本需要实测。关卡卸载不等于所有管线对象被销毁，也不等于对象永远不能回收，实际所有权由缓存策略决定。

## 图形接口与实现范围

Vulkan 提供管线缓存接口，缓存数据具有实现相关的兼容条件。D3D12 有缓存 PSO 与管线库等路径。Metal 提供 `MTLBinaryArchive`，可收集并序列化兼容管线的编译数据。OpenGL 的主要准备对象是 Program，程序二进制与并行编译能力分别由版本、扩展和驱动支持决定。

这些 API 能力不能直接推导某个引擎后端已经使用它们。是否保存运行中新发现的数据、什么时候写盘、如何处理不兼容缓存，都属于具体实现。查目标版本的缓存写入与加载入口，再用实际文件变化和冷暖运行确认。

## 复现与验收

先冻结构建、设备、驱动、画质和路线。在可控测试环境清除指定缓存，记录冷启动准备时间、峰值内存和首次使用事件；同样条件重复运行，记录暖缓存差异。内容路线至少包含首次特效、画质切换、新阴影组合与场景切换。

每个尖峰对应一个假设：若请求在使用前从未出现，是覆盖问题；已请求但未完成，是时机或编译预算问题；已完成仍卡顿，则继续检查对象回收、驱动工作和资源加载。主线程或渲染线程出现等待只是现象，需要时间线指向具体工作。

本文给出调查流程与已核对的接口职责，未运行 Unreal 构建、设备编译或冷暖缓存性能实验。没有项目测量时，预热时长、内存收益和运行时卡顿率均保持未验证。
