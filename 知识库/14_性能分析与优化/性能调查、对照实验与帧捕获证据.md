# 性能调查、对照实验与帧捕获证据

性能调查先确定可复现负载和指标，再设计能排除假设的实验。帧捕获解释执行了什么，GPU 计时解释成本；两者需要结合，单次捕获截图不能代表长期稳定收益。

## 固定测量条件

记录提交、场景、相机路线、设备、API、分辨率、画质、构建和预热步骤。CPU/GPU 频率、温度与后台负载可能改变结果。比较多次稳定窗口，保留中位数和高分位，避免把一次偶然尖峰作为结论。

## 从时间线找关键路径

CPU 记录、提交等待、GPU 执行和呈现可能重叠。CPU 某段“等待”可能是 GPU 已满，也可能是垂直同步或帧限流。先看依赖关系，再决定优化哪个工作者。

```text
复现场景并预热
  → 记录 CPU、GPU、内存和显示节奏
  → 找到关键路径
  → 提出单一可检验假设
  → 只改变相关因素
  → 检查执行路径与图像
  → 重复测量并回归其他场景
```

## 最小对照表

```text
假设：某全屏通道受附件带宽限制
保持：相机、Shader、场景、驱动和构建
改变：目标分辨率，按 1.0 / 0.75 / 0.5 运行
记录：像素数、GPU 时间、外部读写、图像误差
检查：附件数量、格式、通道合并是否相同
结论：仅在路径一致且结果可重复时支持该假设
```

降分辨率可能改变 LOD、灯光列表和资源合并，需要捕获确认，不能只按时间缩放比解释。

## 工具职责

Frame Debugger 用于查看引擎绘制阶段与输入输出，Render Graph viewer 用于查看逻辑资源依赖。RenderDoc 提供 Draw/Dispatch、资源、状态和部分像素历史；PIX、Nsight、RGP 等工具提供平台特定时间线和计数器。Unreal Insights 或引擎 Profiler 用于 CPU、任务与加载。

捕获本身可能插入等待或改变调度。性能数字来自指定测量方法，图像与状态证据来自捕获，两者在记录里分别列出。

## 故障诊断

黑屏先检查输出是否被消费、附件是否写入、viewport 和 Shader 绑定。串帧检查完成值、上传环和描述符回收。拖影检查重投影、深度约定与历史有效性。性能恶化先确认目标路径实际执行，再看它增加的成本维度。

## 验证方法

一次有效调查应同时保留假设、实验条件、重复测量和输出证据。复查者能够在相同构建运行相同路线，并根据数据接受或否定结论。通道更快而整帧更慢时，报告关键路径与资源竞争，不能只报局部收益。
