# 渲染优化验证与移动端实践

优化不是“做了一项改动”，而是同一条件下，某个瓶颈指标得到稳定改善，同时画质、内存、加载和其他场景没有不可接受回退。

## 建立基线

记录：

- 目标设备和系统版本；
- 分辨率、画质、帧率目标；
- 场景和相机路径；
- CPU/GPU 帧时间；
- 内存和包体；
- 温度稳定后的持续性能；
- 截图或画质参考。

基线数据应保存原始 Capture/Profiler 文件，而不只抄一张表。

## 一次只验证一个主要假设

同时改合批、LOD、Shader 和纹理后，即使帧时间变快，也无法知道收益来自哪一项。

推荐流程：

1. 发现稳定瓶颈；
2. 提出成本模型；
3. 设计最小改动；
4. A/B 测试；
5. 检查画质和其他指标；
6. 在多场景、多设备回归；
7. 决定是否保留。

## 统计方式

不要只测一次。至少记录多个稳定区间，并关注：

- Median；
- P95/P99；
- 最坏帧；
- 标准差或波动范围；
- 加载、战斗峰值和场景切换。

提升 0.1 ms 但波动 1 ms 的结果不能证明有效。

## Tile-based GPU

多数移动 GPU 使用 Tile-based Rendering。它先把屏幕分 Tile，在片上 Tile Memory 中完成可见性和部分颜色/深度操作，最后再写回外部内存。

片上内存带宽高、功耗低。真正昂贵的是：

- Attachment Store/Load；
- 中途切换 Render Target；
- 需要把 Tile 内容写回再读取；
- 大量透明混合；
- 全屏 Pass；
- 超大 GBuffer 和多采样数据外存。

## TBDR 和 Immediate Mode

不同移动 GPU 的 Tile 架构并不完全相同。TBDR 可能先完成隐藏面排序，减少不可见片元；其他 Tile-based 方案主要利用片上缓存。

不能把“移动端都是 TBDR”当成统一规则。要查看目标 GPU 厂商文档和 Counter。

## Mobile Deferred

Deferred 在移动端是否合适，取决于 GBuffer 能否留在 Tile、是否使用 Subpass/Input Attachment、灯光数量和材质需求。

如果每个 Pass 都把 GBuffer 写回系统内存再读取，带宽会很高。移动 Deferred 往往使用紧凑 GBuffer、Framebuffer Fetch 或 Tile-local 技术。

## MSAA 在移动端

MSAA 增加样本存储和部分光栅成本，但在 Tile Memory 内完成时可能比多个后处理抗锯齿 Pass 更合适。Resolve 和 Store 到外部内存仍有成本。

具体选择要测试 Forward/Deferred、透明、分辨率和 GPU 架构。

## Overdraw 和透明

透明通常无法靠隐藏面消除，粒子覆盖会重复执行 Shader 和 Blend。

移动端优化：

- 收紧粒子 Quad；
- 控制屏幕面积和重叠，而非只控制数量；
- 远景半分辨率；
- 减少透明纹理采样和分支；
- 简化软粒子深度读取；
- 对 UI 大面积半透明特别警惕。

## 带宽优先思维

移动 GPU 常比桌面更受带宽和功耗限制。可以检查：

- Render Target 格式；
- 是否需要 Alpha；
- 是否可以 Half Resolution；
- 是否重复读写 Scene Color/Depth；
- 纹理压缩和 Mip；
- Temporary RT 生命周期；
- Store/Load Action；
- Buffer 是否连续访问。

减少 ALU 不一定加速一个带宽受限 Shader。适量计算替代纹理读取有时更好。

## 热和 DVFS

移动 CPU/GPU 会根据温度和功耗动态调整频率。刚启动的 60 FPS 不能代表持续性能。

测试应：

- 预热设备；
- 运行足够长时间；
- 记录温度和频率；
- 避免充电、后台应用和环境温度干扰；
- 比较相同热状态。

优化降低功耗后，即使冷机帧时间变化不大，也可能让持续频率更稳定。

## 设备矩阵

至少覆盖：

- 低端目标机；
- 主流目标机；
- 高端机；
- 不同 GPU 厂商；
- iOS/Android 或目标系统版本。

一种压缩格式、精度或 Compute Group Size 在所有设备上不一定同样合适。

## 画质与性能回归（Regression）

性能通过后检查：

- 阴影和 LOD Pop；
- 纹理清晰度和 Streaming；
- Normal/Gradient 压缩；
- TAA 拖影；
- 粒子密度；
- HDR、曝光和色带；
- UI 可读性。

可以使用固定相机截图差异，但动态效果还需要视频和人工观察。

## 可变着色率

可变着色率（Variable Rate Shading，VRS）让一次片元着色覆盖多个像素——例如 2x2 模式下，四个像素共用一次着色结果。几何、深度、模板仍按全分辨率处理，只有着色频率下降。

它的本质是**用画质换性能**：被降频的区域一定更糊。因此核心问题不是"怎么开启"，而是**在哪里开启才不被察觉**。

### 三级粒度

| 粒度 | 控制方式 | 适用 |
|---|---|---|
| 逐绘制 | 提交绘制时指定着色率 | 整类对象统一降频 |
| 逐图元 | 顶点着色器输出着色率 | 按对象内部区域区分 |
| 逐 Tile | 一张低分辨率的着色率图 | 按屏幕区域精细控制 |

逐 Tile 最灵活，因为判据可以来自任何能生成屏幕空间数据的来源。

### 判据从哪里来

按材质或模型逐个人工标注，在成百上千的资产面前不现实，也无法覆盖运行时才确定的情况。可行的判据都是**自动生成**的：

**上一帧画面的局部对比度**。用一个 Compute Pass 统计每个 Tile 的亮度方差或梯度，平坦区域降频、细节丰富区域保持全率。这是最通用的方案，不需要资产配合，代价是一帧延迟与一次额外的分析 Pass。

**运动速度**。运动向量幅度大的区域本就会因运动模糊与视觉暂留而难以分辨细节，可以安全降频。数据现成，几乎零成本。

**景深与径向距离**。会被景深模糊的区域、以及注视点渲染中远离视线中心的区域，降频完全不可见。这两类判据在有对应功能时非常可靠。

**材质分类标记**。GBuffer 中已有分类信息时，可以对特定类别统一降频。它不需要逐资产标注，只需要在分类层面做一次决策——天空、远景地形这类大面积低频内容是天然候选。

实践中通常组合使用：用分类标记做粗筛，用画面对比度做细调。

### 适合与不适合

天空、雾、大面积平坦地形、强景深虚化区域、高速运动区域适合降频——它们本身缺少高频细节，降频的视觉代价接近于零。

角色面部、头发、文字与 UI、锐利边缘、高对比图案不适合。前面关于时域累积的讨论已经说明，高频细节区域的画质问题往往已经很紧张，再降着色率会显著恶化。

### 收益边界

VRS 只降低片元着色成本。如果瓶颈在顶点处理、带宽、绘制提交或深度测试，开启它几乎没有收益。启用前应先确认瓶颈确实在片元着色。

移动端的支持情况差异很大，部分实现只支持较粗的粒度。收益与画质损失都必须在目标机型上实测，不能沿用桌面端结论。
## 移动端资源优化清单

优化顺序应当按收益排列，而不是按"哪里容易改"排列。以下按通常的收益量级组织。

### 纹理

纹理常常是移动端包体与内存的最大单项。

- **压缩格式**。ASTC 在压缩率与画质上通常最优，且支持多种块尺寸以按内容调整质量。仅在不支持 ASTC 的旧设备上回退到 ETC 或 PVRTC；
- **分辨率上限**。按资产在屏幕上的实际占比设定，而非统一标准。远景物件的贴图分辨率可以远低于主角；
- **Mipmap**。不开 Mipmap 不只是画面闪烁问题，更是采样缓存命中率问题——远处物体采样全分辨率纹理会持续冲刷纹理缓存；
- **通道打包**。把多张单通道遮罩合进一张纹理的 RGBA，减少采样次数与资源绑定。

### Shader

- 减少全屏 Pass 的往返次数，合并可以合并的后处理；
- 控制纹理采样数量，尤其是依赖采样（用一次采样结果去算下一次的 UV），它会打断纹理预取；
- 谨慎使用 `discard`，它会影响 Early-Z；
- 精度限定符在移动 GPU 上是实打实的性能差异，能用半精度的不要用全精度。

### 后处理

后处理在移动端的成本主体是带宽而非计算。每一个全屏 Pass 都意味着一次全屏读加一次全屏写。

分辨率是最有效的杠杆：Bloom 等低频效果在半分辨率甚至四分之一分辨率下与全分辨率的视觉差异很小，带宽却降到四分之一或十六分之一。

### 验证顺序

先测量再优化。移动端常见的误判是花大量时间优化 Draw Call，而实际瓶颈在带宽；或优化顶点数，而瓶颈在 Overdraw。
