# 编辑器工具的事务与批处理

拖动一个控件时，属性面板、Gizmo 和资产文件都可能变化。用户按一次撤销，期待这几份状态一起回到操作前。工具因此先把修改表示成计划与事务，再由同一执行路径用于界面和批处理，保存与失败恢复也沿这份变更集处理。

## 用户操作流程

先描述用户任务：

1. 用户从哪里选择输入；
2. 工具如何显示当前状态和问题；
3. 哪些参数必须提供，哪些有安全默认值；
4. 执行前能否预览/变更预览；
5. 执行中如何显示进度和取消；
6. 部分失败如何处理；
7. 结果、日志和撤销在哪里。

如果流程需要用户先按隐藏顺序选中三个对象、切到特定模式、再点按钮，脚本虽然短，却不是稳定工具。

## 分层

建议职责：

```text
UI / Command Line
    -> Application Service
        -> Domain Rules / Operations
            -> DCC or Engine Adapter
            -> File / VCS / Process Adapter
```

- UI 负责输入、展示和交互，不承载批处理算法；
- Application Service 编排用例、事务和进度；
- Domain 层处理命名、验证、映射和转换规则；
- 适配器封装 Maya/Blender/Unity/Unreal API 和外部进程。

这样无界面命令行、编辑器窗口和 CI 可以调用同一核心逻辑，避免“面板能用，命令行是另一套实现”。

MVC 与 MVVM 可以帮助拆分编辑器职责。MVC 中模型保存领域状态，视图展示，控制器把用户操作转换为命令；MVVM 用 ViewModel 暴露可绑定状态和命令，适合属性面板与响应式界面。具体框架可以不同，但 UI 控件不应直接承担资产规则和文件写入。

所见即所得（WYSIWYG）要求编辑视图使用与运行时一致的数据、坐标、材质和约束，并把不可实时预览的差异明确显示。它不是单纯让窗口“看起来像最终画面”；真正标准是用户操作、预览和最终构建结果共享同一数据契约。

## 上下文与显式输入

DCC API 常有两种风格：

- Operator/命令依赖当前选择集、Mode、Active 视图；
- 数据 API 直接读取和修改对象。

交互操作可以借助 Context，但批处理应尽量显式传入对象、场景、路径和设置。必须使用 Operator 时，先验证 Context，再在 `finally` 中恢复选择集/Mode。

不要把 UI 显示名作为稳定身份。应使用对象引用、GUID、包路径或自有稳定ID。

## 编辑事务与撤销

### 序列化层

编辑器通常需要把任意对象映射成可读写属性树。Serialized 对象/Property 可以提供：

- 字段名称、类型与 Attribute 元数据；
- 嵌套对象、数组和引用；
- 读取旧值、验证新值；
- 生成补丁；
- 保存和版本升级。

属性绘制器只根据属性类型和附加标记决定用输入框、Slider、资产选择器或列表。Drawer 不直接绕过序列化层修改业务对象。

若 Inspector 走序列化属性，而 Gizmo 直接写变换，就形成两套数据真相，撤销、保存和运行时同步会不一致。

### 命令、补丁与事务

一次可撤销操作应记录足够信息：

- 目标稳定ID；
- Property/Operation；
- Old Value / New Value；
- Apply / Revert；
- 显示名称和时间。

一次用户手势可能产生许多补丁。拖动十帧不应让用户撤销十次，应合并成一个事务。

事务的撤销通常按子操作反序执行，重做按正序。创建/删除、层级变更和跨对象操作必须一起进入同一事务，不能只记录最后一个字段。

### Unity 与 Unreal 的撤销

Unity 工具应在修改前记录 `Undo.RecordObject` 或使用对应创建/销毁 API，并正确标记待更新/Prefab/场景。直接改序列化外的数据可能无法撤销或保存。

Unreal 编辑器对象通常需要事务/`Modify()`，工具还要区分资产、Actor、Component 和 Package 的保存职责。

具体 API 会随版本变化，应使用当前官方文档并写集成测试。核心原则是不绕过引擎事务和序列化系统。

### 事务执行与补偿

一个重命名事务可把 A 改为临时名、B 改为 A、临时名改为 B，再更新引用。每一步先保存反向操作，只有成功执行的步骤才加入已完成列表。若第三步失败，按反序恢复前两步；撤销整个成功事务则反序执行全部步骤。

```text
applied = []
try:
    for operation in plan:
        verify operation.precondition
        operation.apply()
        applied.append(operation)
except failure:
    failedCompensations = []
    for finished in reverse(applied):
        try: finished.revert()
        except recoveryFailure: failedCompensations.append(recoveryFailure)
    report failure, applied states and failedCompensations
    stop
```

这是进程内顺序执行的事务算法轮廓。每一步的前置条件检查都属于事务失败路径：后续操作的条件失效时，已经完成的操作仍需补偿。单步 `apply` 失败时必须保持原状，或由该步自行恢复部分修改后抛出异常。补偿步骤分别捕获错误，保证一次恢复失败后仍尝试其余反向操作。引擎撤销通常只覆盖登记的对象状态，外部文件和版本控制锁还需补偿或暂存发布。恢复也可能失败，因此记录原值、步骤状态与恢复结果，不能仅在异常处理中清空列表就宣称回滚完成。

本机验证：[独立样例](../examples/revision_09_15/README.md) 中的 `execute_plan` 运行了三项事务检查，覆盖后续前置条件失败、某次补偿失败后继续恢复，以及成功路径不触发补偿。它验证纯内存回调顺序；外部文件恢复、引擎撤销、并发隔离与进程崩溃后的持久恢复需要各自的集成验证。

## 批处理与失败恢复

### 预览与预演

预览不只是弹窗问“确定吗”。它应显示实际变更集：

- 将处理/跳过哪些资产；
- 重命名和移动的旧路径与新路径；
- 哪些 Setting 会变化；
- 哪些文件会覆盖或创建；
- 验证器错误/警告；
- 预计耗时与不可撤销操作。

变更预览与执行应走同一 Planning 逻辑。若预览单独重写一次规则，它可能和真实执行不一致。

可先生成 `Plan`，审查后由执行器应用：

```text
Input -> Analyze -> Plan -> Validate Plan -> Execute -> Verify -> Report
```

### 批处理

批处理不是对选择集做一个 `for` 循环。需要考虑：

- 输入枚举与稳定排序；
- 单项超时、重试和故障隔离；
- 进度、取消和断点续跑；
- 重入与幂等；
- 并行度和 DCC/引擎线程限制；
- 临时目录与原子写入；
- 汇总报告与退出码。

每项写独立结果，整个任务保存 Checkpoint。崩溃后可以从未完成项继续，而不是重新修改全部资产。

### 幂等与可重入

同一输入运行两次，应得到相同最终状态，第二次尽量不产生修改。

例如批量重命名：

- 先构建完整 Rename Map；
- 检查目标冲突和大小写问题；
- 必要时经临时名完成交换；
- 更新引用；
- 已符合目标的项目标记 Skip。

直接边遍历边改名，会让后续查询看到混合状态，也容易出现 A→B、B→A 冲突。

### 文件写入

输出到临时文件，Flush/Close 后验证，再用安全替换更新目标。不要在生成过程中直接截断正式文件。

跨多个文件的任务使用 Staging Directory 和清单。所有输出成功后再 Commit/Publish；失败时删除或保留带状态的 Staging，正式目录保持旧版本。

覆盖源文件前要确认版本控制状态、锁与权限。工具不应擅自覆盖用户未提交修改。

### 检查点与重复执行

以资产GUID和输入内容哈希组成工作项键，清单为每项保存输入哈希、工具版本、输出哈希和状态。开始先标记Running，输出写到暂存文件，验证后发布，再标记Succeeded。若进程在发布后、写检查点前退出，重启会看见Running；此时比较正式输出与本次期望哈希，一致即可补记成功，否则从未完成项重新生成。仅凭Running就再次追加对象或叠加缩放，会重复修改。

重试必须重新读取前置版本。用户在暂停期间修改了源资产，旧计划的输入哈希便失效，执行器应重新分析并显示新计划。多文件原子发布需要独立版本目录与清单切换，具体发布步骤见 [[15_资产与工具管线/资产构建与发布]]；逐文件替换无法保证读者看不到混合版本。

### 进度、取消与错误恢复

假设批处理按GUID排序得到A、B、C三个资产。A发布成功后写入Succeeded；B正在生成暂存输出，此时用户取消。执行器只设置取消标记，让B完成当前不可分割步骤，再于发布前检查标记。若尚未发布，清理或保留有状态的暂存输出，将B、C记为Cancelled，A保持Succeeded。若取消发生在B发布之后，则先核验并记入B的检查点，再停止，不能把已发布结果伪装成未执行。

进度由完成项数与总项数计算，3项中A完成时是1/3；新输入枚举完成后冻结总量，避免进度在执行中悄悄缩小。取消后的重跑先读检查点与输出哈希，跳过A，再验证B、C的前置版本。取消不是事务回滚：若产品要求整批撤销，则须保留全部逆操作并按反序执行，恢复失败继续记录到报告。

错误决定重试位置。参数或资产验证失败时不进入修改步骤，报告具体字段和GUID；文件服务超时可在有限次数内重试，但每次重新核对输入版本；磁盘满时保留暂存状态，先停止发布；执行器内部异常则保存栈和操作编号，进入前述补偿路径。同一错误反复重试却继续叠加修改，会破坏幂等契约。

编辑器对象只能由允许的线程修改。后台任务可以读取冻结输入并生成计划，主线程执行短事务和发布；完成通知携带计划版本。用户在分析期间又拖动对象时，版本不匹配的旧计划被拒绝并重新分析。仅把整个批处理搬到后台，会违反引擎API线程约束。

## 工具版本与数据契约

计划的内容由项目规则、工具版本和本次参数共同决定。例如项目规定名称前缀为角色ID，本次输入为角色17，计划输出17_body；用户偏好只保存窗口和最近目录，不能偷偷覆盖前缀，否则界面和CI的同一输入会生成不同结果。三类配置分别保存，参与结果计算的值都进入计划哈希。

配置模式也属于输入。旧配置将长度保存为厘米，新工具使用米时，迁移步骤把100转换成1并更新模式版本，再执行验证。只给缺失字段填默认值会让资产无声缩小100倍。项目锁定工具与依赖版本，升级时用同一组资产比较迁移计划和输出，失败可回到已锁定版本及原始输入；修改过的文件需要前述检查点或版本控制恢复。

界面与命令行共同调用生成计划、验证、执行和报告四个入口。界面增加选择器、预览和取消按钮，命令行把相同字段作为参数并返回退出码；两者使用相同GUID和配置得到相同计划哈希。属性面板的输入范围由领域验证提供，错误直接定位对象和字段，避免另写一套只在面板中成立的规则。

编辑器适配器和运行时数据分开构建。工具可依赖资产数据库和撤销系统，导出的运行时包只保存消费所需数据。以名称修正器为例，运行时读取修正后的资源引用，不加载重命名窗口或资产数据库接口。构建检查从运行时程序集的依赖闭包确认没有编辑器模块；命令行导出则明确启动包含这些模块的编辑器宿主。程序集名称包含Editor本身不能证明依赖隔离成立。

## 验证路径

先用A、B交换名称的小资产验证成功、第三步失败和补偿失败，再用三项批处理验证发布前取消、发布后检查点前崩溃、输入版本改变和重复运行。保存每次计划哈希、工作项状态、输出哈希与恢复结果，第二次执行已经完成的项应无内容差异。

随后在引擎中分别通过属性面板和Gizmo修改同一字段，撤销、重做、保存、重载后比对值；无界面入口读取同一输入，比较计划与输出。纯内存事务实验只覆盖回调顺序，文件服务中断、崩溃恢复、线程调度、配置迁移和编辑器程序集隔离尚需目标宿主集成测试，本文没有运行这些工程场景。
