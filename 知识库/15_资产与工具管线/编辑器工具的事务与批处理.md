# 编辑器工具的事务与批处理

拖动一个控件时，属性面板、Gizmo 和资产文件都可能变化。用户按一次撤销，期待这几份状态一起回到操作前。工具因此先把修改表示成计划与事务，再由同一执行路径用于界面和批处理，保存与失败恢复也沿这份变更集处理。

## 用户操作流程

以批量重命名为例，用户选择资产后，工具读取稳定ID与版本，生成旧名、新名、引用更新和冲突的变更预览。参数验证与正式执行都读取同一份计划；只读资产、名称冲突或缺失引用在修改前定位到具体ID。用户开始执行后看到按工作项统计的进度，取消在发布安全点生效，最终报告保存成功、跳过、冲突与恢复失败的位置。

交互只负责提供输入和展示这份状态。通过命令行传入相同资产ID、参数与规则版本，也会得到相同计划，界面中的隐式选择和当前视图不参与结果计算。撤销、发布和检查点由计划执行器统一处理，下面沿一次字段拖动和一批文件发布分别说明。

## 分层

职责按以下层次分配：

```text
UI / Command Line
    -> Application Service
        -> Domain Rules / Operations
            -> DCC or Engine Adapter
            -> File / VCS / Process Adapter
```

- UI 负责输入、展示和交互，不承载批处理算法；
- Application Service 编排用例、事务和进度；
- Domain 层处理命名、验证、映射和转换规则；
- 适配器封装 Maya/Blender/Unity/Unreal API 和外部进程。

这样无界面命令行、编辑器窗口和 CI 可以调用同一核心逻辑，避免“面板能用，命令行是另一套实现”。

MVC 与 MVVM 可以帮助拆分编辑器职责。MVC 中模型保存领域状态，视图展示，控制器把用户操作转换为命令；MVVM 用 ViewModel 暴露可绑定状态和命令，适合属性面板与响应式界面。具体框架可以不同，但 UI 控件不应直接承担资产规则和文件写入。

所见即所得（WYSIWYG）要求编辑视图使用与运行时一致的数据、坐标、材质和约束，并把不可实时预览的差异明确显示。它不是单纯让窗口“看起来像最终画面”；真正标准是用户操作、预览和最终构建结果共享同一数据契约。

## 上下文与显式输入

DCC API 常有两种风格：

- Operator/命令依赖当前选择集、Mode、Active 视图；
- 数据 API 直接读取和修改对象。

交互操作可以借助 Context，但批处理应尽量显式传入对象、场景、路径和设置。必须使用 Operator 时，先验证 Context，再在 `finally` 中恢复选择集/Mode。

不要把 UI 显示名作为稳定身份。应使用对象引用、GUID、包路径或自有稳定ID。

## 编辑事务与撤销

### 序列化层

编辑器通常需要把任意对象映射成可读写属性树。Serialized 对象/Property 可以提供：

- 字段名称、类型与 Attribute 元数据；
- 嵌套对象、数组和引用；
- 读取旧值、验证新值；
- 生成补丁；
- 保存和版本升级。

属性绘制器只根据属性类型和附加标记决定用输入框、Slider、资产选择器或列表。Drawer 不直接绕过序列化层修改业务对象。

若 Inspector 走序列化属性，而 Gizmo 直接写变换，就形成两套数据真相，撤销、保存和运行时同步会不一致。

### 命令、补丁与事务

一次补丁保存目标稳定ID、字段路径、旧值、新值与预期对象版本。旧值与新值采用可独立保存的序列化快照，不能让它们引用同一个随后继续修改的列表。Apply先确认对象和字段仍符合前置值，再写新值；Revert检查当前仍是本命令写入的值，再恢复旧值。对象被其他操作改变时，撤销提示冲突，避免用一份旧快照覆盖后来的编辑。

#### 手势合并

鼠标按下时开始手势，读取每个目标字段的初值并保存对象版本。拖动帧只更新事务的最终值，同时通过同一序列化入口预览到模型；初值始终保持按下时的值。松开时验证最终值，把整份补丁作为一条命令推入撤销栈，并清空重做栈；最终值等于初值的字段从命令移除，整份为空便结束手势。按Esc则恢复所有初值，关闭预览并结束手势，不产生撤销记录。

例如位置X从1依次预览为2、3、9，命令保存`old=1,new=9`。撤销恢复1，重做恢复9；如果每帧把old覆盖成当前值，最终只会退到3。多选拖动同时保存A、B的初值，验证所有目标后才开始预览；更新某目标失败时恢复本次手势已经触及的全部字段。预览期间以手势ID独占这些字段，其他窗口的修改排队或结束当前手势后另建命令，因此取消不会覆盖一个并发写入。

```text
Begin: capture stable IDs, versions and immutable old values
Update: validate target; replace new value; apply preview
Commit: validate all; drop unchanged patches; push one command
Cancel: restore old values in reverse order; discard gesture
Undo: verify final values; apply old values in reverse order
Redo: verify old values; apply new values in original order
```

这个轮廓要求所有值验证在发布命令前完成。对象版本会在每次实际编辑后递增，事务记录本次预览产生的版本；持有手势锁期间由自身写入导致的递增可以追踪，外来版本改变则中止并重新分析。命令的撤销和重做也更新版本，不能把旧版本号写回去伪装历史从未发生。编辑器宿主已有成熟撤销系统时，适配器把手势分组映射到宿主事务，避免再叠加一套独立撤销栈。

#### 创建、删除与引用

创建命令在第一次Apply前分配稳定ID，并记录完整对象快照、父ID、兄弟顺序与引用关系。Undo删除同一个ID，Redo用同一个ID恢复；每次重做分配新ID会使其他对象的引用失效。删除命令反过来保存被删对象与受影响引用的快照，恢复时先建立全部对象身份，再接父子关系，最后恢复交叉引用。这样A引用B时，即使恢复顺序先遇到A，也不会把尚未恢复的B误判成永久丢失。

稳定ID在命令仍可能撤销或重做时保留，不分配给新对象。若宿主对象引用在销毁后失效，命令通过自有ID到当前宿主对象的映射重新解析，不能继续使用旧指针。删除一个父节点连带删除子节点时，快照涵盖整棵子树及外部引用处理规则；只保存父节点字段无法重建其子对象。

创建、引用重定向和删除组成一个事务时，重做按依赖顺序创建对象、设置引用、删除旧对象，撤销按反序恢复。恢复所需资产和类型在执行前验证；缺少类型时保留失败记录和快照，禁止把部分恢复显示成成功。对象身份和字段补丁因此使用同一执行器，事务才真正覆盖用户看见的整个操作。

### Unity 与 Unreal 的撤销

Unity 6000.0中，`Undo.RecordObject`在修改前保存对象临时副本，帧末比较字段差异，将变化写入撤销记录。工具在每个实际修改帧先记录再赋值，手势适配器把这些帧归入同一宿主事务组；仅在松开时记录对象，会把已经发生的预览当成初值。父子关系变更、添加组件和销毁对象使用对应专用撤销接口，普通字段记录不能替代这些操作。Prefab实例修改还调用`PrefabUtility.RecordPrefabInstancePropertyModifications`保存实例覆盖，场景及资产保存沿各自宿主入口执行。

Unreal把一次手势映射为跨越该手势寿命的`FScopedTransaction`，创建时开始记录，正常结束时结束记录。游戏线程在第一次实际改动前对每个受影响、可事务化对象调用`Modify()`，把修改前序列化状态放入宿主撤销缓冲。成员数组在父对象中变化就记录父对象；组件自身字段变化还记录组件，单记Actor不会自动覆盖所有独立UObject。拖动期间保留同一事务，不能每帧局部创建和销毁一个作用域对象，否则仍形成多次撤销。

属性面板使用`IPropertyHandle::SetValue`时，句柄负责属性前后通知、事务和包修改，适配器沿该入口更新，避免再重复手工发相同通知。直接写字段的自定义Gizmo则在修改前记录对象并发`PreEditChange`，写入后发带字段信息和Interactive/ValueSet类型的`PostEditChangeProperty`；松开再通知本次持续修改结束。通知使依赖该属性的重建与视图刷新发生，撤销记录负责恢复值，两者各有用途。资产被构造脚本或重建逻辑替换后，重新按稳定ID解析目标，不能继续使用修改前缓存的组件指针。

Actor创建通过编辑器的放置/工厂入口，例如`UEditorEngine::AddActor`并使用可事务化对象标记；删除通过`UEditorActorSubsystem::DestroyActor`等编辑器入口，同时维护选择、关卡及受影响引用。层级和组件增删把所属容器、旧父节点和新父节点一起登记，和前面的对象快照保持同一事务边界。直接运行时Spawn/Destroy、只记录最后一个属性，不能替代编辑器维护的对象集合变化。

取消手势先按保存的初值恢复已预览字段，并走对应属性通知，再取消事务记录；外部文件按补偿清单处理。`FScopedTransaction::Cancel()`与恢复文件、撤销已执行远程操作属于不同动作，工具不依赖它提供跨资源数据库回滚。恢复失败保留诊断及快照。对象的包被标为Dirty只表示需要保存，不表示已经写入磁盘；`Modify`可标脏，必要的显式写入调用`MarkPackageDirty`，最后由保存入口执行权限、版本控制和文件发布检查。取消后也不能无条件把整包标成干净，包里其他字段可能有本手势之外的编辑。

2026-10-23核读的`IPropertyHandle`接口固定为UE5.6；`FScopedTransaction`、`Modify`与编辑器Actor入口引用Epic当前API页。作用域、修改前记录和保存职责按这份接口契约组织，接入工程锁定实际引擎版本后检查所用入口的签名及嵌套事务行为。

具体 API 会随版本变化，应使用当前官方文档并写集成测试。核心原则是不绕过引擎事务和序列化系统。

### 事务执行与补偿

一个重命名事务可把 A 改为临时名、B 改为 A、临时名改为 B，再更新引用。每一步先保存反向操作，只有成功执行的步骤才加入已完成列表。若第三步失败，按反序恢复前两步；撤销整个成功事务则反序执行全部步骤。

```text
applied = []
try:
    for operation in plan:
        verify operation.precondition
        operation.apply()
        applied.append(operation)
except failure:
    failedCompensations = []
    for finished in reverse(applied):
        try: finished.revert()
        except recoveryFailure: failedCompensations.append(recoveryFailure)
    report failure, applied states and failedCompensations
    stop
```

这是进程内顺序执行的事务算法轮廓。每一步的前置条件检查都属于事务失败路径：后续操作的条件失效时，已经完成的操作仍需补偿。单步 `apply` 失败时必须保持原状，或由该步自行恢复部分修改后抛出异常。补偿步骤分别捕获错误，保证一次恢复失败后仍尝试其余反向操作。引擎撤销通常只覆盖登记的对象状态，外部文件和版本控制锁还需补偿或暂存发布。恢复也可能失败，因此记录原值、步骤状态与恢复结果，不能仅在异常处理中清空列表就宣称回滚完成。

本机验证：[独立样例](../examples/revision_09_15/README.md) 中的 `execute_plan` 运行了三项事务检查，覆盖后续前置条件失败、某次补偿失败后继续恢复，以及成功路径不触发补偿。它验证纯内存回调顺序；外部文件恢复、引擎撤销、并发隔离与进程崩溃后的持久恢复需要各自的集成验证。

## 批处理与失败恢复

### 预览与预演

预览不只是弹窗问“确定吗”。它应显示实际变更集：

- 将处理/跳过哪些资产；
- 重命名和移动的旧路径与新路径；
- 哪些 Setting 会变化；
- 哪些文件会覆盖或创建；
- 验证器错误/警告；
- 预计耗时与不可撤销操作。

变更预览与执行应走同一 Planning 逻辑。若预览单独重写一次规则，它可能和真实执行不一致。

可先生成 `Plan`，审查后由执行器应用：

```text
Input -> Analyze -> Plan -> Validate Plan -> Execute -> Verify -> Report
```

### 批处理

批处理不是对选择集做一个 `for` 循环。需要考虑：

- 输入枚举与稳定排序；
- 单项超时、重试和故障隔离；
- 进度、取消和断点续跑；
- 重入与幂等；
- 并行度和 DCC/引擎线程限制；
- 临时目录与原子写入；
- 汇总报告与退出码。

每项写独立结果，整个任务保存 Checkpoint。崩溃后可以从未完成项继续，而不是重新修改全部资产。

### 幂等与可重入

同一输入运行两次，应得到相同最终状态，第二次尽量不产生修改。

例如批量重命名：

- 先构建完整 Rename Map；
- 检查目标冲突和大小写问题；
- 必要时经临时名完成交换；
- 更新引用；
- 已符合目标的项目标记 Skip。

直接边遍历边改名，会让后续查询看到混合状态，也容易出现 A→B、B→A 冲突。

### 文件写入

输出到临时文件，Flush/Close 后验证，再用安全替换更新目标。不要在生成过程中直接截断正式文件。

跨多个文件的任务使用 Staging Directory 和清单。所有输出成功后再 Commit/Publish；失败时删除或保留带状态的 Staging，正式目录保持旧版本。

覆盖源文件前要确认版本控制状态、锁与权限。工具不应擅自覆盖用户未提交修改。

### 条件发布与检查点恢复

工作项键由资产GUID、输入内容哈希、工具版本和参数哈希组成。计划同时记录输出当前的代次g及内容哈希，暂存结果具有期望哈希H。输入版本决定这份计算是否仍适用，输出代次决定它是否仍有权发布；两者分别检查，源资产没变并不意味着正式输出没被人编辑。

将结果写到独立的不可变版本目录，关闭并刷出文件，重新读取核对H，再进入短的发布事务。事务条件比较输入版本和输出代次仍与计划一致；成立时，把资产的当前版本指针从g切到g+1，并同时保存工作项ID、H和发布回执。读者先读指针，再读该版本目录，因此不会看到半套输出。最后的Succeeded是报告状态，可以在发布事务之后补写；证明发布发生的是与指针共同提交的回执。

```text
Plan: save input hash, tool/config hash, expected output generation g
Build: write immutable output version; validate content hash H
Publish transaction:
  compare current input hash and current output generation with Plan
  set current output pointer to new immutable version at g+1
  save receipt(jobId, g+1, H)
Commit
Checkpoint: mark Succeeded
```

条件比较与指针切换属于同一个原子操作。对普通文件执行“读取哈希→发现一致→替换”仍有检查与替换之间的竞态，单次原子重命名也不会替调用方比较版本。资产服务可用数据库条件更新；本地工具可在覆盖全过程持有所有写入者共同遵守的资产锁。任意外部程序可以直接修改正式路径时，协作锁不成立，工具只能改为输出新的版本路径并报告冲突，由用户选择采用，不能自动声称安全覆盖。

重启看到Running时，先查持久发布回执。没有回执且输出代次仍等于g，说明尚未发布，重新核对输入后可复用暂存结果。存在回执且当前仍是回执中的g+1、哈希H，说明发布已完成，补记Succeeded即可。存在回执但当前代次更大，或内容与H不符，说明发布后发生了其他编辑，标记Conflict并保留当前输出和旧计划；只有重新生成计划并采用当前版本作为前提，才可再次发布。

例如计划看到输出代次10，发布结果成为11，进程在补记成功前退出。用户随后编辑成代次12。恢复时即使源输入没变，也不能把11再次覆盖到12。另一个反例是输出内容先改成别的值又改回原值：内容哈希相同，代次已从10增到12，旧计划仍拒绝。代次单调递增使这种往返修改可见；所有正式写入者都要通过同一发布入口更新代次。

若希望已发布批次整体撤销，保留前一版本指针，并在撤销时条件比较当前仍是本批次的发布代次，再切向旧内容的新代次。直接把代次减回原值会使旧计划再次匹配。多个文件的版本目录与清单切换见 [[15_资产与工具管线/资产构建与发布]]；其中旧版本只有在没有读者、检查点和撤销记录引用后才能回收。

[持久参考实现](../examples/mechanism_chain/protocol/reference.py)把内容存为SQLite BLOB，并把代次、发布回执与指针等价的当前资产记录放在同一数据库事务内。它演示了真正原子的条件发布；接入文件目录时，BLOB对应不可变文件及其已验证引用，文件必须先可读，再提交引用。文件刷盘和目录元数据持久性由目标平台提供，数据库事务不能替外部文件完成刷盘。

### 进度、取消与错误恢复

假设批处理按GUID排序得到A、B、C三个资产。A发布成功后写入Succeeded；B正在生成暂存输出，此时用户取消。执行器只设置取消标记，让B完成当前不可分割步骤，再于发布前检查标记。若尚未发布，清理或保留有状态的暂存输出，将B、C记为Cancelled，A保持Succeeded。若取消发生在B发布之后，则先核验并记入B的检查点，再停止，不能把已发布结果伪装成未执行。

进度由完成项数与总项数计算，3项中A完成时是1/3；新输入枚举完成后冻结总量，避免进度在执行中悄悄缩小。取消后的重跑先读检查点、发布回执和输出代次，核对A仍对应其已发布结果，再验证B、C的前置版本；若A后来被编辑，同样记录冲突而不是覆盖。取消不是事务回滚：若产品要求整批撤销，则须保留全部逆操作并按反序执行，恢复失败继续记录到报告。

错误决定重试位置。参数或资产验证失败时不进入修改步骤，报告具体字段和GUID；文件服务超时可在有限次数内重试，但每次重新核对输入版本、输出代次与发布回执；磁盘满时保留暂存状态，先停止发布；执行器内部异常则保存栈和操作编号，进入前述补偿路径。同一错误反复重试却继续叠加修改，会破坏幂等契约。

编辑器对象只能由允许的线程修改。后台任务可以读取冻结输入并生成计划，主线程执行短事务和发布；完成通知携带计划版本。用户在分析期间又拖动对象时，版本不匹配的旧计划被拒绝并重新分析。仅把整个批处理搬到后台，会违反引擎API线程约束。

## 工具版本与数据契约

计划的内容由项目规则、工具版本和本次参数共同决定。例如项目规定名称前缀为角色ID，本次输入为角色17，计划输出17_body；用户偏好只保存窗口和最近目录，不能偷偷覆盖前缀，否则界面和CI的同一输入会生成不同结果。三类配置分别保存，参与结果计算的值都进入计划哈希。

配置模式也属于输入。旧配置将长度保存为厘米，新工具使用米时，迁移步骤把100转换成1并更新模式版本，再执行验证。只给缺失字段填默认值会让资产无声缩小100倍。项目锁定工具与依赖版本，升级时用同一组资产比较迁移计划和输出，失败可回到已锁定版本及原始输入；修改过的文件需要前述检查点或版本控制恢复。

界面与命令行共同调用生成计划、验证、执行和报告四个入口。界面增加选择器、预览和取消按钮，命令行把相同字段作为参数并返回退出码；两者使用相同GUID和配置得到相同计划哈希。属性面板的输入范围由领域验证提供，错误直接定位对象和字段，避免另写一套只在面板中成立的规则。

编辑器适配器和运行时数据分开构建。工具可依赖资产数据库和撤销系统，导出的运行时包只保存消费所需数据。以名称修正器为例，运行时读取修正后的资源引用，不加载重命名窗口或资产数据库接口。构建检查从运行时程序集的依赖闭包确认没有编辑器模块；命令行导出则明确启动包含这些模块的编辑器宿主。程序集名称包含Editor本身不能证明依赖隔离成立。

## 验证路径

先用A、B交换名称的小资产验证成功、第三步失败和补偿失败，再用三项批处理验证发布前取消、发布后检查点前崩溃、输入版本改变和重复运行。保存每次计划哈希、工作项状态、输出代次、输出哈希与恢复结果，第二次执行已经完成的项应无内容差异。还要在发布后插入一次外部编辑，确认恢复进入Conflict并保留该编辑。

从仓库根目录执行以下命令：

```powershell
python -B 知识库/examples/mechanism_chain/protocol/test_protocol.py
```

15项本机检查中，工具部分覆盖1→2→3→9手势的首值、末值、撤销和重做，取消预览，发布回执恢复，发布后外部编辑以及内容往返修改后的代次冲突。相同文件还用真实子进程强退检查SQLite提交前后恢复，为共同提交的边界提供可重复观察。三项补偿检查见前文`execute_plan`。这些实验分别观察手势状态与持久发布结果。

接入引擎时，分别通过属性面板和Gizmo修改同一字段，撤销、重做、保存、重载后比对值；无界面入口读取同一输入，比较计划与输出。再删除带外部引用的父子对象，撤销后核对稳定ID、层级和引用；强制丢失某种资产类型时应得到可恢复失败。引擎撤销、文件刷盘和程序集隔离需要目标宿主集成验证，本机SQLite结果不代表这些工程场景已经执行。
