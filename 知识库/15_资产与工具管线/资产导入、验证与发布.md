# 资产导入、验证与发布

资产管线要把制作源转换成引擎可用、可追踪、可回滚的发布物。成熟流程不依赖某个人记住所有选项，而是把契约、验证、转换和状态写入工具与记录。

## 数据流

一条典型链路：

```text
Authoring Source
  -> DCC Validation
  -> Export / Interchange
  -> Staging
  -> Engine Import
  -> Derived Data
  -> Runtime Cook / Bundle
  -> Publish Manifest
```

每一步都应知道输入、输出、工具版本和失败状态。直接把 DCC 文件拖进最终目录，会把导出选项、依赖和人工修复隐藏在个人电脑中。

## Asset Identity

文件名会改，目录会移动，稳定身份不应只依赖路径。引擎常使用 GUID、Package Path 或内部 Asset ID 管理引用。

命名规范仍有价值，它服务人类检索、批处理和类型判断。但 Rename/Move 必须通过理解引用的 API 完成，不能让文件管理器移动后再人工修断链。

一个 Asset Record 可包含：

- Stable ID；
- Logical Name/Type；
- Source Path 与 Owner；
- Output Path；
- Dependency；
- Tool/Schema Version；
- Content Hash；
- Publish State。

## Importer 是编译器

Importer 把交换格式翻译成引擎内部数据，和编译器很像：

- 解析 Source；
- 校验 Schema；
- 规范化坐标与属性；
- 生成 Mesh/Texture/Animation/Material；
- 计算 Derived Data；
- 写依赖与诊断。

同一输入、配置和工具版本应产生相同输出。若 Import 依赖当前 Selection、时间、随机数或机器绝对路径，CI 和其他成员就难以复现。

## Hash 与增量构建

是否需要重建应由内容与配置决定，而不是只看文件修改时间。可计算：

$$
H_{build}=Hash(H_{source},H_{settings},V_{tool},V_{schema},H_{deps})
$$

Build Hash 不变就复用缓存；任一输入变化就使对应节点和下游失效。

Hash 只说明输入相同，不保证工具本身确定性。多线程顺序、浮点、压缩器和未固定随机种子仍可能让输出不同。可在 CI 对同一输入构建两次比较 Hash。

## Validator 的层级

验证可以分为：

- **结构**：文件可读、Schema、对象/骨骼/材质槽存在；
- **规范**：命名、目录、单位、轴向、Pivot；
- **预算**：Vertex、Texture Size、Bone、Influence、Material/LOD 数量；
- **语义**：Normal/Tangent、颜色空间、Root Motion、Collision；
- **依赖**：缺失贴图、循环引用、Editor-only 引用、重复资源；
- **运行时**：平台格式、内存、Shader Variant、Cook 与加载测试。

每条规则应有稳定 Rule ID、Severity、对象位置、实际值、期望值和修复建议。只打印“资源错误”无法让美术自助解决。

## Error、Warning 与 Info

Severity 代表是否阻止发布：

- Error：数据错误、构建失败或确定违反上线预算；
- Warning：有风险但存在合理例外；
- Info：统计、建议或可优化项。

规则应允许按资产类型和平台配置。Hero Character 与远景 Prop 不应使用同一 Vertex 上限。例外必须有原因、Owner 和过期时间，不能通过关闭整个规则解决。

## Auto-fix 的边界

安全 Auto-fix 通常满足：结果确定、可预览、可撤销、不会丢失创作信息。例如：

- 规范文件名大小写；
- 创建缺失目录；
- 设置已确认的 Import Preset；
- 清理无引用的空材质槽；
- 生成缺失的 Metadata。

高风险操作应只报告或在副本中处理：重新拓扑、合并骨骼、覆盖源文件、改变 UV、强制压缩有损贴图。

批量修复前输出 Dry-run 计划，列出将修改的文件、规则和前后值。

## DCC 侧与引擎侧分工

DCC 侧更适合检查：

- 非法历史、隐藏对象、Freeze/Transform；
- Skeleton、Constraint、Bake Range；
- UV、Non-manifold、命名和导出集；
- Source Texture 与引用路径。

引擎侧更适合检查：

- 实际导入 Vertex/Index/Bone；
- Material/Shader/Texture 设置；
- LODGroup、Collision、Bounds；
- Runtime Reference、Bundle 与平台预算。

同一规则可两端各检查一次，但错误信息要区分“源数据错误”和“导入配置错误”。

## Import Preset 与规则匹配

Importer 设置应按 Asset Type/Path/Metadata 匹配，而不是所有文件同一配置。例如：

- Character Mesh 导入 Skin/Blendshape，Prop 不导入；
- UI Texture 关闭 Mipmap，World Texture 开启；
- Normal Map 使用数据语义和平台压缩；
- Lightmap UV 只对特定静态 Mesh 生成；
- Animation Clip 使用对应压缩误差。

自动修改 Import Setting 可能触发 Reimport。脚本必须防止 Import Callback 递归，且只在配置真正变化时写回。

## Derived Data

LOD、Collision、Lightmap UV、Texture Compression、Shader Compile 和平台 Mesh 都属于可再生成数据。它们应由 Source + Settings 重建，尽量进入共享缓存而不是让每个人提交机器产物。

但昂贵且不可稳定重建的离线模拟/烘焙可能需要版本化。判断标准是：重建时间、许可证、确定性、来源可用性和审查需求。

## Schema 与迁移

Asset Metadata、Importer Setting 和运行时数据都会演进。每份可持久化数据应记录 Schema Version，读取时执行显式迁移：

```text
v1 -> v2 -> v3 -> current
```

迁移函数应可测试、可重复运行，并保留未知字段或给出明确错误。直接用当前默认值覆盖旧字段，会让资产表面“导入成功”，实际语义已经改变。

批量迁移前先扫描影响数量和不可逆步骤，生成备份/Changeset。迁移后运行 Reimport、引用和目标平台 Cook，不能只检查序列化文件能打开。

## 依赖图与循环

导入顺序来自 Dependency Graph。Texture 可先于 Material，Material 可先于 Prefab/Level；图中有环时，简单拓扑排序无法执行。

需要区分真正构建依赖和运行时软引用。可以通过 Stable ID/Deferred Resolve 打断非必要强依赖。对不可避免的环，先建立对象壳，再进行第二阶段引用解析，而不是依赖文件枚举顺序。

依赖变化要触发正确下游失效。若 Material 只记录 Texture Path 而未进入 Dependency Database，Texture 更新可能不会使 Bundle 重建。

## Reimport 与人工修改

自动 Reimport 不能覆盖引擎内人工数据。应明确哪些字段由 Source Authoritative，哪些是 Engine Override。

例如 Mesh Geometry 来自 FBX，但 Collision、LOD Screen Size 或 Material Override 可能在引擎维护。Importer 应保留这些 Override，或把它们放入独立配置资产。若必须覆盖，应在 Preview 中显示丢失内容并阻止静默执行。

## Staging 与原子发布

构建不应直接覆盖当前正式版本。先写 Staging：

1. 生成全部输出；
2. 运行验证与加载测试；
3. 写 Manifest；
4. 成功后原子切换 Published Pointer/Version；
5. 失败则保留上一版本。

这样可以避免批处理到一半时正式目录处于新旧混合状态。

文件移动在同一卷上可能原子，但跨系统发布通常需要版本目录和指针/数据库状态，不应假设复制整个文件夹是原子操作。

## Manifest 与数据血缘

Publish Manifest 记录：

- Asset ID 与发布版本；
- Source/Dependency Hash；
- Tool、Plugin、Engine 和 Schema Version；
- Build 参数与目标平台；
- 输出文件、大小和 Hash；
- Validator 结果与批准例外；
- 构建者、时间、CI Job/Commit。

出现问题时应能从运行时资源追溯到 Source、设置和工具版本，也能查一个 Source 影响哪些 Bundle/Level。

## 用户可读的失败报告

报告按 Asset 和责任分组，不要输出几万行无结构日志。每项提供：

- `Rule ID + Severity + Asset`；
- 问题位置；
- 实际/期望；
- 能否 Auto-fix；
- DCC/引擎中的定位方式；
- 文档链接。

批处理结束要给 Summary：成功、警告、失败、跳过和耗时。错误日志应可保存为 JSON 供 CI 和 Dashboard 使用，也有人类可读 HTML/Markdown。

## 发布门禁

门禁可以逐步提高：

- 本地保存时快速检查；
- 提交前检查受影响资产；
- CI 对变更集做完整 Validator/Cook；
- Nightly 对全库与目标设备做回归；
- Release 构建使用冻结工具链和更严格预算。

本地反馈必须快。把所有检查都推到夜间 CI，会让错误隔天才返回，修复上下文已经丢失。

## 验证方法

- 用合法、边界和故意损坏的 Fixture 测每条 Validator。
- 同一资产重复 Import，确认无无意义 Diff 和无穷 Reimport。
- 修改 Source、Settings、Tool Version、Dependency，确认增量失效范围正确。
- 模拟中途失败，确认 Published 版本不被破坏。
- 从 Manifest 反查 Source 和从 Source 查询下游依赖。
- 在至少一个目标平台执行 Cook/Load，不以 Editor 预览代替运行时验收。
