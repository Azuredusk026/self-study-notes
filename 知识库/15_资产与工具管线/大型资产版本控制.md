# 大型资产版本控制

二进制源文件每次修改形成独立逻辑版本，底层存储是否差分取决于系统，两人同时编辑时字节合并并不理解创作内容。大型资产版本控制需要同时安排历史、带宽、锁和文件粒度，构建验证再确认一个提交确实能生成结果。

## 文本与二进制的差异

代码、JSON、YAML 等文本可以按行比较差异并合并。`.psd`、`.blend`、`.mb`、贴图、音频等二进制通常只能整体替换。

两人同时编辑同一二进制时，最后必须选一个版本或人工在 DCC 重做合并。工具无法凭字节差异理解“保留 A 的角色、B 的灯光”。

因此协作策略包括：

- 独占锁；
- 按资产/关卡/图层拆分文件；
- Ownership 与任务划分；
- 在可组合格式中使用层/Reference；
- 尽早同步和短生命周期分支。

## 历史与存储服务

### Git 的对象历史

普通 Git 克隆会获得分支可达历史对象。大二进制每次更新都产生新 Blob，即使删除当前文件，历史仍持续占空间。

Git 擅长分支与文本合并，但大型资产库会遇到克隆、拉取、检出和仓库维护成本。ZIP 封装不能保证有效差分：压缩数据的局部修改可能改变大段字节，Git 的对象差分压缩也不等于可理解的资产内容对照。审查仍需网格、图像或元数据的专用产物。

### Git LFS

Git LFS 用小型指针文件替代 Git 中的大文件内容，真实对象存储在 LFS 服务。`.gitattributes` 决定哪些模式经过 LFS Filter。

指针大致记录版本、对象标识和尺寸。检出时 Smudge/Filter 下载真实内容。

它解决 Git 主对象库被大文件快速撑大的问题，但不自动解决：

- 二进制合并；
- 服务器存储与带宽配额；
- 已经以普通 Git 提交的大文件历史；
- CI 是否拉取 LFS；
- 文件锁流程；
- 海量小文件的元数据/检出开销。

`.gitattributes` 应在大文件首次提交前配置并进入版本控制。把历史迁移到 LFS 会重写 Commit ID，需要团队统一计划，不能个人随意执行。

### Git LFS Lock

对不可合并格式可启用 Lockable。用户编辑前锁文件，提交后解锁。工具可在 DCC 打开/保存时显示锁负责人。

锁是协作协议，不是完整权限系统。离线编辑、绕过客户端或强制解锁仍可能产生冲突。团队要定义：谁能强制解锁、请假/离职锁如何处理、锁多久提醒。

### Perforce Helix Core

Perforce 是集中式版本控制，常用于大型游戏资产。基本概念：

- Depot 保存版本；
- Workspace 映射本地文件；
- Changelist 组织一次提交；
- 文件类型可设置二进制、文本、独占锁；
- Stream 组织主线与分支；
- Shelve 用于共享未提交改动和审查。

集中式模型便于权限、锁和大型二进制管理。成员可以只同步 Workspace 视图需要的目录，不必获得全部历史内容。

代价是服务器运维、网络依赖、Workspace/Stream 规则和管理员治理。错误的视图或大规模自动 Reconcile 也会制造大量无关变更。

### PlasticSCM / Unity Version Control

PlasticSCM（Unity Version Control）提供 Changeset、Branch、合并、Lock 和面向非程序用户的 Gluon 工作流。Gluon 允许用户选择性下载和提交，不要求理解完整分支模型。

它适合需要分支能力、同时有大量美术成员的团队。实际采用前需要验证：

- 云/自建服务与区域网络；
- 大文件存储和计费；
- Lock Rule；
- Unity/IDE/DCC 集成；
- CI CLI 和服务账号；
- 分支/合并与美术日常流程。

工具名称、许可证和服务能力可能变化，应以当前官方文档为准。

### 选择方案

不是简单按团队人数决定。要测：

- 资产总量、日增量和单文件大小；
- 文本/二进制比例；
- 分支与发布数量；
- 地域、网络和远程办公；
- 锁的频率与粒度；
- 权限与外包隔离；
- CI/构建 Farm 并发；
- 备份、灾备、审计和成本。

用真实项目样本做克隆/同步、Switch、提交、锁、CI 和恢复演练，比根据宣传功能表选择可靠。

## 协作与恢复

### 文件粒度

版本控制无法弥补不合理的资产结构。一个 20 GB 单体关卡会让锁和提交都难以并行。

可拆分：

- World Partition/关卡实例/Sublevel；
- Prefab/Blueprint/场景对象；
- USD 层/Reference；
- 材质、模型、动画与贴图独立资产；
- 配置与生成缓存分离。

拆得过细又会增加引用、加载和文件数量。边界应对应 Ownership、并行编辑和运行时职责。

### 派生文件

Generated/派生数据分三类：

- 可快速确定重建：忽略并缓存；
- 重建昂贵但确定：共享构建缓存/产物；
- 不可稳定重建或需要审查：作为正式资产版本化。

忽略规则、LFS 模式和构建输出目录要由管线维护。个人临时文件、Autosave、Library/DerivedDataCache 不应进入提交。

### 分支、主干与合入队列

二进制资产不适合长期分支。两个分支分别修改同一场景或源文件，数周后几乎无法自动合并。资产团队通常更适合短生命周期任务分支、频繁同步主干和明确锁定。

一次 Changelist/Changeset 应表达一个可审查工作单元。模型、贴图、材质和引用调整若共同构成同一交付，应一起提交，避免主干出现“模型已换但材质还没来”的中间状态。

大型团队可使用合并 Queue：候选变更先在目标主干最新状态上 Rebase/合并，运行验证器、Cook 和测试，通过后再按队列合入。这样减少多个“各自在旧主干上通过 CI”的变更连续合入后互相破坏。

发布 Branch 要限制内容回灌。修复应有明确 Cherrypick/Integrate 记录，避免同一二进制在主干和发布分支被独立修改后无法判断哪个是权威版本。

### 二进制资产审查

Code 审查页面看不到 `.fbx` 或 `.uasset` 的有意义差异。管线可以自动生成审查产物：

- 前后 Turntable/Screenshot/Video；
- 包围范围、顶点、材质、骨骼、纹理和内存差异；
- 引用增加/删除与资源包影响；
- 验证器结果和预算变化；
- DCC 源数据、导入器 Setting 和工具版本；
- 场景/Prefab 的结构化语义差异。

Perforce Shelve、Git PR 产物或 Plastic Changeset 预览都可承载这些结果。审查者关注视觉和数据变化，而不是对无法阅读的二进制文件直接批准。

自动截图要固定相机、灯光、曝光、背景和引擎版本。否则环境变化会制造无意义差异。

### 锁与任务系统

锁信息应出现在 DCC/Editor 内，而不是等保存失败才发现。资产面板可以显示负责人、任务、分支、锁时间和联系方式。

锁最好与任务边界一致：一个人负责角色网格，另一人仍可编辑独立动画和材质。若所有内容嵌在一个源文件里，锁粒度只能粗化，这也是拆分源资产的理由。

长时间锁应自动提醒，但不能在用户仍有未提交修改时自动释放。强制解锁前先联系负责人、保存 Shelve/备份，并留下审计记录。

### 跨职能合作

技术规则要和美术、策划、程序共同制定。有效流程：

1. 用实际失败案例和性能数据说明问题；
2. 定义可交付结果与责任边界；
3. 先提供本地快速检查和清楚修法；
4. 再把同一规则放入 CI 门禁；
5. 对合理例外设置负责人和到期时间；
6. 统计高频失败，优先改工具而不是反复培训。

冲突不应只靠“谁的职位高”。区分视觉目标、技术约束、排期和工具缺口，用可复现测试讨论取舍。

### 故障与恢复

- 定期验证 Server Backup 可恢复，不只确认备份任务成功。
- 演练误删、错误提交、锁遗留和 LFS 对象缺失。
- CI 产物有保留期与不可变版本号。
- 发布使用 Tag/Label/Changelist + 清单可复现。
- 大规模迁移先在镜像库验证，并冻结写入窗口。

版本控制不是备份的替代品。权限误操作、服务器损坏和恶意删除都需要独立备份与审计。

### 并行修改合入

两个人改同一资产时，版本库只能保存字节变化，未必理解绑定、材质和图层怎样合并。能做语义合并的文本资产先验证合并结果；缺乏可靠合并器的二进制源使用锁或明确交接。CI 再把提交中的源、工具版本和配置一起重建，才能证明某个版本可复现，而不只是文件已经上传。

## 检出契约

这是版本工具中立伪代码，stablePath来自项目资产数据库。锁和写权限由实际服务检查。

```text
verify current revision and lock owner
sync required source and LFS objects
edit under agreed ownership
submit source, metadata and dependency changes together
release lock after successful submission
```

检出验证可以用内容哈希连接两层存储。Git 中的指针声明 LFS 对象的 SHA-256 和字节数，工作区取得真实文件后计算同样的值，两者一致才说明这次输入到位。版本库提交成功但 LFS 上传失败时，其他机器仍可能拿不到对象；提交和对象可用性应共同进入构建检查。恢复演练既恢复 Git 元数据，也恢复 LFS 对象与访问配置。

## 验证方法

从干净工作区检出指定提交，检查大文件对象实际到位。模拟锁冲突、离线编辑与部分提交，确认源和metadata成组恢复。二进制语义合并以工具支持为条件。
