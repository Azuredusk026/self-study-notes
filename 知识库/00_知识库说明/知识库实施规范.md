# 知识库实施规范

知识库面向引擎开发者与技术美术，文章以一个主要技术问题为单位。结构、正文、代码、图片和证据共同构成作者工作流。

## 文章决策

每篇分别记录文章边界与正文动作。边界描述概念去向，正文动作描述实际工作，可以有多项。

| 字段 | 取值与用途 |
|---|---|
| `boundary_action` | KEEP保持主问题；SPLIT分开独立问题；MERGE归入同一主问题；OVERVIEW负责关系与路线；REDIRECT提供跳转 |
| `content_actions` | KEEP有效正文；REWRITE重写叙述；DEEPEN补机制与实现；FACT-CHECK核对断言；RESTRUCTURE重建语义层级 |
| `writing_review` | 通过、需重写、待复读；记录章节和具体依据 |
| `title_review` | PASS、REWRITE、SPLIT、OVERVIEW；记录标题审查结论；本轮全部页面已有结论，SPLIT/OVERVIEW保留延后采用状态 |
| `category_review` | PASS、RECLASSIFY、SPLIT、MERGE、CREATE、OVERVIEW；目录与文章归属分别记录 |

例如NPR材质页可以保持边界，同时重建层级并重写正文。只按边界动作筛选任务会漏掉阅读体验与证据工作，执行时以正文动作和质量矩阵追踪完成状态。

一个问题可包含多种方案。描边可比较壳扩张、模板、屏幕检测和手绘结构线；Billboard的锚点与假深度进入独立问题。拆分前比较输入输出、前提、实现、调试、来源和维护频率。只有概要材料的候选先承担导读职责。

## 标题与命名规范

标题首先表达文章的主要问题或核心概念。标题负责定位，H2/H3负责展开内部机制。理解正文后再命名：读取全文、标题树、代码与相关主题，确认范围、方案家族和概念主归属。

标题不是内容目录。H2/H3承担技术组成，标题让读者形成准确的阅读预期。缩短之后重新检查覆盖度：只读标题时，对象、主要问题和重要限定是否仍然明确，预期范围是否明显大于或小于正文。必要限定词保留；独立问题先处理文章边界，短标题不能掩盖边界问题。

### 按文章职责选择标题

核心概念、机制、技术问题、解决方案、工程问题、比较和导读都可以成为标题。采用最自然的句式，同一领域允许不同结构。必要的引擎、平台或机制限定词保留，长度由准确定位的需要决定。

同题的多个方法可集中比较，标题仍指向这个问题，例如“描边”。标题如果不断增加术语才能覆盖正文，先复查各部分是否有独立输入输出、实现、诊断、取舍与来源，再决定拆分。`术语A、术语B与术语C`只在确有比较或关系价值时采用，标题不以正文关键词清单为默认格式。

导读名称表达关系或学习目标，例如“渲染命令的组织方式”；具体名称根据实际内容选择。三个概念属于同一分类，也可能分别需要主归属文章。

### 使用读者习惯的术语

选择工程师实际使用、搜索和讨论的叫法。Render Graph、Command Buffer、Render Pass、GBuffer、Shader Variant、Billboard、GPU Culling和Async Compute等稳定术语可以直接保留英文；“描边”“植被风动”等自然中文同样适用。首次解释与别名写进正文或术语表。

本知识库采用`Render Graph`作为该概念的标题和主叫法。“渲染图”“Frame Graph”作为检索别名，依赖编译、Pass剔除、资源寿命与调度由正文展开。既有文章标题审查与正文术语统一分别记录，按任务范围执行。

### 候选与最终选择

生成3–5个有不同命名思路的候选，如概念名、问题式、机制式或工程限定式。候选要能解释各自的定位，不靠“详解”“原理与实现”“深入解析”等后缀轮换制造差异。

选择顺序为范围准确、行业习惯、简洁、检索记忆、深度匹配及主归属清楚。边界KEEP的文章仍独立审查标题。`title_review`与`boundary_action`分别保存；发现边界问题时记录SPLIT建议，实际迁移按授权范围进行。

“标题很难起”也是诊断信号。多个术语才能解释清楚时，重新检查主要问题；单一概念删去限定后会改变重点时，比较概念加限定与问题式候选。命令提交、资源同步、抗锯齿、纹理采样等范围敏感候选在采用前单独记录覆盖度与确认结果。

Render Graph是主概念标题的示范：正文展开依赖、编译、剔除、寿命和调度，标题定位稳定概念。它用于解释命名理由，其他主题按自己的边界保留限定。

### 文件与引用同步

标题采用后，同步H1、文件名、Wiki/Obsidian双链、Markdown链接、导读、知识地图、术语主归属和当前审计/迁移登记。历史审计快照保留原路径与原统计，通过命名映射定位当前页面。修改前检查同名目标与大小写冲突，修改后验证反链、标题和文件名一致。

标题审查只调整命名与必要引用；正文的问题边界和技术内容变更作为独立任务处理。完整复用提示词见 [标题审查提示词](../../skills/kb-structure-audit/references/title-review-prompt.md)。

## 一级目录分类规范

一级目录表示稳定知识领域与工程上下文。它回答“这一领域主要解决哪一类问题”，文章回答其中的独立问题。每个领域用一句话定义使命，再记录核心问题、读者、稳定概念、前提、下游、维护方式与内部子领域。

### 根据语义判断归属

文章归属由主要问题、核心概念、知识模型和学习路线决定。关联用于双链，主归属用于完整解释。API、算法、优化和架构是可能交叉的描述维度，作为文章类型、标签或路线使用；一级目录选知识领域。

检查目录是否混合独立问题族、读者群、模型、维护生命周期或学习路线。多个维度都独立时进入拆分审查。Render Graph、Render Pass、GPU资源寿命、同步和调度共享帧执行与资源依赖模型，适合组成渲染架构领域；音频回调和文字塑形则有独立模型、读者与验证。

### 数量只触发复查

1–2篇时检查是否只是材料不足或确有独立领域；13–20篇时复读内部子领域；超过20篇时全面检查语义边界。3–12篇也可能混合不同问题。数量不决定通过、拆分或合并，目标是语义平衡。

领域只有一篇但有独立模型和读者时，可以保留使命清楚的入口。多个小领域共享模型且互相重复时，再考虑合并。目录数量与文章数量均不作为配额。

### 通用概念与引擎实现

通用概念在领域主归属解释，强版本实现保存引擎、包、平台与源码条件。Unity或Unreal出现在正文中，并不决定分类。需要集中维护渲染引擎接口时，可建立“渲染引擎实现”领域，以相机、场景、通道与后端接入为使命，用引擎子入口组织；概念仍链接通用渲染架构。

资产制作到运行加载分别属于生产管线与资源运行系统，共享契约通过链接连接。Gameplay、AI和物理的关系也以状态、意图、控制和求解的主要职责判断。

### 审查、方案与采用

先审查完整目录体系及文章主问题、反链、导读和既有迁移映射，再提出最小调整、语义重构、长期演进2–3个方案。方案给出领域使命、逐篇归属、保留项、依赖、迁移风险和批准状态。

目录与文章分别记录`category_review`：PASS为当前合理；RECLASSIFY为文章或材料改归属；SPLIT为目录含独立领域；MERGE为领域合并；CREATE为需要新领域；OVERVIEW为目录适合组织入口。未审查状态单独记录。文章内部混合问题仍用`boundary_action`判断，分类不代替拆文。

命名、边界和目录分别验收。分类审查阶段交付方案，批准具体迁移后再移动文件并同步引用。编号是排序与身份，不承载概念关系；采用时尽量保留稳定路径或使用明确映射。提示词见 [分类审查提示词](../../skills/kb-structure-audit/references/category-review-prompt.md)。

## 质量矩阵

| 维度 | 验收问题 | 记录证据 |
|---|---|---|
| 范围 | 是否只有一个主要问题，章节是否有归属？ | 主问题、章节映射与概念主归属 |
| 结构 | 只读标题能否理解机制与方案家族？ | 围栏外H2/H3/H4及父子关系 |
| 深度 | 能否解释数据、因果、限制和失效？ | 机制推导、故障与成本 |
| 实现 | 是否有明确上下文和可复现路径？ | 样例、版本、输入输出、操作与预期 |
| 证据 | 重要断言能否定位依据？ | 规范章节、源码提交、实验或限定观察 |
| 写作 | 是否像工程师沿问题推理，主语和因果清楚？ | 段落复读、正例对照与修订结果 |
| 标题 | 是否短、准、自然，并对应唯一的主要问题或核心概念？ | 正文范围、不同候选、术语依据、文件与引用同步 |
| 信息架构 | 文章是否属于语义稳定、边界清楚的领域，目录是否帮助建立领域地图？ | 领域使命、主问题、读者、学习与维护边界、逐篇归属 |
| 视觉 | 图是否解释必要关系，来源与许可是否完整？ | 图注、资产登记与技术核对；无图可适用 |

各维度分别记录“通过、需改进、待验证、不适用”与依据。图片缺失本身不构成质量缺口，流程或数据列表也不能自动证明实现完成。词频、字节、代码块与图片数用于发现复读候选。

## 代码、图像与事实

代码区分完整最小样例、机制片段和伪代码。环境信息与编译、运行、捕获、性能状态分别记录。实际执行并取得证据的项目才记通过。

解释图优先使用可审查的确定性源文件。确有必要的技术解释可用AI图。来源和用户图片使用原始资产，保留作者、链接、许可、目标章节与意图。真正的Shader输出、编辑器截图和性能结果由真实运行或来源提供。

来源是断言证据。官方规范和源码也需要读具体版本与条件；知乎和工程博客提供实践线索，重要结论交叉核验。冲突按版本、API、平台、术语和实验方法调查。未证实的实现细节保持明确状态。

## 阶段与标杆

| 阶段 | 工作与完成条件 |
|---|---|
| P0标准 | 作者标准、写作、标题与分类规范、四个项目技能、九维质量矩阵和全库动作登记 |
| P0首篇试点 | 建立NPR导读及描边、Billboard、风动主归属；描边具备完整叙述、代码、必要图和证据记录 |
| 标杆评审 | 用户判断描边的范围、层级、语言、代码、图与验证是否达到阅读目标，并评审至少一篇不同技术主题的同等文风 |
| 后续试点 | 按批准范围继续渲染架构、GPU、GBuffer与Shader变体试点 |
| 批量迁移 | 文风已通过跨主题验证；架构主题深度试点达到实施验收并获得迁移授权后，按P0/P1/P2/P3执行 |
| 全局验收 | 链接、主归属、标题、代码、资产、事实、写作、地图和迁移完整性 |

全库语言现代化是P0工作，覆盖保持边界的文章。写作标准已获用户批准并通过跨主题验证。批量迁移采用方案B，最终目录与标题先冻结，再一次落定路径。SPLIT与OVERVIEW保留延后标题及边界状态，按P0至P3完成正文现代化，每15–25页检查路径、引用、地图、登记、资产和diff。全库处理记录见 [逐批登记](../../skills/kb-structure-audit/batch-review.json)，冻结路径见 [最终路径表](../../skills/kb-structure-audit/final-path-map.json)。本轮113页均有正文修订或保留复读记录；语言自检与用户阅读评审分别记录。

描边是已认可的文风标杆，也是范围、层级与技术深度的示范。作者学习问题推进、因果解释、轻重和过渡，按自己的技术依赖组织章节。Render Graph跨主题文风与结构评审通过，编译器版本表、内容与执行依赖、反向剔除及寿命算法由串行参考实现说明，并有15项CPU机制检查。目标引擎图编译、跨队列执行与GPU性能仍按实际运行证据验收。标杆认可与目标引擎运行证据分别记录。
