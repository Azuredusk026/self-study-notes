# 游戏AI决策模型

决策系统把感知到的信息变成可执行意图。最基础的循环是 Sense-Think-Act：感知层更新可用事实，决策层选择目标或动作，执行层向移动、动画和技能系统发请求。三层分开后，行为逻辑不必直接读场景里的所有对象，也不必亲自修改角色位移。

最直接的 脚本式AI 把行为顺序写在脚本或关卡事件中，适合高度确定的演出。规则式AI 用“条件 → 动作”规则响应世界事实，适合边界清楚、组合数量可控的系统。两者都需要把条件、执行副作用和优先级显式化，否则规则会形成难以追踪的覆盖关系。

BDI 用信念、愿望、意图描述 Agent：信念是它当前相信的世界状态，愿望是候选目标，意图是已经承诺执行的计划。它的价值在于区分“知道什么、想做什么、正在坚持什么”，适合需要有限理性和持续意图的角色；实现时仍要定义信息过期、目标冲突和重规划条件。

## 反应式行为组合

### FSM 与 HFSM

有限状态机用状态和转移表达行为，适合待机、巡逻、追击、攻击这类边界明确的小系统。问题通常不是 FSM 本身，而是把感知、动画、技能和高层目标全塞进一张图，最后产生任意状态到任意状态的转移。

层次状态机把共享逻辑放到父状态，例如“战斗”下再分追击和攻击，可以减少重复转移。状态进入、更新、退出的副作用必须清楚；跨帧异步行为要能取消，否则退出状态后旧回调仍可能生效。

### 行为树

行为树从根节点向下运行。顺序节点依次执行子节点，遇Failure停止、遇Running保留运行分支；选择节点依次尝试，遇Failure继续，遇Success或Running停止，装饰节点修改条件、次数或返回值，叶节点执行条件判断和动作。常见返回值是 Success、Failure、Running。

黑板保存目标、最后可见位置、危险程度等共享事实。它是受控的数据接口，不该成为任意系统都能写的全局字典。键最好有类型、来源和更新时间；短期感知与长期记忆要区分。

逐帧 Tick 整棵树实现简单，但大量 NPC 会浪费预算。事件驱动或条件观察可以只在相关黑板值变化时重新评估。Running 节点仍需收到更新和取消通知。调试器应记录当前路径、节点返回值、条件变化和中止原因。

行为树擅长表达设计师可读的层次与优先级，但树太大时会出现重复条件和隐式依赖。可把移动、战斗等稳定能力封装成可测试 Task，而不是不断复制子树。

节点实现常对应软件设计模式。父类用模板方法固定进入、Tick、退出与取消流程，子类只实现具体判断或动作；装饰节点包裹子节点，增加条件、循环、冷却或返回值变换。模式名称不是目标，关键是让节点生命周期和组合语义一致。

#### 中止语义

行为树真正难的不是节点类型而是中止。以Unreal行为树的Observer Aborts为例，Self指定中止自身及其运行子树，Lower Priority指定中止右侧低优先节点，Both结合两种范围，None关闭观察者中止。重评估由条件结果或黑板值变化触发；这些是中止范围，不是所有行为树统一的条件执行规则。追击子树正在跑而“看见敌人”变假，攻击请求要被取消、按定义好的取消顺序退出 Running 子节点与父节点，并复位每个节点的内部索引。

实现上把条件注册成对黑板键的观察（Observer 中止），键变化时主动触发重评估，也可按固定Tick轮询；两者分别受事件派发阶段与Tick周期限制，中止时机由调度契约规定。漏掉退出的症状很典型：角色被打断后仍朝旧目标走两步，因为移动请求没有随子树一起取消。

### 顺序节点执行

顺序节点按顺序执行子节点，遇到 `Running` 时保存当前索引，遇到 `Failure` 时立即失败：

```cpp
Status Sequence::Tick(Context& ctx)
{
    while (currentChild < children.size()) {
        Status status = children[currentChild]->Tick(ctx);
        if (status == Status::Running) return status;
        if (status == Status::Failure) {
            currentChild = 0;
            return status;
        }
        ++currentChild;
    }
    currentChild = 0;
    return Status::Success;
}
```

树被中止时还要把正在运行的子节点复位，并释放移动、动画等外部请求。本片段是记忆型顺序节点，Running时保存索引。反应式顺序节点也可每次从首个条件重评估，但必须将动作的首次进入与持续Tick分开，并在路径变化时中止原运行节点，避免重复初始化。调试视图应显示当前 Running 路径、进入时间、退出状态和黑板读取值。

### Utility AI

效用系统给候选行为计算分数，再选择最高或按概率采样。一个需求值可以通过曲线映射到 $[0,1]$，多个评分因素再组合。乘法会让任意低分强烈压低总分，加法更容易让不同数量的条件产生偏差，因此需要统一归一化规则。

最高分硬切换容易在相近行为间抖动，可加入迟滞、冷却、最短持续时间或当前行为加成。随机性应使用可复现种子，并显示每个候选的输入、曲线和最终分数。Utility AI 适合“此刻更值得做什么”，但不会自动生成一长串满足前置条件的计划。

#### 效用的组合与迟滞

```cpp
float ScoreAction(const Action& action, const Blackboard& bb)
{
    float score = 1.0f;
    for (const Consideration& c : action.considerations) {
        float input = c.eval(bb);               // 原始量先归一化到 [0,1]
        float s = c.curve.Evaluate(input);      // 曲线映射到效用
        s = pow(s, c.weight);                   // 权重以指数进入，保持 [0,1]
        score *= s;
        if (score < 1e-4f) return 0.0f;         // 乘性组合下低分不可逆，提前出局
    }
    return score;
}
```

这里展示乘法组合，输入与曲线输出在 $[0,1]$ 内，指数权重为正。零分会否决动作，适合表达必要条件。条件数量不同会影响分数，跨动作比较前需选择并验证归一化策略，例如加权几何平均；补偿公式属于项目策略，需要用测试局势校准。防抖可以给当前动作增加迟滞阈值，只在新动作明显更优时切换。

## 目标规划

### GOAP

目标导向行动规划把世界表示成有限事实。动作声明前提、效果和成本，目标描述希望满足的事实。规划器从当前状态搜索一条动作序列，例如“拿到武器 → 接近掩体 → 攻击”。

事实数量太多会让状态空间爆炸。应只保留会影响计划选择的抽象信息，连续量通常离散成区间。动作成本可以包含时间、风险和资源，但各项尺度需要统一。环境变化使前提失效时再重规划，不能每帧无条件重新搜索。

#### 规划的反向搜索

```cpp
Plan GoapPlan(WorldState start, Goal goal, Action[] actions)
{
    bestCost[goal.facts] = 0; // 其他事实集的默认成本为无穷；动作成本非负
    open.Push({ goal.facts, {}, 0 });           // 待满足事实、已选动作、累计成本
    while (!open.IsEmpty()) {
        Node node = open.PopLowestCost();
        if (node.cost != bestCost[node.required]) continue;
        if (start.Satisfies(node.required))     // 当前世界已满足全部剩余前提
            return Reverse(node.actions);
        foreach (Action& action in actions) {
            if (!action.effects.Intersects(node.required)) continue;
            if (action.negativeEffects.Intersects(node.required)) continue;
            Facts remaining = node.required - action.effects + action.preconds;
            if (remaining.ContainsContradictoryValues()) continue;
            if (node.cost + action.cost >= bestCost[remaining]) continue;
            bestCost[remaining] = node.cost + action.cost;
            open.Push({ remaining, node.actions + action,
                        node.cost + action.cost });
        }
    }
    return null;
}
```

这是回归规划的算法轮廓。每步用动作效果满足部分目标，再把动作前提加入剩余需求。片段将正效果、负效果与前提表示成事实集合，负效果与目标冲突时拒绝，合并后同一键出现矛盾值时也拒绝。bestCost按规范化事实集合索引，默认无穷；完整实现还需搜索预算、稳定平局规则和具体状态编码，冲突示例见“异步动作与规划冲突”。当前状态尚未满足某项前提时，其他动作可能建立它，不能据此直接剪枝。布尔事实可用位掩码保存；多值状态需要显式的键值表示与冲突规则。

计划只是意图，不保证底层动作一定成功。执行器要报告完成、失败、取消和超时，规划器据此更新事实。调试时同时保存搜索过的状态、被拒绝的前提和最终成本。

### HTN

层次任务网络从高层复合任务出发，按分解方法的条件把它分解，直到得到原子任务。比如“守卫区域”可根据警报状态分解成巡逻，或分解成搜寻、呼叫支援和交战。

HTN 的搜索空间通常比完全自由的 GOAP 小，因为设计师已经提供合理分解。代价是知识更多地写在分解方法中，内容覆盖不全时可能没有可用方案。它适合流程和战术结构清楚的玩法，也方便把关卡设计经验编码进去。

### 分解方法与状态推进

HTN可用“守卫”例子推演：安静条件选择方法[巡逻]；警报条件选择[前往报警点,搜寻,报告]。规划器按顺序检查原子动作的前提，并将其效果应用到临时状态，再检查下一动作。若前往失败，执行器不应继续搜寻，而是报告失败并重新选方法；方法都不可用时返回无计划。只展开任务名称而不推进临时状态，会产生下一步前提永远不成立的计划。

FSM的相同例子从巡逻收到敌人事件进入追击，退出先取消旧巡逻移动，进入再创建追击请求；若进入时目标已经销毁，转入搜寻或失败状态。行为树则可把“敌人有效、追击、攻击”放入记忆顺序，追击Running保留索引；目标失效时观察者中止并取消请求。这些不同的推进方式都必须遵守动作实例ID，才能拒绝迟到结果。

BDI可以把最后看见敌人的位置记作带时间的信念，候选愿望为追击和自保，当前意图为前往掩体。新目标分数稍高时仍保留意图，受到致命威胁时按重考虑规则取消并换成自保；信念过期则移除目标，而不是继续把旧位置当实时观察。这里的承诺与重考虑条件是显式项目规则，BDI名称本身不会生成它们。

## 模型选择

小而确定的局部行为用 FSM；需要清晰优先级和可视化编排时用行为树；多个需求持续竞争时用 Utility；动作前提会组合成不同计划时用 GOAP；流程有稳定层级与领域知识时用 HTN。实际项目经常组合：Utility 选高层目标，行为树负责执行，局部技能内部再用状态机。

架构边界比算法名称更重要。感知只提供带时效的信息，决策输出请求，动作系统验证资源与规则，动画系统负责表现。服务端或确定性模拟中的权威结果不能由不可复现的黑盒决策直接决定。

## 异步动作与规划冲突

每次动作进入时生成实例ID，移动完成回调携带这份ID。行为树中止后递增或注销当前实例，迟到回调先核对ID，再修改黑板。否则旧追击请求完成时可能把新攻击状态标成成功。退出负责释放外部请求，复位索引只是节点内部清理。

回归规划中，动作满足一个目标却可能破坏另一个。目标是“有弹药且在掩体”，候选动作“冲出掩体捡弹药”虽然增加弹药，却删除在掩体事实，不能直接用集合减加判为满足。展开前检查动作负效果与当前目标冲突；通过后把未满足目标与动作前提合并，并对矛盾键值拒绝该分支。

效用比较同样要固定语义。一个动作乘三个0.8得到0.512，另一个只乘一个0.8得到0.8，差异可能只是条件数量。若条件表示独立必要因素，乘法可保留否决作用；若只是同尺度偏好评分，加权几何平均等策略更适合跨动作比较。选择后用固定局面验证，而不是只调到某一帧看起来正确。

## 验证方法

- 确定性回放：固定种子与世界快照离线重放整局决策，逐帧比对每个 NPC 的当前节点与动作序列；任何分叉都要能定位到具体黑板键的变化。
- 中止测试集：为每类 Observer 中止构造“打断瞬间”用例，确认被打断动作的退出执行了、外部请求被取消、黑板残留状态被清理。
- 黑板审计：记录每个键的写入者与时间戳，检查是否有系统绕过受控接口直接改写，短期感知键是否按过期时间清理。
- Utility 回归：录制典型局势（残血、弹尽、被围），确认期望动作得分第一；每个评分因素的输入、曲线输出与总分写日志，分数异常时可回放归因。
- GOAP 计划校验：对生成的计划逐步骤检查前提在模拟中成立；动作执行失败时确认执行器上报失败并触发重规划，而不是原地干等。
- 预算检查：统计单帧决策耗时的 P99；大量 NPC 时确认事件驱动重评估生效，检查持续 Running 任务更新与条件重评估各占多少成本。事件驱动和逐帧 Tick 都可以成立，选择取决于实现语义与预算。
