# 导航、寻路与移动控制

游戏 AI 的移动是一条连续链路：先把世界变成可搜索的数据，再求出全局路线，最后让角色在局部范围内避障并跟随；一次 `FindPath` 只覆盖其中一环。每一层解决的问题不同。全局寻路不该处理每一帧的角色碰撞，局部避障也无法替代对死路和楼层连接的判断。

## 可行走空间表示

Waypoint Graph 适合路线由设计师明确控制的场景，节点少、语义清楚，但覆盖大地图的维护成本高。规则 Grid 容易生成和动态修改，也方便使用 Manhattan 距离，不过内存随地图面积增长，锯齿路径需要额外平滑。

NavMesh 用凸多边形覆盖可行走表面。一个凸多边形内部任意两点可直接连线，因此搜索节点远少于细网格，适合连续的三维地表。稀疏体素八叉树更适合飞行、太空或水下等真正的三维导航，但邻接构造、内存布局和动态更新都更复杂。

表示里不仅要有“能否通过”，还应保存区域代价、坡度、角色半径、门和跳跃等 Off-Mesh Link。不同体型不能盲目共享一张只按点角色生成的网格。

## A* 与启发函数

A* 按下面的估价选择下一个节点：

$$f(n)=g(n)+h(n)$$

$g(n)$ 是起点到当前节点的实际成本，$h(n)$ 是剩余成本估计。令 $h=0$ 就是 Dijkstra。若 $h$ 不高估真实成本，也就是 admissible，A* 可以保持最优；估价越接近真实距离，通常扩展节点越少。

网格允许四方向移动时可用 Manhattan Distance，允许任意方向时通常用 Euclidean Distance。启发函数必须和移动规则匹配。为了更快而把 $h$ 加权是可行的工程取舍，但会放弃严格最优，不能把它误写成普通 A*。

Open Set 可用最小堆保存候选节点。使用重复入堆的实现时，每条记录同时保存入堆时的路径成本；弹出后与最新成本比较，跳过过期记录。调试视图显示已访问节点、父节点和路径成本，便于解释搜索为何失败。

### A* 主循环

```cpp
Path AStar(const Graph& graph, NodeId start, NodeId goal)
{
    CostTable bestCost(graph.NodeCount(), Infinity);
    ParentTable parent(graph.NodeCount(), InvalidNode);
    MinHeap open;
    bestCost[start] = 0;
    open.Push({start, 0, Heuristic(start, goal)});
    while (!open.Empty()) {
        Entry entry = open.Pop();
        if (entry.cost != bestCost[entry.node]) continue;
        if (entry.node == goal) return Reconstruct(parent, goal);
        for (const Edge& edge : graph.Neighbors(entry.node)) {
            float candidate = entry.cost + edge.cost;
            if (candidate >= bestCost[edge.to]) continue;
            bestCost[edge.to] = candidate;
            parent[edge.to] = entry.node;
            open.Push({edge.to, candidate,
                       candidate + Heuristic(edge.to, goal)});
        }
    }
    return NoPath;
}
```

这是算法伪代码。堆按估计总成本排序，边代价非负，启发函数在目标处为零。节点找到更短路径后可以再次入堆，因此也支持可采纳但不一致的启发函数。每次搜索独立初始化成本表；弹出目标时得到路径。

在同一张图上分别运行 Dijkstra 和使用可采纳启发函数的 A*，两者路径成本应相等。A* 成本更高时检查启发函数及重开节点逻辑；成本更低时检查代价定义和两种实现。Dijkstra 在非负代价图上已给出最优成本。扩展节点数用于比较搜索效率。

## NavMesh 生成

常见生成流程先把场景三角形体素化，按角色允许的坡度和台阶高度标记 Walkable Span，再合并连通区域。过小孤岛会被删除，区域边界被提取为 Contour，最后简化并三角化或合并成凸多边形。

角色半径通常通过侵蚀可行走区域处理，让寻路中心线天然远离墙面。若半径、台阶高度或体素尺寸设置不合理，会出现窄门消失、楼层粘连和台阶断裂。生成质量需要在几何精度、节点数量和烘焙时间之间平衡。

体素尺寸是精度与内存的杠杆：高度方向至少要能区分相邻台阶，水平方向决定窄通道能否保留。Recast 风格参数的典型起点：`cellSize` 取角色半径的三分之一到二分之一，`cellHeight` 小于台阶高度的二分之一，`walkableSlopeAngle` 按玩法上限取 45 度上下，`minRegionSize` 过滤桌面大小的孤岛。每次改参数后用同一测试关卡核对四件事：窄门是否保留、台阶是否可上、悬空边缘是否被正确侵蚀、烘焙耗时是否可接受。

动态障碍可用 Tile 局部重建、临时 Cost Volume 或运行时避障。频繁移动的小角色不适合每帧切 NavMesh；真正改变拓扑的大门、桥和破坏区域才需要更新全局表示。

## 路径走廊与 Funnel

在 NavMesh 上搜索得到的通常是一串相邻多边形，也叫 Corridor，不是最终转向点。相邻多边形的公共边形成 Portal。Funnel Algorithm 从起点维护左右两条边界，当漏斗交叉时输出一个拐点，再从该点重新展开。

漏斗的三个要素是：apex 为已确认的最近拐点，左右边界为尚未确认的候选射线。每加入一个 Portal 端点，用二维叉积符号判断它落在左右边界内侧还是外侧：在内侧只收缩对应边界，越过对侧边界则漏斗交叉，此时对侧端点成为新拐点输出，apex 移到该点并重新展开。全部判定都是叉积符号，不需要归一化和除法。最常见的实现错误是 Portal 方向不统一：左右端点的判定依赖公共边按同一行进方向排序，生成走廊时必须先统一。

Funnel 能把沿多边形中心的折线路径改成走廊内的短路径。结果仍要考虑角色转弯半径、速度和动画，不能让大型角色瞬间贴墙折返。车辆更适合加入曲率约束或使用专门的运动规划。

## Steering 与跟随

全局路径决定去哪里，Steering 决定这一小段怎样移动。常用行为包括 Seek、Arrive、Velocity Matching、Separation 和 Obstacle Avoidance。期望速度与当前速度之差产生加速度：

$$a=\frac{v_{target}-v}{\Delta t}$$

实际实现还要限制最大加速度、角速度和停止距离。直接把多个 Steering 向量相加容易互相抵消，通常需要优先级、权重或分层仲裁。动画 Root Motion 与物理位移也要选定一个权威来源，否则会出现脚滑和回拉。

## 局部避障

Velocity Obstacle 把“未来会碰撞的速度”表示成速度空间中的禁区，再选择禁区外的新速度。RVO 让双方各承担一部分避让责任；ORCA 用半平面约束求接近首选速度的可行解，群体运动会更平滑。

这类方法处理短期动态碰撞很好，但不理解全局死锁。窄门两侧人群、对称迎面和高密度拥堵仍可能振荡。工程上常加入通行优先级、车道、预约、局部重寻路或等待状态。角色半径、预测时间和邻居数量都会影响效果与成本。

## 调试与边界

导航调试至少要能显示可行走区域、区域代价、Portal、全局路径、局部速度、邻居集合和阻塞原因。一次寻路成功不等于角色最终可达，还要验证电梯、门、跳跃动画、动态障碍和目标移动。

性能上把请求分帧调度并设置扩展节点预算。对大量单位可缓存共享路径走廊，但每个角色仍保留局部避障。若最终表现异常，应先判断错误属于世界表示、全局搜索、路径平滑、运动控制还是动画同步，不要把所有问题都归为“NavMesh 有问题”。

### 到达行为

路径跟随先选择走廊中的前视目标，再用到达行为生成期望速度。输入位置和速度位于同一世界空间：

```cpp
Vec3 offset = target - position;
float distance = Length(offset);
float targetSpeed = maxSpeed * Saturate(distance / slowRadius);
Vec3 desiredVelocity = distance > 1e-4f
    ? offset / distance * targetSpeed
    : Vec3(0);
Vec3 acceleration = ClampLength(
    (desiredVelocity - velocity) / timeToTarget, maxAcceleration);
```

`slowRadius` 让角色接近目标时减速，`timeToTarget` 控制响应速度。Steering 输出是运动请求，Character Controller 仍负责碰撞、坡面和实际位移。验证时显示前视目标、期望速度和实际速度；角色在拐角振荡通常来自前视距离、路径更新频率或加速度上限不匹配。

## 验证方法

- A* 最优性：固定图、边代价和起终点，对比 Dijkstra 与可采纳启发函数的 A*。路径成本必须相等；不同的最优路径可以有相同成本。
- 启发函数分档对比：$h=0$、精确 $h$、加权 $h$ 各跑一次，记录扩展节点数与路径成本，确认加权换来的速度提升幅度与最优性损失。
- NavMesh 体检：烘焙结果上随机撒点向下射线，命中点必须落在可行走多边形内；沿多边形边随机采样做胶囊扫掠，确认没有穿墙缺口。
- 烘焙参数回归集：固定一组测试关卡（窄门、台阶、斜坡、断桥），每次改参数跑一遍并对比连通区域截图。
- Funnel 正确性：输出路径的每一段必须完全位于走廊多边形并集内，逐段做点在多边形测试。
- 避障压测三场景：对称迎面、窄门对冲、环形围堵，固定种子运行并统计死锁次数与平均绕行时间，作为避障参数的回归基线。
- 分帧调度下统计单帧寻路耗时峰值，超预算时确认是扩展节点上限生效还是请求被直接截断。
