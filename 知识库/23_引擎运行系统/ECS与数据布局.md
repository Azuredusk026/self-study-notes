# ECS与数据布局

更新一千个位置，如果每次读取都跳到分散对象，很多缓存内容并未用于这次计算。数据布局先看热点字段，ECS再按组件组合建立查询。连续访问与结构变更成本一起决定收益，不能只凭框架名称判断性能。

## 访问模式与存储布局

CPU 执行速度和内存访问速度差距很大。一次 Cache Miss 可能让执行单元等待许多周期。优化前先回答：

- 一次更新真正需要哪些字段；
- 相邻迭代是否访问相邻地址；
- 数据是否被多个线程写入同一 缓存行；
- 分支是否让同一批数据走完全不同的路径。

AoS 把一个对象的所有字段放在一起，适合整对象访问。SoA 把同类字段放在连续数组中，适合只处理位置、速度等少数字段的批量循环。实际系统常用混合布局，目标是贴合访问模式。

ECS 的 Archetype 会按组件组合分组，Chunk 内存放相同布局的 Entity。System 查询需要的组件集合后，可以顺序遍历匹配 Chunk。新增或删除组件会让 Entity 跨 Archetype 搬迁，因此结构变化不适合在热点循环中频繁发生。

## ECS 的三个角色

ECS 是数据导向设计在游戏架构上的一种具体落地：

- **Entity**：提供稳定身份，组件数据由存储系统维护。它的特性完全由附加的组件决定；
- **Component**：保存供系统访问的数据，具体框架可另有托管组件等形式；
- **System**：处理特定组件组合的逻辑，遍历所有持有相关组件的实体并执行操作。

与面向对象的对比常被简化为“组合优于继承”，但真正的性能差异来自内存布局。

当面向对象实现把每个实体单独分配在堆上时，不同对象会散布在不同地址。遍历一千个敌人更新位置时，每次访问都要跳到新的内存地址，缓存行里大部分内容是当前用不到的字段（名字、血量、AI 状态）。

ECS 把同类组件存成紧凑数组。更新位置时，位置数据与速度数据各自连续排列，一次缓存行加载能覆盖多个实体的有效数据，硬件预取也能正常工作。

这带来第二个收益：批处理天然适合并行。系统对一段连续数据做同构操作，若每个任务只写自己的区间、其余输入只读，就能避免写冲突；缓存行边界也按任务分开时，还能减少假共享。连续布局本身并不证明线程安全。

## Archetype 与查询

真实引擎中的 ECS 还要解决“如何快速找出持有某组组件的全部实体”。常见做法是 Archetype：把组件组合相同的实体归入同一块存储，查询退化为遍历若干个匹配的 Archetype 块。

Unreal 的 Mass 框架采用这种组织方式。它的代价也由此而来：**给实体增删组件会改变它的 Archetype，需要在存储块之间搬移数据**。频繁增删组件的设计会把这条路径变成新瓶颈，可以评估用状态字段或启用位表达，是否合适取决于查询方式。

### ECS的适用条件

ECS 的收益取决于批处理规模和访问局部性，成本同时包含框架开销与随工作量增长的查询、搬迁和桥接开销：

- 实体数量少时，缓存优势不明显，而架构复杂度的增加是实打实的；
- 逻辑高度个性化时，组件组合会碎片化，Archetype 数量膨胀，查询退化；
- 调试比 OOP 困难，一个实体的状态分散在多处存储中；
- 与引擎既有的对象体系交互需要桥接层，跨界访问往往抵消性能收益。

选择依据是热点访问、同构程度、结构变化频率及桥接成本。实体数量只能提示潜在规模，不能单独决定架构；用代表性工作负载比较布局和总帧成本后，再确定哪些系统采用批处理。

## 结构搬迁与句柄稳定性

假设源块的行依次是实体4、7、9。实体4增加一个组件以后，目标组合已经变化，需要把它的已有字段复制到目标块，并初始化新组件。源块第0行留下空位，可以把末尾的实体9搬到这里，再把源块数量减一。实体ID始终为9，但它的行号已经从2变成0。

```text
目标行 = 目标块追加(源块[row]的共享组件, 新组件初值)
location[被迁移实体] = 目标行
last = 源块.count - 1
if row != last:
    源块[row] = 源块[last]
    location[源块[row].entityId] = (源块, row)
源块.count -= 1
```

这段伪代码假定组件可按当前类型规则搬迁，实际C++组件还要处理构造、析构、对齐和异常约束。`location`是稳定身份到当前存储位置的映射；漏改被交换实体的位置，会让后续查询读到另一个实体。迭代器和组件裸引用也可能失效，所以结构命令先排队，等持有这些引用的任务结束后集中执行。

查询缓存通常缓存“哪些组件组合符合条件”，每帧再枚举这些组合的实际块。查询条件为位置与速度时，同时带有生命值的组合仍匹配；组合数增加主要扩大匹配集合和碎片，不能简单等同于每实体查询成本。普通状态值变化保留布局，频繁开关状态可用状态字段或框架提供的启用位，但要衡量额外分支和查询过滤代价。

## 批量更新

CPU机制伪代码中两个数组按实体对应，位置写入区间由当前任务独占，速度只读。

```text
for chunk matching [Position, Velocity]:
    for i in 0..chunk.count-1:
        position[i] += velocity[i] * dt
defer structural changes until iteration completes
```

## 验证方法

固定工作负载比较AoS、SoA与Chunk布局的访问、分配和时间。结构变化检查实体搬迁与引用失效，不同组件组合统计查询碎片。并发调度由任务系统管理。
