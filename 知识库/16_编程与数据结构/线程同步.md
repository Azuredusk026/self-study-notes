# 线程同步

消费者醒来，队列仍可能为空，因为通知不是对状态的永久承诺。线程同步先保护共享谓词，再使用锁、条件变量或原子发布建立访问关系。原子更新不自动保护整个对象寿命。

## 锁与等待原语

Mutex 提供互斥所有权，未获得锁的线程通常进入等待。Recursive Mutex 允许同一线程重复获取，但容易掩盖职责和调用层级问题。Read-write Lock 允许多个 Reader 或一个 Writer，只有读多写少且临界区足够大时才可能受益。

Semaphore 保存可用许可数量，适合限制并发资源或通知多个工作项。条件变量让线程在等待状态时睡眠。共享状态在锁保护下更新，再通知等待者。线程醒来后需要重新检查条件，因为可能发生伪唤醒，也可能有其他线程先消费了数据。

Spin Lock 在短时间内循环尝试，不进入睡眠。它只适合临界区极短、锁持有者很快会运行的场景。锁持有期间做 IO、等待另一个锁或被操作系统抢占，会让 Spin 浪费 CPU。

## 原子操作与内存顺序

Atomic Read-modify-write 保证多个线程对同一原子对象的更新不会丢失。原子性不自动保证一组普通内存操作的整体事务，也不解决对象生命周期。

编译器和 CPU 可以在不改变单线程结果的前提下重排内存访问。Acquire/Release 建立跨线程的 Happens-before 关系：发布线程先写数据，再用 Release 发布标志；消费线程用 Acquire 读到标志后，才能可靠观察此前的数据写入。Sequential Consistency 提供更直观的全局顺序，约束通常更强。

Lock-free 表示系统整体能持续推进，不代表每个线程都不会饥饿，也不代表一定比 Mutex 快。无锁结构还要处理 ABA、内存回收、伪共享和复杂验证。

## 数据竞争与死锁

两个线程并发访问同一内存位置，其中至少一个写入，且没有同步关系时形成 Data Race。C++ 中这通常是未定义行为。只在调试时“看起来结果正确”不能证明线程安全。

经典死锁需要四个条件同时成立：互斥、持有并等待、不可抢占、循环等待。常见预防方式是统一锁顺序、缩小锁范围、一次获取整组锁、避免持锁调用未知代码，并在调试构建记录 Lock Graph。

Livelock 中线程持续响应对方却没有实际进展；Starvation 表示某个线程长期得不到资源。公平锁、退避和任务优先级可以缓解，但也会改变吞吐和延迟。

## 条件变量的谓词等待

生产者修改队列和停止标记时持有同一互斥锁，消费者用谓词处理虚假唤醒：

```cpp
std::unique_lock lock(queueMutex);
queueReady.wait(lock, [&] { return stopping || !jobs.empty(); });

if (stopping && jobs.empty())
    return;

Job job = std::move(jobs.front());
jobs.pop_front();
lock.unlock();
job.Run();
```

等待会原子地释放锁并休眠，唤醒后重新获得锁再检查谓词。任务执行放在解锁之后，避免一个长任务阻塞所有生产者和消费者。若停止标记在另一把锁下修改，可能丢失唤醒或形成数据竞争；压力测试应覆盖空队列停止、多生产者和连续虚假通知。

## 并发错误怎样缩小范围

先列出共享数据的写入者与读者，再把锁、消息队列或原子发布点画到时间线上。两个线程各自运行正常，不说明交错后也正常。调试器、线程检测工具和压力测试分别提供现场、候选竞争与复现线索；证明访问顺序还要回到语言内存模型。

## 验证方法

空队列停止、虚假通知、多生产者与取消分别压测。记录锁图和等待，使用竞态工具检查普通访问；Acquire必须读到对应Release发布值，不能靠两个关键字建立任意同步。
