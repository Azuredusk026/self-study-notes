# C++工程边界

设编辑器加载一个资产插件：宿主调用CreateAsset创建对象，后台任务处理资产，最后关闭插件。这个过程先后跨过翻译单元、动态库接口和异步任务寿命。头文件能编译只证明声明可见；符号能加载也不能证明双方对字节和释放责任理解一致。下面沿这一个插件的构建、创建和卸载说明各层边界。

## C++构建与模块边界

### C++ 构建链

插件的asset.cpp和宿主的editor.cpp分别编译，二者通过公共头约定CreateAsset。每个文件先经过下面的构建链：

```text
Source
 -> Preprocess
 -> Compile
 -> Object File
 -> Link
 -> Executable / Static Library / Dynamic Library
```

预处理器展开 `#include`、宏和条件编译。编译器对每个翻译单元生成目标文件。链接器解析跨文件符号、库依赖和最终地址。

若editor.cpp看不到参数类型，编译阶段就失败。声明可见而链接器找不到CreateAsset定义，会产生Unresolved External；两个目标文件都提供同一强符号则可能产生Multiple Definition。生成程序后找不到插件或导出入口，属于运行加载问题。入口存在但双方解释参数不同，则已经进入ABI不匹配，错误可能直到调用时才暴露。

排错先判断阶段，不要看到“编译失败”就反复改代码。

### 头文件与翻译单元

资产接口头同时被宿主和插件包含，通常保存声明、必要类型以及需要在调用侧实例化的内联与模板。实现放在`.cpp`，修改解码算法便不必让所有调用方重新编译；公共头改变则使包含它的翻译单元重新构建。

减少不必要的头文件包含：

- 能前置声明时不引入完整定义；
- 私有实现可使用 PImpl 隔离依赖；
- 稳定公共接口与高频变化实现分开；
- 隐式实例化通常需要模板定义可见；对支持的具体类型显式实例化后，可以把相应定义放在 `.cpp`，并用 `extern template` 抑制调用侧的重复实例化。

包含保护/`#pragma once` 防止同一翻译单元重复包含，但不解决跨翻译单元的单一定义规则。

例如a.cpp与b.cpp都包含定义了普通全局变量的公共头，各自编译都能成功，链接时却可能产生重复定义。包含保护只在单个翻译单元内起作用，不能合并这两份定义。让头只声明`extern int counter`，并在一个.cpp提供定义，才使两个调用方引用同一实体；C++17的内联变量则遵循另一套允许多处定义的契约。

### 静态与动态库

静态库在链接时把所需目标文件合入最终产物。部署简单，但多个程序可能各自包含一份，更新需要重新链接。

这里的资产处理器采用动态库，宿主按受控搜索路径加载插件及依赖，再解析导出入口。双方必须匹配调用约定和参数布局；创建对象后，还要保证它的析构函数所在模块一直加载到对象销毁。独立替换因此要求先排空旧模块的调用、对象与回调，后文会沿这条顺序关闭插件。

跨 DLL 分配、另一侧释放若使用不同堆/CRT，可能崩溃。边界常提供成对 `Create/Destroy`，由分配方负责释放。

### ABI 与 C接口

若直接让CreateAsset返回std::string或C++对象，宿主就同时依赖插件的类布局、标准库实现和异常约定。这里用C ABI导出入口：整数规定宽度，字节缓冲配长度，对象以不透明句柄返回。接口头提供版本和结构大小，失败返回错误码；消息写入调用方缓冲，或由插件提供对应释放函数。这样宿主消费的是明确的接口字段，而不是猜测插件私有对象的布局。

不要跨边界直接传 `std::string`、`std::vector` 或编译器私有对象，除非所有模块严格锁定同一工具链。

## 类型布局与资源语义

### C++ 类型与布局

插件内部仍可用STL容器、迭代器和算法保存资产。模板在编译期生成具体类型代码，内部选择不必暴露为公共接口。继承与虚函数支持运行时多态，但会引入对象布局、间接调用和 ABI 约束；数据导向热路径更常用显式数据与批处理。

结构体的填充字节由成员对齐要求决定，成员顺序会改变 `sizeof`。联合体让多个成员共享同一段存储，必须记录当前有效成员；现代 C++ 更适合用 `std::variant` 表达带标签联合。任何跨文件、网络、GPU 或插件边界的数据结构都应固定宽度、布局和版本，不能直接依赖编译器默认内存表示。

### C++ 对象模型与虚函数

资产插件内部可以用基类管理不同解码器。普通非虚成员函数不存放在每个对象内。对象主要保存非静态数据成员和编译器需要的隐藏信息。含虚函数的对象通常带一个虚表指针，指向该动态类型的虚函数表。通过基类指针或引用调用虚函数时，程序根据动态类型查表完成运行时分派。

标准规定的是多态行为，不规定虚表的具体内存布局。常见实现可以帮助理解成本，但不能作为跨编译器 ABI 契约。

关键规则：

- 派生类使用 `override` 让编译器检查是否真正重写；
- `final` 可以禁止继续重写或继承；
- 纯虚函数 `= 0` 使类型成为抽象类；
- 允许通过普通基类指针执行delete的多态接口应提供虚析构；
- 构造和析构期间的虚调用只分派到当前构造层级；
- 对象按值赋给基类会发生对象切片，派生部分被丢弃。

虚调用的主要代价是一次间接调用，并可能限制内联。真正风险通常是对象分散、指针追逐和所有权不清。稳定扩展点适合接口多态，海量同构对象的热循环更适合连续数据与显式类型分组。

### 复制、移动与异常安全

解码器获得文件和输出缓冲后，失败路径也必须释放它们。资源类型应优先遵守 Rule of Zero：让标准容器和智能指针管理资源，类型本身不手写析构、复制和移动。直接持有资源的 C++ 类型，需要一起设计析构、复制构造、复制赋值、移动构造和移动赋值。这是五法则（Rule of Five）。优先用标准资源包装类型承担所有权，减少手写这些操作的需要。

移动操作按类型契约转移或重建资源。标准库类型的移后对象通常处于有效但未指定的状态，具体可执行哪些操作仍取决于操作前提；自定义资源类型也要明确移后状态与允许的操作。`std::move` 只是把表达式转换为右值引用，不会自动搬运；是否移动取决于目标类型是否实现移动操作。

容器和工具代码常讨论三种异常保证：基本保证要求失败后没有资源泄漏且对象不变量成立，值可以变化；强保证要求因异常失败时状态不变；不抛异常保证要求异常不会离开函数。RAII、先构造临时结果再交换，以及不抛异常的移动能帮助实现更强保证。

例如赋值要同时更新缓冲与长度，先释放旧缓冲再分配新缓冲，分配失败就无法保持旧值。先用RAII临时对象分配并复制全部数据，成功后以不抛异常的交换提交，失败则临时对象释放自身，原对象保持不变。强保证依赖提交动作不失败；若交换还要分配，这条推理便不成立。

### 布局与边界字节

固定宽度不自动固定布局。例如uint8_t后接uint32_t，在第二字段按4字节对齐的常见ABI下，中间会插入3字节填充。调用双方对结构尺寸、字段偏移、对齐和调用约定使用同一契约，并在各自构建中检查sizeof与offsetof。extern "C"约束语言链接，不会取消填充、统一大小端或把无效指针变成安全输入。文件和网络因此逐字段编码；同进程插件才在已锁定的ABI下共享结构内存。

## 所有权与模块接口

RAII和唯一、共享、弱引用的完整语义见 [[16_编程与数据结构/对象生命周期]]。插件边界把这些规则落实到创建、销毁和卸载三个入口。前面的布局与异常保证在这里成为调用协议：宿主先提供有效接口头，插件校验并构造，成功后才交出句柄。

### C ABI契约

声明片段使用固定位宽版本和不透明句柄，创建与释放由同一模块实现。调用约定与导出宏按平台补齐。

```cpp
struct AssetApi { uint32_t version; uint32_t size; };
extern "C" int CreateAsset(const AssetApi* api, void** handle);
extern "C" int DestroyAsset(void* handle);
```

### 接口结构的版本协商

接口调用者先保证指针指向至少包含version和size的有效可读头部；空指针检查不能证明任意非空地址都可访问。插件读取这个头部以后验证版本和size，并要求声明范围内的内存仍由调用者保持有效。size允许调用方传入较长的新结构，旧插件只读取自己认识的前缀；传入比必需前缀更短的结构则拒绝。字段增加在尾部才能维持这种前缀约定，改变原字段类型、对齐或含义需要升级不兼容版本。

创建函数先检查输出句柄指针本身非空，再把它指向的句柄槽置空，参数校验通过后才构造对象；内部异常在导出边界转为错误码。只有成功时句柄才转交调用者。DestroyAsset返回0表示销毁成功，空句柄也返回0；返回非零要求对象保持有效，宿主保留原句柄和关闭记录。销毁函数先完成可能失败的校验，再进入不抛异常的实际析构，避免对象已经部分销毁却返回可重试错误。任意无效指针仍不能作为对象访问；跨模块的重复销毁检测需要句柄表与代数，单纯`delete`不具备这个保证。

CreateAsset成功后，宿主把句柄登记到该模块代次的对象表，记录匹配的Destroy入口；登记完成才归还本次创建的调用计数，销毁完成才移除对象记录。热替换产生新的模块代次，新代次的函数表只接收自己的句柄。对象内存仍存在时，虚表与析构代码仍依赖原模块，所以旧对象与旧函数表一起保留到本代清理完成。

宿主若把CreateAsset排队，任务记录先固定模块代次、输入版本和参数缓冲持有，再进入Queued。工作线程在模块入口内同时检查Running与任务仍为Queued，取得调用计数并改为Invoking；队列取消只可领取Queued，Invoking结果必须等调用返回。重复队列通知按任务身份读取状态，不能再次创建对象。Closing关闭领取后，尚未调用的项转Cancelled并释放输入；已经调用的项仍完成登记，随后进入正常关闭清单。

调用前还预留对象表条目与结果记录空间。预留失败就不进入插件；成功返回后以不分配内存的写入保存句柄、模块代次和Destroy入口，再把任务改为Recorded，最后释放输入与调用计数。这样Create已成功而结果登记失败不会留下一份无人跟踪的插件对象。创建返回错误则记录原错误并归还空条目；宿主进程重启从资产版本重新建立任务，进程内任务身份和裸句柄均不跨进程续用。

### 普通销毁与对象借用

模块处于Running时也会单独关闭资产。A借用缓存B，A的任务仍在运行，此时关闭B必须先阻止新的借用。模块调用计数只保留代码，B另有Active、Stopping、Destroyed状态、对象使用计数和依赖者集合。模块入口门与对象表采用固定顺序加锁：先模块门、后对象表；检查入口状态、领取模块令牌和对象令牌在这段共同临界区内完成。宿主公开句柄使用槽位与对象代数定位表项，插件裸地址保存在表内。普通调用先在对象入口锁内检查模块代次、对象代数与Active，再取得对象使用令牌和模块调用令牌；调用退出同时归还两者。跨异步任务的使用令牌在投递前取得，持续到任务确认退出。

建立A→B时，宿主在同一对象表锁内检查A、B均Active、检查无环并预留依赖记录，再发布借用字段。边从字段可见起一直保留到A停止使用并清除字段，包含A析构访问B的期间。关闭B也取得这把锁：存在存活依赖者时返回Busy并列出A，B保持Active；调用方先关闭A或显式解除借用，再重试B。对象使用计数归零只说明当前调用结束，依赖边为空才说明A将来也不会再访问B。

依赖者为空时，关闭入口把B从Active改为Stopping并登记唯一关闭记录。后来的普通调用和新借用均拒绝，重复关闭加入同一完成结果。关闭执行者先RequestStop，再等待B的任务、回调和使用计数归零，随后调用Destroy。实际析构期间保留B指向其提供者的边；成功后才共同移除对象记录、释放这些边、递增槽位代数并保存关闭结果。等待释放对象表锁，工作者才能归还令牌。关闭执行者自身持模块令牌，模块卸载必须等这次普通销毁退出。

例如A→B存在时，线程甲关闭B得到Busy；线程乙关闭A后，A先停止任务，析构仍能读取B。A销毁回执提交并删除A→B后，甲重试B才能进入Stopping。若甲先关闭了没有依赖者的B，随后建立A→B会在同一锁内看到Stopping并失败，A的借用字段保持原值。两个关闭者竞争同一个B时只有一份记录进入析构，旧代数句柄始终不能访问复用后的槽位。

RequestStop或Destroy的可恢复错误保留Stopping、原句柄、依赖和模块引用，由同一关闭执行者续行；Destroy返回失败必须满足前文的对象完整性契约。对象无法安全重试时进入隔离故障，保留依赖闭包。模块进入Closing后接管已有单对象关闭记录，等待其完成，再冻结剩余对象表；已停止的B不会重复析构。

### 调用入口与卸载协作

停止新入口与统计在途调用必须共享同一同步门。宿主为每代模块保存状态、调用计数、后台活动计数和存活对象表。普通调用在锁内检查Running和模块代次，再增加调用计数，释放锁后进入插件；退出路径无论成功还是异常都减少计数。对象句柄活着与一次调用正在执行分别记录，避免卸载等待存活对象计数归零、对象却又等卸载方调用Destroy的循环。

插件创建的后台任务与延迟回调先取得本代活动令牌，再投递到线程池；投递失败立即归还，执行完成或取消确认后归还。宿主常驻跳板保存模块代次、活动令牌和任务状态。Closing时尚未开始的普通回调由跳板丢弃并归还令牌，已经进入插件的回调执行完再归还。若取消接口只禁止将来调度，宿主还须从调度器取得“该队列项已移除”或“正在执行且已退出”的确认。单纯把插件函数裸指针留在队列里，执行时才领取令牌，会使旧回调在模块卸载后跳入无效地址。

宿主用单一关闭执行者保存Closing、Draining、Destroying和Unloaded阶段。接纳创建及依赖修改时，在同一入口锁内同时增加“对象表修改在途数”和调用计数，提交或失败后再归还。进入Closing时在这把锁内关闭普通入口，随后撤销外部事件注册，先等对象表修改在途数归零，冻结完整对象表和依赖表。此时只等已经接纳的有界创建与修改，后台活动尚未排空。随后通过专用RequestStop向冻结表中的每个对象发出幂等停止请求；这些清理调用可在Closing执行，仍计入调用计数。若状态检查与计数增加分开，关闭方可能在两者之间看到零并卸载DLL，迟到调用随后就会进入已卸载代码。

例如CreateAsset已经接纳、构造尚未结束时进入Closing，关闭执行者等待该调用将新句柄登记到对象表后再枚举，因此不会漏掉新对象。创建入口在返回前完成对象登记，不等待关闭方的Stop信号；需要长期工作的部分在登记后交给持活动令牌的后台任务。若某插件无法在创建阶段退出，关闭记录停在Closing并报告该调用，保留模块；等待全部后台活动归零后才发停止信号则可能形成死锁。

RequestStop只改变停止状态、唤醒工作者和撤销工作来源，保留工作者仍访问的对象。已持令牌的工作者可登记完成所需的子任务，子令牌先领取再释放父令牌；外部普通工作来源已经关闭。进入Draining后，宿主等待调用计数和后台活动计数同时归零。等待释放计数锁，也释放工作者退出需要的业务锁。持令牌的插件回调将卸载请求投递给宿主后返回，由宿主执行关闭；同步等待卸载会等待回调自己退出。

### 对象依赖与关闭续行

设资产解码器A借用缓存B，A的后台工作与析构都会访问B。创建A以前，B先进入本代对象表；建立借用时记录`A→B`，要求B仍存活，并检查加入后不存在从B到A的可达路径。依赖表更新与借用字段发布在同一同步协议内完成，检查失败保持字段原值。卸载执行者在关闭普通入口后等待在途修改退出，便得到冻结的依赖表。

宿主先对A、B都发停止请求，再等待两类活动计数归零。进入Destroying后，选择没有存活依赖者的对象执行Destroy：本例只有A符合，A销毁成功后移除其依赖边，B才可销毁。Destroy按契约完成同步资源释放并捕获内部异常，不创建新后台任务；需要等待异步释放的工作放在RequestStop与Draining阶段，因此归零条件在销毁期间保持成立。宿主的关闭执行者自身保留模块句柄，完成最后一次Destroy后才调用平台卸载入口。

两个对象需要相互协作关闭时，把协作放在RequestStop阶段；各自确认停止后解除双向业务关系，再留下无环的析构依赖。需要原子管理的互相引用对象也可由组合所有者统一关闭。模块之间同样登记提供方依赖，例如解码器模块A调用缓存模块B，就让A清理完成后再清理B；宿主常驻调度器是关闭流程的执行者，关闭期间保持可用。

每代关闭记录保存当前阶段、每个对象的停止请求状态和销毁回执，以及尚未退出的任务身份。超时使模块留在Draining，保留对象、函数表与依赖模块；续行重新检查计数并继续等待，已确认的停止请求可以按幂等契约重发。Destroy成功立即移除对象并保存回执，单一关闭执行者不会在续行中再次销毁它。Destroy返回失败时要求对象仍可供诊断与再次关闭；无法提供这一保证的插件进入隔离故障状态，宿主保留模块并阻止后续普通调用。进程内关闭记录随进程结束而失效，新的进程通过正常加载和资产恢复重建对象，不复用旧地址。

### Win32 与 COM 边界

插件若把窗口消息注册为任务来源，关闭流程也要撤销这份来源。Win32 GUI程序从消息队列取出事件，经`TranslateMessage`和`DispatchMessage`送到窗口过程`WndProc`。`WPARAM`、`LPARAM`的含义由消息类型决定，平台层据此解码为稳定事件，宿主跳板再按模块代次决定能否交给插件。已排队事件仍经过跳板检查，注销来源与排空在途执行分别完成。

COM用接口与二进制契约连接组件。对象通过`QueryInterface`查询接口，用`AddRef/Release`管理引用计数，接口以GUID标识。资产解码器持有的COM接口也属于关闭资源；智能指针只管理引用释放，还需遵守创建线程的Apartment和接口封送要求。

COM引用也按交接点计数。成功的`QueryInterface`给调用者一份需要Release的接口引用；借用指针只在原所有者保证寿命期间使用，要留到异步任务就取得独立引用。Release降到零后对象可立即销毁，不能继续通过该指针查询状态。线程先初始化所需Apartment，释放自己持有的接口后再结束对应COM初始化；跨Apartment按接口契约封送，复制一个裸指针不会把线程访问权限一并转移。

## 验证方法

分别制造缺符号、ABI版本不匹配与加载缺库，确认诊断阶段准确。测试空指针、字段size和成对释放；编译器私有容器不跨稳定插件接口。通用所有权见对象生命周期。
