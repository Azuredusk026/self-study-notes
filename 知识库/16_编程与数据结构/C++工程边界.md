# C++工程边界

设编辑器加载资产插件M，先创建缓存B，再在界面线程T创建解码器A。A借用B的缓存页，后台任务W处理资产，T还管理A的窗口和COM接口。用户关闭A时，W尚未退出，随后又要求卸载M。宿主既要让清理在正确线程完成，也要把这次单对象关闭交给模块协调者，最后才释放B和插件代码。

下面沿这个插件的构建、创建、使用和关闭说明各层边界。头文件能编译只证明声明可见；符号能加载也不能证明双方对字节和释放责任理解一致。到了关闭阶段，保留模块、保护对象和安排清理线程又是三份分别需要兑现的约定。

## C++构建与模块边界

### C++ 构建链

插件的asset.cpp和宿主的editor.cpp分别编译，二者通过公共头约定CreateAsset。每个文件先经过下面的构建链：

```text
Source
 -> Preprocess
 -> Compile
 -> Object File
 -> Link
 -> Executable / Static Library / Dynamic Library
```

预处理器展开 `#include`、宏和条件编译。编译器对每个翻译单元生成目标文件。链接器解析跨文件符号、库依赖和最终地址。

若editor.cpp看不到参数类型，编译阶段就失败。声明可见而链接器找不到CreateAsset定义，会产生Unresolved External；两个目标文件都提供同一强符号则可能产生Multiple Definition。生成程序后找不到插件或导出入口，属于运行加载问题。入口存在但双方解释参数不同，则已经进入ABI不匹配，错误可能直到调用时才暴露。

排错先判断阶段，不要看到“编译失败”就反复改代码。

### 头文件与翻译单元

资产接口头同时被宿主和插件包含，通常保存声明、必要类型以及需要在调用侧实例化的内联与模板。实现放在`.cpp`，修改解码算法便不必让所有调用方重新编译；公共头改变则使包含它的翻译单元重新构建。

减少不必要的头文件包含：

- 能前置声明时不引入完整定义；
- 私有实现可使用 PImpl 隔离依赖；
- 稳定公共接口与高频变化实现分开；
- 隐式实例化通常需要模板定义可见；对支持的具体类型显式实例化后，可以把相应定义放在 `.cpp`，并用 `extern template` 抑制调用侧的重复实例化。

包含保护/`#pragma once` 防止同一翻译单元重复包含，但不解决跨翻译单元的单一定义规则。

例如a.cpp与b.cpp都包含定义了普通全局变量的公共头，各自编译都能成功，链接时却可能产生重复定义。包含保护只在单个翻译单元内起作用，不能合并这两份定义。让头只声明`extern int counter`，并在一个.cpp提供定义，才使两个调用方引用同一实体；C++17的内联变量则遵循另一套允许多处定义的契约。

### 静态与动态库

静态库在链接时把所需目标文件合入最终产物。部署简单，但多个程序可能各自包含一份，更新需要重新链接。

这里的资产处理器采用动态库，宿主按受控搜索路径加载插件及依赖，再解析导出入口。双方必须匹配调用约定和参数布局；创建对象后，还要保证它的析构函数所在模块一直加载到对象销毁。独立替换因此要求先排空旧模块的调用、对象与回调，后文会沿这条顺序关闭插件。

跨 DLL 分配、另一侧释放若使用不同堆/CRT，可能崩溃。边界常提供成对 `Create/Destroy`，由分配方负责释放。

### ABI 与 C接口

若直接让CreateAsset返回std::string或C++对象，宿主就同时依赖插件的类布局、标准库实现和异常约定。这里用C ABI导出入口：整数规定宽度，字节缓冲配长度，对象以不透明句柄返回。接口头提供版本和结构大小，失败返回错误码；消息写入调用方缓冲，或由插件提供对应释放函数。这样宿主消费的是明确的接口字段，而不是猜测插件私有对象的布局。

不要跨边界直接传 `std::string`、`std::vector` 或编译器私有对象，除非所有模块严格锁定同一工具链。

## 类型布局与资源语义

### C++ 类型与布局

插件内部仍可用STL容器、迭代器和算法保存资产。模板在编译期生成具体类型代码，内部选择不必暴露为公共接口。继承与虚函数支持运行时多态，但会引入对象布局、间接调用和 ABI 约束；数据导向热路径更常用显式数据与批处理。

结构体的填充字节由成员对齐要求决定，成员顺序会改变 `sizeof`。联合体让多个成员共享同一段存储，必须记录当前有效成员；现代 C++ 更适合用 `std::variant` 表达带标签联合。任何跨文件、网络、GPU 或插件边界的数据结构都应固定宽度、布局和版本，不能直接依赖编译器默认内存表示。

### C++ 对象模型与虚函数

资产插件内部可以用基类管理不同解码器。普通非虚成员函数不存放在每个对象内。对象主要保存非静态数据成员和编译器需要的隐藏信息。含虚函数的对象通常带一个虚表指针，指向该动态类型的虚函数表。通过基类指针或引用调用虚函数时，程序根据动态类型查表完成运行时分派。

标准规定的是多态行为，不规定虚表的具体内存布局。常见实现可以帮助理解成本，但不能作为跨编译器 ABI 契约。

解码器的派生实现用`override`让编译器核对重写签名，稳定终点可用`final`限制扩展；接口中的纯虚函数`=0`要求具体解码器提供实现。宿主若通过普通基类指针delete解码器，基类必须提供虚析构，派生资源才能按正确类型释放。

构造和析构期间，虚调用只到当前构造层级。基类构造函数因此不能调用虚函数来初始化尚未构造的派生缓冲。解码器也以指针或引用传递；把派生对象按值赋给基类会切掉派生部分，后续再调用已经无法恢复原解码器状态。

虚调用的主要代价是一次间接调用，并可能限制内联。真正风险通常是对象分散、指针追逐和所有权不清。稳定扩展点适合接口多态，海量同构对象的热循环更适合连续数据与显式类型分组。

### 复制、移动与异常安全

解码器获得文件和输出缓冲后，失败路径也必须释放它们。资源类型应优先遵守 Rule of Zero：让标准容器和智能指针管理资源，类型本身不手写析构、复制和移动。直接持有资源的 C++ 类型，需要一起设计析构、复制构造、复制赋值、移动构造和移动赋值。这是五法则（Rule of Five）。优先用标准资源包装类型承担所有权，减少手写这些操作的需要。

移动操作按类型契约转移或重建资源。标准库类型的移后对象通常处于有效但未指定的状态，具体可执行哪些操作仍取决于操作前提；自定义资源类型也要明确移后状态与允许的操作。`std::move` 只是把表达式转换为右值引用，不会自动搬运；是否移动取决于目标类型是否实现移动操作。

容器和工具代码常讨论三种异常保证：基本保证要求失败后没有资源泄漏且对象不变量成立，值可以变化；强保证要求因异常失败时状态不变；不抛异常保证要求异常不会离开函数。RAII、先构造临时结果再交换，以及不抛异常的移动能帮助实现更强保证。

例如赋值要同时更新缓冲与长度，先释放旧缓冲再分配新缓冲，分配失败就无法保持旧值。先用RAII临时对象分配并复制全部数据，成功后以不抛异常的交换提交，失败则临时对象释放自身，原对象保持不变。强保证依赖提交动作不失败；若交换还要分配，这条推理便不成立。

### 布局与边界字节

固定宽度不自动固定布局。例如uint8_t后接uint32_t，在第二字段按4字节对齐的常见ABI下，中间会插入3字节填充。调用双方对结构尺寸、字段偏移、对齐和调用约定使用同一契约，并在各自构建中检查sizeof与offsetof。extern "C"约束语言链接，不会取消填充、统一大小端或把无效指针变成安全输入。文件和网络因此逐字段编码；同进程插件才在已锁定的ABI下共享结构内存。

### Win32 与 COM 边界

A在T创建窗口并注册消息来源。Win32 GUI程序从消息队列取出事件，经`TranslateMessage`和`DispatchMessage`送到窗口过程`WndProc`。`WPARAM`、`LPARAM`的含义由消息类型决定，平台层据此解码为稳定事件，宿主跳板再按模块代次决定能否交给M。来源注册、已排队事件和正在执行的窗口过程分别持有状态，关闭时才能分别注销、取消和排空。

COM用接口与二进制契约连接组件。对象通过`QueryInterface`查询接口，用`AddRef/Release`管理引用计数，接口以GUID标识。资产解码器持有的COM接口也属于关闭资源；智能指针只管理引用释放，还需遵守创建线程的Apartment和接口封送要求。

COM引用也按交接点计数。成功的`QueryInterface`给调用者一份需要Release的接口引用；借用指针只在原所有者保证寿命期间使用，要留到异步任务就取得独立引用。Release降到零后对象可立即销毁，不能继续通过该指针查询状态。线程先初始化所需Apartment，释放自己持有的接口后再结束对应COM初始化；跨Apartment按接口契约封送，复制一个裸指针不会把线程访问权限一并转移。

## 所有权与模块接口

RAII和唯一、共享、弱引用的完整语义见 [[16_编程与数据结构/对象生命周期]]。插件边界把这些规则落实到创建、销毁和卸载三个入口。前面的布局与异常保证在这里成为调用协议：宿主先提供有效接口头，插件校验并构造，成功后才交出句柄。

### C ABI契约

声明片段使用固定位宽版本和不透明句柄，创建与释放由同一模块实现。调用约定与导出宏按平台补齐。

```cpp
struct AssetApi { uint32_t version; uint32_t size; };
extern "C" int CreateAsset(const AssetApi* api, void** handle);
extern "C" int DestroyAsset(void* handle);
```

### 接口结构的版本协商

接口调用者先保证指针指向至少包含version和size的有效可读头部；空指针检查不能证明任意非空地址都可访问。插件读取这个头部以后验证版本和size，并要求声明范围内的内存仍由调用者保持有效。size允许调用方传入较长的新结构，旧插件只读取自己认识的前缀；传入比必需前缀更短的结构则拒绝。字段增加在尾部才能维持这种前缀约定，改变原字段类型、对齐或含义需要升级不兼容版本。

创建函数先检查输出句柄指针本身非空，再把它指向的句柄槽置空，参数校验通过后才构造对象；内部异常在导出边界转为错误码。只有成功时句柄才转交调用者。DestroyAsset返回0表示销毁成功，空句柄也返回0；返回非零要求对象保持有效，宿主保留原句柄和关闭记录。销毁函数先完成可能失败的校验，再进入不抛异常的实际析构，避免对象已经部分销毁却返回可重试错误。任意无效指针仍不能作为对象访问；跨模块的重复销毁检测需要句柄表与代数，单纯`delete`不具备这个保证。

CreateAsset成功后，宿主把句柄登记到该模块代次的对象表，记录匹配的Destroy入口；登记完成才归还本次创建的调用计数，销毁完成才移除对象记录。热替换产生新的模块代次，新代次的函数表只接收自己的句柄。对象内存仍存在时，虚表与析构代码仍依赖原模块，所以旧对象与旧函数表一起保留到本代清理完成。

宿主若把CreateAsset排队，任务记录先固定模块代次、输入版本、类型声明的执行线程和参数缓冲持有，再进入Queued。本例A的创建由T执行；执行线程在模块入口内同时检查Running与任务仍为Queued，取得调用计数并改为Invoking。队列取消只可领取Queued，Invoking结果必须等调用返回。重复队列通知按任务身份读取状态，不能再次创建对象。Closing关闭领取后，尚未调用的项转Cancelled并释放输入；已经调用的项仍完成登记，随后进入正常关闭清单。

调用前还预留对象表条目、停止与收尾及销毁的派发槽、结果记录空间。预留失败就不进入插件；成功返回后以不分配内存的写入保存句柄、模块代次、线程要求和Destroy入口，再把任务改为Recorded，最后释放输入与调用计数。这样Create已成功而结果登记失败不会留下一份无人跟踪的插件对象，后续关闭也已有可用记录。创建返回错误则记录原错误并归还空条目；宿主进程重启从资产版本重新建立任务，进程内任务身份和裸句柄均不跨进程续用。

## 对象使用与关闭

M的对象表已经登记B和A，A→B表示后台工作与析构都还可能访问缓存。W持有A的使用令牌，延迟回调Q另持一份；A的停止、显式收尾和销毁派发槽在发布对象前预留，清理线程记录为T。宿主常驻协调者可以运行在另一线程，负责推进步骤，T负责实际执行这些线程受限的调用。下面沿关闭A、接管、排空、清理、销毁B和卸载M继续。

### 调用入口与依赖登记

宿主为每代模块保存状态、调用计数、后台活动计数和对象表；每个对象另有Active、Stopping、Destroyed状态、使用计数、代数与依赖者集合。模块调用计数保留代码，对象使用计数保留当前访问，存活对象表保留仍须调用Destroy的对象。三者分别记录，卸载方才能先销毁对象而不与等待条件形成循环。

宿主公开句柄使用槽位与对象代数，插件裸地址保存在表内。普通调用按“模块门→对象表”的固定顺序加锁，在同一临界区核对Running、模块代次、对象Active及代数，并取得模块和对象令牌，再释放锁进入插件。所有退出路径归还令牌。关闭入口也经过这把门，因此检查通过而未登记的调用不会落在卸载之后。

B先登记入对象表，建立A→B时在对象表锁内检查两者Active、预留依赖记录并检查无环，再发布借用字段；检查失败保持字段原值。边保留到A停止使用、析构结束且清除字段。瞬时使用计数为零不表示A以后不会再访问B，依赖边承担这份长期保护。

后台任务与延迟回调在投递前取得对象使用及模块活动令牌。宿主常驻跳板保存代次、任务身份与状态；投递失败归还令牌，执行结束或取消确认后归还。取消接口只禁止将来调度时，还须确认队列项已移除，或正在执行的调用已退出。裸插件函数指针不能在卸载后才领取保护。

### 普通销毁与对象借用

模块Running时单独关闭B，入口先检查依赖者。存在A→B就返回Busy并列出A，B保持Active。调用方先关闭A或显式结束借用再重试B。关闭没有依赖者的A时，把A置Stopping并登记唯一记录C_A，拒绝后续普通调用及新借用；重复关闭等待同一结果。

单对象协调者S先将A的RequestStop派给T，保存返回回执，再等待A的任务、回调和使用者退出。本例Q取消确认后归还使用令牌，W仍持有自己的令牌，所以C_A停在Waiting。B继续保留缓存，A还不能Destroy。若模块继续Running，S会在排空和显式收尾后，经后文清理入口销毁A；成功时共同移除对象、释放A→B、递增槽位代数并保存回执。

协调者持模块引用到收尾结束，等待期间释放对象表与业务锁。失败保留Stopping、原句柄和依赖闭包，安全可重试的步骤续行；部分析构无法保证对象完整时进入隔离故障。关闭A以后再关闭B，才允许B释放原来借出的缓存；瞬时使用计数归零不能替代这条依赖。

新借用与普通关闭在同一入口排序。B先有A→B就返回Busy；无依赖者的B先进入Stopping，后来的A→B便被拒绝。两个关闭者竞争同一对象只有一份记录进入析构，旧句柄的代数也不能访问复用槽位。

### 关闭记录与执行权

关闭记录解决重复请求，执行权决定谁能推进它。每份记录保存关闭ID、对象代数、协调者ID、所有权代次、阶段及当前步骤。步骤状态为Ready、Queued、Invoking、Completed或Waiting；RequestStop和Destroy各有稳定步骤ID。协调者负责选择步骤，实际插件调用可在指定清理线程执行。排队跳板在宿主门内比较协调者及所有权代次，把Queued改为Invoking，再取得模块和清理保护，随后释放锁进入插件。重复派发只查询同一步骤。

单对象关闭与模块关闭相遇时，模块协调者先登记接管请求。原协调者不再登记新步骤，在一个没有插件调用在途的边界交出记录；宿主门内共同替换协调者、递增所有权代次并保留原阶段与已完成回执。Waiting只是等待计数或工作完成，能直接交接；Queued先取消或使旧跳板失去授权，原排队项的保留一直等到它确认退出。尚未Invoking的步骤可由新协调者继续，旧协调者凭旧代次无法再次调用。

Invoking时保留原调用者，模块协调者订阅该步骤回执并继续给其他对象发停止请求。调用返回后，宿主先按原步骤ID登记结果，再交接剩余工作；已成功的Destroy共同删除对象与依赖边，模块清单直接排除它。调用尚未返回，接管方就不能再执行一次Destroy。线程失联或调用超时也不改变这个事实，关闭保留模块与在途状态，进入故障处理。

此时用户要求卸载M，模块协调者H取得C_A的Waiting记录：在宿主门内把协调者S改为H，所有权代次从3增至4，原RequestStop回执保持。S的旧通知再到达时不能推进记录。若卸载请求来得更晚、S已进入A的Destroy，H只订阅这次结果，同时先停止B的业务；它不会重新领取A的销毁权。

### 模块关闭与停止请求

关闭整个插件时，宿主常驻协调者保存Closing、Draining、Destroying和Unloaded阶段。进入Closing在模块门内关闭普通入口，再撤销外部业务事件来源。创建及依赖修改在模块门内核对入口状态，同时增加对象表修改在途数和调用计数，提交或失败后共同归还。已接纳的这些修改由该计数保护，协调者先等待它们提交或失败，再冻结新增与依赖修改；已有单对象关闭按前节交接。清单内对象随销毁回执删除，冻结不阻止既有关闭步骤结清。

CreateAsset尚未返回时，关闭方等待它完成无分配登记，因此不会漏掉新对象。创建入口必须有界返回，长期工作登记后交给后台任务；无法退出的构造使关闭停在Closing并保留模块。这里尚未等待全部后台活动，协调者先推进清单内各对象的停止步骤，工作者才有机会退出。已有RequestStop回执的对象沿原记录等待排空，Destroy已Invoking的对象只等待该调用，不能再向它并发发送RequestStop。其他对象的停止不必等待这次在途Destroy。

H沿A的原停止记录等待W，同时登记B的RequestStop。停止请求幂等地停止业务来源、唤醒工作者并撤销预约，B停止业务后仍保留A需要的缓存。Closing时跳板丢弃尚未开始的普通回调并归还令牌，已进入插件的调用执行完再归还；W结束既有停止工作所需的清理任务按清理派发协议登记。注销来源、取消队列项和排空执行分别完成。

### 工作排空与清理准备

H先进入Draining，等待所有可能访问A待释放资源的使用者退出，再授权显式收尾。这个集合包括关闭入口前接纳的普通调用、W及其停止子任务、Q和其他已排队或正在执行的业务回调，以及已经领取资源访问权限的清理调用。每次访问在进入前登记相应令牌，退出或取消确认后归还；A进入Stopping关闭新增普通访问。仅W退出，不能证明窗口或COM接口已经无人使用。

例如关闭入口前，调用U已取得A的使用令牌，正在读取COM接口。W和Q先退出，U还持一份，H只能等待，不能先让T执行Release。U返回并归还后，H在同一宿主门内核对RequestStop回执、资源访问计数为零和当前所有权代次4，关闭这一集合的继续领取，再把显式收尾步骤置Queued。这次核对与授权共同发生，等待期间不持对象锁。停止子任务若还需访问资源，就仍在等待集合中；它必须先结清，不能在收尾授权后追加。

已持令牌的工作者可产生完成既有停止工作所需的子任务，先增子计数再释放父计数；普通工作来源始终关闭。等待释放计数锁和工作者退出所需的业务锁。插件回调要求卸载时只向宿主投递请求并返回，H在外层收尾，回调不能同步等待自己退出。

可能失败的IO、业务结算、资源申请和异步释放在此阶段完成，逐项保存结果。进入Destroying前校验清理权限、参数及所需记录空间，析构只消费准备好的不抛异常同步清理。提供者B停止业务后仍保留缓存、分配器和句柄表，直到A清理结束；停工作者与释放依赖数据是不同边界。

### 清理线程与关闭派发

解码器A持有的窗口和COM接口在界面线程T清理。线程约束与寿命是两件事：保留模块使代码可调用，不能让任意线程取得操作窗口或接口的权限。对象登记时同时保存RequestStop、显式收尾和Destroy各自的线程或Apartment要求。协调者据此选择执行位置，调用步骤仍由前节的唯一记录保护。

T随后在Draining中释放COM引用并销毁窗口。收尾步骤及其同步清理回调另持步骤保护，它们不属于已经关闭的业务访问集合，否则会出现收尾等待自己退出的循环。宿主只允许绑定当前步骤、目标资源及对象代数的清理重入；回调返回后才能保存收尾完成。

显式收尾把每份COM引用与每个窗口登记为独立资源步骤，派发前预留结果空间。某资源操作确认成功后立即清空其字段并在宿主门内保存Completed；后续步骤失败时只重试尚未完成的资源，不能再次Release已归还的引用。返回失败且资源保持有效的步骤保存失败回执，保留原字段再重试。

资源步骤仍Invoking时等待原调用；字段更新与完成登记之间禁止异步取消执行线程。线程异常终止而无法判断释放结果时隔离该记录，保留模块，不以重试猜测。全部资源步骤完成后才保存整体收尾回执，后续Destroy只消费这个已收尾状态。本例A的析构也要求T，但要等模块进入Destroying后另行授权。

宿主在发布对象前预留停止、收尾与销毁的派发槽及结果空间，进入Destroying前再核验参数和关闭令牌；容量不足在发布前失败。清理跳板只接受绑定C_A、具体步骤、A的对象代数和当前所有权代次4的消息。插件不能借清理消息创建普通业务任务；普通事件入口保持关闭。

协调者投递后暂停推进，步骤仍明确保持Queued或Invoking，T的常驻事件循环继续服务关闭消息、COM派发和必要的窗口销毁消息。T收到消息后核验步骤，再在该线程同步调用插件，返回时保存回执。协调者和T都不能阻塞等待一项必须由自身事件循环完成的工作；界面触发关闭时只登记请求并返回，宿主后续轮次继续推进。消息处理引发重入时，普通业务仍被入口拒绝，清理重入则比较步骤状态，Invoking项不能再次进入。

窗口过程也通过宿主跳板保留模块。调用DestroyWindow时，宿主在T的调用作用域保存当前步骤和目标窗口的清理权限；同步触发的WM_DESTROY和WM_NCDESTROY由跳板核对这份上下文后进入资源清理分支，完成注销和释放。普通输入与重新加载资产仍被拒绝，消息类型本身不授予清理权限。该同步窗口回调属于当前窗口清理步骤，不能再次请求同一步骤或在回调内等待整个模块卸载。

Destroying阶段由协调者一次授权一个对象的销毁步骤，必要时借上述预留通道派到T；插件函数本身同步返回。协调者等待回执期间不持对象锁。这份宿主关闭派发与插件新建异步工作分别计数：前者是已登记步骤的执行位置，后者在销毁阶段禁止。

跨线程依赖清理还要满足提供者的线程契约。Draining可先将资源交回B所属线程，等待回执后清空A对应字段，原依赖边仍保留到A析构结束。确需在析构内同步跨线程调用时，准备合法封送接口或宿主清理代理，由B所属线程执行；以“等待线程→服务线程”建立等待图，要求无环且服务消息循环存活。有环就把相关结算拆到Draining完成，再进入销毁。本例B的缓存归还接口允许在A所在的T调用，锁保护缓存数据，依赖边保护其寿命。

T或其Apartment未能处理清理消息时，记录保持Queued或Invoking，保留对象、模块和依赖。超时不能把Destroy搬到任意工作线程重试。最后一个相关对象及关闭跳板退出后，才撤销清理通道、结束对应COM初始化并允许T退出；插件代码卸载还要等待后文的模块条件。

T完成显式收尾后，H等待收尾回执和同步回调退出。H共同检查各对象收尾完成、模块既有调用与后台活动为零、本阶段清理计数归零，才进入Destroying。A、B仍在对象表，A→B仍保留。尚未授权的Destroy槽只是预留记录，不计为正在执行的任务，因此不会形成“必须先析构才能排空、必须先排空才能析构”的循环。

### 关闭期间的依赖清理调用

H完成准备后进入Destroying，授权A在T执行Destroy。A最后仍需归还B的缓存页，所以H签发限定清理令牌，绑定C_A、A的对象代数、B及允许的操作。宿主核对既有A→B、双方对象与模块保留以及当前关闭阶段，允许批准的同步读取、归还和结算。普通令牌不能转换为这份权限，清理也不创建新业务对象、依赖或工作者。

入口在宿主控制锁内登记双方清理在途计数及模块保留，然后释放锁调用。跨模块按稳定模块ID顺序取得控制锁；执行插件和等待时不持这些锁。提供者按对象同步协议处理并发归还与统计更新，计数保护寿命，对象锁保护数据。Draining中的异步停止子任务另持清理活动令牌，Destroying只允许当前授权销毁步骤在其指定线程内同步清理。

T的跳板把该步骤从Queued改为Invoking，再调用A的Destroy。A用清理令牌归还缓存页，B的归还函数返回后，A完成析构；宿主保存成功回执并共同删除A和A→B。T的跳板退出前仍持模块保护，H等待这份保护归还。B此时还须满足使用者及清理在途为零，才可释放缓存和对象。伪造调用者、缺少原依赖或请求启动新缓存任务均拒绝并保留诊断；实际析构使用的权限已在准备阶段核验。

普通单对象关闭沿相同入口执行，B可仍为Active；插件内部直接借用指针也遵守同一资源保留条件。关闭阶段的推进与在途归零在共同入口比较，不能在锁外观察零后再放入新的清理调用。

### 依赖销毁与卸载续行

H确认A成功回执和跳板退出后，才授权B的Destroy。本例B的清理允许在H的执行线程运行；它同步释放剩余缓存，返回成功后从对象表移除。销毁按无存活依赖者的对象推进，每个函数在指定线程同步返回并捕获内部异常，期间禁止插件新增异步任务。需要双向协作的业务关系在RequestStop及Draining阶段结清并解除，留下无环析构依赖；互相引用对象也可由组合所有者统一关闭。模块依赖同样保证调用方清理后提供方才结束，宿主调度器一直保持可用。

关闭记录保存阶段、协调者与所有权代次、步骤状态、指定线程、销毁回执和未退出任务身份。超时保留当前阶段与全部尚存对象、函数表及依赖模块，续行重新检查计数和步骤账本；已确认返回的RequestStop可按幂等契约重发，在途步骤继续等待。Destroy成功立即移除对象并保存回执，续行不会再次析构；Destroy失败要求对象保持完整，可诊断并再次关闭，否则隔离故障并阻止普通调用。

最后一次Destroy返回且其跳板归还保护后，H确认M的对象表、清理在途及关闭派发队列均为空，撤销M这一代的清理通道，再调用平台卸载入口，写Unloaded并释放模块引用。T若服务其他模块则继续运行；只有T的全部所属资源与关闭消息结清后，才能结束对应COM初始化并退出线程。M已卸载与T可退出分别判断，宿主调度器保持可用到最后一份关闭回执消费完成。

进程内续行从C_A、B的关闭记录、步骤回执和当前计数继续：A已经销毁就直接等待其旧跳板或推进B，T上的步骤仍Invoking就等待原调用，Queued项按当前授权派发。进程结束后裸地址与这些运行中记录失效，新进程从资产状态正常加载并重建对象。
