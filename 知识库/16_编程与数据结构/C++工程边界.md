# C++工程边界

头文件能编译，插件加载却仍可能失败，因为链接符号、对象布局和分配器跨越了不同边界。C++工程先区分编译、链接与运行加载，再固定ABI、类型布局和资源释放方。

## C++构建与模块边界

### C++ 构建链

一个典型流程：

```text
Source
 -> Preprocess
 -> Compile
 -> Object File
 -> Link
 -> Executable / Static Library / Dynamic Library
```

预处理器展开 `#include`、宏和条件编译。编译器对每个翻译单元生成目标文件。链接器解析跨文件符号、库依赖和最终地址。

常见错误对应不同阶段：

- 语法或类型错误：编译阶段；
- Unresolved External：声明可见，但链接不到定义或库；
- Multiple Definition：同一强符号重复；
- Missing DLL/Entry Point：运行加载阶段；
- ABI Mismatch：能链接或加载，但类型布局/调用约定不一致。

排错先判断阶段，不要看到“编译失败”就反复改代码。

### 头文件与翻译单元

头文件通常放声明、内联与模板和必要类型；`.cpp` 放实现。头文件被多少文件包含，影响增量编译范围。

减少不必要的头文件包含：

- 能前置声明时不引入完整定义；
- 私有实现可使用 PImpl 隔离依赖；
- 稳定公共接口与高频变化实现分开；
- 隐式实例化通常需要模板定义可见；对支持的具体类型显式实例化后，可以把相应定义放在 `.cpp`，并用 `extern template` 抑制调用侧的重复实例化。

包含保护/`#pragma once` 防止同一翻译单元重复包含，但不解决跨翻译单元的单一定义规则。

### 静态与动态库

静态库在链接时把所需目标文件合入最终产物。部署简单，但多个程序可能各自包含一份，更新需要重新链接。

动态库在运行时加载，多个模块可共享并独立替换，但需要处理：

- 导出/导入符号；
- 搜索路径与依赖 DLL；
- 调用约定；
- CRT/分配器边界；
- C++ ABI、编译器和构建配置；
- 库卸载时仍存活的对象/回调。

跨 DLL 分配、另一侧释放若使用不同堆/CRT，可能崩溃。边界常提供成对 `Create/Destroy`，由分配方负责释放。

### ABI 与 C接口

C++ 类、STL容器、异常和名字修饰容易受编译器/版本影响。长期稳定插件接口常暴露简单 C ABI：

- 固定位宽整数和 POD 结构体；
- 指针与长度；
- 不透明句柄；
- 显式版本与结构大小；
- 调用方提供缓冲或成对释放函数；
- 错误码 + 错误消息查询。

不要跨边界直接传 `std::string`、`std::vector` 或编译器私有对象，除非所有模块严格锁定同一工具链。

### Win32 与 COM 边界

Win32 GUI 程序从消息队列取出事件，经 `TranslateMessage` 和 `DispatchMessage` 送到窗口过程 `WndProc`。`WPARAM`、`LPARAM` 的解释取决于消息类型，可能保存整数、位域或指针。窗口创建、输入、缩放和销毁都通过消息发生；引擎平台层应把它们转换成稳定事件，再交给上层系统。

COM 用接口和二进制契约连接不同组件。对象通过 `QueryInterface` 查询支持的接口，用 `AddRef/Release` 管理引用计数，接口以 GUID 标识。DirectX 与许多 Windows API 返回 COM 对象，C++ 中应使用智能指针封装引用计数，并明确线程 Apartment、初始化与释放顺序。

## 类型布局与资源语义

### C++ 类型与布局

STL 提供容器、迭代器和算法，模板在编译期生成具体类型代码。继承与虚函数支持运行时多态，但会引入对象布局、间接调用和 ABI 约束；数据导向热路径更常用显式数据与批处理。

结构体的填充字节 由成员对齐要求决定，成员顺序会改变 `sizeof`。联合体让多个成员共享同一段存储，必须记录当前有效成员；现代 C++ 更适合用 `std::variant` 表达带标签联合。任何跨文件、网络、GPU 或插件边界的数据结构都应固定宽度、布局和版本，不能直接依赖编译器默认内存表示。

### C++ 对象模型与虚函数

普通非虚成员函数不存放在每个对象内。对象主要保存非静态数据成员和编译器需要的隐藏信息。含虚函数的对象通常带一个虚表指针，指向该动态类型的虚函数表。通过基类指针或引用调用虚函数时，程序根据动态类型查表完成运行时分派。

标准规定的是多态行为，不规定虚表的具体内存布局。常见实现可以帮助理解成本，但不能作为跨编译器 ABI 契约。

关键规则：

- 派生类使用 `override` 让编译器检查是否真正重写；
- `final` 可以禁止继续重写或继承；
- 纯虚函数 `= 0` 使类型成为抽象类；
- 允许通过普通基类指针执行delete的多态接口应提供虚析构；
- 构造和析构期间的虚调用只分派到当前构造层级；
- 对象按值赋给基类会发生对象切片，派生部分被丢弃。

虚调用的主要代价是一次间接调用，并可能限制内联。真正风险通常是对象分散、指针追逐和所有权不清。稳定扩展点适合接口多态，海量同构对象的热循环更适合连续数据与显式类型分组。

### 复制、移动与异常安全

资源类型应优先遵守 Rule of Zero：让标准容器和智能指针管理资源，类型本身不手写析构、复制和移动。直接持有资源的 C++ 类型，需要一起设计析构、复制构造、复制赋值、移动构造和移动赋值。这是五法则（Rule of Five）。优先用标准资源包装类型承担所有权，减少手写这些操作的需要。

移动操作按类型契约转移或重建资源。标准库类型的移后对象通常处于有效但未指定的状态，具体可执行哪些操作仍取决于操作前提；自定义资源类型也要明确移后状态与允许的操作。`std::move` 只是把表达式转换为右值引用，不会自动搬运；是否移动取决于目标类型是否实现移动操作。

容器和工具代码常讨论三种异常保证：基本保证要求失败后没有资源泄漏且对象不变量成立，值可以变化；强保证要求因异常失败时状态不变；不抛异常保证要求异常不会离开函数。RAII、先构造临时结果再交换，以及不抛异常的移动能帮助实现更强保证。

## 所有权与模块接口

RAII和唯一、共享、弱引用的完整语义见 [[16_编程与数据结构/对象生命周期]]。插件边界还要确定分配与释放属于同一运行库，卸载前没有存活回调或对象。

## C ABI契约

声明片段使用固定位宽版本和不透明句柄，创建与释放由同一模块实现。调用约定与导出宏按平台补齐。

```cpp
struct AssetApi { uint32_t version; uint32_t size; };
extern "C" int CreateAsset(const AssetApi* api, void** handle);
extern "C" void DestroyAsset(void* handle);
```

## 接口结构的版本协商

插件读取结构前先验证指针、版本和size。size允许调用方传入较长的新结构，旧插件只读取自己认识的前缀；传入比必需前缀更短的结构则拒绝。字段增加在尾部才能维持这种前缀约定，改变原字段类型、对齐或含义需要升级不兼容版本。

创建函数先把输出句柄置空，参数校验通过后再构造对象；内部异常在导出边界转为错误码。只有成功时句柄才转交调用者，销毁函数接受空句柄但不能把任意无效指针当有效对象。跨模块的重复销毁检测需要句柄表与代数，单纯 `delete` 不具备这个保证。

卸载顺序是停止入口、等待调用结束、销毁存活对象、注销回调、最后卸载模块。对象数据即使还在堆里，虚表和析构函数可能已随DLL消失，因而“内存仍分配着”不能保证对象可用。

## 验证方法

分别制造缺符号、ABI版本不匹配与加载缺库，确认诊断阶段准确。测试空指针、字段size和成对释放；编译器私有容器不跨稳定插件接口。通用所有权见对象生命周期。


## 实现与证据
