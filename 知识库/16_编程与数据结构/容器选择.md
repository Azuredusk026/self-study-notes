# 容器选择

链表插入是常数时间，找到那个节点却可能遍历整表。容器选择先列出主要操作与引用稳定性，再比较数组、哈希和有序树。实际缓存和分配常常决定理论复杂度能否兑现。

## 操作决定容器

### 先定义操作

选择结构前列出：

- 插入、删除、查找、遍历哪个最频繁；
- 是否需要稳定顺序；
- Key 是否唯一；
- 数据量和峰值；
- 是否多线程/GPU；
- 是否需要序列化、Diff 和确定性；
- 查询是精确、范围还是最近邻。

没有工作负载，“HashMap 比 List 快”没有意义。

### Array、List 与 Deque

连续 Array/Vector：

- Index $O(1)$；
- 尾部追加摊还 $O(1)$；
- 中间插删 $O(N)$；
- Cache Locality 好；
- Reallocation 会使 Pointer/Iterator 失效。

Linked List 已知节点时插删 $O(1)$，但查找是 $O(N)$，每节点分配与指针跳转对 Cache 不友好。现代实时代码中，它往往没有理论图上看起来那么便宜。

Deque 适合两端插删和 Queue。具体块布局与迭代性能取决于实现。

### `std::vector` 的容量与失效

`std::vector` 保存一段连续元素，通常区分 `size` 与 `capacity`。`size` 是已经构造的元素数量，`capacity` 是当前存储可容纳的元素数量。尾部插入超出容量时会申请更大连续空间，把旧元素移动或复制过去，再释放旧空间。

扩容倍率由标准库实现决定，标准只要求尾部追加具有摊还常数复杂度。常用操作的区别：

- `reserve(n)` 只保证容量至少为 `n`，不创建元素；
- `resize(n)` 改变元素数量，可能构造或销毁元素；
- `push_back` 加入已有对象，`emplace_back` 用参数在尾部构造对象；
- `clear` 销毁元素但通常保留容量；
- `shrink_to_fit` 是非强制请求，不能依赖它一定释放内存。

Reallocation 会使指向元素的 Pointer、Reference 和 Iterator 全部失效。未扩容的尾部插入也会使 End Iterator 失效。需要长期身份时，应保存稳定 ID、索引加版本号，或选择具有相应稳定性保证的结构。

`vector` 的连续性通常让它成为默认顺序容器。频繁中间插入并不自动意味着 `list` 更快；还要计算查找节点、每节点分配和 Cache Miss。

### Stack、Queue 与 Priority Queue

Stack 是 LIFO，适合 DFS、解析和撤销层级；Queue 是 FIFO，适合 BFS、Job 和事件顺序。

Priority Queue 通常由 Binary Heap 实现：

- 查看最小/最大：$O(1)$；
- 插入：$O(\log N)$；
- 弹出：$O(\log N)$。

A*、Dijkstra 和调度器会用它选择当前代价最小节点。若需要更新已有节点 Priority，要保存 Handle/Index 或允许重复插入并在弹出时跳过旧记录。

### Hash Table

Hash Table 平均查找/插入 $O(1)$，但碰撞、扩容和恶意 Key 可退化。

关键：

- Hash 与 Equality 必须一致；
- Mutable Key 放入后不能改变参与 Hash 的字段；
- Load Factor 影响内存与碰撞；
- Rehash 会产生峰值；
- 普通 Hash 遍历顺序不应作为确定性输出顺序。

资产构建需要稳定结果时，输出前按 Canonical Key 排序，或使用有序结构。不要依赖某次运行的 Dictionary 枚举顺序。

`std::unordered_map` 常由 Bucket Array 加冲突链或等价结构实现。Hash 先定位 Bucket，再在 Bucket 内用 Equality 找 Key。`load_factor = size / bucket_count`，超过阈值时 Rehash 会重建 Bucket 分布，并产生时间和内存峰值。

平均 $O(1)$ 依赖 Hash 分布和装载因子。Key 集中到少量 Bucket 时会退化到线性查找。自定义 Key 必须让相等对象得到相同 Hash；Hash 相同的对象仍可不相等。

开放寻址表把元素直接放在 Bucket Array 中，Cache Locality 较好，但删除、探测序列和高装载率更敏感。链式或节点式实现更容易保持节点地址，却增加指针和分配成本。标准只规定接口、复杂度与失效规则，不固定 `unordered_map` 的内部冲突策略。

### Tree

Tree 表达层级：Scene Graph、Skeleton、UI、文件目录和 BVH。

Depth-first Search（DFS）适合递归处理子树、序列化和后序删除。Breadth-first Search（BFS）适合按层级处理和找最少边数路径。

Recursive DFS 简洁，但极深树可能 Stack Overflow。大型/不可信数据使用显式 Stack，并检测 Cycle。场景“应该是树”也可能因损坏引用形成环。

平衡 Binary Search Tree 保持查询、插入、删除 $O(\log N)$，并支持有序遍历。若只需要 Key Lookup，Hash 往往更直接；若需要 Range/Order，Tree 更合适。

### 红黑树与有序关联容器

红黑树用颜色约束限制最长路径：根通常视为黑色，空叶为黑色，红节点不能有红孩子，从任一节点到后代空叶的黑节点数量相同。由此树高保持在 $O(\log N)$。

插入或删除破坏约束后，通过 Recolor 和左旋、右旋恢复平衡。红黑树追求的是较宽松的高度界，不像 AVL 树那样严格平衡，因此更新时通常需要较少旋转。

`std::map`、`std::set` 的标准保证有序遍历和对数级查找、插入、删除。很多标准库用红黑树实现，但具体结构不是 C++ 标准的一部分。节点式有序容器通常保持未删除元素的 Iterator/Reference 稳定，代价是每节点分配、指针开销和较差的空间局部性。

需要范围查询和有序遍历时，选择有序容器。只按键精确查找时，可以考虑哈希表。数据量较小或更新少时，排序后的 `vector` 加二分查找也值得测试，它通常更紧凑且有较好的访问局部性。
