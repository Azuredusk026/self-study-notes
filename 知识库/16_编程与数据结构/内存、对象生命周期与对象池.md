# 内存、对象生命周期与对象池

内存问题要区分分配位置、所有权、生命周期和访问方式。对象数量相同，分散的小对象、连续数组、托管对象和 GPU Resource 的成本完全不同。

## Stack 与 Heap

Thread Stack 保存调用帧、返回地址和局部数据。作用域结束时 Stack Pointer 回退，分配释放很快，但容量有限。

Heap 支持动态大小和跨作用域生命周期。Allocator 要维护空闲块、对齐和并发，频繁小分配可能造成开销与碎片。

“值类型在 Stack、引用类型在 Heap”只是 C# 入门近似。值类型可以嵌在 Heap Object、Array 或被 Boxing；JIT/AOT 也可能优化。真正要看对象布局和逃逸/运行时行为。

## Virtual、Physical 与 GPU Memory

进程看到 Virtual Address Space，操作系统按 Page 映射 Physical Memory。提交大块地址不一定立刻占用全部物理页，但首次访问、Page Fault 和换页会影响性能。

GPU Resource 可能位于独立 VRAM 或 Unified Memory。Upload/Readback Heap、Staging Buffer 与 Device-local Resource 有不同访问成本。

移动 SoC 的 CPU/GPU 共享物理内存，不等于拷贝和带宽免费。Cache Coherence、Tile Memory、总线和资源同步仍然存在。

## 分配器与碎片

外部碎片是空闲总量足够，但没有足够大的连续块；内部碎片是分配块因对齐/Size Class 大于实际请求。

常见策略：

- Arena/Linear Allocator：整批分配、整批释放；
- Pool/Slab：固定 Size Class，快速复用；
- Stack Allocator：后进先出；
- Buddy Allocator：按二次幂拆分合并；
- General Heap：灵活但 Metadata 和碎片更复杂。

帧临时数据适合 Frame Arena。生命周期不同的数据混入同一 Arena 会导致无法及时释放。

## Ownership

每个资源要回答：谁创建、谁拥有、谁可借用、何时释放、异步任务是否仍在使用。

C++ 使用 RAII、`unique_ptr`、容器和明确 Handle；C# 使用 Managed Reference、`IDisposable`、`using` 和引擎资源 API。GC 只管理 Managed Memory，不会自动正确关闭 File、Socket、Native Handle 或 GPU Resource。

Finalizer 时间不确定，也会增加 GC 工作。Native Resource 应提供确定性 `Dispose/Release`，并让重复调用安全。

## Managed Heap 与 GC

C# Managed Object 分配后由 Garbage Collector 追踪可达性。对象不可达不等于立刻释放，Collection 会在特定时机扫描、移动或回收。

不同 .NET/Unity Runtime 的 GC 实现和 Generation/Incremental 行为有差异，应以当前平台文档和 Profiler 为准。

实时程序关注：

- 每帧分配速率；
- Collection 频率和暂停时间；
- Live Set 大小；
- 大对象与碎片；
- Native/Managed 双份内存；
- 临时分配峰值。

“这一帧 GC 没运行”不代表分配免费。分配会增加未来回收工作和峰值。

## 常见 C# 隐式分配

- 字符串拼接、格式化和 `Substring`；
- LINQ Enumerator/Closure；
- Lambda Capture；
- Boxing；
- 每帧创建 List/Array/Dictionary；
- API 返回新数组；
- 异步状态机和 Task；
- 日志参数和 Stack Trace。

不要因此全面禁止 LINQ 或 String。Editor Tool 和低频操作更重视可读性；Runtime 热路径用 Profiler 定位后再替换。

复用 Collection 时 `Clear()` 通常保留 Capacity。它减少重分配，但也可能让一次峰值后长期占用大数组。

## Native Container 与 Pinning

Unity NativeArray/NativeList 等使用 Native Memory，并配合 Job/Burst 和显式生命周期。Allocator 类型表达 Temp、TempJob、Persistent 等预期范围。

忘记 `Dispose` 会产生 Native Leak。过早释放而 Job 仍在运行会造成非法访问。

Pinning Managed Object 让 GC 不能移动该对象，方便 Native Interop，但长时间大量 Pin 可能增加碎片。更稳妥的是使用固定 Native Buffer 或短时间 Pin 并批量传输。

## Data Locality

CPU Cache 以 Cache Line 读取。连续遍历 Array/Struct of Arrays 通常比随机追逐对象指针更快。

Array of Structures：

```text
[pos vel age][pos vel age][pos vel age]
```

Structure of Arrays：

```text
[pos pos pos][vel vel vel][age age age]
```

如果 Update 只读取 Position/Velocity，SoA 减少无关数据进入 Cache，也适合 SIMD。但编辑器对象和复杂多态逻辑未必值得改成 SoA。

## Cache 映射与写策略

Direct-mapped Cache 中每个内存块只能进入一个 Cache Set，硬件简单但容易发生冲突抖动。Set-associative 允许一个 Set 内有多个 Way，是容量、命中率和查找成本的常见平衡。Fully-associative 允许放入任意位置，冲突少但查找和替换成本高，通常只用于较小结构。

一个 Set 满时需要 Replacement Policy，例如 LRU、近似 LRU 或随机替换。Write-through 在写 Cache 时同步更新下层内存，行为直接但写流量大；Write-back 先标记 Dirty，驱逐时才回写，减少流量但一致性和状态管理更复杂。游戏代码通常不能选择硬件策略，但可以通过连续访问、减少工作集和避免多个热数组落入同一冲突模式来提高命中率。

## Unity Object 的两层身份

`GameObject`、`Component`、`Texture`、`Mesh` 等 UnityEngine.Object 通常有 Managed Wrapper 和 Native Engine Object。C# 引用释放只影响 Managed 可达性，不等于 Native Resource 立刻释放。

Unity 特殊的 Null 比较会考虑 Native Object 是否已被销毁。对象看似 `== null` 时 Managed Wrapper 仍可能存在，普通 C# `ReferenceEquals` 语义不同。

## Instantiate 的成本

创建 Prefab/GameObject 可能涉及：

1. Managed Wrapper/脚本对象分配；
2. Native GameObject、Transform、Component 分配；
3. Prefab/Serialized Field 复制与引用解析；
4. Transform Hierarchy 注册；
5. Renderer、Physics、Animation、Audio 等子系统注册；
6. `Awake`、`OnEnable` 等生命周期回调；
7. 脚本在回调中继续分配、查找和加载；
8. 后续渲染/物理结构更新。

成本不是“new 一个 C# 对象”。复杂 Prefab 的 Component、子层级和回调往往比单次 Managed Allocation 更贵。

GPU Resource 是否此刻真正创建/上传取决于 Asset 和引擎状态，不能笼统说每次 Instantiate 都上传全部 Mesh/Texture。

## Destroy 的成本

Unity `Destroy` 通常标记 Native Object 在安全时机销毁，不一定立即释放。销毁可能触发：

- `OnDisable`/`OnDestroy`；
- Hierarchy 和子系统注销；
- Native Resource 引用变化；
- Managed Wrapper 未来由 GC 回收；
- 批量销毁造成帧末峰值。

`DestroyImmediate` 主要用于受控 Editor 情景，Runtime 或遍历集合时滥用可能破坏状态。

Native Asset 是否卸载还取决于其他引用、AssetBundle/Addressables Handle 和资源管理策略。

## 对象池解决什么

Pool 复用已经创建的对象，减少反复 Instantiate/Destroy、注册、分配和 GC。适合生命周期短、频繁出现、结构相同的对象，例如弹丸、命中特效和部分 UI Item。

典型状态：

```text
Inactive -> Acquire -> Active -> Release -> Inactive
```

Pool 不应只调用 `SetActive`。需要定义 Reset Contract：

- Transform、Velocity、Animation、Particle；
- Event Subscription、Coroutine/Task；
- MaterialPropertyBlock 和临时引用；
- Physics State、Trail History；
- Gameplay Owner、Timer、Damage State。

漏 Reset 会让上一任对象状态污染下一次使用。

## Pool 的代价

- 预热增加加载时间和初始内存；
- 过大池长期保留 Native/Managed/GPU 资源；
- Active/Inactive 切换仍可能触发生命周期和子系统成本；
- 对象结构/Prefab 更新后池中旧实例可能不兼容；
- Pool 隐藏真实 Ownership，产生未归还或重复归还；
- 低频对象池化只增加复杂度。

容量策略可设置 Initial、Max、Overflow：超过 Max 时拒绝、临时创建或回收最旧对象。选择要符合 Gameplay，不应静默抢走仍在使用的对象。

## Pool 与生命周期回调

首次 Instantiate 会调用 `Awake`；反复激活通常调用 `OnEnable/OnDisable`，不会再次调用 `Awake`。若业务把每次使用初始化放在 `Awake`，Pool 后就会出错。

建议定义显式 `OnAcquire(context)` / `OnRelease()`，让每次租用状态可测试。引擎生命周期只负责底层接入。

## 资源引用与泄漏

常见“泄漏”不是内存永远无法释放，而是仍有引用：

- Static Collection/Event；
- Closure/Task；
- Editor Window Cache；
- Addressables Handle 未 Release；
- AssetBundle 依赖引用；
- Native Plugin Handle；
- Pool 长期持有实例；
- RenderTexture/ComputeBuffer 未 Dispose。

Memory Snapshot 应看引用链、Native Size、Managed Size 和增长趋势。只看到总内存高，不能直接判断泄漏。

## 验证方法

- 记录 Allocation Count/Bytes、GC Alloc、Collection Pause 和 Native Allocation。
- 比较 Instantiate、Activate、Acquire、Release 和 Destroy 的 CPU 时间。
- 对 Prefab 分别测试空对象、脚本、Renderer、Physics、Particle 和复杂层级。
- Pool 压测峰值、容量耗尽、重复 Release、场景切换和 Domain Reload。
- 做前后 Memory Snapshot，检查 Managed Wrapper、Native Object、Asset 和引用链。
- 测低内存设备与长时间运行，不能只看编辑器短采样。
