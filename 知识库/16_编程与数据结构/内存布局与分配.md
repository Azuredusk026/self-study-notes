# 内存布局与分配

总字节数一样，连续数组和分散对象的访问成本仍可能不同。内存布局先看工作集与访问顺序，分配器再按寿命和尺寸组织复用。虚拟地址、物理页和GPU资源也不能混为同一种预算。

## 栈与堆

线程栈保存调用帧、返回地址和局部数据。作用域结束时栈指针回退，分配释放很快，但容量有限。

堆支持动态大小和跨作用域生命周期。分配器要维护空闲块、对齐和并发，频繁小分配可能造成开销与碎片。

“值类型在栈、引用类型在堆”只是 C# 入门近似。值类型可以嵌在堆对象、数组或被装箱；JIT/AOT 也可能优化。真正要看对象布局和逃逸/运行时行为。

## 虚拟地址与物理存储

进程看到虚拟地址空间，操作系统按页映射物理内存。提交大块地址不一定立刻占用全部物理页，但首次访问、缺页异常和换页会影响性能。

GPU资源 可能位于独立 VRAM 或 统一内存。Upload/Readback 堆、暂存缓冲与 设备本地资源 有不同访问成本。

移动 SoC 的 CPU/GPU 共享物理内存，不等于拷贝和带宽免费。缓存一致性、片上瓦片内存、总线和资源同步仍然存在。

## 分配器与碎片

外部碎片指空闲总量足够、却没有足够大的连续块；内部碎片指分配块因对齐或尺寸类别向上取整，实际占用大于请求值。

常见策略：

- 线性分配器：整批分配、整批释放；
- 对象池/Slab：固定尺寸类别，快速复用；
- 栈分配器：后进先出；
- Buddy 分配器：按二次幂拆分合并；
- 通用堆：灵活但元数据和碎片更复杂。

帧临时数据适合帧分配区。生命周期不同的数据混入同一分配区 会导致无法及时释放。

以64字节空闲区为例，先分配两个16字节块，再释放第一个；若后32字节仍空闲，总空闲48字节却可能无法容纳一个40字节块，这就是外部碎片。固定32字节尺寸类服务20字节请求，则每块有12字节内部浪费。池减少查找和碎片变化，但不能消除尺寸向上取整。

Buddy可以从64拆成两个32，再把其中一个拆成两个16；释放一个16时，只有同阶伙伴也空闲才能合并成32。仅有另一个不相邻的16空闲，不能组成所需32。栈分配器则记录分配前游标，只允许逆序回退；释放下层块会覆盖仍活跃的上层块。具体固定槽位复用见 [[16_编程与数据结构/对象池]]。

Buddy的合并也依赖精确身份。以相对分配区基址的偏移o和块大小b表示块，同阶伙伴偏移为`o XOR b`。只有伙伴在同一分配区、同阶空闲表中确实空闲，才移除两块，以较小偏移和2b继续合并；“旁边有足够空闲字节”不能替代伙伴判断。分配先把请求加上头部与对齐开销，再向上取到可支持的阶，元数据记录实际阶，释放时才能返回正确空闲表。

## 数据局部性

CPU 缓存以缓存行读取。连续遍历数组/分量数组通常比随机追逐对象指针更快。

结构数组：

```text
[pos vel age][pos vel age][pos vel age]
```

分量数组：

```text
[pos pos pos][vel vel vel][age age age]
```

如果更新只读取位置/速度，SoA 减少无关数据进入缓存，也适合 SIMD。但编辑器对象和复杂多态逻辑未必值得改成 SoA。

## 缓存映射与写策略

直接映射缓存中每个内存块只能进入一个缓存组，硬件简单但容易发生冲突抖动。组相联缓存允许一个组内有多个路，是容量、命中率和查找成本的常见平衡。全相联缓存允许放入任意位置，冲突少但查找和替换成本高，通常只用于较小结构。

一个组满时需要替换策略，例如 LRU、近似 LRU 或随机替换。直写在写缓存时同步更新下层内存，行为直接但写流量大；写回先标记脏标记，驱逐时才回写，减少流量但一致性和状态管理更复杂。游戏代码通常不能选择硬件策略，但可以通过连续访问、减少工作集和避免多个热数组落入同一冲突模式来提高命中率。

设教学缓存有4组、每行64字节，组号为`floor(address/64)%4`。地址0和256均进入组0，直接映射下交替读会反复互相驱逐，即使总共只用两行；两路组相联可同时保存它们，第三个同组热块才需要替换。真实缓存的索引、地址翻译与替换策略更复杂，这个模型仅解释冲突失效，不能由数组间距直接预测目标CPU耗时。

## 帧分配器

伪代码输入非负大小、游标与容量，使用固定宽度无符号整数；MAX为该整数最大值。基址满足本次对齐要求，对齐为可表示的正二次幂，且容量不超过MAX。输出当前分配区中的独占区间，整批使用结束以后才能重置。

```text
if cursor > capacity: fail
if cursor > MAX - (alignment - 1): fail
offset = (cursor + alignment - 1) & ~(alignment - 1)
if offset > capacity: fail
if size > capacity - offset: fail
cursor = offset + size
return base + offset
```

线性游标的这段计算要求独占分配入口。多个任务共享分配区时，整个读取游标、计算对齐、验证容量和写回新游标在同一锁内执行；只把最后写回改成原子操作，两个任务仍可能领取同一范围。无锁实现则以旧游标为比较值做CAS，失败后重新计算对齐和容量。析构登记也归所属分配代次管理，任务持有引用直到构造成功并完成登记，Closing等待这些步骤结束后才能开始析构。高并发时给工作线程独立子区减少游标争用，整批复用仍统一等待全部子区消费者。

## 对齐与批次寿命

线性分配器用游标推进，但地址对齐要以实际基址为准。若基址已满足最大对齐，对正的二次幂a可取 `aligned=(cursor+a-1)&~(a-1)`。先检查 `cursor<=MAX-(a-1)`，求出aligned后检查 `aligned<=capacity`，最后检查 `size<=capacity-aligned`，才能避免加法回绕让超大请求误判为可用。

例如游标13、对齐16、请求20字节，返回区间[16,36)，消耗3字节对齐空隙。

分配存储与构造对象是两步：在返回区间内构造非平凡对象时，成功后才登记析构记录；构造失败只在本次分配仍是尾部、没有后续分配且尚未向其他线程发布时恢复游标，已经发布的分配则保留空洞到整批回收。重置前先等全部使用者结束，再按构造逆序调用已登记析构函数，最后清游标并换代。只清游标会跳过文件句柄、堆缓冲等成员资源的释放。析构期间仍可能读取同批对象，因此全部存储保持有效到析构阶段结束；跨对象析构依赖需要与这个顺序一致。

下一次重置到0之前，所有引用这段存储的任务都必须完成；仅结束CPU帧不代表GPU上传或后台写入已结束。可按帧槽位保存完成值，再循环复用分配区。

布局收益由读取字段决定。若每个对象64字节而热循环只读其中8字节，将热字段集中后可能减少传输，但把所有字段都拆开也会增加多流读取与索引维护。分别测热点循环与完整帧，不把微基准直接当成项目收益。

## 异步批次与复用

以三个帧槽位为例，第f帧使用`slot=f%3`。每个槽位记录游标、代次、引用它的CPU任务计数，以及各GPU队列提交时返回的完成值。开始复用前先等待CPU计数为零，再逐个确认队列已完成值不小于槽位记录的提交值，最后按构造逆序执行已登记的析构，再递增代次并把游标清零。析构结束前保留整个槽位存储；这一步与前述非平凡对象的回收契约一致。GPU提交完成值只能在实际提交后登记；仅给槽位标上帧号不能证明GPU已经读完。

例如槽位记录图形队列值41、复制队列值17，当前完成值为42和16，即使CPU任务都结束仍不可重置；复制队列达到17以后才满足全部读者完成条件。任务若又生成子任务，先为子任务增加引用，再释放父任务引用，避免计数短暂归零。槽位从Open进入Closing之后禁止外部新任务领取引用；领取引用、关闭入口与观察CPU计数归零在同一同步门内完成，防止零计数检查后又有人开始使用。已持有引用的任务仍可登记子任务，子任务引用增加先于父引用释放；GPU提交值也在该任务释放最后引用之前写入槽位；同一队列有多次提交时以原子最大值保存该队列最后需要等待的完成值，禁止迟到的小值覆盖大值。否则CPU计数先归零、重置后才补记GPU提交值，仍会让GPU读到复用数据。跨批次保留的数据复制到长寿命存储并改写引用，不能让一个长任务永久阻止帧分配区复用。完成值的提交、等待与资源可见性细节见 [[13_渲染架构/GPU资源生命周期]]。

## 验证方法

统计分配数、峰值、碎片和访问事务。以不同访问顺序比较耗时，arena重置前确保异步读者结束；对齐与加法检查溢出。OS页表机制以虚拟内存为前置。
