# 内存布局与分配

设一帧更新一批粒子，CPU计算位置和速度，随后复制队列把结果送给GPU。我们先决定热字段怎样连续读取，再为这批数据分配对齐存储、构造辅助对象，最后等待CPU与GPU消费者退出后复用帧槽。总字节数相同并不意味着访问成本相同；CPU帧结束也不意味着这一批存储已经能重用。

## 栈与堆

更新函数的局部计数器可以随调用结束，但粒子数组还要交给后续任务。线程栈保存调用帧、返回地址和局部数据。作用域结束时栈指针回退，分配释放很快，但容量有限。

堆支持动态大小和跨作用域生命周期。分配器要维护空闲块、对齐和并发，频繁小分配可能造成开销与碎片。

“值类型在栈、引用类型在堆”只是 C# 入门近似。值类型可以嵌在堆对象、数组或被装箱；JIT/AOT 也可能优化。真正要看对象布局和逃逸/运行时行为。

## 虚拟地址与物理存储

进程看到虚拟地址空间，操作系统按页映射物理内存。提交大块地址不一定立刻占用全部物理页，但首次访问、缺页异常和换页会影响性能。

这批粒子的GPU资源可能位于独立VRAM或统一内存。上传堆、读回堆、暂存缓冲与设备本地资源有不同访问成本；选择CPU分配器之前，先确定CPU结果是直接供GPU读取，还是复制到另一资源。

移动SoC的CPU与GPU共享物理内存，不等于拷贝和带宽免费。缓存一致性、片上瓦片内存、总线和资源同步仍然存在。

## 数据局部性

粒子更新只读位置和速度，绘制准备还会读取年龄。CPU缓存按缓存行搬运数据，访问布局因此先由这些循环决定。连续遍历能让同一缓存行中的多个字段被实际使用，随机追逐对象指针则可能每次只用一行中的少数字节。

结构数组：

```text
[pos vel age][pos vel age][pos vel age]
```

分量数组：

```text
[pos pos pos][vel vel vel][age age age]
```

如果更新只读取位置/速度，SoA能减少无关字段进入缓存，也便于SIMD批处理。绘制准备同时需要年龄时，又要读取另一条数据流；布局收益因此由各阶段实际读取的字段共同决定。例如每个对象64字节、热循环只读8字节时，集中热字段可以减少无效传输，但所有字段都拆开也会增加索引与多流维护。分别测粒子更新和完整帧，才能判断局部收益是否保留到最终结果。

## 缓存映射与写策略

直接映射缓存中每个内存块只能进入一个缓存组，硬件简单但容易发生冲突抖动。组相联缓存允许一个组内有多个路，是容量、命中率和查找成本的常见平衡。全相联缓存允许放入任意位置，冲突少但查找和替换成本高，通常只用于较小结构。

一个组满时需要替换策略，例如 LRU、近似 LRU 或随机替换。直写在写缓存时同步更新下层内存，行为直接但写流量大；写回先标记脏标记，驱逐时才回写，减少流量但一致性和状态管理更复杂。游戏代码通常不能选择硬件策略，但可以通过连续访问、减少工作集和避免多个热数组落入同一冲突模式来提高命中率。

设教学缓存有4组、每行64字节，组号为`floor(address/64)%4`。地址0和256均进入组0，直接映射下交替读会反复互相驱逐，即使总共只用两行；两路组相联可同时保存它们，第三个同组热块才需要替换。真实缓存的索引、地址翻译与替换策略更复杂，这个模型仅解释冲突失效，不能由数组间距直接预测目标CPU耗时。

## 分配器与碎片

热字段布局确定以后，还要决定这一批存储怎样取得和归还。同一帧一起退休的粒子临时数据可使用线性分配区，跨帧保存的资产则需要不同寿命的分配器。外部碎片指空闲总量足够、却没有足够大的连续块；内部碎片指分配块因对齐或尺寸类别向上取整，实际占用大于请求值。

常见策略：

- 线性分配器：整批分配、整批释放；
- 对象池/Slab：固定尺寸类别，快速复用；
- 栈分配器：后进先出；
- Buddy 分配器：按二次幂拆分合并；
- 通用堆：灵活但元数据和碎片更复杂。

粒子的帧临时数据一起进入帧分配区；跨帧资产若混入同一区，会使整个区必须等资产结束才能重置。

以64字节空闲区为例，先分配两个16字节块，再释放第一个；若后32字节仍空闲，总空闲48字节却可能无法容纳一个40字节块，这就是外部碎片。固定32字节尺寸类服务20字节请求，则每块有12字节内部浪费。池减少查找和碎片变化，但不能消除尺寸向上取整。

Buddy可以从64拆成两个32，再把其中一个拆成两个16；释放一个16时，只有同阶伙伴也空闲才能合并成32。仅有另一个不相邻的16空闲，不能组成所需32。栈分配器则记录分配前游标，只允许逆序回退；释放下层块会覆盖仍活跃的上层块。具体固定槽位复用见 [[16_编程与数据结构/对象池]]。

Buddy的合并也依赖精确身份。以相对分配区基址的偏移o和块大小b表示块，同阶伙伴偏移为`o XOR b`。只有伙伴在同一分配区、同阶空闲表中确实空闲，才移除两块，以较小偏移和2b继续合并；“旁边有足够空闲字节”不能替代伙伴判断。分配先把请求加上头部与对齐开销，再向上取到可支持的阶，元数据记录实际阶，释放时才能返回正确空闲表。

## 帧分配器

这里为粒子上传数据和本帧辅助对象采用线性分配器。伪代码输入非负大小、游标与容量，使用固定宽度无符号整数；MAX为该整数最大值。基址满足本次对齐要求，对齐为可表示的正二次幂，且容量不超过MAX。输出当前分配区中的独占区间，整批使用结束以后才能重置。

```text
if cursor > capacity: fail
if cursor > MAX - (alignment - 1): fail
offset = (cursor + alignment - 1) & ~(alignment - 1)
if offset > capacity: fail
if size > capacity - offset: fail
cursor = offset + size
return base + offset
```

线性游标的计算要求独占分配入口。多个任务共享分配区时，读取游标、计算对齐、验证容量和写回新游标都在同一锁内执行。只把最后写回改成原子操作，两个任务仍可能领取同一范围。无锁实现以旧游标为比较值做CAS，失败后重新计算对齐与容量。高并发时也可给工作线程独立子区，整批复用仍等待全部子区消费者。

## 对齐与批次寿命

粒子数组中的SIMD字段需要16字节对齐。前面的位运算以基址已经满足对齐为前提；若外部给出的基址只有较低对齐，单独对齐偏移仍会返回错位地址。分配区因此在创建时取得满足最大请求对齐的基址，超过该对齐的请求交给单独的过对齐分配路径。

例如游标13、对齐16、请求20字节，返回区间[16,36)，消耗3字节对齐空隙。零大小请求可以返回当前对齐位置，但不产生可解引用的独占字节；若调用者需要唯一对象身份，应使用独立句柄或分配至少一个字节，不能把零长度返回地址当作唯一ID。

### 构造登记与提交次序

存储可用了，辅助对象还需要构造。设对象B保存粒子统计缓冲，对象A保存上传描述，A的析构函数还要向B写回最终统计。两个任务可能先为A预留存储，再为B预留存储，B却先完成构造。按照预留槽的逆序析构会先销毁B，使A的最后一次访问悬空。

这里为每代分配区保存独立的构造记录表与提交链。记录状态为Reserved、Committed、Aborted或Destroyed，句柄携带槽位、批次代次和记录身份。任务先持有批次引用，在记录锁内预留记录槽与依赖列表空间，再领取对象存储。任何容量不足都在调用构造函数之前返回失败；多线程的失败预留保留字节空洞到整批回收，避免回退游标覆盖后来分配的对象。

构造函数在锁外执行。它取得的同批依赖必须已经Committed，尚在Reserved中的对象由任务调度建立前置关系，等其提交后再构造依赖者。构造期间对象指针只归本任务使用，成功提交以前不向消费者发布。构造抛出异常时，C++释放已完成构造的成员与基类，外层记录置Aborted；外层对象没有完成构造，记录表不会再次调用它的析构函数。裸资源由构造过程中的RAII临时对象持有，防止失败路径泄漏。

构造成功后，任务在同一记录锁内校验本代身份和依赖记录，分配下一个提交序号，将对象指针、析构函数和依赖列表写入预留槽，并把槽接到提交链尾部。链节点已经预留，写入与连接均不分配内存；序号空间也在开始新构造前检查，批次记录容量限制保证序号可表示。提交完成才发布句柄，最后归还任务引用。Closing允许已持引用的构造任务提交，退休过程等待其退出，因此状态关闭不会在对象构造成功后制造一次登记失败。

本例中B先提交得到序号1，A随后提交得到序号2；清理按提交链逆序执行A、B。两个无依赖对象并发完成时，由提交锁确定唯一顺序。这里的逆序是分配器定义的提交次序，与存储预留次序及CPU指令完成时刻分别记录。

### 析构依赖与变更检查

提交后增加析构借用也经过记录接口：若A析构要读取B，登记边`A→B`，要求两者同代、均Committed且`sequence(A)>sequence(B)`。构造时的依赖自动满足此条件，提交后的新边在写入对象字段前检查；元数据空间不足或顺序不符时，字段保持原值。所有边都指向更小序号，逆序析构就会在销毁A时保留B，并且不会形成环。访问记录表与发布字段之间使用同一对象同步协议，正在运行的消费者只能看到变更前或变更后的完整关系。

若B后来也要在析构时读取A，接口会拒绝`B→A`。业务层可在CPU和GPU消费者退出后执行显式收尾，把双向关联结算为各自独立的值，再在记录锁内清除借用边与对应字段；收尾需要失败时，批次停留在Closing并保留存储，记录已完成的收尾步骤后重试。也可把互相依赖的对象交给一个组合所有者，内部明确安排关闭与销毁顺序。外部对象则通过独立所有权令牌保持到本批析构完成，跨代裸指针无法提供这份保证。

批次析构函数要求不抛异常，且只访问已登记依赖或自身资源；异步写入和可能失败的业务结算放在上述收尾阶段。退休执行者独占遍历提交链，逐个调用析构并标记Destroyed，期间保留全部对象存储和记录表，最后统一清空。若程序违背不抛异常约定，进入故障处理而不重新执行已开始的析构；它无法假设部分执行的析构可以安全重试。只清游标则会跳过文件句柄、堆缓冲等成员资源释放。

## 异步批次与复用

粒子更新结束后，上传仍可能在复制队列中排队。以三个帧槽位为例，第f帧使用`slot=f%3`。每个槽位记录游标、代次、CPU任务引用计数、构造记录表，以及各GPU队列实际提交时返回的完成值。槽位从Open进入Closing后等待CPU计数归零，再确认各队列已完成值不小于该槽提交值，完成可能失败的显式收尾，最后按提交链逆序析构。全部析构结束才递增代次、清游标并重新开放。GPU提交完成值来自实际提交；帧号不能证明GPU已经读完。

例如本批记录图形队列值41、复制队列值17，当前完成值为42和16，即使A、B的构造任务都退出，A仍不能析构；复制队列达到17后才完成消费者排空，再按序号2、1销毁A、B。旧句柄上的代次仍为上一批，新的领取接口先检查代次，拒绝访问复用后的对象。

领取外部任务引用、关闭入口与观察CPU计数归零在同一同步门内完成。Closing关闭外部领取；已持引用的任务仍可生成子任务，但先增加子引用再释放父引用。构造登记和GPU提交值也在任务释放最后引用之前完成。多次提交以同步的最大值保存同一队列最后需要等待的完成值，防止迟到的小值覆盖大值。消费者排空以后析构阶段禁止创建本批任务或GPU提交，才能使排空条件在清理期间保持成立。

跨批次数据复制到长寿命存储并改写引用；若必须借用本批对象，长期消费者继续持有引用，槽位保持Closing，调度器选择另一个可用槽位或等待。GPU队列故障无法确认完成时也保留该槽，直到设备恢复流程证明旧提交停止访问。完成值、等待与可见性细节见 [[13_渲染架构/GPU资源生命周期]]。

## 验证方法

统计分配数、峰值、碎片和访问事务。以不同访问顺序比较耗时，arena重置前确保异步读者结束；对齐与加法检查溢出。OS页表机制以虚拟内存为前置。
