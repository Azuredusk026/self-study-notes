# 剔除、透明与混合

减少不可见工作要尽量发生在昂贵阶段之前。剔除是在提交或光栅化前排除对象和图元；深度测试是在样本阶段拒绝被挡住的片元；透明混合则需要保留并组合多个可见层。

## 背面剔除

封闭网格通常只需要看到朝外的一面。GPU 根据屏幕空间绕序判断三角形正反面，再按 Rasterizer State 剔除 Front 或 Back。

常见问题：

- 负缩放翻转绕序；
- DCC、引擎和 API 的坐标手性不同；
- 法线方向正确不代表三角形绕序正确；
- 双面材质关闭剔除后，片元成本和过度绘制会增加。

## 视锥剔除

CPU 或 GPU 用对象 Bounds 与六个视锥平面测试。完全在任一平面外的对象不可见。

通常先用 Bounding Sphere 或 AABB 做便宜粗测。Bounds 太大会保留很多不可见对象；Bounds 太小会错误剔除动画、粒子或 Shader 位移后的几何。

视锥可以表示成六个朝内的平面。平面使用单位法线 $\mathbf n$ 和常数 $d$：

$$
distance(\mathbf p)=\mathbf n\cdot\mathbf p+d
$$

Bounding Sphere 的球心到任一平面的距离小于 $-r$ 时，整个球位于平面外：

```cpp
bool IsSphereVisible(const Frustum& frustum,
                     Vector3 center, float radius)
{
    for (const Plane& plane : frustum.planes) {
        float distance = Dot(plane.normal, center) + plane.d;
        if (distance < -radius)
            return false;
    }
    return true;
}
```

AABB 可以使用投影半径测试。设半尺寸为 $\mathbf e$，平面法线为 $\mathbf n$，AABB 在法线方向的投影半径为：

$$
r=e_x|n_x|+e_y|n_y|+e_z|n_z|
$$

再使用与 Bounding Sphere 相同的 `distance < -r` 判断。Plane 法线必须归一化，否则距离和半径不在同一尺度。提取投影矩阵平面时还要核对矩阵行列主序、NDC 深度和反向 Z。

## 遮挡剔除

视锥内的物体仍可能被墙体和近处物体挡住。遮挡剔除需要根据已有遮挡信息判断 Bounds 是否可能可见。

常见方案：

- 离线 PVS/Portal；
- Hardware Occlusion Query；
- Software Rasterizer；
- 基于上一帧或当前帧 Hi-Z 的 GPU Occlusion Culling。

遮挡判断本身有成本，也会引入延迟和保守误差。小物体、动态遮挡和相机快速移动需要特别处理。

## Alpha Test

Alpha Test/Clip 根据阈值保留或丢弃片元。保留下来的部分仍可以写深度，因此适合树叶、栅栏和硬边镂空。

主要问题：

- `discard/clip` 可能限制 Early-Z；
- 边缘会产生采样锯齿；
- Mipmap 会平均 Alpha，远处覆盖率可能变化；
- 双面叶片容易增加 Overdraw。

Alpha-to-Coverage 可以把 Alpha 转换成 MSAA Coverage，改善边缘，但依赖 MSAA 样本数和平台实现。

## Alpha Blend

普通非预乘 Alpha 的常见公式：

$$
C_{out}=\alpha_sC_s+(1-\alpha_s)C_d
$$

$C_s$ 是源颜色，$C_d$ 是目标颜色。

预乘 Alpha 的源 RGB 已经乘过 Alpha：

$$
C_{out}=C_s+(1-\alpha_s)C_d
$$

预乘表示在纹理过滤、边缘颜色和多次合成时通常更稳定，但资源制作、Shader 输出和 Blend State 必须使用同一约定。

## 为什么透明需要排序

标准 Alpha Blend 不满足交换律。先画 A 再画 B，和先画 B 再画 A 的结果不同。因此透明物体通常从远到近绘制，并开启深度测试、关闭深度写入。

对象级排序不能解决：

- 两个透明网格相交；
- 一个网格内部三角形顺序错误；
- 粒子互相穿插；
- 玻璃需要折射后方画面。

两个事实叠加造成了这个长期存在的问题。其一，`SrcAlpha, OneMinusSrcAlpha` 这一混合公式对前后两项不对称，结果依赖绘制顺序；相比之下 `One, One` 加法混合前后对称，所以发光特效通常不受排序困扰。其二，引擎的透明排序粒度是逐对象的，而离线渲染器按逐像素求解可见性，这解释了为什么同一份资产在 DCC 里正常、进引擎却出现穿插错误。

单个网格内部的三角形绘制顺序由索引缓冲的排列决定。引擎不会重排它，所以网格内部的自遮挡错误无法靠对象排序修复。

## 常见透明方案

### Sorted Transparency

最常见。成本可控，但排序不可能覆盖所有相交情况。

### Additive

加法混合接近可交换，适合火花和发光粒子，但无法表达正常遮挡和吸收。

### Weighted Blended OIT

Weighted Blended OIT 用两个 Render Target 累积透明颜色和剩余透射率。对每个透明片元，可使用：

$$
A_{rgb}\mathrel{+}=C\alpha w,\qquad
A_a\mathrel{+}=\alpha w
$$

$$
R\mathrel{*}=(1-\alpha)
$$

$w$ 是随深度和 Alpha 变化的权重。累积目标使用加法混合，Revealage 目标使用乘法混合。合成时：

$$
C_t=\frac{A_{rgb}}{\max(A_a,\varepsilon)},\qquad
\alpha_t=1-R
$$

再把 $(C_t,\alpha_t)$ 合成到不透明颜色上。这种方法的资源和绘制次数稳定，适合粒子、烟雾和大量近似透明层。

它没有保存精确层顺序，因此不同深度的强颜色、接近不透明的表面和玻璃吸收会有偏差。权重函数只能调整误差分布，不能恢复被丢掉的排序信息。

### Per-pixel Linked List

片元阶段用原子计数器在全局 Node Buffer 分配节点，并通过 Head Pointer Texture 建立每像素链表。Resolve Pass 遍历链表、按深度排序，再按顺序混合。

它能保留精确片元属性，但必须设置最大节点容量。大量 Overdraw 会耗尽 Buffer，溢出策略需要明确。链表写入的随机访存、原子竞争、排序和清空 Head Pointer 都有成本。

### Depth Peeling

Depth Peeling 用多轮重绘逐层"剥离"深度。每一轮只保留当前最靠近相机的那一层，把它的深度记下来；下一轮凡是深度不比记录值更远的片元一律丢弃，于是暴露出第二层，如此递推。

单轮的判据很简单：采样上一轮的深度图，当前片元深度不大于它就 `discard`。深度图是屏幕空间资源，采样时必须用屏幕坐标而非模型 UV：

```glsl
float depth = i.pos.z / i.pos.w;
float2 screenUV = i.screenPos.xy / i.screenPos.w;
float prevDepth = tex2D(_DepthRendered, screenUV).r;

if (_PeelIndex > 0 && depth >= prevDepth - 1e-6)
    discard;

o.depthTarget = depth;      // 供下一轮比较
o.colorTarget = shadedColor; // 本层颜色
```

第 0 轮不做剥离判断，直接得到最近层。比较时的 $10^{-6}$ 容差用于吸收浮点误差，容差过小会让同一层反复出现，过大会跳过薄层。深度目标需要足够精度，单通道浮点格式是常见选择。多数实现无法同时读写同一张深度图，需要先拷贝一份再作为下一轮的输入。

层数用尽后从最远层向前合成，每层用标准公式叠加：

$$
C\leftarrow C_{back}(1-\alpha_{front})+C_{front}\alpha_{front}
$$

成本与收益都很直白。剥离 $n$ 层就要把透明几何绘制 $n$ 遍，代价随层数线性增长。收益是逐像素精确，且截断误差可控——超出层数的部分被丢弃，但第 5、6 层之后的贡献通常已被前几层的累积不透明度压得很低，肉眼难以察觉。

朴素实现需要为每层保存一张颜色纹理，显存开销可观。两种收敛方式：从后往前剥离并即时混合，只需一张累积纹理；或保持从前往后剥离，用前向累积公式就地合成：

$$
C\leftarrow C\alpha+C_{back}(1-\alpha),\qquad
\alpha\leftarrow 1-(1-\alpha)(1-\alpha_{back})
$$

这个前向形式不完全等价于严格的后向合成，但在多数内容上差异很小，能省下数张全屏纹理。

与 Per-pixel Linked List 相比：Depth Peeling 显存占用更小、行为更稳定、层数截断的画质退化更平缓；链表法单次遍历完成收集，总体更快，但受 Buffer 容量与原子竞争影响，在极端 Overdraw 下行为不可预测。

## 针对性的轻量方案

通用 OIT 方案不了解具体资产的特性，因此无法做极端简化。当内容形态固定时，针对性方案往往以极小代价解决绝大部分问题。

### 固定深度法

适用于头发这类"中心大面积接近不透明、仅边缘半透明"的资产。先用一个 Pass 只把不透明区域的深度写入，不输出颜色；后续半透明绘制受这层深度约束，被遮挡的部分被直接剔除，不可能再画到前面去。

由于不透明区域占据模型的绝大部分，这一层深度就固定了绝大多数像素的前后关系。仅在"半透明边缘遮挡半透明边缘"时仍不正确，而这部分面积很小，通常可接受。

它的价值在于同时保住了两端：纯 Alpha Test 边缘生硬，纯 Alpha Blend 边缘柔和但排序错误，这个方案得到柔和边缘加上基本正确的深度关系。

关键在于把"哪些像素算作不透明"与 Alpha Clip 阈值对齐：

```glsl
// _Cutoff 与深度 Pass 的 Alpha Clipping 阈值一致
output.a = saturate(mainTex.a / (_Cutoff + 1e-4));
clip(mainTex.a - 1e-4);
```

### 预计算顺序法

既然网格内部顺序由索引缓冲决定，就可以离线为若干观察方向各排好一套索引，运行时按当前视角切换。

做法是把三角形按其顶点在某个方向轴上的坐标和排序，生成正序与反序两套索引数组；运行时用相机到物体中心的方向与物体各轴做点积，挑选最接近的一套写回网格索引。

方向采样密度取决于内容的旋转自由度。左右转动为主的角色头发，四个方向已能覆盖；需要完整球面覆盖时，赤道 8 个方向加上下各 45 度处 6 个方向，共 22 个方向可以相当精确地表达。

代价是每个方向一套索引数组的内存，以及切换时回写索引缓冲的开销。它只解决网格内部的三角形顺序，不处理不同对象之间的相交，且对顶点数大的网格排序预计算耗时明显。

### 方案选择

| 方案 | 精度 | 主要成本 | 适用 |
|---|---|---|---|
| 对象排序 | 对象级 | 排序 CPU 开销 | 分离良好的透明体 |
| 固定深度法 | 除边缘外正确 | 一个额外深度 Pass | 头发等中心不透明资产 |
| 预计算顺序 | 三角形级 | 索引内存与回写 | 旋转自由度受限的固定资产 |
| Weighted Blended | 近似 | 两个 RT，一趟绘制 | 粒子、烟雾等低 Alpha 层 |
| Depth Peeling | 逐像素精确 | 绘制 n 遍 | 层数有限、要求精确 |
| Per-pixel Linked List | 逐像素精确 | 原子操作与 Buffer 容量 | 桌面端、Overdraw 可预估 |

## 透明性能

透明通常不能利用普通不透明物体的完整深度拒绝。同一区域覆盖很多层时，Pixel Shader 和 Blend 都会重复执行。

优化方向：

- 控制屏幕覆盖面积，而不只是粒子数量；
- 使用紧贴内容的粒子网格；
- 降低透明 Shader 和纹理采样成本；
- 近远景使用不同粒子复杂度；
- 在移动端注意 Blend、带宽和 Tile Memory；
- 用 Overdraw 视图和 GPU Counter 验证。

## 验证方法

- 让相机绕透明物体旋转一周，观察是否出现随角度突变的排序错误。
- 逐层输出 Depth Peeling 的中间结果，确认每一轮确实剥离出新的一层而非重复同一层。
- 逐步减少剥离层数，观察画面从哪一层开始出现可见差异，据此定层数上限。
- 把混合方式临时换成加法，若排序错误消失，说明问题确实来自混合公式的顺序依赖。
- 用 Overdraw 视图确认透明层数，而不是只统计粒子数量。
