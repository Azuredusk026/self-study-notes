# 光栅化、插值与深度模板

光栅化把三角形的连续覆盖转换为屏幕上的离散样本。深度和模板决定这些样本能否继续处理或写入结果。

## 三角形覆盖

经过裁剪和透视除法后，三角形落到屏幕坐标。光栅器根据边函数判断一个样本点位于三角形内部、外部还是边界。

共享边需要统一规则，否则两个三角形可能同时覆盖或同时漏掉边界样本。常见实现使用 Top-left Rule，但具体定义由 API 规范决定。

## 重心坐标

三角形内的点可以表示为三个顶点的加权和：

$$
P=\lambda_0P_0+\lambda_1P_1+\lambda_2P_2,
\qquad \lambda_0+\lambda_1+\lambda_2=1
$$

三个 $\lambda$ 就是重心坐标。光栅器用它插值颜色、UV、法线等 Vertex Shader 输出。

## 为什么 UV 不能只做屏幕线性插值

透视投影后，屏幕距离和三维距离不再线性对应。如果直接在屏幕空间线性插值 UV，纹理会在倾斜表面上滑动或扭曲。

透视正确插值会先插值 $a_i/w_i$ 和 $1/w_i$：

$$
a(P)=
\frac{\sum_i\lambda_i(a_i/w_i)}
{\sum_i\lambda_i(1/w_i)}
$$

Shader 语言通常默认对普通 Varying 使用透视正确插值。`noperspective`、`flat/nointerpolation` 等修饰符会改变行为。

## 导数从哪里来

Pixel Shader 常按 2x2 Quad 一起执行。`ddx` 和 `ddy` 可以用相邻 Lane 的值估计屏幕方向变化。纹理系统据此估计 Mipmap LOD。

控制流发散、三角形边缘和 Helper Invocation 会让导数行为更复杂。不要在不一致分支中假设导数一定稳定。

## 深度值不是线性距离

透视投影需要把较多精度分配给近处，因此常规深度缓冲通常与视空间距离非线性对应。用它直接做世界距离会出错，需要通过投影参数重建。

深度精度受 Near Plane 影响很大。Near 设得过近，会浪费大量可用精度。

### 伪深度的来历

透视投影把视锥内的点压到标准立方体。屏幕位置由相似三角形直接给出，但两个视空间深度不同的点可能投影到同一屏幕位置，因此需要保留一个可比较的深度量。

为了让深度表达式与 $x'$、$y'$ 形式一致、便于用齐次坐标和矩阵统一表示，深度取以 $z$ 为分母的线性分式：

$$
z'=\frac{az+b}{z}
$$

以 Direct3D 约定为例，近裁剪面 $z=N$ 映射到 0，远裁剪面 $z=F$ 映射到 1。代入两个边界条件解得：

$$
a=\frac{F}{F-N},\qquad b=\frac{-FN}{F-N}
$$

这就是深度非线性的根源：$z'$ 是 $z$ 的分式函数，不是线性函数。几何上相当于把远平面上的内容压缩到近平面尺度，越远压缩比越大，可分辨的深度差就越粗。若远平面是 2x2、近平面是 1x1，远处内容压缩后损失约一半横向精度，深度方向同理。

OpenGL 传统约定把 NDC 深度映射到 $[-1,1]$，Direct3D 映射到 $[0,1]$。重建深度和写投影矩阵时必须确认当前 API 与引擎的约定。

### Reversed-Z 为什么有效

浮点数在 0 附近的可表示值远比在 1 附近密集。常规映射把远处放在接近 1 的区间，恰好落在浮点精度最稀疏的地方，非线性压缩与浮点分布的稀疏区叠加，远处 Z-Fighting 因此格外严重。

Reversed-Z 把近平面映射到 1、远平面映射到 0。远处落进浮点密集区，两种非线性相互抵消，深度精度在整个范围内分布得更均匀。配合浮点深度格式时收益最大；配合定点格式（如 D24）时浮点分布的优势不存在，收益有限。

启用时必须同步四处：投影矩阵、深度 Clear Value（清成 0 而非 1）、深度比较函数（Less 改为 Greater）、以及所有手工重建深度的代码。只把采样结果做 `1-z` 是错误的。

### 缓解深度冲突

- 收窄 Near 与 Far 的比值。Near 的影响远大于 Far，把 Near 从 0.01 提到 0.1 的收益通常比压缩 Far 大得多；
- 避免共面或极近的几何，这是美术侧能解决的绝大部分情况；
- 使用 Polygon Offset / Depth Bias 给特定图元一个可控偏移；
- 启用 Reversed-Z 配合浮点深度。

## 深度缓冲与深度纹理

这是两个容易混淆的概念，服务于不同使用者。

**深度缓冲**由 GPU 与窗口系统管理，用于可见性判定与 Early-Z。它随管线自动写入，开发者只控制 Depth Write 与比较函数。

**深度纹理**是供着色器采样的资源，服务于后处理、软粒子、屏幕空间效果和深度重建。深度缓冲在多数平台不能直接当作纹理采样，需要一次拷贝或一个专门的 Pass 来产生。

两者的写入条件也不同。关闭 Depth Write 的对象不写深度缓冲，但它是否出现在深度纹理里，取决于深度纹理由哪条路径生成，而不取决于该对象的 Depth Write 状态。

生成深度纹理的常见路径：

- **Shader Replacement**：用替换着色器把符合条件的对象重画一遍。兼容性最好，代价是不透明物体的 Draw Call 翻倍；
- **深度拷贝**：从已渲染的深度附件拷出。不增加 Draw Call，但要求硬件支持深度拷贝，且 MSAA 情况下需要额外解析；
- **延迟渲染直接复用**：GBuffer 阶段已经写好深度，无需额外操作。

Unity URP 提供 `CanCopyDepth` 一类的运行时判断，在不支持拷贝或开启 MSAA 时回退到独立的 Depth Prepass。具体行为随 URP 版本变化，需要在目标版本的 Frame Debugger 中确认。

## 从深度重建位置

屏幕空间效果经常需要由深度反推世界位置。两条常用路径：

**逆变换法**：由屏幕 UV 与深度组装 NDC 坐标，乘以逆 View-Projection 矩阵，再做齐次除法。

$$
\mathbf{p}_{world}=\frac{M_{VP}^{-1}\,\mathbf{p}_{ndc}}{w}
$$

**射线插值法**：预先计算相机到远平面四角的射线，在屏幕上插值得到当前像素的视线方向，再按线性深度沿射线前进。省去逐像素矩阵乘法，但要求插值的是视空间线性深度，不是原始深度值。

两条路径的前提不同，必须逐项核对：NDC 的 Y 方向、深度区间是 $[0,1]$ 还是 $[-1,1]$、是否启用 Reversed-Z、UV 原点在左上还是左下。任何一项与平台约定不符，结果都会整体偏移或翻转。

### 由深度重建世界位置

输入是屏幕 UV 与深度纹理采样值，输出世界空间位置。以 Direct3D 风格的 $[0,1]$ 深度区间为例：

```hlsl
float3 ReconstructWorldPos(float2 uv, float rawDepth)
{
    float2 ndcXY = uv * 2.0 - 1.0;
#if UNITY_UV_STARTS_AT_TOP
    ndcXY.y = -ndcXY.y;
#endif
    float4 ndc = float4(ndcXY, rawDepth, 1.0);
    float4 world = mul(_InvViewProjMatrix, ndc);
    return world.xyz / world.w;
}
```

`rawDepth` 必须是未经线性化的原始深度，与写入时的约定一致；若已调用过线性化函数，再走逆 VP 矩阵会得到错误结果。启用 Reversed-Z 时投影矩阵已包含反转，此处不需额外处理。

验证方法是把重建结果对 1 米取模输出为颜色，画面应出现贴合场景表面的规则网格。网格在斜面上扭曲说明透视除法有误；随相机移动而滑动说明用错了矩阵或深度约定。

### Reversed-Z

Reversed-Z 让近处映射到较大深度，远处映射到较小深度，并把比较从 Less 改为 Greater。配合浮点深度，它可以利用浮点数在 0 附近更密集的表示，改善远距离精度。

它不是简单把深度贴图做 `1-z`。投影矩阵、Clear Value、比较函数和深度重建都要一致。

## Depth Test 和 Depth Write

Depth Test 判断新样本能否通过。Depth Write 决定通过后是否更新深度。两者独立。

常见情况：

- 不透明物体：测试开，写入开；
- 半透明物体：测试开，写入通常关；
- 天空：常在背景深度位置绘制；
- UI 或叠加效果：根据需求关闭测试或使用特殊比较。

## Early-Z

如果 GPU 在 Pixel Shader 之前就能确定深度失败，就可以跳过这次昂贵的像素着色。这是 Early-Z 的核心收益。

Early-Z 不会提前计算法线，也不需要先执行 Pixel Shader。它利用已有深度和光栅器产生的候选深度做测试。

可能阻碍或限制 Early-Z 的情况：

- Pixel Shader 修改深度；
- 使用 `discard/clip`，硬件不能提前确认样本最终存在；
- Shader 有某些可见副作用，例如 UAV 写入；
- 深度比较或写入状态不适合提前执行；
- 绘制顺序导致深度缓冲尚未包含近处遮挡物。

具体硬件可能仍有 Conservative Early-Z 等优化，不能仅凭 Shader 代码断言一定开启或关闭。

失效的代价往往不止当前这一次绘制。部分硬件在遇到上述情况时会关闭整个 Render Pass 的 Early-Z，直到下次清空深度缓冲才恢复。因此 Alpha Test 材质与不透明材质混排，可能连累本可受益的绘制。较新的 GPU 在这方面更智能，但不应作为可依赖的前提。

Early-Z 的收益还高度依赖绘制顺序。理想情况下由近及远绘制可以完全消除 Overdraw，由远及近则收益为零。这就是不透明队列按距离从前往后排序的原因。排序发生在 CPU，场景复杂时排序本身也构成开销。Unity 在硬件支持 HSR（Hidden Surface Removal，常见于 PowerVR 架构）时会跳过这项排序，说明排序成本被判断为低于重复深度写入的成本。

## Depth Prepass

Depth Prepass 先用简单 Shader 写一遍不透明深度，再执行主材质 Pass。它可以提高重像素 Shader 场景的 Early-Z 命中率，也能提前提供深度给后续效果。

代价是多画一遍几何，增加 Draw、顶点处理和深度带宽。材质很轻、遮挡少或移动端带宽敏感时不一定划算。

### 两个 Pass 的状态配置

第一个 Pass 只写深度：开启 Depth Write，比较函数 Less，`ColorMask 0` 关闭颜色输出，片元着色器不做任何计算。第二个 Pass 关闭 Depth Write，比较函数改为 **Equal**。

比较函数改为 Equal 是这套方案的关键。深度已经是最终结果，只有深度值精确相等的片元才是可见片元，其余在 Early-Z 阶段被拒绝，像素着色器只对最终可见的片元执行一次。

Equal 比较要求两个 Pass 算出完全一致的深度值。两个 Pass 的顶点变换必须逐指令一致，否则浮点结果的细微差异会让片元全部落选、物体整块消失。顶点动画、风场扰动或不同的优化级别都可能破坏这个前提。

### 多 Pass 打断合批

把两个 Pass 写在同一个 Shader 里会打断动态批处理，产生额外的 Draw Call 与 SetPass Call。常见做法是把 Prepass 抽成独立 Shader 或独立的渲染流程，先用它整批绘制全部不透明对象，原 Shader 只保留第二个 Pass。

需要区分两类开销。SRP Batcher 合并的是 SetPass Call 而不是 Draw Call——它减少的是 CPU 侧的状态设置准备工作，Draw Call 数量并不下降。CPU 的主要成本来自状态切换准备，而非把命令字节放进 GPU 缓冲区本身。

### 什么时候划算

Depth Prepass 不是普遍成立的优化。它把一次额外的几何遍历换取 Overdraw 的减少，收益取决于两者的相对大小：

- 像素着色器复杂、Overdraw 严重、难以按距离排序时，收益明显；
- 材质轻、场景平坦、几何密集时，额外的顶点处理与深度带宽可能超过节省的像素着色。

移动端还要单独权衡。TBDR 架构本身具备 HSR 能力，额外的几何遍历带来的带宽与 Tiling 成本可能直接抵消收益。

Unity URP 12 引入的 Depth Priming 是这一思路的管线级实现：`DepthOnly` Pass 的结果被后续 Pass 直接用于 Equal 比较，不再在 Prepass 后清除深度。Unity 公布的测试显示 macOS 上 GPU 耗时改善约 16%，Windows Vulkan 上 CPU 约 3%、GPU 约 7.5%。CPU 收益来自免去不透明排序，GPU 收益来自消除不透明 Overdraw；半透明部分不受影响。

### Alpha Test 材质的分层处理

头发、树叶等 Alpha Test 材质天然打断 Early-Z，且面片互相遮挡产生大量 Overdraw。典型的分层方案：

1. Prepass：开启 Alpha Test，关闭颜色输出，关闭背面剔除，开启 Depth Write，比较 Less；
2. 不透明主体：关闭 Depth Write，比较 Equal；
3. 半透明背面：剔除正面，关闭 Depth Write；
4. 半透明正面：剔除背面，开启 Depth Write。

先用一个 Pass 把 Alpha Test 的结果固化进深度，后续 Pass 就能在 Early-Z 中受益。代价是绘制次数增加，需要与实际 Overdraw 量权衡。

## Hi-Z

Hierarchical Z 把深度缓冲构造成层级摘要。粗层级表示一块区域的保守深度范围，可以快速拒绝整块图元、Occlusion Query、SSR/Ray March 步进或 GPU Culling 中的不可见区域。

Hi-Z 是分层加速，不等于 Early-Z 本身。Early-Z 描述测试时机，Hi-Z 描述利用层级深度加速判断的方法。

## Stencil

Stencil Buffer 保存少量整数位。每个样本可以根据比较结果执行 Keep、Replace、Increment 等操作。

常见用途：

- 标记角色或区域，限制后处理；
- Light Volume 中限制灯光计算；
- Portal 和 Mask；
- 镜面、描边和特殊材质分类。

Stencil 很便宜，但位数有限。项目需要统一位分配，否则不同系统会互相覆盖。

### 用模板做对象分类

超出单个效果的用法是把模板当作全局的像素分类系统：几何阶段给每类对象写入约定的模板值，后续各 Pass 用模板测试筛选自己关心的像素。

这与在 Shader 内读取材质 ID 分支判断是两种不同层次的手段：

| | 模板测试 | Shader 内分类标记 |
|---|---|---|
| 决定的事 | 这个像素要不要进这个 Pass | 进来之后走哪个分支 |
| 执行时机 | 光栅化阶段，硬件完成 | 片元着色器内 |
| 成本 | 不通过测试的像素连着色器都不执行 | 需要执行着色器才能判断 |

合理的分工是：模板做大类切分（天空、角色、场景），着色器内的分类标记做大类内部的细分（角色中的皮肤、头发、布料）。

### 位分配与数值顺序

模板通常只有 8 位，所有系统共享，因此位分配必须全局规划。一种常见结构是低位留给临时标记（如光体积），高位段编码对象大类。

数值的**排列顺序**可以用来减少比较次数。若角色、普通物体、地形依次取递增值，一次 `LessEqual` 比较配合适当的读掩码就能同时覆盖这三类，而把天空这类取更高值的对象排除在外：

```text
Character = 0x10
Lit       = 0x20
Terrain   = 0x30
Sky       = 0x80

readMask = 0x70, reference = 0x10, compare = LessEqual
→ 一次比较命中全部三类 PBR 对象，排除天空
```

用数值区间换比较次数，是位宽紧张时的实用手法。代价是分配方案被顺序约束，后续插入新类别可能需要重排。

### 位宽紧张下的取舍

8 位很快会不够用。一个真实的取舍案例是：皮肤原本占用独立的模板值，后来被合并进角色类别。

- **收益**：排除全部角色像素（贴花与投影必须排除角色）只需一次比较，而不是逐类比较；
- **代价**：无法单独用模板筛出皮肤像素，屏幕空间次表面散射这类需要精确圈定皮肤区域的效果失去了模板门控。

这个取舍成立的前提是目标平台本来也跑不动屏幕空间 SSS，皮肤的差异改由着色器内的分类标记处理，不增加 CPU 开销。换一个平台，结论可能完全相反。

这类决策应当连同理由一起记录。只看到最终的位分配表，后来者无法判断哪些位置可以调整、哪些是刻意为之。
### 模板描边的执行顺序

模板描边需要两次绘制同一对象。第一遍正常绘制并把可见样本的模板值写成 1；第二遍略微放大几何，只在模板值不等于 1 的位置输出描边颜色：

```cpp
glEnable(GL_STENCIL_TEST);
glStencilOp(GL_KEEP, GL_KEEP, GL_REPLACE);

glStencilMask(0xFF);
glStencilFunc(GL_ALWAYS, 1, 0xFF);
DrawObject(materialPass);

glStencilMask(0x00);
glStencilFunc(GL_NOTEQUAL, 1, 0xFF);
glDisable(GL_DEPTH_TEST);
DrawObject(outlinePass); // Vertex Shader 沿法线扩张位置

glEnable(GL_DEPTH_TEST);
glStencilMask(0xFF);
glStencilFunc(GL_ALWAYS, 0, 0xFF);
glDisable(GL_STENCIL_TEST);
```

输入是同一网格、正常材质 Pass 和扩张描边 Pass；输出写入当前颜色附件和共享 Depth/Stencil Attachment。第一遍的 `GL_REPLACE` 只应发生在通过所选测试的样本上。第二遍关闭模板写入，防止描边区域污染后续对象。

关闭深度测试能得到完整轮廓，也会让被遮挡部分透出来；保留深度测试可只显示可见轮廓。沿对象空间法线等比例扩张在非均匀缩放、尖角和远近透视下会宽度不稳，屏幕空间描边或背面膨胀需要单独处理。验证时清空模板为 0，并逐次查看两遍 Draw 的模板输入、模板输出和颜色输出。

## 验证方法

- 使用 Overdraw 或 Early-Z Counter 检查像素着色是否真的减少。
- 对比 Front-to-back 和 Back-to-front 绘制顺序。
- 关闭 Depth Write，观察后续物体的遮挡变化。
- 用极近 Near Plane 制造深度精度问题，再调整验证。
- 在帧捕获中检查 Depth Compare、Clear Value、Stencil Ref 和每个 Face 的操作。
- 启用 Depth Prepass 后确认第二个 Pass 的比较函数确实是 Equal，且物体没有整块消失。
- 切换 Reversed-Z 后检查 Clear Value 与比较函数是否同步修改。
- 把深度重建结果按固定距离取模输出为条纹，检查是否贴合场景表面。
