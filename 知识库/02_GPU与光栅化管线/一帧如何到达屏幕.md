# 一帧如何到达屏幕

渲染不是 CPU 调一个 `Draw()`，GPU 就立刻画完。CPU 先准备资源和命令，驱动或图形 API 记录工作，GPU 再按队列和管线执行。两边通常并行，看到的画面可能对应前面已经提交的帧。

## CPU 端做什么

一帧常见的 CPU 工作包括：

- 更新游戏逻辑、动画和 Transform；
- 做可见性判断和渲染对象排序；
- 选择 Pipeline State、Shader、材质和资源；
- 更新 Constant/Uniform Buffer 和实例数据；
- 记录 Draw、Dispatch、Copy 和 Barrier；
- 把 Command Buffer 提交到 GPU Queue。

现代 API 强调提前创建 Pipeline State、显式管理资源状态和批量记录命令，目的是减少驱动在每次 Draw 时做隐式检查和重建状态。

## GPU 为什么使用流水线

一批顶点完成 Vertex Shader 后，不必等整帧结束，后续阶段就可以处理已经完成的结果。不同阶段同时处理不同图元，提高硬件利用率。

这不代表每个阶段的成本都能完全重叠。最慢的阶段、资源依赖、同步和内存访问仍会限制吞吐量。

## 图形管线的主要阶段

不同 API 命名略有差异，但核心过程接近。

### Input Assembly

读取 Vertex Buffer 和 Index Buffer，根据拓扑把索引解释成点、线或三角形。

Index Buffer 让相邻三角形共享顶点，但 Vertex Shader 是否能复用结果还取决于 Post-transform Vertex Cache 和索引顺序。

### Vertex Shader

至少需要输出裁剪空间位置。它还可以输出 UV、颜色、法线、切线、世界位置等后续插值数据。

常见误解是 Vertex Shader “一个网格顶点只运行一次”。实际执行次数受索引、缓存命中、实例、Pass 和裁剪等因素影响。

### 可选细分和几何阶段

Tessellation 可以把 Patch 细分成更多图元。Geometry Shader 可以基于图元生成或丢弃几何，但传统 Geometry Shader 的吞吐和扩展性经常不理想。现代管线更常讨论 Compute、Mesh Shader 或 GPU-Driven 几何处理。

Stream Output 可以把顶点、细分或几何阶段的输出写回 Buffer，而不经过光栅化。它适合几何缓存、粒子更新和调试，但写回带宽、可输出格式和阶段吞吐受限。现代实现也常用 Compute Shader 完成同类任务。

### Primitive Assembly、Clipping 和 Viewport

顶点被组装成图元。GPU 在齐次裁剪空间对视锥边界做裁剪，再做透视除法和 Viewport 变换。

背面剔除通常根据投影后三角形绕序判断。它发生在光栅化前，可以避免后续像素工作。

### Rasterization

光栅化判断三角形覆盖哪些像素样本，生成片元，并计算重心坐标用于插值。

光栅化不负责完整材质光照。它解决的是“连续几何覆盖哪些离散样本”。

### Pixel/Fragment Shader

读取插值数据、纹理和常量，计算颜色、深度或其他 Render Target 输出。Shader 可能完全不执行：如果硬件能提前确认样本深度失败，Early-Z 可以先拒绝它。

### Output Merger

执行深度测试、模板测试和混合，把 Shader 输出写入 Color/Depth/Stencil Attachment。某些测试可以提前执行，但逻辑上仍属于输出合并相关操作。

## Render Target 和 Attachment

一个 Pass 可以写多个颜色目标，例如 Deferred Geometry Pass 同时写 Base Color、Normal 和材质参数。Depth/Stencil 通常是单独 Attachment。

Render Target 的格式会影响：

- 每像素字节数和带宽；
- 是否支持混合；
- 精度和动态范围；
- 是否能作为 Shader 输入或 Storage/UAV；
- 平台上的压缩和 Tile Memory 行为。

## Graphics、Compute 和 Copy Queue

现代 GPU 可能提供不同能力的 Queue：

- Graphics Queue：执行 Draw，也通常能执行 Compute 和 Copy；
- Compute Queue：适合异步计算；
- Copy/Transfer Queue：专门搬运资源。

把工作放到 Async Compute 不代表免费。只有当它能与图形阶段使用不同硬件资源并真正重叠，而且同步和带宽成本可控时才有收益。

## CPU-GPU 并行和帧延迟

CPU 可以在 GPU 渲染第 $N$ 帧时准备第 $N+1$ 帧。好处是吞吐量高，代价是输入到显示的延迟可能增加。

当 CPU 过快时，Fence、Swapchain 帧数或引擎的最大排队帧会限制它。调用会等待 GPU 的 Readback、资源重用或同步点时，CPU-GPU 并行会被打断。

## Swapchain 与显示呈现

Swapchain 保存一组可轮换的显示图像。GPU 渲染 Back Buffer，Present 再把完成的图像交给显示系统。双缓冲或三缓冲影响等待方式、吞吐和额外延迟。

没有同步时，显示器可能在一次扫描过程中读到两帧，形成 Screen Tearing。VSync 把 Present 对齐刷新周期，可以消除撕裂，但 GPU 错过刷新窗口时会等待，并可能增加输入延迟。可变刷新率（VRR）让显示器在支持范围内跟随帧完成时间，减少固定刷新下的重复帧和等待。它仍需要帧率上限、排队帧和低延迟策略配合。

帧率稳定不等于低延迟。分析呈现问题要同时记录 CPU 提交、GPU 完成、Present Mode、Swapchain 队列和显示刷新时间。

## 如何从帧捕获验证

在 RenderDoc、PIX 或 Nsight Graphics 中可以检查：

- Event 列表中的 Draw/Dispatch/Copy 顺序；
- 每次 Draw 使用的 Pipeline State 和资源绑定；
- Vertex/Index Buffer 输入；
- Shader 输入输出；
- Render Target、Depth/Stencil 和 Blend State；
- 一个资源在哪个 Pass 写入，在哪个 Pass 被读取。

Frame Debugger 通常展示引擎整理后的事件。RenderDoc 更接近实际图形 API 命令。两者观察层次不同，不应互相代替。
