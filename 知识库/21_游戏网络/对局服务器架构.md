# 对局服务器架构

同一场对局的消息不能随机分给多台服务器。对局架构先确定权威实例，再安排会话路由与持久化边界。实时热状态与交易状态有不同延迟和一致性要求，故障恢复必须保持单一所有者。

## 会话与服务职责

常见链路是 Login 验证身份，Gateway 维持外部连接并做限流，Lobby/Matchmaking 组织队伍，Game Server 运行权威对局。Inventory、Social、Ranking 等服务按业务需要独立。服务间传递稳定 ID，不依赖进程内对象地址。

Dedicated Server 没有本地玩家，权威边界清楚，适合竞技和持久世界。Listen Server 由一名玩家同时做主机，成本低但主机有延迟优势，退出会触发 Host Migration。P2P 适合少量协作或中继场景，NAT、安全和作弊风险更难处理。

## 发现、负载与实例

Service Discovery 维护可用实例，Load Balancer 按区域、容量和会话粘性分配。实时对局通常先创建 Instance，再把玩家路由到固定实例；不能把同一场对局的逐帧消息随机发到不同服务器。

Consistent Hashing 在节点变化时减少 Key 迁移，可用于缓存或分片路由，但热点账号和热门区域仍会倾斜。选择分片键前要看访问模式，而不是只追求平均数量。

进程应支持健康检查、优雅下线和容量上报。健康不只是端口能连，还要包括 Tick 延迟、队列积压和关键依赖状态。

## 存储与一致性

实时 Game Server 保持战斗热状态，持久化服务保存账号、库存和进度。数据库不应参与每一帧移动。对局结果可先写耐久日志或事件，再异步更新派生榜单。

强一致用于支付、所有权和稀缺物品；允许短时最终一致的社交显示和统计可以异步。Transaction 只覆盖明确边界，跨服务用 Outbox、Saga 或补偿，而不是假设一次远程调用等同数据库事务。

## 安全与可观测性

Gateway 承担基础 DDoS 防护、连接上限和 Rate Limit，业务服务继续验证权限。服务间身份、密钥轮换和最小权限不能因为在“内网”就省略。管理接口与玩家流量隔离。

日志、Metric 和 Trace 使用统一 Request/Session/Match ID。实时服务重点看 Tick Time、连接数、丢包、队列、序列化字节、AOI 实体数和跨区失败。告警应对应可行动阈值，并有降级策略，例如停止接受新局而不是拖垮已有对局。

## 故障与测试

测试不只做正常登录。需要注入服务重启、数据库超时、重复消息、乱序、分区网络和节点扩缩容。确认交易幂等、玩家不会同时存在于两个权威实例、旧会话无法重放操作，并验证监控能定位故障范围。

无缝大世界、全球低延迟和绝对防作弊都不是单一架构开关。设计时先写清玩家规模、交互半径、Tick Rate、持久化要求和可接受故障，再选择分区与一致性策略。

## 会话路由

伪代码以MatchId和epoch定位当前实例，响应迟到或实例失效时重新查询，不直接复制权威状态。

```text
route = ResolveMatch(matchId, epoch)
validate session and match ownership
send command to authoritative instance
persist result through idempotent transaction boundary
```

## 验证方法

服务重启、重复请求与数据库超时分别注入，检查交易幂等和实例唯一权威。监控同时记录Tick、队列和连接，健康不能只看端口。
