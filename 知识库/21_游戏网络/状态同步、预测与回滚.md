# 状态同步、预测与回滚

联机同步的核心不是让所有机器每一帧完全相同，而是明确哪些状态由谁权威决定、客户端允许临时预测到什么程度，以及出现差异时怎样平滑回到正确结果。

## 三类同步思路

Snapshot Replication 由服务端定期发送世界快照，客户端在已收到的快照间插值。实现直观，适合动作与射击，但带宽随实体和状态量增长。

Lockstep 或 Frame Sync 只同步每个 Tick 的输入，各端运行同一模拟。带宽较低，也方便回放，但要求确定性；浮点、容器遍历顺序、随机数和线程调度差异都可能让状态逐渐分叉。

State Sync 直接同步关键状态或状态差异，常和输入同步混合使用。实际项目不必追求一个标签覆盖所有系统：角色移动可预测，物理物体走快照，库存和任务走可靠事务。

## 压缩与基线

位置、旋转和速度可按玩法允许误差 Quantize。Delta Compression 只发送相对已确认 Baseline 的变化，因此必须知道接收方拥有哪个基线。周期性 Keyframe 可在丢包或加入中途时恢复完整状态。

复制优先级通常由距离、可见性、变化幅度和玩法重要性决定。AOI 先筛选相关实体，再按带宽预算安排字段。省略更新不等于删除实体，生命周期消息要有独立可靠语义。

## 客户端预测与校正

本地玩家若等待服务器确认才移动，输入延迟会直接等于网络往返。Client Prediction 立即用本地输入模拟，同时把带序号的输入发给服务端并保存在 Input Buffer。

服务端返回权威状态和最后处理的输入序号后，客户端执行 Reconciliation：回到权威状态，丢弃已确认输入，再重放剩余输入。预测代码和服务端规则应共享或保持严格一致。视觉层可缓慢消化小误差，而碰撞和玩法状态立即以权威值为准。

直接对权威位置做 Lerp 会把问题藏起来，也可能永远追不上。应先重放得到正确预测结果，再单独做 Render Offset 平滑。

## 远端实体插值

其他玩家通常不预测输入，而是把显示时间故意放在最新服务器时间之后一小段 Interpolation Delay，在两个快照之间插值。缓冲越大越平滑，但画面越旧。

短暂缺包时可按速度 Extrapolation 或 Dead Reckoning，时间过长则冻结或切安全状态，避免无限漂移。位置和旋转的插值要与传送、死亡等离散事件区分，事件不能被当成普通连续值穿过去。

## 回滚与命中判定

格斗和高响应游戏可保存过去若干 Tick 的状态。迟到输入到达后回到旧 Tick，应用输入并重新模拟到当前，这要求模拟可恢复、确定且副作用可延迟提交。

射击游戏的 Lag Compensation 常按射手看到的历史时间把目标碰撞体回退，再做命中测试。它改善高延迟玩家的命中感，但会让被击者感觉已经躲到墙后仍中弹。回退窗口必须有限，并以服务端收到的合法输入与时钟估计为依据，不能接受客户端任意时间戳。

## 权威边界

客户端可以预测表现，不能决定伤害、掉落、库存和最终位置。服务端验证输入频率、移动能力、碰撞、资源和技能前提。完全拒绝所有偏差会误伤网络抖动玩家，完全信任客户端则给作弊留下入口，规则需要带容差且可审计。

## 断线、重连与回放

重连需要新的会话身份、完整或增量快照和安全的输入恢复边界。旧连接的延迟包不能影响新会话。玩家在断线期间由服务端托管、暂停还是移除，属于玩法规则，不该由传输层临时决定。

Replay 可以记录输入、权威事件或快照。只记输入体积小，但依赖版本和确定性；定期快照加事件更容易跳转和兼容。回放格式应写入构建版本、Tick Rate、随机种子和内容版本。

## 验证方法

- 模拟延迟、抖动、丢包、乱序和短时断网。
- 显示客户端 Tick、服务器 Tick、缓冲长度、预测误差与校正次数。
- 用状态 Hash 定位确定性首次分叉的 Tick。
- 对传送、碰撞、移动平台、技能打断和对象销毁做专门测试。
- 分别统计网络状态与渲染平滑后的状态，避免视觉结果掩盖同步错误。
