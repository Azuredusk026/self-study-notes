# 延迟补偿命中

射手看到目标还在门外，服务器收到射击时，目标已经走进门里。两端看到的是不同时间的目标。延迟补偿让服务器按射手所见时刻查询有限窗口内的碰撞历史，再把命中结果应用到当前权威状态。

全文跟踪同一发射击：输入会话C的17号输入由射手实例S7、武器W3发出；服务器在Tick600消费它，此时服务器时间为10.000秒，射手开火画面采用的远端时刻为9.820秒。W3原有2发弹药，目标实例T4还在门外。显示时间决定查哪份历史，Tick600决定使用哪个枪口和何时扣弹，后续结算Tick决定伤害作用于哪份当前状态。这三个边界分别保存，才能解释异步等待与恢复。

## 射击与显示时间

客户端预测本地角色，远端角色却在历史快照间插值。因此射击请求至少要关联输入序号、射击朝向和该帧使用的远端显示时间。客户端记录开火帧实际采用的远端播放时刻r及服务器纪元，服务器用时钟映射估计射击生成时刻，核对画面年龄与许可插值窗口。稳定播放时可写成下面的关系，目标查询使用通过校验的实际r：

$$t_q=r_{fire},\qquad d_{actual}=t_{fire,server}-r_{fire}$$

例如服务器当前10.000秒，估计请求在9.920秒生成，远端插值延迟为0.100秒，实际r为9.820秒时查询该时刻的目标碰撞体。这里的80毫秒已经体现在射击生成时刻里，不能再次减去一次单程延迟。

服务器核对序号、开火间隔、弹药、枪口位置和朝向变化，再检查查询时间是否落在允许窗口及实际历史范围。客户端时间戳是请求数据；服务端按会话样本、最大补偿窗口和配置允许的插值延迟限制它。过旧请求可明确拒绝，不能悄悄把任意旧时间夹到最早一帧并声称重建了原画面。

快照页的播放时间r有独立速率控制，缓冲恢复期间未必等于估计服务器时间减去目标延迟。因而不能只重新计算`t_fire-Dtarget`代替开火帧真正显示的r。请求记录`(输入会话,输入号,显示纪元,呈现段,播放状态,viewReady,r,关键实体样本引用)`。服务器限制`d_actual`在会话协商的画面年龄范围内，并按快照页的状态机检查连续呈现段：Playing的r按许可速率推进，Frozen保持r不动但仍受最大画面年龄限制，Waiting与viewReady=false均拒绝依赖该视图的历史命中。Frozen不能被当作普通0.95倍播放，也不能给客户端无限保持旧目标的权限；视图过旧就暂停请求。缓冲重建或缺失的新运动段补齐后，先按会话规则登记新呈现段及重同步标记，重新检查画面年龄与有效状态，再建立新的r推进锚点，不能沿用旧段速率比较。超窗、纪元不符或缺少历史时明确拒绝。客户端声明只提供候选视图，不获得任意查询历史的权限。

### 实体新鲜度与视图校验

全局r递增不能证明每个目标都在这个时刻有有效样本。快照页的实体求值器返回段ID、实际取样时间和validAtR；某个低频目标已超过自己的外推上限时，全局仍可能Playing。客户端从玩法定义的查询关键集合聚合viewReady，集合包括可受击体与潜在遮挡物。集合中存在Stale或Missing就暂停依赖该视图的开火请求，装饰实体可独立降级。

服务器不把这个布尔值当作证明。它保存该观察者已确认生成身份、已发送运动样本ID及时间，按配置的最大外推与画面年龄核对请求引用的样本是否足以支持r，并检查关键对象的覆盖集合。客户端可以报告丢包导致无法显示，服务器却不能仅凭客户端自称有效便接受任意旧目标。发送日志也不能证明客户端实际收到，因此规则只限制可接受视图的范围；精确重建客户端采用的轨迹还需要下一节的样本引用方案。权威历史策略始终保留估计姿态与权威姿态之间的误差边界。

### 显示估计与权威历史

实际r解决查询哪一个时刻，并不保证客户端在r显示的位置等于服务器该时刻的权威位置。本文采用同一r查询权威历史的规则：命中以权威轨迹为准，客户端插值与有限外推的误差仍可能造成所见偏差。两份快照之间的线性插值会省略中间曲线，加速期间的速度外推也没有未来信息，给它一个准确时间戳不能补回这份轨迹。

把门口的T4改为加速运动：最新快照在9.720秒给出x=0米、速度1米/秒，随后服务器沿X以20米/秒²加速。客户端外推到r=9.820秒显示x=0.1米；权威历史此时为`1*0.1+0.5*20*0.1²=0.2米`。若小目标半宽0.04米，朝客户端所见x=0.1开出的射线可能错过历史中心x=0.2。在r=9.820秒恰好达到该实体的外推上限时，这份估计仍处于允许窗口。若之后全局r继续推进，该实体进入Stale并保留x=0.1，validAtR变为假，关键集合门控拒绝相关命中请求。若包时间轴也恰好在r=9.820秒进入Frozen，允许的查询仍使用权威9.820秒的x=0.2，误差不会因为全局r停止推进而自动消失；恢复时在相同r重新求显示姿态。

年龄窗口限制可请求多旧的视图，外推上限限制估计持续多久，二者都不等同于精确重建所见几何。

若玩法要求复现允许的客户端展示轨迹，服务器还需保留发给该客户端的快照版本和相同插值/外推规则，请求引用左右快照ID或外推源ID、呈现段、模式与r；服务端检查这些快照确已发送、相容且处于许可窗口，再按同一规则重建展示碰撞体。客户端自报位置不能代替这份重建。本文的权威历史策略不采用这条展示轨迹判定，两种规则的公平性与误差由明确场景比较，结果记录采用的策略版本。

射手枪口与远端目标采用不同边界。按 [[21_游戏网络/客户端预测]] 的输入协议，服务器在实际消费开火输入的Tick先执行本步移动，再从该步权威角色姿态计算枪口并判射击；朝向也来自该输入并受变化速率与动作状态校验。客户端采样时刻的映射用于年龄和反重放检查，不把射手退回那个墙钟时刻。目标和可回溯遮挡物查询实际`t_q`，与射手当时采用的远端显示时刻对应；碰撞姿态依照上述权威历史规则求得。若输入在服务端队列多等了一步，枪口仍使用该输入实际消费步，而不是误取早一步的射手历史。此双边界规则不把本地预测射手和远端插值目标强行放在同一个历史时刻。

## 历史碰撞体

每个服务器 Tick 保存可受击实体的稳定ID与代数、碰撞体位置、旋转、尺寸和有效状态。查询时间落在两帧之间时，连续运动可插值；传送、生成和销毁把历史分段，跨段时按玩法规则处理，不能在不存在的位置生成中间碰撞体。

历史查询可使用独立碰撞场景，也可暂时替换实时碰撞体后在作用域退出时恢复。独立场景避免查询期间触发实时物理回调，代价是额外存储和索引。历史长度为 $W$ 秒、频率为 $f$、实体数为 $N$、每实体记录 $B$ 字节时，原始存储约为 $WfNB$，还要计入索引和分配成本。

动态门和平台也会改变遮挡。把角色退回过去、门却留在现在，是一套混合时间规则。本文选择角色、可移动门与平台全部在`t_q`查询，静态场景用固定几何。门开关等离散变化保存事件时间，查询时取不晚于`t_q`的最近状态；角色传送也按事件切段。服务器接纳输入时记录采用的补偿时间和策略版本，并固定查询所需的历史样本版本。异步查询持有这些样本直到结果进入模拟提交队列，环形历史缓冲不能在此期间覆写它们；可复制所需区间，或按引用计数延迟槽位复用。仅固定时间而未保留对应样本，等待中的查询仍可能遇到历史淘汰。查询任务退出后释放内存历史持有；持久查询包还受Pending恢复保护，终态和回执按射击身份保存。

## 最小射线查询

用球形受击体可以先验证时间插值与命中算法。设单位射线方向为 $d$，起点为 $o$，历史球心为 $c$，半径为 $r$。代入 $|o+td-c|^2=r^2$，令 $m=o-c$，则 $b=m\cdot d$、$q=m\cdot m-r^2$，判别式为 $b^2-q$。

```python
disc = b*b - q
if disc < 0:
    return None
enter = -b - sqrt(disc)
leave = -b + sqrt(disc)
if leave < 0:
    return None
return max(0, enter)
```

这是求交机制片段，输出射线前方距离，所有位置与半径使用米；起点在球内时输出0。完整参考函数见下方。把T4在9.820秒的球心设为(5,0,0)、半径1，S7的枪口为原点，射线沿正X，命中距离应为4；把球心改到(-5,0,0)时不应命中。真实角色需要胶囊或骨骼碰撞体，并比较所有有效遮挡的最近命中。

## 历史遮挡与实时状态隔离

继续改变同一发射击的历史输入：T4球心在9.800秒为(5,0,0)、9.840秒为(5,2,0)，查询9.820秒得到(5,1,0)。射线沿X轴、半径0.5米时不命中；若误用9.80秒记录就会命中。门在9.81秒关闭时，门的历史状态也必须在9.82秒参与最近交点比较，否则角色虽然回溯正确，遮挡规则仍混用了时间。

临时替换实时碰撞体的实现必须覆盖所有退出路径：进入查询前保存每个被改对象的变换和启用状态，在禁止实时物理步进与回调的查询范围内安装历史状态，执行查询后用作用域清理恢复，异常和提前返回也走恢复。记录对象代数，避免把已经销毁重建的新对象恢复成旧对象位置。独立历史场景则将查询数据与实时世界隔离，后续只把命中ID和距离交回权威逻辑。

## 命中提交与验证

查询只回答历史上击中了谁。对所有有效历史受击体与遮挡体求正向最近交点，再选距离最小者；遮挡更近便阻断，距离相同按预先规定的遮挡优先与稳定ID次序处理，避免容器遍历顺序决定命中。查询结果返回目标ID、实例代数、距离和使用的历史时间，不直接改实时物理状态。

### 接纳与弹药所有权

在Tick600，S7持有W3，弹匣剩2发。模拟线程先完成输入与视图校验，在同一耐久模拟提交中登记射击身份、输入摘要、S7、W3、枪口、方向、伤害参数、策略版本和固定历史查询数据，并把弹药从2减为1。这一发此刻已经接纳，形成独立的射击记录；弹药支出与记录一起提交，不能只写其中一项。重复请求按身份与摘要找到原记录，摘要不同则拒绝。

本文选择接纳即消耗的规则。历史未命中、目标已死亡、查询失败或超时都消耗这一发；接纳前的弹药不足和非法输入则不消耗。这样查询等待不再借用可变化的武器库存。射手随后死亡、丢弃W3或重生为S8，已接纳射击仍可结算，结果不会扣S8或新武器的弹药。伤害归属保留S7的稳定身份，即使其活动对象已销毁也能生成战报。需要退款的玩法必须另定义针对原库存实例的退款事务，不能在任意当前武器上加一。

同步查询可在同一次模拟提交内得到最终结果。异步查询则保存Pending并派发纯查询任务，任务只能读取固定数据，不访问活动射手或修改世界。冷却在接纳时更新；该射手后续输入可继续消费，下一发再次检查剩余弹药和冷却。输入ACK表示输入已消费，动作结果可以仍为Pending，客户端保留相应事件身份直到收到终态。

### 查询完成与结算顺序

查询任务返回射击身份、对局执行纪元、尝试代次、查询包哈希、历史版本和最近交点。任务只把结果放进完成队列；进入队列尚不等于伤害提交。模拟线程在每个Tick的固定结算阶段，持队列锁交换出当时的结果集合，随后到达的结果留到下一Tick。它逐项核对射击仍为Pending、纪元及代次匹配、输入包与策略版本一致，按射击身份去除重复。同一尝试若出现不同内容的结果，按查询损坏终结并报警，不让先遍历到的结果决定伤害。

集合内的有效结果按接纳序号排序；未完成的更早射击不阻塞集合中的后续射击。因此Tick604完成的后一发可以先于Tick605才完成的前一发结算。要求严格开火顺序的玩法需等待全部前序终态，并承担队头阻塞。本页采用按Tick截取完成集合的规则，排序只在该集合内生效。

截止也在这个阶段决定。17号输入接纳于600、固定截止于606；606先采用交换出的有效完成集合，再把仍为Pending且到期的射击加入超时集合。完成集合内按接纳序号结算，超时集合也按同一序号稳定排列。交换队列之后才到达的17号命中不能撤销本Tick的超时。截止使用对局模拟时间，停机期间暂停，恢复不重给六个Tick。

结算时对同一目标实例当前仍存活的对象施加伤害。T4在9.820秒被击中而结算时已死亡，终态为无伤害；重生的T5不承接T4的命中。同Tick两发都指向生命只够承受一发的T4时，排序在先的一发先改生命，后一发读取修改后的状态。结果记录使用的历史时刻与当前目标代数，才能区分几何未命中、目标已失效和实际伤害。弹药在600已扣，结算不再扣一次。

### 权威决策与Tick日志

完成集合来自线程调度，恢复时重新运行查询不能重现它原先在哪个Tick到达。因此本页把上述集合转成显式的权威决策批次，作为 [[21_游戏网络/对局服务器架构]] “运行中恢复的状态链”所规定的Tick输入。每个Tick记录该阶段是否执行、排序后的采用项及超时项；空集合也记录为空。每个采用项保存射击身份、尝试代次、查询包哈希和完整最近交点或无命中结果，超时项保存原截止Tick。批次还固定结算规则版本，回放不从工作线程重新收取结果。

从已提交状态Sk计算下一步时，模拟线程依次消费本Tick玩家输入、执行玩法阶段，再按记录的决策批次执行结算归约。Tick日志保存输入顺序、决策批次、状态版本和事件发件箱；伤害、射击终态、事件ID、输入消费记录与新状态在同一耐久Tick事务中提交。写入失败时该Tick不能发布权威ACK、伤害确认或命中提示，实例停止推进并从最后已提交边界恢复。这里的批次不是独立于状态提前确认的另一笔提交。

以17号与18号射击竞争T4最后10点生命为例，若604的采用批次只有18号，605才采用17号，那么回放也先在604扣除18号的伤害，605把17号结为目标已死。即使恢复机器重新计算17号更快，也不会交换这两个结果。若606的已提交批次把17号列为超时，回放直接执行超时，不采纳重算出的命中。这正是记录“哪个结果在哪一步成为权威输入”的作用。

### 查询包与崩溃恢复

接纳17号之前，服务器将9.820秒查询所需历史几何、静态场景版本、枪口、方向及策略参数写成不可变查询包，校验并持久化，再把包哈希与Pending纳入Tick600事务。几何范围覆盖整条许可射线上的受击体和遮挡体，门也包含在内。包由Pending和未退出工作任务共同保护；终态落盘后仍等待旧任务退出再释放内存，持久文件按快照与日志保留根回收。

替代实例先隔离旧执行者并取得新对局纪元，从一致快照重放已提交Tick日志到最后耐久Tick。重放时消费日志中的原决策批次，以原顺序还原弹药、目标生命、Pending、超时与事件发件箱；此阶段不开工作线程，也不再次广播事件。已提交终态只重送同一事件ID的回执。快照必须包含Pending所引用的包、固定截止、已采用的尝试代次和输入消费状态，日志与包保护在快照引用发布前持续存在。

完成已提交日志的重放后，才为剩余Pending写入新纪元、递增尝试代次的恢复记录并耐久提交，然后用原包重新派发。旧纪元或旧代次结果都被拒绝。最后耐久Tick为603而原查询在604未提交前算完时，这个未确认结果可以丢失；新尝试从恢复后的下一Tick开始参与新的完成集合。恢复只承诺重现已经提交的决策，没有把未提交的线程完成顺序变成权威历史。

若最后耐久边界已包含606的超时阶段，就不存在这发的Pending。若恢复停在605，下一个606仍先截取新纪元有效完成集合，再终结到期项，原截止不移动。原包丢失或校验失败时，将Pending作为查询数据损坏决策写入下一耐久Tick并报警，保留600已提交的弹药支出，不使用当前几何补算。

| 射击17的阶段 | 耐久记录 | 恢复与消费者行为 |
|---|---|---|
| 600接纳 | C/17、S7/W3、弹药2→1、包哈希、截止606、Pending | 输入ACK可推进17；客户端保留动作等待项 |
| 602射手死亡 | S7死亡，射击仍Pending | T4查询仍使用9.820秒的原包，重生S8库存不变 |
| 603退出，尚无终态 | 重放到603仍Pending | 登记新尝试后派发原包，后续Tick记录新的决策集合 |
| 604采用有效命中 | 批次、T4伤害、终态和事件发件箱共同提交 | 客户端按原事件ID确认命中；重发只查询同一结果 |
| 或606采用超时 | 超时决策、终态和事件共同提交 | 607晚到命中被拒绝，客户端结束等待，保留开火事实 |

这些行描述同一发的不同故障分支。600接纳前崩溃时，弹药和Pending都不存在；604提交后丢响应时，恢复直接补送回执。输入ACK只证明输入已消费，枪口效果、弹药确认和最终命中分别消费自己的接纳或终态事件。

### 观察与反例

先录制目标横穿射线的轨迹，核对显示r、枪口所属输入步、历史最近交点和当前结算目标。再把同一发射击放入门关闭、传送、销毁、重复请求和超窗场景，分别检查时间选择与拒绝原因。异步路径还应在接纳后死亡、接纳落盘后退出、伤害落盘后丢响应及截止边界注入故障；每次追踪原武器弹药、Pending、目标生命和事件ID，才能分清查询完成与权威提交。
