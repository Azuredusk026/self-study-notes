# 游戏网络传输

一次send并不对应一次recv，UDP也不保证消息到达。游戏网络传输先定位端点，再根据消息有效期选择可靠性、顺序与拥塞策略。序列化长度与分帧保证接收端能安全识别完整消息。

## 端点怎样建立通信

### 分层、地址与端点

OSI 七层模型适合解释职责，实际互联网协议栈常按链路、网络、传输和应用理解。游戏代码主要面对 IP 路由、TCP/UDP/QUIC 传输与应用协议；网卡帧、交换与路由仍会影响 MTU、丢包和延迟，但不应泄漏成每个玩法系统的细节。

IPv4 地址标识网络接口，端口标识主机上的传输端点，协议、地址和端口共同确定通信目标。私网地址通常需要 NAT 映射；服务监听地址、外网可达地址和客户端看到的地址可能不同。连接问题应分别检查 DNS、路由、防火墙、端口监听和会话握手。

同一局域网发送 IPv4 包时，主机先根据子网掩码判断目标是否本地。本地目标通过 ARP 查询 IP 对应的链路层地址；远端目标把帧交给 Default Gateway，再由路由器逐跳转发。DHCP 可以为客户端分配地址、网关、DNS Server 和租约。抓包定位连接问题时，应分清链路可达、IP 路由、传输端口和应用握手四个层次。

IPv6 使用更大的地址空间，并通过邻居发现等机制处理本地寻址。应用应尽量使用地址族无关的解析与 Socket API，不能把文本 IPv4 地址或固定长度写进协议结构。

### DNS

Domain Name System 把域名解析为地址和其他记录。客户端先查询本机缓存，再请求配置的递归解析器。解析器在需要时逐级查询根、顶级域和权威服务器，并按 TTL 缓存响应。应用的解析路径还受操作系统和网络配置影响。

常见记录：

- A：IPv4 地址；
- AAAA：IPv6 地址；
- CNAME：别名指向另一个域名；
- MX：邮件服务器；
- TXT：文本验证和策略信息；
- SRV：带端口、优先级和权重的服务发现。

DNS 返回多个地址时，客户端需要连接回退和超时策略。TTL 到期、负缓存、递归服务器故障和本地网络劫持都会影响结果。DNS 解析成功只说明获得了候选地址，不代表端口可达或服务健康。

## 消息怎样在链路上传输

### TCP 与 UDP

TCP 提供有序、可靠的字节流，带拥塞控制，适合登录、聊天、配置和不频繁的事务。一个前部包丢失会阻塞后续字节交付，实时状态若全部走同一连接可能产生 Head-of-Line Blocking。

UDP 是数据报，不保证到达、顺序和唯一性，但应用可以决定哪些数据值得重传。高频位置快照过期后通常无需补发，关键技能和库存操作则需要可靠确认。选择 UDP 不等于忽略拥塞与安全，也不等于天然更快。

可靠 UDP 常加入 Sequence Number、ACK/NACK、滑动窗口、超时重传和重复包过滤。不同消息可设置可靠有序、可靠无序或不可靠。重传策略必须考虑 RTT 和拥塞；无上限地补包会在网络恶化时进一步堵塞链路。

ARQ 是通过确认、超时和重传恢复丢包的一类机制。Sliding Window 允许多个包同时在途，避免 Stop-and-Wait 每次只利用一个 RTT。窗口既限制未确认数据量，也用于判断序号范围、重复包和累计确认。

KCP 在 UDP 上实现面向消息的可靠传输，以更积极的重传和窗口策略换取较低延迟。它仍需要应用提供 UDP 收发、定时更新、会话标识和拥塞参数。可靠传输并不适合所有实时状态，过期快照应优先丢弃而不是排队补齐。

### TCP 连接与可靠性

TCP 用 Sequence Number 标识字节位置，用 ACK 表示下一段期望字节。Receiver Window 实现流量控制，限制发送方不能淹没接收 Buffer；Congestion Window 则根据网络拥塞调整在途数据量。两者取较小值决定实际发送窗口。

建立连接使用三次握手：客户端发送 SYN，服务端回复 SYN+ACK，客户端再 ACK。第三步让双方都确认收发方向、初始序号和连接参数。断开通常需要双方分别发送 FIN 和 ACK，因为 TCP 支持半关闭；主动关闭方可能进入 TIME_WAIT，保留一段时间以吸收旧包并确保最后 ACK 可重传。

可靠性来自校验、序号、累计或选择确认、超时重传和重复数据去除。Retransmission Timeout 根据 RTT 和抖动估计。收到多个重复 ACK 时可进行 Fast Retransmit，不必等待完整超时。

拥塞控制通常经历 Slow Start、Congestion Avoidance、Fast Retransmit 和 Recovery。具体算法可以是 Reno、CUBIC、BBR 或平台实现，应用不能假设窗口增长方式固定。丢包、ECN 和 RTT 变化会影响发送速率。

Nagle Algorithm 会合并未确认的小块写入，减少小包数量；Delayed ACK 会稍晚发送确认。两者叠加可能增加交互延迟。实时小消息可以评估 `TCP_NODELAY`，但关闭 Nagle 后仍应在应用层批量消息，避免产生大量包头和系统调用。

TCP Keepalive 用于长时间空闲后探测失效连接，默认间隔通常不适合快速游戏断线判断。应用层 Heartbeat 能同时携带 Tick、延迟和会话状态，并使用业务需要的超时。

### 数据包与序列化

协议需要明确包头、消息类型、长度、版本、序号和校验方式。TCP 是字节流，没有天然消息边界，因此必须 Length Prefix 或其他 Framing。UDP 保留数据报边界，但还要处理 MTU，尽量避免 IP Fragmentation。

所谓 TCP 粘包不是 TCP 把消息错误合并，而是应用把一次 `send` 当成一次 `recv`。字节流只保证顺序，不保留调用边界；接收端必须循环读取并按长度或分隔协议组帧，也要处理半包。

多字节数字要约定 Endianness。序列化格式应限制长度、层级和枚举范围，不能信任远端给出的数组大小。高频状态可用 Bit Packing、Quantization 和 Delta Compression，控制面消息更看重兼容与可诊断性。

协议演进要区分可选字段和破坏性修改。客户端、服务端版本不一致时应明确拒绝或走兼容分支，不能靠解析异常猜测。

## 诊断

网络问题至少记录时间、连接、消息类型、序号、字节数、RTT、丢包率、重传和队列长度。抓包能看见传输事实，游戏内 Network Profiler 则要关联到实体和系统。模拟延迟、抖动、丢包、乱序和限带宽，比只在本机回环测试更接近真实环境。

### TCP 字节流分帧

TCP 保证有序字节流，不保留发送时的消息边界。接收 Buffer 需要先等待固定长度头，再等待完整 Payload：

```cpp
while (receiveBuffer.Size() >= sizeof(PacketHeader)) {
    PacketHeader header = PeekNetworkOrderHeader(receiveBuffer);
    if (header.payloadBytes > maxPayloadBytes) {
        Disconnect("oversized packet");
        return;
    }
    size_t packetBytes = sizeof(PacketHeader) + header.payloadBytes;
    if (receiveBuffer.Size() < packetBytes) break;
    receiveBuffer.Consume(sizeof(PacketHeader));
    Bytes payload = receiveBuffer.Consume(header.payloadBytes);
    DispatchValidated(header.messageType, payload);
}
```

片段中的 `sizeof(PacketHeader)` 代表已定义的固定线协议头长；实际实现应使用明确常量，逐字段解码，不能让 C++ padding 改变线上格式。总长度加法也要检查整数溢出。头字段需要固定字节序，长度在分配内存前校验，消息类型进入反序列化器前校验权限和版本。一次 `recv` 可能只得到半个包，也可能得到多个包。用随机切分的输入字节流做测试，解析结果应与发送边界无关。

本机机制检查：20种随机字节切分得到相同的消息序列；模型使用2字节长度头，没有建立真实 Socket。检查代码见 [reference.py](../examples/mechanisms/reference.py)，运行 `python 知识库/examples/mechanisms/reference.py`。引擎画面、GPU捕获与性能另外验证。
