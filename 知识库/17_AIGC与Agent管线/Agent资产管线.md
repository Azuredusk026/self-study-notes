# Agent资产管线

一张餐桌放进房间后，几何检查通过了，入口到座位的通道却被挡住。规划器把桌子移开，视觉审核又要求取消这次布局。此时系统既要恢复任务自己的修改，也要保留期间发生的人工编辑；工具超时或进程中断还可能让执行结果暂时未知。

模型从需求中找出候选资产，工具把资产写入场景，验证器判断结果是否符合要求。三者处理不同的信息：模型处理语义与候选，工具执行明确的状态变化，验证器读取实际产物。任务记录连接这些步骤，中断以后据此恢复。

本文沿任务J布置房间R和桌子T。J先创建房间与桌子，移动A调整桌子位置，导航拒绝后移动B让出通道。技术门禁通过时进入视觉审核；审核取消则逆序撤销B、A和创建操作。人工编辑与取消相遇时，审核者决定保留哪些对象，执行器据决议继续清理。发布是另一条分支：审核批准绑定完整布局哈希，消费者加载该版本。下文的版本、回执和游标都对应这批对象。

## 室内场景的结构化规划

```text
Room { zones, anchors, pathways, placements, lightingIntent, constraints }
Placement { assetId, transform, parentId, operationId }
```

先确定房间功能区和通道净空，再查询尺寸合适的资产，最后求解位置与朝向。验证器用包围体或精确碰撞检查穿插，用导航数据检查可达性，再检查门窗净空、墙地锚点、功能距离与渲染预算。模型读取失败位置和原因，重新提出有限候选。

例如餐桌摆放满足几何不相交，却挡住门到座位的通路，碰撞检查可以通过，导航检查仍应拒绝。把两项规则分别记录，才能让返工针对通道，而不是反复缩小所有家具。

### 规划的数值约束

假设房间内可通行矩形为4米乘3米，入口沿宽度方向需保留1米净空。候选桌子宽1.6米，若中心距左墙0.5米，半宽0.8米会越墙0.3米，布局校验先拒绝；中心移到1米后包围盒合法，仍须检查门到座位路径。规划输出使用米和房间局部坐标，执行器再用房间世界变换生成实例，避免厘米资产和米场景混用。

资产尺寸取自选定的不可变资产版本。操作完成后，验证器读取真实实例变换和碰撞数据；计划中的位置只是期望值，不能代替实际场景。目录更新、房间移动和其他家具变化还可能使计划的输入过期，执行条件见“读取版本与条件执行”中的读取集合。

规划到执行先统一几何单位。资产顶点与尺寸元数据转换为米，实例局部矩阵L和完整祖先世界矩阵P共同把顶点送到世界空间，`x_world=P×L×x_asset`。碰撞、门窗净空和导航均消费这份世界几何；变换只施加一次。任务仍保存局部矩阵，验证器则保存实际世界几何哈希及其读取版本，位置记录与空间度量分别承担自己的职责。

### 缩放与空间度量

角色配置中的半径、高度、台阶和净空阈值都使用世界米。假设房间局部通道宽1米，世界半径0.4米的角色需要0.8米净宽。父变换沿通道宽度方向缩放0.5后，实际净宽为0.5米，应拒绝通行；父变换放大2倍后净宽为2米，可以继续检查其他条件。直接在局部空间按0.4膨胀，两种缩放都会使用相同的1米宽度，无法得出正确结论。

完整父变换的线性部分记A。局部位移d对应世界距离`length(A*d)`，平方为`dᵀ*Aᵀ*A*d`。只含旋转时长度保持；统一缩放s使局部半径变为`r/abs(s)`；非均匀缩放或剪切下，世界半径r的球在局部满足`dᵀ*Aᵀ*A*d<=r²`，不能用一个相同半径的局部球替代。例如X缩放0.5、Y缩放2，世界半径0.4对应的局部轴半径分别为0.8和0.2。

本管线直接在世界空间完成检查，避免给每种规则另设局部距离算法。把变换后的碰撞网格、家具占地和门的完整开合扫掠送入验证器；有剪切的层级使用最终顶点或由其生成的保守凸体，宿主碰撞组件仅支持特定缩放时，不能把未支持的变换交给它并沿用旧碰撞体。法线用逆转置变换并归一化，反射变换同时调整三角形绕序与碰撞面的朝向约定；坡度相对世界Up检查。矩阵不可逆或数值精度不足以可靠求逆时，操作在硬约束阶段拒绝，保留原对象及具体诊断。

平面布局采用世界Up定义的水平平面与正交单位基，把世界占地投影为以米计的多边形。先按角色世界半径向外膨胀家具，再向内收缩房间边界，得到角色中心可行域；轴对齐包围盒只用于保守快速拒绝。门保留开合扫过区域，座位目标使用座位前方的世界交互点。高度、坡度、台阶和低天花板由世界几何另行检查；多层与斜坡场景将这些世界三角形交给导航生成器，保留高度段，不能把重叠投影连接成同一层。

世界网格的格长也以米计。只有整个格子处于可行域才标为可走，邻格连线与拐角余量一并检查。入口有效格到合法交互站位作连通查询，间隙小于角色直径时膨胀后的障碍相连，路径断开；保守误拒绝通过减小世界格长或精确导航验证处理。碰撞和导航使用执行器回读的实际变换；与计划不一致时输出对应对象、世界位置和距离。

### 交互站位与可达性

桌面上的交互触点与角色站位承担不同作用。资产版本为座位保存交互槽、局部脚点或允许站位区、接近侧、期望朝向、支撑层，以及投影容差、交互距离和射线规则。规划器先把这些位置按实际实例矩阵变到世界空间，再把角色的世界体型交给验证器。朝向由变换后的前向投影到世界水平面并归一化，角色保持世界Up直立；前向退化时该姿态失败。布局并不会随家具缩小角色身体或交互距离。

假设座位脚点距墙世界0.2米，角色半径0.4米，同侧最近可走脚点距墙至少0.4米。投影需偏移0.2米：若槽位只允许0.1米，就拒绝这个站位；允许0.25米时，再检查实际胶囊、朝向、从视点或手部到触点的距离与遮挡。墙另一侧或楼上即使有更近导航面，也不属于这个槽的支撑层和接近侧。精确目标、区域目标及起点接入的计算见[[20_游戏AI/游戏AI导航#交互目标与导航投影]]。

技术报告为每个必需交互槽保存原目标、采用脚点、偏移、姿态、支撑面、实际交互检查和完整路线结果。必需槽至少有一个完整可达且可交互的姿态才通过；部分路径和候选耗尽分别记录失败原因，附近存在可走点本身不构成通过。区域目标采用导航篇的区域求交与姿态验证，有限采样未找到结果时返回候选耗尽，不把它作为整个连续区域不可达的证明。报告还绑定资产、角色配置、场景几何和导航源哈希，审核消费的是这份完整结果。

### 缩放变化与补偿验证

J的读取集合包含完整祖先链、实例局部矩阵、资产碰撞与交互槽版本和角色世界体型。任一祖先缩放变化都会使世界几何及导航源哈希变化；即使T的局部位置没变，也重新构建候选世界几何、站位区和触点，不能只更新世界中心。支撑层按新几何重新绑定，原支撑面ID与位置接近不能替代这次检查。技术验证等待匹配该几何哈希的导航数据，重新完成投影、姿态和路线检查；旧导航查询结果不参与新门禁。

例如R平移到世界X=10并沿X缩放0.5，撤销B恢复T局部X=1时，世界X为10.5。补偿用当前父矩阵重新生成家具的世界形状、门扫掠和交互点，再检查硬约束并生成布局诊断。通路因缩放变窄可作为隔离中间态的失败诊断继续逆序清理；最终保留对象时，世界0.5米通道仍不能通过0.8米净宽门禁。空间度量正确性、补偿是否可提交、最终结果是否可发布因此各有明确判据。

### 读取版本与条件执行

J根据房间R的世界变换r1，把局部位置换成桌子T的世界位置。人工随后把R移动到r2，T对象版本和父子关系都可能保持原值。此时仅比较T，执行器仍会接纳按r1算出的旧位置。问题出在操作读取了R，却只保护了T的写入。

计划因此保存读取集合与修改集合。读取项记录稳定ID、字段语义和版本；修改项记录目标ID、预期版本及绝对目标值。J使用以下依赖：

| 输入 | 版本保护的内容 | 变化后的处理 |
|---|---|---|
| R及祖先变换、边界、门窗、其他家具 | 变换、几何、碰撞与挂接记录 | 重建受影响世界变换和可行域，重算布局与碰撞 |
| 区域对象集合 | 区域集合版本，包含新增与移除 | 重新枚举障碍，防止只比较旧对象漏掉新椅子 |
| 桌子资产 | 不可变资产哈希，尺寸、枢轴、碰撞与LOD依赖哈希 | 重新选型或按新版本重算尺寸和预算 |
| 导航与角色 | 导航区域代次、源几何哈希、角色半径与规则版本 | 等待匹配源几何的导航构建，重新查询通路 |
| 技术与视觉检查 | 规则、相机、预览配置及实际场景清单哈希 | 产生新的验证尝试及批准候选 |

读取集合从同一场景快照建立。空间查询同时登记覆盖区域的集合版本；即使查询结果为空，新增对象也会改变该版本。宿主若不能提供细粒度版本，就比较整个暂存场景快照代次。版本粒度粗会增加重算，却能保持依赖完整。外部资产、导航和规则采用已固定的不可变版本，宿主保存其引用；外部服务的活动入口先解析为具体哈希，再参与计划，避免在两个系统之间假设一次原子比较。

执行器在宿主提交边界共同检查读取集合、修改集合、场景令牌和任务许可，通过后才写对象、关系、新版本与操作回执。所有场景写入者，包括人工工具，都经过同一版本化入口。检查与写入之间没有可插入的场景修改；采用快照方案时，条件替换活动快照，并把回执放在同一快照内。只在调度器中检查一次，再向宿主发送普通移动命令，会重新打开竞争窗口。

R从r1变成r2时，旧操作得到`DependencyChanged`及不匹配的读取项，场景不发生该操作的修改。调度器关闭这份计划的后续派发，使其技术报告、预览和批准失效；读取新快照，重新求世界位置、碰撞和导航。即使最终局部位置仍相同，也生成新计划版本、新验证尝试和新操作ID。已经应用的A保留原回执，新的B以A的实际输出为输入；取消时仍按真实操作链补偿。不得把新读取版本填进原操作后直接执行旧目标。

执行中的读取集合也随本任务写入变化。创建T使区域集合从c0变c1，移动A使T从v1变v2；B必须消费相应宿主回执，将这些输出加入新的快照，再做自身的计划校验。只有登记在回执上的精确承接可以更新输入；“同一任务写入”不能自动证明导航、布局和预算仍然成立。

返工有固定终止规则：每次报告保存失败规则ID、位置、相关对象与实际值，规划器每轮只提交有限候选；同一规则在相同资产集合和输入版本下连续3轮未改善则停止自动返工，进入人工审核或失败队列。技术通过只推进到视觉审核，发布前再次核对产物哈希和批准版本，不能把工具执行成功当作任务批准。

在J中，移动A后的实际布局形成验证尝试V1，通路失败报告引用桌子T及其版本；移动B消费新快照并重新验证，形成V2。V1的迟到成功不能替代V2，因为验证回执同时绑定场景快照哈希、完整输入依赖、规则版本和尝试ID。执行器完成的只是移动，V2通过后才允许视觉审核这份布局；审核期间任一对象变化都会使绑定的候选哈希失效。

### 连续站位区域的验证结果

V2检查桌子T的座位槽时，先取得世界脚点区`[0.65,1]×[-0.6,0.6]`米，与同层导航面求交后X上界收至0.9。距离、40°朝向和挡板遮挡再把它切成上下两片；推荐点(0.65,0)被挡板遮住，上片的q=(0.75,0.525)才成为候选。

q的触点距离约0.9155米。身体净空通过后，半径0.01米探头的中心终点位于触点沿表面法线外移0.01米处，中心行程约0.90732米，挡板间隙约0.02838米。完整扫掠避开障碍，球面在允许片接触目标，验证器才接受该姿态。区域裁剪、身体、探头轨迹和接触的全部计算见[[20_游戏AI/游戏AI导航#连续区域的数值推演]]。

验证器从实际入口求到q的完整路线，记录目标分片、区域哈希、实际脚点、朝向、支撑面、目标接触片与法线、探头中心终点及形状版本，再把这份结果连同完整读取版本交给V2。若目标分片不可达，继续检查另一个分片；姿态成立与路线成立都由同一场景快照证明。挡板实际半宽由0.1变0.18米时，加上0.02米余量后的可见条件与40°朝向约束没有交集，两个分片均为空，技术门禁报告该槽无合法交互区域，不能退回使用原推荐点。

布局或体型配置变化时，目标区域、接触终点和扫掠都由新快照重算，形成新的验证尝试；V2继续归属B的快照。取消的中间报告与最终保留布局分别按后文“补偿中间状态与最终门禁”交接。

## 任务状态与产物

桌子的几何、通路和审核结果需要分别归档。J沿以下记录推进，后面的恢复协议处理其中任一步被中断的情况。

| 阶段 | 消费的记录 | 产生的记录 |
|---|---|---|
| 创建与移动A | 固定资产、场景读集和条件计划 | 宿主回执、实际对象与关系版本 |
| V1拒绝、移动B | V1失败位置及新的场景读集 | B回执、V2绑定的实际快照 |
| 视觉审核 | V2报告、同一快照的预览 | 批准记录或取消请求 |
| 发布 | 批准候选及完整不可变清单 | 入口代次与发布回执 |
| 取消 | 全部已接纳操作的终态 | 补偿链、冲突决议及残留清单 |

### 状态推进

任务从接收需求进入解析、规划、计划校验、执行、技术验证和视觉审核。每次转换记录前置条件、输入、输出和责任方。执行失败进入返工或失败状态，取消先停止派发新操作，等待已发工具返回终态或完成对账，再按登记补偿已应用的变更，最后进入取消终态；只有对应产物通过门禁，才能进入批准状态。

```text
Received -> Parsed -> Planned -> PlanValidated -> Executing
         -> TechnicalValidation -> VisualReview -> Approved
Approved -> Publishing -> Published
Any active stage -> Rework / Failed / Cancelling
Cancelling -> Cancelled / CompensationConflict
CompensationConflict -> Cancelling / CancelledWithRetainedObjects
```

这是流程状态定义。调度器将当前状态与输入输出ID持久化，模型上下文只用于重建推理所需的信息。若资产已经生成但状态记录丢失，恢复时通过操作ID与产物清单对账，而不是重新生成一份。

### 任务与产物记录

任务记录保存需求、目标平台、约束、工作流版本、工具权限、当前阶段、尝试次数、输入输出ID、验证结果和成本。产物记录保存稳定ID、内容哈希、来源与许可、派生关系、模型与工具版本、提示词、随机种子、编辑历史和发布状态。

这条派生链让维护者能回答“哪个输入产生了这个模型”“换一个依赖会影响哪些下游资产”。文件名相同而哈希不同，就是不同内容。人工调整形成新版本，并保存它相对上一生成版本的字段差异。重跑时以旧生成G0为共同基线，比较人工版本U与新生成G1：U未改的字段可用G1；只有U改的字段保留U；两者都改且值不同则进入冲突。对象删除与引用变化按稳定ID参与相同对照。比如人工移动了桌子，新计划也换了桌子尺寸，保留人工位置后还要重新检查净空，不能只把人工字段贴回去就认定新布局有效。

## 推理与工具接口

### 角色与数据契约

需求解析角色输出尺寸、风格、预算和格式，缺失与冲突单独记录。规划角色把需求分解成功能区、通道和约束；资产选择角色在批准目录内筛选候选；执行角色只应用已校验的目标布局。验证角色读取结果与既定规则，输出具体失败位置和返工建议。

每个角色声明输入、可调用工具、输出结构、判断标准和失败表达。输出先经过结构校验，再进入下一阶段。模型生成了合法JSON，只能说明字段可解析；资产是否存在、尺寸是否兼容、布局是否可达，仍由数据查询与规则检查决定。

提示词保存稳定职责和少量示例，当前资产通过检索返回有限候选。查询先按许可、平台、尺寸上限和格式等硬约束过滤，再把剩余条目的稳定ID、版本、尺寸、预算与预览交给模型排序。模型选中的ID必须属于该次结果集合，资产版本写入计划。没有满足硬约束的候选时报告缺失条件，不能生成一个目录中不存在的ID来让计划通过。

计划校验还检查父子引用无环、每个目标ID唯一、变换数值有限，以及每项操作所需权限。结构合法后才计算几何和预算；执行器只接受同一计划哈希，不允许模型在执行过程中无记录地换资产。这样每次决策都能对应到实际查询结果与被批准的计划。

### 工具参数与执行边界

```text
search_assets(query, constraints)
get_asset_metadata(asset_id)
spawn_asset(asset_id, transform, parent, operation_id)
move_asset(instance_id, transform, operation_id)
validate_scene(scene_id, ruleset)
render_preview(camera_id, preset)

```

这是接口示意。变换参数注明单位与坐标系，资产与场景使用稳定ID，修改操作带操作ID、计划哈希、读取集合和修改集合。返回值包含结果、实际变更的产物、错误码、警告与重试属性，便于调度器区分输入错误和暂时性故障。

规划器只读需求与目录，执行器写入任务专属暂存场景，验证器读取产物并写报告，发布器在批准条件满足后切换正式版本。路径与网络范围由执行层校验；外部文档、资产名和元数据始终作为数据处理，其中出现的命令不能改变工具权限。

### 调度职责

调度器负责状态转换、截止时间、取消、并发配额、持久化和人工审核。模型在需要语义判断的节点提出候选，确定的执行与门禁由代码推进。工具长期无响应时，调度器保留请求ID并查询状态，避免把超时误记为未执行。

## 操作登记与恢复对账

工具返回超时以后，调度器只知道没有收到结果，不知道场景是否已经写入。创建操作先生成稳定目标ID与操作ID，把期望变更写入任务记录；执行器检查目标ID是否存在，存在时核对内容版本，缺失时才创建。操作结果写入失败时，恢复过程据目标ID重新读取产物并补齐记录。

登记表保存`Prepared、Applied、Recorded`三种状态。Prepared先落盘；调用工具后，只有收到成功回执或读取到匹配的持久操作标记，才能记Applied；结果与产物清单写入同一登记事务后记Recorded。崩溃可能让表仍是Prepared而场景实际已应用，因此状态名本身不能证明副作用发生与否。恢复Prepared时先按操作ID查询宿主持久回执与接纳状态；已应用则补登记，仍在执行则等待或对账，确认未接纳才考虑派发。此时任务必须仍允许正向执行，并重新比较原读取、修改集合；条件已过期就记DependencyChanged并返工，取消中则终结未接纳项，禁止补发。Applied补写结果，Recorded直接返回原结果。工具若不支持稳定ID或查询，则需要隔离暂存场景，通过场景差异与清单对账；模型不能凭聊天里的“成功”替代这份证据。

场景对账完成后，产物清单进入技术验证；人工修改形成新哈希和新验证尝试。补偿按对象ID、操作标记和版本共同定位，只恢复仍属于该次操作的内容，发布步骤另按批准记录与发布代次仲裁。

## 工具执行的并发交接

“查询目标不存在，再创建”有两个执行者同时通过检查的竞争。每个暂存场景由一个串行执行器持有，调度器分配带代次的场景写入令牌；工具入口同时核对场景ID与令牌代次。接管在宿主入口关闭旧代次，把已接受的调用排空或判定其终态，再发新代次。入口的代次检查和写入入队在同一互斥区完成，检查通过的请求归属当时的串行队列；不能在检查后异步把请求交给一个不再核验代次的写线程。排空失败时保持接管未完成，停止旧宿主及其持有场景写权限的工具子进程，并确认它们已经终止、写入队列已关闭，再恢复宿主进程并重建场景快照；这些条件成立后才启用新执行器。无法确认旧调用终止时，使用新的隔离场景和独立写入口恢复任务，原场景保持隔离，旧结果不得进入新场景；不能仅靠进程重启请求已经发出就认定排空完成。仅给租约设超时而不在工具入口拒绝旧令牌，旧进程恢复后仍可能写场景。

### 创建操作与持久标记

在这个单写前提下，创建操作先登记`操作ID、确定的目标ID、资产版本、期望变换、场景代次`。稳定操作参数的摘要包含目标ID、资产版本、期望变换、计划哈希和读取/修改集合；场景写入令牌代次属于本次调用的授权封套，单独核对并记录，不进入稳定业务摘要。同一操作ID带不同业务参数直接报告冲突；参数一致时检查目标实例上保存的操作ID与版本，存在且匹配就返回该实例。接管后的执行器以新令牌重试原操作ID，先证明自己拥有当前写权限，再对账旧操作内容；若把旧场景代次也作为不可变业务参数，就会在接管时把合法恢复误判成异参。

确认原操作未接纳且目标不存在时，先检查完整读取、修改集合。创建在未挂接的对象上准备资产版本、变换与操作标记，再在宿主事务内复核条件，共同挂接完整对象、推进版本并保存操作回执，最后返回结果。宿主若不支持这种事务，就在隔离场景副本完成全部属性和标记，以完整场景快照作为提交单位，不能把多个可中断字段写入假装成一次原子创建。若创建后进程崩溃，接管者读取场景标记补齐记录；标记存在但内容已被人工修改，则进入冲突审核，不能覆盖人工版本。

没有可持久标记的宿主，先保存隔离场景快照和对象清单，再据快照差异对账，正式场景始终在批准后接收完整版本。

移动操作在同一串行入口登记目标ID、预期对象版本、绝对目标变换和原变换。宿主原子地写入目标变换、新版本与操作标记；恢复时若标记和目标状态匹配，就补登记并返回原结果，不能再叠加一次位移。若目标仍是登记的原版本且完整读取集合仍匹配，才执行这次变更；若已变成第三个版本，即使位置碰巧相同也进入冲突，避免覆盖人工编辑。宿主不能原子保存这些字段时，仍以隔离场景的完整快照提交。补偿的首步要求当前版本等于最后一次移动产出的版本；同一任务后续操作已经补偿时，使用下文的持久承接记录确定预期版本。每次恢复都生成新版本，外部写入造成的版本变化进入冲突。创建的稳定ID解决对象重复，移动的版本比较解决同一对象上的重复写与覆盖，两者共同支持完整布局重试。

## 失败恢复

### 幂等与重试

同一操作ID的重试返回已有结果或继续未完成操作。布局更新可以描述完整期望状态，执行器比较当前场景后只应用差异。生成目标ID、写场景和记录结果之间的空隙，按前述恢复对账处理。

输入验证失败进入修正流程；服务繁忙与短暂断连采用有限退避重试；容量不足交给调度器更换工作进程或采用批准的降级参数。模型、种子、分辨率或候选变化会形成新的变体ID，使原始请求与降级产物可区分。

重试策略记录次数上限、退避、抖动、可重试错误码和总截止时间。相同输入稳定触发工具缺陷时保存诊断，进入修复队列。重复请求不会改变确定性错误的根因。

### 生成服务与不确定结果

图像或模型生成可能在场景写入之前调用外部服务。请求登记同时保存提供方任务ID或提供方支持的幂等键，超时后先查询该任务；成功时把输出下载到任务的不可变产物目录，核对哈希后才进入导入。改变种子或降级模型形成新变体ID，原任务记录继续保留，便于取消迟到结果或回收费用与资源。

提供方若既不支持幂等键也不能查询，响应丢失后便无法判断它是否已经计算。此时登记为结果不确定，停止自动重复付费调用；可明确建立新尝试，但每次尝试各自记录成本，只有被选中的输出进入下游。稳定场景目标ID能避免重复放置资产，却不能让这种外部计算自动变成恰好一次。

### 补偿与版本恢复

创建暂存场景、放置资产、生成预览、导入验证和发布通常跨越多个工具。每步记录实际创建的ID与对应补偿：移除本操作创建的实例、释放临时资源或恢复发布指针。补偿也按操作ID幂等执行，且核对对象版本，避免删除后来被其他任务修改的内容。

每步成功后先保存实际结果与补偿参数，再派发依赖它的下一步。取消状态先置为Cancelling，使调度器停止新派发；对于已发请求逐项查询终态，迟到成功也登记到补偿列表。随后逆依赖顺序执行补偿，每项保存待补偿、已补偿或版本冲突。断电后继续相同列表，不能重新猜测哪些对象已经删除。

补偿操作也先登记独立的操作ID、原操作ID、预期当前版本和目标恢复状态。恢复变换与补偿标记在同一宿主提交中保存；响应丢失后先查询该标记，匹配便补记完成，不再用已经改变的对象版本判定冲突。删除则在场景清单保留带对象ID、原版本与补偿ID的墓碑；对象缺失而没有匹配墓碑时先对账，不能把任何一次删除都归为本次补偿成功。墓碑至少保留到任务恢复窗口结束，且所有可能重试的执行者已退出。

### 补偿中间状态与最终门禁

J的A布局挡住通路，B才把通路让开。取消先撤销B，必然再次经过A的布局，再撤销A和创建操作。如果每一步都要求通过正式布局的导航门禁，这条正常取消链会停在第一步。任务因此分别记录宿主硬约束、补偿中间检查和发布门禁，规则集明确每条规则属于哪一类。

宿主硬约束保护每次提交都必须成立的条件：对象身份及版本匹配、授权有效、变换有限且可表示、父子关系无环、引用有目标，以及宿主资源容量上限。违反这些条件时整步拒绝，保持原场景，进入补偿冲突或明确的容量故障。布局通路、家具穿插、艺术净空与目标渲染预算属于最终布局门禁；其未通过的中间结果记录具体失败项，留给后续补偿继续消除。

这种中间态在任务专属暂存场景内执行。进入Cancelling时，宿主在同一许可入口关闭该场景的正向业务写入、运行模拟、普通预览交付和发布许可，保存补偿会话ID、起始快照及补偿列表；已接纳消费者先退出或固定自己的不可变快照，再开放补偿写入。维护预览明确读取Compensating快照与失败项，正式消费者继续读取原已发布版本。宿主只接受补偿列表或审核决议授权的操作；Cancelling允许这些操作通过，普通规划命令仍被拒绝。人工工具的编辑仍走版本入口，并使受影响的补偿条件失配。

每一步先在当前不可变快照上计算候选，检查硬约束，同时产生布局诊断；只有硬约束通过才条件提交。导航诊断绑定候选几何哈希，尚无匹配导航数据时记Pending，不借用旧导航宣称可达。匹配数据就绪后按该候选重新绑定交互支撑层、投影站位并检查姿态与路线；诊断只归属这份候选，下一补偿已改变场景时只能补齐历史记录。中间诊断的Pending或失败均不授权发布，也不阻止逆序清理。硬约束规则、诊断规则和快照读取版本都写入补偿尝试。补偿会话与当前隔离状态由宿主耐久保存，重启先恢复它们再开放入口。

没有外部编辑时，撤销B恢复A的局部布局并产生v4，通路失败随回执记录；执行器继续撤销A产生v5，再删除T、删除空房间R，按墓碑确认所有任务对象已清理，进入Cancelled。场景为空时验收对象与关系清单为空，不对已删除座位继续查询通路。若人工编辑造成冲突，就保留隔离与当前游标，按后文决议续行。

含Retained或Waived的结果先形成完整残留清单。J的在途操作全部结清后，维护方创建接管任务JR，引用该清单与不可变残留快照；宿主关闭J的补偿写入权限，按场景令牌交接规则授予JR维护权限。J保持取消终态，JR承担后续修复、审核与发布。

JR建立验证尝试VR1，绑定最终残留快照哈希、读取集合、角色与规则版本。VR1重新生成站位区域、目标表面接触及完整路线；补偿中间候选的迟到结果只补原尝试，原V2也保持历史归属。后续人工修改产生新哈希时，让VR1失效并建立VR2，审核消费被当前快照接纳的那一次完整报告。

未通过或导航仍Pending时，原任务J仍报告CancelledWithRetainedObjects，但残留资产继续由维护方接管，场景保持隔离并返回门禁结果；清理终态不代表可运行或可发布。门禁通过后形成绑定VR1或其后继验证身份、最终快照与报告哈希的新审核候选，JR的批准记录引用该候选，按批准与发布事务交付。已发布任务的取消先按撤回协议处理正式入口，暂存补偿不会直接改写消费者正在使用的不可变版本。

### 补偿坐标与父变换

任务的变换记录采用父局部空间。每项保存父ID与关系代次、输入局部矩阵、输出局部矩阵，以及计算时读取的祖先变换版本。执行接口需要世界矩阵时，宿主用同一快照的父世界矩阵P计算W=P×L；回执同时保存实际局部矩阵L与用于换算的P版本。位置使用米，矩阵乘法与引擎约定一致。父矩阵不可逆时拒绝需要世界到局部换算的操作，保持对象不变。

取消恢复的是本任务修改的局部字段。设R最初位于世界X=0，A将T局部X从0移到1，B从1移到2；人工再将R移到世界X=10，T自身版本仍为v3。撤销B的候选局部X为1，按当前R计算世界X=11。原世界X=1不是这次局部恢复的目标，写回它会把人工移动父对象的结果抵消。

父变换变化使原导航与净空结论失效。补偿器先取得新快照，构造候选局部恢复，按当前祖先和区域对象集合验证硬约束，并用匹配的导航版本生成布局诊断；导航未就绪记Pending。补偿读取集来自这次计算；原读取集保留为历史依据，不能直接替换其版本后沿用旧世界目标。宿主共同比较新读集、T的承接版本v3、父ID和关系代次，再提交局部X=1、新对象版本及补偿回执。

人工在检查后再次移动R时，提交返回DependencyChanged，场景不写入；调度器消费本次拒绝回执，重读并重算。

补偿链槽位保持不变，每次改变读取集合或目标都登记新的补偿尝试ID，载荷及摘要在该尝试内固定；响应未知时先查原尝试，只有确定拒绝或未接纳且已经关闭原提交权限，才建立下一尝试。原T版本已被外部修改则进入补偿冲突。

候选局部恢复违反宿主硬约束时进入CompensationConflict，报告规则与实际值；碰撞、净空和通路的中间诊断随补偿记录保存，按前述隔离规则继续清理。审核可保留当前局部状态，或批准绑定当前快照的明确局部目标；宿主仍比较全部依赖。人工重挂父对象改变关系代次，自动恢复停在冲突，审核须明确选择保留新父关系还是恢复旧关系。本文的正向布局写入也归一为这份局部契约，世界目标只作为宿主调用的派生值。

补偿回执保存空间、父关系、新读集、输入输出局部矩阵与版本。宿主已经恢复到世界X=11但响应丢失时，接管者先消费原回执承接游标；即使R随后移到20，也不会再次执行补偿把T拉回11。再次恢复仍读取同一补偿ID，后续撤销A则以最新快照独立计算局部X=0对应的世界目标。

### 连续移动的补偿承接

桌子最初处于版本v1。操作A把它移到靠墙位置，产生v2；操作B为通道再调整一次，产生v3。取消时先撤销B，把变换恢复到A完成后的值，但对象版本继续增加为v4。撤销A接下来必须检查v4；v2记录的是历史内容，不能当作此时的并发控制版本。

任务为每个对象保存正向操作链和补偿游标。链中每项包含前驱操作、输入版本、输出版本、修改字段及其原值；同一对象的正向写入按这条链串行完成。取消排空在途请求后，游标指向末项B，预期版本为v3。宿主在一次提交中比较v3，恢复B的原值，并保存补偿ID、输入v3、输出v4、下一待补偿项A和恢复内容摘要。该回执证明v4来自本任务撤销B，而非另一位编辑者。

调度器据持久回执把游标推进到A，预期版本设为v4。撤销A仍使用A登记的原变换，生成v5，再以相同方式推进。字段恢复之外的对象内容保持当前值；每一步检查整个对象版本，因而外部修改任何受版本管理的字段都会中止自动补偿。若人工在v4之后写出v5，撤销A以v4作条件比较便失败，即使人工恰好把桌子放回相同位置，也不会被误认为任务自身的恢复。

宿主提交成功而游标尚未更新就崩溃时，恢复先按补偿ID读取回执，再推进游标；游标更新和回执消费标记在登记数据库同一事务中完成。宿主侧回执随对象变化原子保存，不能仅由调度器在收到响应后补写。宿主不支持字段事务时，对象、版本与回执共同进入隔离场景快照提交。恢复者核对回执链的对象ID、任务ID和前驱补偿ID，只接受这条连续链上的输出版本，不能接受“来自同一任务”的任意版本。

创建操作也参与同一条链：家具的后续移动全部撤销后，创建补偿使用游标承接的最新版本删除家具，并保留删除墓碑。子对象存在冲突时，父对象的删除依赖尚未满足，任务停在CompensationConflict。

### 父子关系与跨对象版本

桌子挂入房间同时改变两份数据：T的父引用和R的子对象集合。本文把对象字段与关系分别版本化；对象版本保护变换、资产引用等字段，关系记录`(关系ID, 父ID, 子ID, 关系代次)`保护挂接，父对象另有单调递增的关系集合版本。创建桌子的一次宿主提交共同写入T、关系、R的新集合版本及操作回执；删除则共同写墓碑、删除关系、递增R的集合版本。跨房间移动也在同一提交中修改两边集合和T父引用。宿主以完整场景快照提交时，这些记录同属一个快照。

J创建R时得到对象版本r1、集合版本c0，挂入T后为c1。取消删除T得到c2；删除R接纳c2，需要删除T的持久回执证明c1到c2的变化属于当前补偿链。R自己的字段仍比较r1。任务维护每个受影响对象和关系集合的承接游标，一次跨对象回执列出全部输入、输出版本，调度器在同一登记事务中推进全部游标；不能只推进T而遗漏R。删除R还检查当前集合确实为空，集合版本匹配与空集合两个条件都成立才删除。

人工向R加入椅子会产生c3；即使J的桌子已删除，删除R比较c2仍失败。人工新增后又删除椅子会得到c4，集合虽空也不能跳过版本冲突。反过来，人工只改桌子的颜色会改变T对象版本，使删除T停止，关系继续存在，删除R的依赖保持阻塞。这样任务自身的清理可承接，外部改动仍留下明确冲突。

### 冲突决议与续行

冲突记录保存待补偿项、预期与实际版本、实际字段差异、受阻后继和场景快照哈希。任务停止这条依赖链，独立且无共享写集合的补偿可以继续；取消入口仍关闭新业务派发。审核决议拥有稳定决议ID，绑定冲突记录代次、观察到的全部对象与关系版本，以及明确的恢复目标。决议的接纳、游标变更和依赖状态共同持久化；审核期间对象再变化，条件比较失败，产生新一轮冲突。

| 决议 | 宿主与登记动作 | 后继处理 |
|---|---|---|
| 保留人工结果 | 比较观察版本，保存保留对象与关系的回执，将该对象剩余补偿项置为Retained | 删除依赖这些对象的父对象同样置为Retained，保留关系闭包；其他独立项继续 |
| 批准恢复 | 比较观察版本，把审核批准的完整目标字段作为新的补偿操作执行，回执记录决议ID与新版本 | 以新回执承接游标，继续审核指定的剩余补偿项；再次冲突就停止 |
| 放弃本项补偿 | 明确把当前实际状态列为残留并置为Waived，保存责任人与原因 | 默认把同对象剩余补偿置为Retained，并向父关系传播保留闭包；只有审核逐项绑定剩余补偿及恢复目标才允许继续，不能当作已经删除 |

例如撤销B产生v4后，人工改色生成v5，撤销A冲突。批准恢复可以只恢复A的原位置而保留v5颜色：审核目标明确列出这两项，宿主比较v5后产生v6。接下来删除T仍会删除人工颜色，所以批准恢复必须同时逐项批准“继续删除T”，或者把创建补偿标为Retained；批准一次移动不隐含批准删除。选择保留T时，A与创建T的补偿转Retained，R及其挂接关系随之保留，其他临时预览仍可删除。

若在撤销B发生冲突时选择放弃B，默认保持T的实际状态：B为Waived，A和创建T为Retained，R也进入保留闭包。调度器不能仅跳过B再撤销A或删除T；这会绕过“当前状态列为残留”的决议。需要继续A时，审核决议必须列出A和后续创建补偿各自的目标及保留/删除选择，宿主仍按观察版本和决议ID条件提交。

宿主已执行决议而调度器崩溃时，以决议ID查询回执，补齐游标与依赖标记；不存在匹配回执才比较观察版本并执行。重复审核提交返回原决议，新的决议只能针对尚未结清的冲突代次。全部在途请求已对账、所有补偿项为Compensated时进入Cancelled；含Retained或Waived则进入CancelledWithRetainedObjects，并输出对象、关系及责任清单。存在未决冲突始终保持CompensationConflict。取消结果的消费者据终态决定释放任务配额，并据残留清单接管保留资产，不能把“取消完成”解释成空场景。

## 资产验收与发布

B完成后，V2读取B回执对应的不可变场景快照。技术门禁检查文件、依赖、坐标、单位、枢轴、网格、材质、纹理、LOD和碰撞，再检查目标平台内存、绘制、着色器与加载预算。DCC导入、引擎构建和实际运行分别保存结果；规则集有独立版本，例外由规定的审核者批准。

### 审核与不可变候选

V2通过后，视觉审核同时显示需求、固定相机预览、来源、工具版本、技术报告和不确定项。确定性验证负责可测规则，模型评分可辅助语义分类，关键视觉方向和正式发布按项目审核权限确认。

### 批准记录与发布回执

批准记录绑定`任务ID、验证尝试ID、报告哈希、产物清单哈希、输入哈希、规则版本、审核版本`。发布前将全部产物写入不可变存储并从发布环境核对依赖可读取，正式入口只保存这份清单的引用。如此发布后不需要再逐个修改活动场景对象；客户端读取入口后加载完整场景版本，加载失败保留原版本并返回失败，避免显示一半新布局。

控制数据库在一个事务中检查：任务仍允许发布、批准记录仍有效且版本匹配、正式入口代次等于计划的expectedGeneration。成功时共同写入新入口、新代次和以操作ID为键的发布回执。批准撤销也更新同一数据库记录；若撤销先提交，发布比较失败；若发布先提交，撤销随后触发明确的撤回操作。仅在进程里先查批准、过一会儿再更新指针，会漏掉这段并发窗口。

发布调用超时后按操作ID查询回执，有回执就返回当时的新代次，不再次覆盖入口。没有回执时重新检查全部条件再尝试。取消若与发布并发，由该事务中的任务状态判定先后：取消先登记则发布失败；发布已完成则按撤回流程条件更新入口。撤回只在入口仍是本任务发布的代次时恢复旧内容，并产生更高的新代次；若后续任务已发布，保留其结果并报告冲突。这样即使入口内容发生往返，旧操作也不能因哈希碰巧相同而覆盖新版本。

例如任务发布代次11后结果响应丢失，人工又发布12。恢复根据回执确认11成功，既不重放到13，也不把12撤回到10。批准、发布、取消和恢复都围绕同一份持久回执判断，任务日志则保存这些结果供追踪。

日志保存每次工具调用、状态变化、重试、补偿和批准记录。密钥与个人信息在写日志前脱敏；完整提示词和私有输入保存在对应访问范围内。

评估使用固定历史任务与失败集，同时记录检索准确率、布局通过率、人工返工率、工具恢复成功率、预算漏检、平均成本及人工修改保留率。生成数量增加而正式通过率下降，意味着系统把成本转移给了人工审核。
