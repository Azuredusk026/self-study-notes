# Agent资产管线

一张餐桌放进房间后，几何检查通过了，入口到座位的通道却被挡住。规划器把桌子移开，视觉审核又要求取消这次布局。此时系统既要恢复任务自己的修改，也要保留期间发生的人工编辑；工具超时或进程中断还可能让执行结果暂时未知。

模型从需求中找出候选资产，工具把资产写入场景，验证器判断结果是否符合要求。三者处理不同的信息：模型处理语义与候选，工具执行明确的状态变化，验证器读取实际产物。任务记录连接这些步骤，中断以后据此恢复。

## 室内场景的结构化规划

```text
Room { zones, anchors, pathways, placements, lightingIntent, constraints }
Placement { assetId, transform, parentId, operationId }
```

先确定房间功能区和通道净空，再查询尺寸合适的资产，最后求解位置与朝向。验证器用包围体或精确碰撞检查穿插，用导航数据检查可达性，再检查门窗净空、墙地锚点、功能距离与渲染预算。模型读取失败位置和原因，重新提出有限候选。

例如餐桌摆放满足几何不相交，却挡住门到座位的通路，碰撞检查可以通过，导航检查仍应拒绝。把两项规则分别记录，才能让返工针对通道，而不是反复缩小所有家具。

### 规划的数值约束

假设房间内可通行矩形为4米乘3米，入口沿宽度方向需保留1米净空。候选桌子宽1.6米，若中心距左墙0.5米，半宽0.8米会越墙0.3米，布局校验先拒绝；中心移到1米后包围盒合法，仍须检查门到座位路径。规划输出使用米和房间局部坐标，执行器再用房间世界变换生成实例，避免厘米资产和米场景混用。

生成计划到执行之间目录也可能更新。任务应保存选中资产的版本哈希，执行前重新核对；尺寸变化后继续使用旧布局，即使JSON完全合法也会穿插。操作完成后读取真实实例变换和碰撞结果作为验证输入，不能验证模型原先写下的计划来代替实际场景。

规划到执行还需要确定几何单位。资产尺寸元数据先转换为米；实例的局部朝向与缩放将其包围体送到房间局部坐标，房间世界变换只在最后施加一次。候选家具的占地区域按角色半径向外膨胀，房间边界则向内收缩相同半径，得到角色中心可行域。旋转家具使用变换后的占地多边形，轴对齐包围盒可作保守快速拒绝；门还要保留开合扫过的区域，不能只检查门关闭时的薄片。

将可行域离散到网格时，只有整个格子都处于可行域才标为可走，邻格连接也检查连线和拐角余量。以入口处的有效格为起点作连通查询，目标使用座位前方的交互点，不能把桌椅中心放在障碍内部再要求可达。间隙宽度小于角色直径时膨胀后的障碍连在一起，路径自然断开；格子过粗造成的保守误拒绝通过减小格长或精确导航验证处理。网格与走廊计算见[[20_游戏AI/游戏AI导航]]。碰撞校验与导航校验读取执行器回读的实际变换；模型计划只作为期望值，实际实例和计划不一致也产生具体失败项。

返工有固定终止规则：每次报告保存失败规则ID、位置、相关对象与实际值，规划器每轮只提交有限候选；同一规则在相同资产集合和输入版本下连续3轮未改善则停止自动返工，进入人工审核或失败队列。技术通过只推进到视觉审核，发布前再次核对产物哈希和批准版本，不能把工具执行成功当作任务批准。

## 任务状态与产物

### 状态推进

任务从接收需求进入解析、规划、计划校验、执行、技术验证和视觉审核。每次转换记录前置条件、输入、输出和责任方。执行失败进入返工或失败状态，取消先停止派发新操作，等待已发工具返回终态或完成对账，再按登记补偿已应用的变更，最后进入取消终态；只有对应产物通过门禁，才能进入批准状态。

```text
Received -> Parsed -> Planned -> PlanValidated -> Executing
         -> TechnicalValidation -> VisualReview -> Approved
Approved -> Publishing -> Published
Any active stage -> Rework / Failed / Cancelling
Cancelling -> Cancelled / CompensationConflict
```

这是流程状态定义。调度器将当前状态与输入输出ID持久化，模型上下文只用于重建推理所需的信息。若资产已经生成但状态记录丢失，恢复时通过操作ID与产物清单对账，而不是重新生成一份。

### 任务与产物记录

任务记录保存需求、目标平台、约束、工作流版本、工具权限、当前阶段、尝试次数、输入输出ID、验证结果和成本。产物记录保存稳定ID、内容哈希、来源与许可、派生关系、模型与工具版本、提示词、随机种子、编辑历史和发布状态。

这条派生链让维护者能回答“哪个输入产生了这个模型”“换一个依赖会影响哪些下游资产”。文件名相同而哈希不同，就是不同内容。人工调整形成新版本，并保存它相对上一生成版本的字段差异。重跑时以旧生成G0为共同基线，比较人工版本U与新生成G1：U未改的字段可用G1；只有U改的字段保留U；两者都改且值不同则进入冲突。对象删除与引用变化按稳定ID参与相同对照。比如人工移动了桌子，新计划也换了桌子尺寸，保留人工位置后还要重新检查净空，不能只把人工字段贴回去就认定新布局有效。

## 推理与工具接口

### 角色与数据契约

需求解析角色输出尺寸、风格、预算和格式，缺失与冲突单独记录。规划角色把需求分解成功能区、通道和约束；资产选择角色在批准目录内筛选候选；执行角色只应用已校验的目标布局。验证角色读取结果与既定规则，输出具体失败位置和返工建议。

每个角色声明输入、可调用工具、输出结构、判断标准和失败表达。输出先经过结构校验，再进入下一阶段。模型生成了合法JSON，只能说明字段可解析；资产是否存在、尺寸是否兼容、布局是否可达，仍由数据查询与规则检查决定。

提示词保存稳定职责和少量示例，当前资产通过检索返回有限候选。查询先按许可、平台、尺寸上限和格式等硬约束过滤，再把剩余条目的稳定ID、版本、尺寸、预算与预览交给模型排序。模型选中的ID必须属于该次结果集合，资产版本写入计划。没有满足硬约束的候选时报告缺失条件，不能生成一个目录中不存在的ID来让计划通过。

计划校验还检查父子引用无环、每个目标ID唯一、变换数值有限，以及每项操作所需权限。结构合法后才计算几何和预算；执行器只接受同一计划哈希，不允许模型在执行过程中无记录地换资产。这样每次决策都能对应到实际查询结果与被批准的计划。

### 工具参数与执行边界

```text
search_assets(query, constraints)
get_asset_metadata(asset_id)
spawn_asset(asset_id, transform, parent, operation_id)
move_asset(instance_id, transform, operation_id)
validate_scene(scene_id, ruleset)
render_preview(camera_id, preset)
publish_staging(job_id, expected_hash)
```

这是接口示意。变换参数注明单位与坐标系，资产与场景使用稳定ID，修改操作带操作ID。返回值包含结果、实际变更的产物、错误码、警告与重试属性，便于调度器区分输入错误和暂时性故障。

规划器只读需求与目录，执行器写入任务专属暂存场景，验证器读取产物并写报告，发布器在批准条件满足后切换正式版本。路径与网络范围由执行层校验；外部文档、资产名和元数据始终作为数据处理，其中出现的命令不能改变工具权限。

### 调度职责

调度器负责状态转换、截止时间、取消、并发配额、持久化和人工审核。模型在需要语义判断的节点提出候选，确定的执行与门禁由代码推进。工具长期无响应时，调度器保留请求ID并查询状态，避免把超时误记为未执行。

## 操作登记与恢复对账

工具返回超时以后，调度器只知道没有收到结果，不知道场景是否已经写入。创建操作先生成稳定目标ID与操作ID，把期望变更写入任务记录；执行器检查目标ID是否存在，存在时核对内容版本，缺失时才创建。操作结果写入失败时，恢复过程据目标ID重新读取产物并补齐记录。

登记表保存`Prepared、Applied、Recorded`三种状态。Prepared先落盘；调用工具后，只有收到成功回执或读取到匹配的持久操作标记，才能记Applied；结果与产物清单写入同一登记事务后记Recorded。崩溃可能让表仍是Prepared而场景实际已应用，因此状态名本身不能证明副作用发生与否。恢复Prepared时先按目标ID查询宿主，存在且业务摘要匹配就补登记，确实不存在才执行；Applied补写结果，Recorded直接返回原结果。工具若不支持稳定ID或查询，则需要隔离暂存场景，通过场景差异与清单对账；模型不能凭聊天里的“成功”替代这份证据。

场景对账完成后，产物清单进入技术验证；人工修改形成新哈希和新验证尝试。补偿按对象ID、操作标记和版本共同定位，只恢复仍属于该次操作的内容，发布步骤另按批准记录与发布代次仲裁。

## 工具执行的并发交接

“查询目标不存在，再创建”有两个执行者同时通过检查的竞争。每个暂存场景由一个串行执行器持有，调度器分配带代次的场景写入令牌；工具入口同时核对场景ID与令牌代次。接管在宿主入口关闭旧代次，把已接受的调用排空或判定其终态，再发新代次。入口的代次检查和写入入队在同一互斥区完成，检查通过的请求归属当时的串行队列；不能在检查后异步把请求交给一个不再核验代次的写线程。排空失败时保持接管未完成，停止旧宿主及其持有场景写权限的工具子进程，并确认它们已经终止、写入队列已关闭，再恢复宿主进程并重建场景快照；这些条件成立后才启用新执行器。无法确认旧调用终止时，使用新的隔离场景和独立写入口恢复任务，原场景保持隔离，旧结果不得进入新场景；不能仅靠进程重启请求已经发出就认定排空完成。仅给租约设超时而不在工具入口拒绝旧令牌，旧进程恢复后仍可能写场景。

### 创建操作与持久标记

在这个单写前提下，创建操作先登记`操作ID、确定的目标ID、资产版本、期望变换、场景代次`。稳定操作参数的摘要只包含目标ID、资产版本、期望变换等业务内容；场景写入令牌代次属于本次调用的授权封套，单独核对并记录，不进入稳定业务摘要。同一操作ID带不同业务参数直接报告冲突；参数一致时检查目标实例上保存的操作ID与版本，存在且匹配就返回该实例。接管后的执行器以新令牌重试原操作ID，先证明自己拥有当前写权限，再对账旧操作内容；若把旧场景代次也作为不可变业务参数，就会在接管时把合法恢复误判成异参。

目标不存在才创建：先在未挂接的对象上设置资产版本、变换与操作标记，再在宿主事务中将完整对象挂入场景并保存，最后写返回记录。宿主若不支持这种事务，就在隔离场景副本完成全部属性和标记，以完整场景快照作为提交单位，不能把多个可中断字段写入假装成一次原子创建。若创建后进程崩溃，接管者读取场景标记补齐记录；标记存在但内容已被人工修改，则进入冲突审核，不能覆盖人工版本。

没有可持久标记的宿主，先保存隔离场景快照和对象清单，再据快照差异对账，正式场景始终在批准后接收完整版本。

移动操作在同一串行入口登记目标ID、预期对象版本、绝对目标变换和原变换。宿主原子地写入目标变换、新版本与操作标记；恢复时若标记和目标状态匹配，就补登记并返回原结果，不能再叠加一次位移。若目标仍是登记的原版本，则执行这次变更；若已变成第三个版本，即使位置碰巧相同也进入冲突，避免覆盖人工编辑。宿主不能原子保存这些字段时，仍以隔离场景的完整快照提交。补偿的首步要求当前版本等于最后一次移动产出的版本；同一任务后续操作已经补偿时，使用下文的持久承接记录确定预期版本。每次恢复都生成新版本，外部写入造成的版本变化进入冲突。创建的稳定ID解决对象重复，移动的版本比较解决同一对象上的重复写与覆盖，两者共同支持完整布局重试。

## 失败恢复

### 幂等与重试

同一操作ID的重试返回已有结果或继续未完成操作。布局更新可以描述完整期望状态，执行器比较当前场景后只应用差异。生成目标ID、写场景和记录结果之间的空隙，按前述恢复对账处理。

输入验证失败进入修正流程；服务繁忙与短暂断连采用有限退避重试；容量不足交给调度器更换工作进程或采用批准的降级参数。模型、种子、分辨率或候选变化会形成新的变体ID，使原始请求与降级产物可区分。

重试策略记录次数上限、退避、抖动、可重试错误码和总截止时间。相同输入稳定触发工具缺陷时保存诊断，进入修复队列。重复请求不会改变确定性错误的根因。

### 生成服务与不确定结果

图像或模型生成可能在场景写入之前调用外部服务。请求登记同时保存提供方任务ID或提供方支持的幂等键，超时后先查询该任务；成功时把输出下载到任务的不可变产物目录，核对哈希后才进入导入。改变种子或降级模型形成新变体ID，原任务记录继续保留，便于取消迟到结果或回收费用与资源。

提供方若既不支持幂等键也不能查询，响应丢失后便无法判断它是否已经计算。此时登记为结果不确定，停止自动重复付费调用；可明确建立新尝试，但每次尝试各自记录成本，只有被选中的输出进入下游。稳定场景目标ID能避免重复放置资产，却不能让这种外部计算自动变成恰好一次。

### 补偿与版本恢复

创建暂存场景、放置资产、生成预览、导入验证和发布通常跨越多个工具。每步记录实际创建的ID与对应补偿：移除本操作创建的实例、释放临时资源或恢复发布指针。补偿也按操作ID幂等执行，且核对对象版本，避免删除后来被其他任务修改的内容。

每步成功后先保存实际结果与补偿参数，再派发依赖它的下一步。取消状态先置为Cancelling，使调度器停止新派发；对于已发请求逐项查询终态，迟到成功也登记到补偿列表。随后逆依赖顺序执行补偿，每项保存待补偿、已补偿或版本冲突。断电后继续相同列表，不能重新猜测哪些对象已经删除。

补偿操作也先登记独立的操作ID、原操作ID、预期当前版本和目标恢复状态。恢复变换与补偿标记在同一宿主提交中保存；响应丢失后先查询该标记，匹配便补记完成，不再用已经改变的对象版本判定冲突。删除则在场景清单保留带对象ID、原版本与补偿ID的墓碑；对象缺失而没有匹配墓碑时先对账，不能把任何一次删除都归为本次补偿成功。墓碑至少保留到任务恢复窗口结束，且所有可能重试的执行者已退出。

### 连续移动的补偿承接

桌子最初处于版本v1。操作A把它移到靠墙位置，产生v2；操作B为通道再调整一次，产生v3。取消时先撤销B，把变换恢复到A完成后的值，但对象版本继续增加为v4。撤销A接下来必须检查v4；v2记录的是历史内容，不能当作此时的并发控制版本。

任务为每个对象保存正向操作链和补偿游标。链中每项包含前驱操作、输入版本、输出版本、修改字段及其原值；同一对象的正向写入按这条链串行完成。取消排空在途请求后，游标指向末项B，预期版本为v3。宿主在一次提交中比较v3，恢复B的原值，并保存补偿ID、输入v3、输出v4、下一待补偿项A和恢复内容摘要。该回执证明v4来自本任务撤销B，而非另一位编辑者。

调度器据持久回执把游标推进到A，预期版本设为v4。撤销A仍使用A登记的原变换，生成v5，再以相同方式推进。字段恢复之外的对象内容保持当前值；每一步检查整个对象版本，因而外部修改任何受版本管理的字段都会中止自动补偿。若人工在v4之后写出v5，撤销A以v4作条件比较便失败，即使人工恰好把桌子放回相同位置，也不会被误认为任务自身的恢复。

宿主提交成功而游标尚未更新就崩溃时，恢复先按补偿ID读取回执，再推进游标；游标更新和回执消费标记在登记数据库同一事务中完成。宿主侧回执随对象变化原子保存，不能仅由调度器在收到响应后补写。宿主不支持字段事务时，对象、版本与回执共同进入隔离场景快照提交。恢复者核对回执链的对象ID、任务ID和前驱补偿ID，只接受这条连续链上的输出版本，不能接受“来自同一任务”的任意版本。

创建操作也参与同一条链：家具的后续移动全部撤销后，创建补偿使用游标承接的最新版本删除家具，并保留删除墓碑。子对象存在冲突时，父对象的删除依赖尚未满足，任务停在CompensationConflict。这样取消既有确定的执行顺序，也能在任意一步中断后继续。

例如先创建房间，再创建其中的家具，取消时先删除仍匹配本次版本的家具，再删除房间。家具已被人工修改则保留并报告冲突，房间也不能自动删除。只有所有在途请求终态已知、所需补偿已完成，任务才进入Cancelled；仍有冲突时停在待处理状态。源文件以新版本保存，历史提供可恢复字节，操作登记提供确切的恢复范围。

## 资产验收与发布

技术门禁检查文件、依赖、坐标、单位、枢轴、网格、材质、纹理、LOD和碰撞，再检查目标平台内存、绘制、着色器与加载预算。DCC导入、引擎构建和实际运行分别保存结果；规则集有独立版本，例外由规定的审核者批准。

### 审核与不可变候选

视觉审核同时显示需求、固定相机预览、来源、工具版本、技术报告和不确定项。确定性验证负责可测规则，模型评分可辅助语义分类，关键视觉方向和正式发布按项目审核权限确认。

### 批准记录与发布回执

批准记录绑定`任务ID、产物清单哈希、输入哈希、规则版本、审核版本`。发布前将全部产物写入不可变存储并从发布环境核对依赖可读取，正式入口只保存这份清单的引用。如此发布后不需要再逐个修改活动场景对象；客户端读取入口后加载完整场景版本，加载失败保留原版本并返回失败，避免显示一半新布局。

控制数据库在一个事务中检查：任务仍允许发布、批准记录仍有效且版本匹配、正式入口代次等于计划的expectedGeneration。成功时共同写入新入口、新代次和以操作ID为键的发布回执。批准撤销也更新同一数据库记录；若撤销先提交，发布比较失败；若发布先提交，撤销随后触发明确的撤回操作。仅在进程里先查批准、过一会儿再更新指针，会漏掉这段并发窗口。

发布调用超时后按操作ID查询回执，有回执就返回当时的新代次，不再次覆盖入口。没有回执时重新检查全部条件再尝试。取消若与发布并发，由该事务中的任务状态判定先后：取消先登记则发布失败；发布已完成则按撤回流程条件更新入口。撤回只在入口仍是本任务发布的代次时恢复旧内容，并产生更高的新代次；若后续任务已发布，保留其结果并报告冲突。这样即使入口内容发生往返，旧操作也不能因哈希碰巧相同而覆盖新版本。

例如任务发布代次11后结果响应丢失，人工又发布12。恢复根据回执确认11成功，既不重放到13，也不把12撤回到10。批准、发布、取消和恢复都围绕同一份持久回执判断，任务日志则保存这些结果供追踪。

日志保存每次工具调用、状态变化、重试、补偿和批准记录。密钥与个人信息在写日志前脱敏；完整提示词和私有输入保存在对应访问范围内。

评估使用固定历史任务与失败集，同时记录检索准确率、布局通过率、人工返工率、工具恢复成功率、预算漏检、平均成本及人工修改保留率。生成数量增加而正式通过率下降，意味着系统把成本转移给了人工审核。
