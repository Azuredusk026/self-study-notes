# 资源打包、依赖与异步加载

资源分包的核心不是按文件格式分类，而是管理依赖、生命周期、更新边界、IO 粒度和内存释放。

## 资源依赖图

Prefab 可能依赖 Mesh、Material、Texture、Animation 和其他 Prefab。打包系统需要把它们变成有向依赖图。

加载一个入口资源时，系统必须先保证依赖可用。卸载时，也要确认没有其他资源继续引用共享依赖。

## 为什么按格式分包通常不够

把所有 Texture 放一个包、所有 Prefab 放一个包，会产生：

- 一个场景只用少量纹理，却要下载或挂载很大的纹理包；
- 更新一张纹理导致整个公共包版本变化；
- 生命周期不同的资源被绑在一起；
- 无法按玩法、关卡和 DLC 独立更新。

格式可以作为构建规则的一部分，但更重要的是：

- 同时使用和卸载；
- 更新频率；
- 下载优先级；
- 共享范围；
- 包大小和文件数量；
- 是否常驻。

## 共享依赖

假设场景 A、B 都引用纹理 T。

### 错误情况

如果 A 和 B 分别把依赖自动内嵌，T 可能在两个 Bundle 中各存一份。安装包、下载和内存都可能重复。

### 公共 Bundle

把 T 放到 Shared Bundle，A/B 只记录依赖。加载场景前先加载 Shared。

代价是 Shared 更新会影响依赖版本，包过大也会变成新的耦合点。共享包应按稳定依赖组划分，不是把所有公共资源放一个超级包。

## Unity AssetBundle

AssetBundle 保存平台相关的序列化资源。构建会生成 Bundle 和依赖 Manifest/Hash。

需要区分：

- 加载 Bundle 文件；
- 从 Bundle 反序列化 Asset；
- 实例化 GameObject；
- 释放 Asset 引用；
- 卸载 Bundle 容器。

这些步骤的 CPU、IO 和内存成本不同。

`Unload(false)` 与 `Unload(true)` 的具体行为和风险需要按 Unity 版本核对。不能在仍有实例引用时粗暴卸载底层资源。

## Addressables 和 YooAsset

它们在 AssetBundle 上提供更高层能力：

- Address/Label；
- 依赖解析；
- Catalog/Manifest；
- 下载、缓存和版本；
- 引用计数或 Handle；
- 异步 API；
- Editor 模拟和构建分析。

框架减少重复实现，不会自动替你设计正确分组。错误的 Group、Label 和生命周期仍会造成重复和泄漏。

## 异步加载阶段

“异步”可能只覆盖部分过程：

1. 网络下载；
2. 磁盘读取；
3. 解压；
4. 反序列化；
5. GPU Upload；
6. 主线程对象创建和激活；
7. Shader/PSO 首次使用。

文件读取在后台完成，不代表实例化和 GPU Upload 没有主线程尖峰。

## 预加载和时间窗口

把下一关资源在结算界面后台加载，是把成本移动到用户不敏感的时间窗口。仍要控制：

- 同时 IO 数量；
- 下载和解压带宽；
- 峰值内存；
- 当前场景和下一场景重叠驻留；
- 取消和失败恢复；
- 加载完成后的激活尖峰。

## 引用计数

共享资源可以用引用计数管理：加载入口增加引用，释放入口减少引用，归零后允许卸载。

引用计数的问题：

- 循环引用；
- Handle 丢失；
- 实例销毁但引用未释放；
- 异步请求取消时计数不平衡；
- 引擎内部或全局缓存仍持有引用。

需要配套资源快照和泄漏检测。

## 版本和热更新

资源版本通常使用内容 Hash，而不是只用文件名或人工版本号。

更新流程要考虑：

- Catalog 和 Bundle 的原子一致性；
- CDN 缓存；
- 断点续传和校验；
- 旧版本回滚；
- 本地缓存淘汰；
- 加密和压缩；
- 代码版本是否理解新资源格式。

## 分包检查

- 是否有重复依赖？
- 公共包是否过大？
- 一个功能的下载集合是否可解释？
- 更新一张资源会使多少 Bundle 失效？
- 加载和卸载是否按生命周期闭环？
- 场景切换峰值是否同时保留两套大资源？
- 真机 Shader、Texture 和 Mesh Upload 是否产生尖峰？

## 验证方法

- 导出依赖图和重复 Asset 报表。
- 对每个 Bundle 记录大小、依赖、更新频率和所有者。
- 用 Memory Profiler 检查卸载前后对象和 Native Resource。
- 模拟断网、取消、版本不一致和磁盘不足。
- 记录下载、IO、解压、反序列化、实例化和 GPU Upload 各阶段时间。
