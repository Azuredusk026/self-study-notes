# 数据导向设计与任务系统

数据导向设计（Data-Oriented Design）关注“处理哪些数据、按什么顺序访问、如何并行”，而不是先建立对象继承关系。它不是对 OOP 的全面替代。稳定的工具接口可以保持对象化，帧内热点数据则更适合连续布局和批量处理。

## 从访问模式开始

CPU 执行速度和内存访问速度差距很大。一次 Cache Miss 可能让执行单元等待许多周期。优化前先回答：

- 一次更新真正需要哪些字段；
- 相邻迭代是否访问相邻地址；
- 数据是否被多个线程写入同一 Cache Line；
- 分支是否让同一批数据走完全不同的路径。

AoS 把一个对象的所有字段放在一起，适合整对象访问。SoA 把同类字段放在连续数组中，适合只处理位置、速度等少数字段的批量循环。实际系统常用混合布局，目标是贴合访问模式。

ECS 的 Archetype 会按组件组合分组，Chunk 内存放相同布局的 Entity。System 查询需要的组件集合后，可以顺序遍历匹配 Chunk。新增或删除组件会让 Entity 跨 Archetype 搬迁，因此结构变化不适合在热点循环中频繁发生。

## ECS 的三个角色

ECS 是数据导向设计在游戏架构上的一种具体落地：

- **Entity**：只是一个唯一 ID，不含任何数据与行为。它的特性完全由附加的组件决定；
- **Component**：纯数据容器，不含逻辑；
- **System**：处理特定组件组合的逻辑，遍历所有持有相关组件的实体并执行操作。

与面向对象的对比常被简化为"组合优于继承"，但真正的性能差异来自内存布局。

传统 OOP 把一个实体的全部数据封在一个对象里，不同对象散布在堆的各处。遍历一千个敌人更新位置时，每次访问都要跳到新的内存地址，缓存行里大部分内容是当前用不到的字段（名字、血量、AI 状态）。

ECS 把同类组件存成紧凑数组。更新位置时，位置数据与速度数据各自连续排列，一次缓存行加载能覆盖多个实体的有效数据，硬件预取也能正常工作。

这带来第二个收益：批处理天然适合并行。系统对一段连续数据做同构操作，切分给多个线程既无数据竞争也无假共享——前提是这些数组确实按缓存行对齐切分。

## Archetype 与查询

真实引擎中的 ECS 还要解决"如何快速找出持有某组组件的全部实体"。常见做法是 Archetype：把组件组合相同的实体归入同一块存储，查询退化为遍历若干个匹配的 Archetype 块。

Unreal 的 Mass 框架采用这种组织方式。它的代价也由此而来：**给实体增删组件会改变它的 Archetype，需要在存储块之间搬移数据**。频繁增删组件的设计会把这条路径变成新瓶颈，应当用标记位或状态字段替代。

### 什么时候不该用 ECS

ECS 的收益需要规模来兑现，成本却是固定的：

- 实体数量少时，缓存优势不明显，而架构复杂度的增加是实打实的；
- 逻辑高度个性化时，组件组合会碎片化，Archetype 数量膨胀，查询退化；
- 调试比 OOP 困难，一个实体的状态分散在多处存储中；
- 与引擎既有的对象体系交互需要桥接层，跨界访问往往抵消性能收益。

判据是数量级与同构性：成千上万个行为相似的实体适合 ECS，几十个各自特殊的对象不适合。实践中常见的是混合架构——主角与关键 NPC 走传统对象模型，群体单位与投射物走 ECS。
## 任务图

任务系统把一帧工作拆成小任务，并显式记录依赖。A 写入位置、B 读取位置时，B 必须等待 A；两个只读任务可以并行。Task Graph 的边表达数据依赖，比按模块名称猜执行顺序可靠。

任务太大会浪费核心，任务太小会让调度和同步成本占主导。常见做法是把批量循环分块，并设置最小粒度。调度器可以给每个 Worker 一个双端队列：本线程从一端取任务，空闲线程从另一端窃取，减少争用。

Fiber 或 Coroutine 允许任务等待依赖时让出执行权，而不是阻塞整个 Worker 线程。它们仍然需要清晰的栈空间、恢复点和生命周期。等待期间保存了指向临时栈数据的引用，会产生难以复现的错误。

## 同步与内存顺序

Mutex 适合保护较长的复合操作，原子操作适合简单状态转换。Lock-Free 只保证系统整体持续前进，Wait-Free 才保证每个参与者在有限步骤内完成。无锁结构还要处理 ABA、内存回收和正确的 Memory Order，不能因为“没有锁”就默认更快。

Release 写和 Acquire 读可以建立 Happens-Before 关系。编译器和 CPU 都可能在规则允许时重排访问。Debug 版本偶然正常不能证明并发正确。

False Sharing 指多个线程修改同一 Cache Line 上不同变量。逻辑上没有共享，硬件仍会反复转移缓存行所有权。按线程分块、填充热点计数或改为局部累积后汇总可以缓解。

## 落地与验证

先用 Profiler 找到真实热点，再记录每个任务的耗时、等待、队列长度和工作窃取次数。验证内容应包括单线程结果对照、不同 Worker 数量、随机调度、长时间压力和关闭阶段。

DOP、ECS 和 Job System 可以独立采用。ECS 解决数据组织和查询，Job System 解决执行调度。把两者绑定为一个不可拆的框架，会增加工具链和调试成本。

### 显式任务依赖

下面的伪代码把动画、物理和渲染准备之间的读写关系写进任务图。`Combine` 只表达依赖，不主动等待 CPU：

```cpp
JobHandle animation = ScheduleParallel(UpdateAnimation, entities, frameInput);
JobHandle physics = Schedule(StepPhysics, fixedStep, previousPhysics);
JobHandle transforms = ScheduleParallel(UpdateWorldTransforms,
                                        entities, Combine(animation, physics));
JobHandle visibility = ScheduleParallel(CullRenderables,
                                        renderables, transforms);
SubmitRendering.After(visibility);
```

每个任务需要声明读取和写入的数据范围，调度器才能判断哪些任务可并行。若两个任务写同一数组，即使代码中没有锁，也存在数据竞争。验证时记录任务开始、结束、等待原因和工作线程利用率；大量短任务会把时间耗在调度上，过大的任务又会留下长尾。
