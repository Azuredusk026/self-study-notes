# 引擎分层、世界与对象模型

游戏引擎不是一组互不相关的模块。它要让平台、资源、运行时功能和制作工具围绕同一套数据契约工作。分层的价值不是目录整齐，而是让依赖方向、对象所有权和更新时机可以被解释。

## 分层与依赖方向

常见的职责可以概括为：

- 平台层封装窗口、文件、线程、时间、输入和图形 API；
- 核心层提供数学、容器、内存、反射、序列化和任务基础；
- 资源层把磁盘资产转换为运行时对象，并管理依赖与生命周期；
- 功能层实现渲染、物理、动画、音频、AI 和 Gameplay；
- 工具层编辑同一套世界与资产数据，但不应偷偷依赖游戏运行状态。

上层可以依赖下层公开接口，下层不应反向知道某个具体玩法。跨层通信优先通过稳定的数据结构、句柄和服务接口完成。随意使用全局单例会把生命周期和线程归属隐藏起来，最终常见的问题是退出顺序、热重载和测试互相冲突。

渲染硬件接口（Render Hardware Interface，RHI）位于引擎渲染器与 Direct3D、Vulkan、Metal 等图形 API 之间，统一 Buffer、Texture、Pipeline、Command 和同步对象。RHI 应保留底层 API 的关键能力与代价；若把资源状态、Queue 和内存模型全部隐藏，跨平台抽象会退化成大量隐式同步和最低能力公约数。

## 反射与代码生成

C++ 缺少满足引擎序列化、编辑器和脚本绑定所需的完整运行时反射，常使用 Clang AST 或自定义 Header Tool 扫描标记类型，生成 Schema、注册表、Accessor 和模板代码。生成链需要固定编译参数、宏环境和模块顺序，否则工具看到的类型与编译器实际类型不一致。

Schema 保存字段名、类型、版本和 Attribute；Accessor 统一属性读写、校验与通知；模板生成序列化、编辑器面板或脚本桥接代码。生成文件应是可重复构建产物，源类型变化要精确触发增量更新，并检测重名 ID、循环依赖和陈旧注册信息。

## Entity、Component 与世界

Entity 通常只提供稳定身份。Component 保存某一方面的数据，System 按组件组合执行逻辑。一个对象由多个组件组合出来，比深继承树更容易替换功能。

运行时引用更适合使用带代数或版本号的 Handle，而不是长期保存裸指针。对象销毁后，Handle 校验可以拒绝访问已经复用的槽位。世界管理器负责对象注册、场景归属、空间索引和销毁队列；组件不能假设依赖对象永远存在。

场景不是单纯的对象数组。大型世界还需要 Cell、Layer 或 Chunk 等空间单元，用于流式加载、可见性、物理激活和编辑协作。跨区引用要么通过软引用和 ID 延迟解析，要么由更高层的持久对象持有。

## Tick 与阶段

每帧更新需要明确阶段，例如：

1. 收集输入和网络消息；
2. 更新 Gameplay 与 AI；
3. 运行物理并处理接触结果；
4. 更新动画、相机和表现状态；
5. 生成渲染快照并提交；
6. 执行延迟销毁和场景切换。

Pre-Tick、Tick、Post-Tick 不是命名习惯，而是时序契约。事件立即分发可能造成重入，队列分发会引入一帧内的延迟。系统必须说明采用哪一种语义。

固定时间步适合物理和确定性要求较高的逻辑，渲染通常按显示帧率更新。累计器可以在一帧执行零次或多次固定更新，但需要限制追赶次数，避免卡顿后出现“死亡螺旋”。

## 线程与快照

逻辑线程和渲染线程不能同时随意修改同一对象。常见做法是让逻辑世界拥有写权限，在同步点生成只读渲染快照。双缓冲或环形缓冲能减少互斥等待，但会带来一帧延迟和额外内存。

并行化前先确认数据所有权。只把 Tick 函数丢进线程池，通常会把隐式依赖变成数据竞争。系统级阶段、任务依赖和只读数据边界比“多开线程”更重要。

## 验证

可以画一张对象生命周期图，标出创建、注册、激活、更新、停用和销毁。再检查每条跨系统引用由谁拥有、何时失效。场景切换、热重载和退出流程是最容易暴露所有权错误的测试。
